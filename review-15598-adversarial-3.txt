=== MATERIAL FINDING ===

P1 [HIGH, confirmed in code] The backfill exception "rows whose creation audit row proves a signed-in session"
cannot be implemented truthfully. A naive implementation reopens the laundering path.
  - The api_key.created audit row (api-keys/service.ts:231-248, and the runner path at :484-492) records
    actorKind 'user' and actorId = the user, whoever acted: a signed-in session, a user token, or an org API key
    acting with its creator's authority. `changes` holds name, scopes, role, kind, scopedToUserId, canCreateIssues
    and expiresAt. It holds no credential kind, no session id and no token id. Nothing in the row distinguishes a
    session.
  - An implementer told to "upgrade where the audit row proves a session" will probably treat actorKind 'user' as
    proof, which marks every pre-migration key as `session`. created_by_user_token_id catches keys minted by tokens
    after that column existed, but not keys minted by an org API key, MCP pairing, or keys from before the column.
    Any such key whose plaintext an agent held becomes an eligible grantee, which is exactly what A2 exists to stop.
  - Personas have no creation audit carrying credential kind either, so the same applies.
  FIX: backfill EVERY existing api_keys and personas row as `unknown`, with no audit-based upgrade. Eligibility
  starts only with keys and personas created after the migration ships, where the creation path sets created_via
  from the authenticated context. In AC-4, make the fallback the only path: the tester creates the grantee key
  through a signed-in session after deploy and waits 60 minutes, recorded as a limitation. Add one NEG-6 case: a
  pre-migration key whose creation audit row shows actorKind 'user' is refused as `unknown`.
