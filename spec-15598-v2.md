# Spec: P0 product gap: no route to mint an org API key whose value is delivered to a host without passing through the agent

Ticket: GoodQA goodqa#15598
Author: agent:aaef3bc78b40c0c22 (sonnet)
Click-test: required
Sign-off: main
Review-policy: standard
Baseline: bugtracker origin/main 26d95f46ada7 (paths relative to that tree; origin/main later moved only by deploy records)

## Outcome

With a user token that holds the new ability `tokens.mint_to_vault` (never the user's clicks, never an ask), an agent can mint a new org API key whose value the agent can never obtain: the server seals the key into an org vault secret that is blind to every credential except one pre-existing, human-created grantee principal, and answers only the key id, prefix and vault secret id. A host that holds the grantee reads the value with the existing `vault-env/reveal` into a mode-600 file. Every other opener of vault plaintext (about thirty call sites) refuses a blind secret through one choke point. This unblocks moving people-watch to t2-dev (goodqa#14518) and, because the minted artifact is an org API key (not a user token; `user_tokens_create` stays dark), it serves AC-12 of goodqa#15561 only if the desktop-session start accepts that key's abilities (see AC-5, which is a separate, checked claim).

## Decisions (sources)

- Design A: mint-to-vault, blind-pinned to a named grantee. Source: ticket:GoodQA goodqa#15598 ("mint into the org vault ... returning only id and prefix") and main decision 2026-11-10 "go with A (mint-to-vault, blind-pinned to a named grantee)".
- No human approval at mint time and no `approvalAlways`: key and token creation runs on the user token and is never surfaced to the user as an ask. Compensating controls named by main: a scope ceiling, an explicit grantee plus `org:manage_api_keys`, a per-token rate limit and audit, an alert to the org owner on each mint, the token never in any response, log or agent context. Source: main decision 2026-11-10 (feedback "Use user token for GoodQA"; CLAUDE.md section 4.1).
- Bootstrap grantee: an existing key or persona the click-tester host already holds, never one the agent can read. Source: main decision 2026-11-10.
- ASSUMPTION A1 (review-driven, not main's words): the route needs its OWN token ability `tokens.mint_to_vault`, which does NOT imply `tokens.create_other_keys` and is not part of `all` unless named; the token used for the live proof lacks `tokens.create_other_keys`. Reason: a token that can also call plain `POST /api-keys` receives plaintext keys in the response, so the blind mint would add nothing against a compromised agent (review F2). The new route has no `approval` entry (main's decision). Source: inferred: from the adversarial review of this spec and main's no-approval decision.
- ASSUMPTION A2 (review-driven): grantee eligibility is the human-bootstrap control: the grantee must be a principal that no agent credential could have received in plaintext and that existed before the mint: created by a signed-in person's session (not by any user token, not by MCP pairing, not by an automation), at least 60 minutes old, same org, not revoked, not a runner key, not user-scoped, not the key being minted. This moves the one human act to when the grantee was created, not to mint time. Source: inferred: from the adversarial review (F3 option 2/3) and main's "never one you can read".
- ASSUMPTION A3 (review-driven): the mint transaction itself creates a vault-env allow-list entry bound to exactly this secret id and grantee (a row in the blind table that vault-env consults, never a prefix pattern and never an edit of the org's editable vault-env config). It does not change who else may read anything. Source: inferred: from the adversarial review (F3) because `vault-env/config` writes are session-only.

## Design

D1. Route `POST /v1/orgs/:orgId/api-keys/mint-to-vault` (`modules/api-keys/routes.ts`), body: `name`, `scopes`, `maxOrgRole?`, `canCreateIssues?`, `expiresAt` (REQUIRED, at most 90 days, so no never-expiring key sits in the vault), `delivery: { vaultName, grantee: { principalType: 'persona'|'api_key', principalId } }`, `idempotencyKey` (UUID, required). No `scopedToUserId` (user-scoped keys cannot use the vault). Response `{ apiKey: { id, prefix, name, scopes, expiresAt }, vaultSecretId, vaultName }` with `cache-control: no-store`; never the token or any sealed field.
D2. Token gate: new ability rule in `lib/user-token-policy.ts` (`USER_TOKEN_ABILITY_RULES`, plus the literal allow list): ability `tokens.mint_to_vault`, no `approval`, not session-action, not delegable to a bound desktop session (refused as `user_token_non_delegable`), refused to org API keys and commander-turn grants. A signed-in session may call it (it already can mint keys by hand). The ceiling `assertApiKeyWithinUserToken` applies: the minted scopes and role never exceed the caller's token and role.
D3. Single choke point for the blind pin: every opener of vault plaintext (`openSecretPlaintext` / `openVaultSecret`, about thirty non-test sites listed in the adversarial report: vault reveal, vault-env, requested-secret, secret-requests, agent-browser secret broker, automation http step-test and saved-workflow reconcile, network, deploy, machine, inference, SMTP, mailer, marketing, SEO, social, Cloudflare, GHL, Sanity, Ahrefs, workers, private-network, commander harness, messaging) goes through one wrapper `openSecretPlaintextFor(db, row, caller)` that refuses a secret with a `vault_blind_mints` row unless the caller is the grantee on `vault-env/reveal` (by the authenticated principal id, in the same org, grantee still eligible) or a signed-in person's session (AuthContext without `userTokenId`, `apiKeyId`, MCP dispatch marker or desktop-session binding; the field tested is named in the test). A repo-wide census test fails if any non-test file calls the raw opener outside the wrapper (the user-token policy census pattern). The lookup fails CLOSED: a missing table, a query error or an unknown caller refuses.
D4. Integrity paths: `PATCH /vault/secrets/:id` (value, rename, description), grant PUT/DELETE, delete and any move or convert refuse a blind secret for every agent credential; human-session only. A rename cannot redirect the host (vault-env resolves by name; the blind row binds the secret id and the grantee rule names the exact id, never a pattern).
D5. Grantee eligibility (A2) is checked in the mint transaction with a row lock on the grantee principal; uniform errors: not found, not eligible, other org and not allowed all answer the same 400 `grantee_not_eligible` (no existence oracle). The minting agent cannot name its own principal: the grantee is refused if it equals the request's own `apiKeyId`, persona, or any principal created through the minting token or any user token.
D6. Idempotency: `vault_blind_mints.idempotency_hash` = SHA-256 of (minting token id, org, idempotencyKey, canonical body), with a DB UNIQUE index on (org_id, minted_via_token_id, idempotency_key_hash), inserted first in the transaction, so concurrent duplicates are decided by the database. A repeat with the same key and body returns the original `{ id, prefix, vaultSecretId }` only while the key is not revoked, else 410 `mint_replay_revoked`; the same key with a different body is 409 `idempotency_key_reused`; a rate-limited or refused request does not consume the key.
D7. Rate limit (ASSUMPTION A4, numbers are a proposal): 5 mints per hour per token and 20 per day per org, counted from `vault_blind_mints` rows in the transaction under a per-token advisory lock (not an in-memory limiter), 429 `api_key_mint_rate_limited` with retry-after; refused requests are ledgered in `user_token_events` (token resolved before the limiter). Source: inferred: from main's "per-token rate limit".
D8. Audit and alert: `user_token_events` row and `audit_events` row `api_key.mint_to_vault` (key id, prefix, grantee ref, vault name, scopes, via token id; never the value), written in the same transaction (a rolled-back mint leaves none). The alert goes to the org owner by the direct account email the vault already uses for rotate (`vault/routes.ts` rationale), unmutable and unbatched, with grantee label, scopes, expiry and token id, never the value; a send failure neither rolls back nor leaks.
D9. Redaction: the token exists in memory only between mint and seal; it is never a query parameter or log field; the handler catches every failure and throws a fresh `AppError` without cause; database errors with parameters are scrubbed; Sentry breadcrumbs are scrubbed; a forced failure after the seal is tested.
D10. Revoke and rotation: `vault_blind_mints` has FKs with ON DELETE CASCADE to `vault_secrets` and `api_keys`; readability requires (by join, not a cleanup job) that the minted key is not revoked, the grantee is still eligible and not revoked, and the minting token chain is not revoked IS NOT required (a host key outlives the minting token; stated, since a surprising coupling would break hosts). Revoking the key, deleting the secret, or revoking the grantee ends the host's read.
D11. Rollout and rollback: ship the migration and the choke point and census first, then the route behind a platform flag `apiKeys.mintToVault` (default off). Rollback: set the flag off; never drop the table while rows exist (dropping it would unblind every minted secret); to remove the feature, revoke the minted keys and delete the blind secrets first. The code fails closed when the table is missing.
D12. Surface: HTTP only (no MCP tool, no OpenAPI listing for agents until main decides; the route is added to the route registry and the user-token allow list; docs entry in `docs/`). The MCP `get_secret`, `read_requested_secret` and `call_api` paths are covered by the choke point and tested through the real tool.

## Scope

- In: `modules/api-keys` (route, `mint-to-vault.ts`), `packages/db` migration and schema (`vault_blind_mints`), the wrapper and every call site of the raw opener, `modules/vault`, `vault-env`, `secret-requests`, `lib/user-token-policy.ts`, the platform flag, tests (`apps/api/test/api-key-mint-to-vault.test.ts`, the census test), a docs entry.
- Out: design B (host file through the machine agent), UI, minting user tokens, any change to the existing `POST /api-keys` response, the secret-request pin (kept as is).

## Acceptance criteria

- AC-1: With a token holding `tokens.mint_to_vault` and the abilities the minted scopes imply (and `org:manage_api_keys` and `org:manage_vault` for the owning user), `POST /v1/orgs/:orgId/api-keys/mint-to-vault` creates the key and the blind vault secret in one transaction and answers only id, prefix and vault secret id; the token appears nowhere (full token and its secret portion without the prefix, byte search over responses, headers, `user_token_events`, `audit_events`, notifications, the captured test log stream and the Sentry scrub output), excluding only the sealed `vault_secrets` row and the grantee's own reveal response. Verify by: `pnpm exec vitest run test/api-key-mint-to-vault.test.ts` from `apps/api` on t2-dev; failing first against a variant with the blind check removed (each NEG fails against that variant), not merely a 404. Source: ticket:GoodQA goodqa#15598
- AC-2: The grantee reads the value through `vault-env/reveal` and the key authenticates; nobody else can through any opener: the minting token, another token of the same user, the org owner through a token, a non-grantee key or persona, MCP `get_secret` and `read_requested_secret` (tested through the real tools), automation http step-test and saved workflow, SMTP, deploy, inference and connector paths, `vault/secrets/:id/reveal`, and a desktop session bound to a token; a signed-in person's session can. A census test fails if any non-test code opens vault plaintext outside the wrapper. Verify by: same test file plus the census test and the existing `vault`, `vault-env` and `secret-requests` suites (named in the run log). Source: ticket:GoodQA goodqa#15598
- AC-3: Controls hold: the minted key is never broader than the caller's token and role; `expiresAt` is required and bounded; grantee eligibility (A2) and uniform errors; the minting token cannot also mint plaintext keys (NEG-8); DB-backed rate limit; idempotency decided by a unique index under concurrency; atomic audit; unmutable owner email; revoke ends the host's read. Verify by: same test file, one named test per NEG. Source: ticket:GoodQA goodqa#15598
- AC-4: Live proof after deploy and after enabling `apiKeys.mintToVault` for a disposable org: the independent click-tester (not the author) uses a token with `tokens.mint_to_vault` and without `tokens.create_other_keys`, a grantee principal created through a signed-in session at least an hour earlier on the tester host, and runs: mint, then on the host the exact CLI command `goodqa vault-env reveal with the vault name and an output file argument` (or the equivalent shipped CLI invocation named by the tester) with mode 600 verified by `stat`, never printing the value; an authenticated read using the file (`curl -sS -o /dev/null -w '%{http_code}' -H @file` against an org list, expecting 200) without the agent reading the file; the refusals proven live with a NON-grantee org API key and an org owner through a user token on `vault-env/reveal`, the vault reveal route, and an automation http step-test using the blind secret as credential; cleanup revokes the key and deletes the secret. Verify by: `spec_flow.py click-test` by the independent tester. Source: ticket:GoodQA goodqa#15598
- AC-5: the AC-12 artifact (a separate, checked claim) for goodqa#15561 is an org API key only if the desktop-session start accepts it; otherwise AC-12 stays blocked on a user-token mint route (out of scope here). Verify by: reading `POST /v1/me/desktop-session` policy and recording the answer on goodqa#15561 before any click-test claims it. Source: ticket:GoodQA goodqa#15561

- NEG-2 (AC-1): a failure after the key insert and before the vault write rolls back both and writes no audit, ledger or notification row. Source: ticket:GoodQA goodqa#15598
- NEG-3 (AC-2): the minting token, a second token of the same user and the org owner through any token are refused on `vault-env/reveal` and `vault/secrets/:id/reveal` with the same status, body and headers as a nonexistent secret id (byte-compared). Source: ticket:GoodQA goodqa#15598
- NEG-4 (AC-2): a non-grantee org API key or persona, MCP `get_secret`, `read_requested_secret`, and a desktop session bound to a token are refused on every opener, tested through the real MCP tools. Source: ticket:GoodQA goodqa#15598
- NEG-5 (AC-2): every non-vault opener (automation http step-test and reconcile, SMTP setup and deliver, deploy connection, inference path, network connector, mailer, social, Cloudflare, Sanity, Ahrefs, workers) refuses a blind secret for an org owner through a user token AND through a signed-in session when the call is not the grantee reveal; a new call site that bypasses the wrapper fails the census test. Source: ticket:GoodQA goodqa#15598
- NEG-6 (AC-3): grantee spoofing and laundering: a grantee in another org, a revoked or nonexistent id, the key being minted, the request's own key or persona, a key or persona created through any user token (the same or another token of the same user) or through MCP pairing, a principal younger than 60 minutes, a runner key and a user-scoped key are all refused with the same uniform 400 `grantee_not_eligible` before anything is minted. Source: ticket:GoodQA goodqa#15598
- NEG-7 (AC-3): authentication is by the authenticated principal id only: a caller cannot become the grantee by name, header or body; a principal of another org with the same id string is refused. Source: ticket:GoodQA goodqa#15598
- NEG-8 (AC-3): a token with `tokens.mint_to_vault` and also `tokens.create_other_keys` is refused by the new route (or the proof token is shown to lack it and plain `POST /api-keys` with that token is refused); a token lacking `tokens.mint_to_vault` is refused through the real policy gate; a token in ask-first mode gets no approval row on this route (as decided). Source: ticket:GoodQA goodqa#15598
- NEG-9 (AC-2): PATCH value, rename, description, grant PUT and DELETE, delete and move on a blind secret are refused for every agent credential; a rename plus a new secret under the old name does not redirect the host. Source: ticket:GoodQA goodqa#15598
- NEG-10 (AC-3): scope escalation and lifetime: scopes or `maxOrgRole` above the caller's token or role, `machines` or launch-family scopes while dark, a runner kind with wrong scopes, a missing `expiresAt` and an `expiresAt` beyond 90 days are refused; a token with only `read` cannot mint a `write` key. Source: ticket:GoodQA goodqa#15598
- NEG-11 (AC-3): double submit: at least two truly concurrent requests (Promise.all) with the same idempotency key produce exactly one key and one secret, both responses carry the same ids, decided by the unique index. Source: ticket:GoodQA goodqa#15598
- NEG-12 (AC-3): replay: the same key with a different body is 409; a missing or malformed key is 400; a retry after a lost response returns the original ids; a replay by another token cannot learn the ids; a replay after the key was revoked is 410; a refused or rate-limited request does not consume the key. Source: ticket:GoodQA goodqa#15598
- NEG-13 (AC-3): the sixth mint in an hour for one token and the twenty-first in a day for the org are refused 429 with retry-after, counted from the database (a second app instance, simulated by a fresh limiter state, cannot bypass); refusals mint nothing and are ledgered. Source: ticket:GoodQA goodqa#15598
- NEG-14 (AC-2): fail closed: with the blind table missing, or the lookup throwing, every opener refuses secrets rather than opening them; the route refuses to mint. Source: ticket:GoodQA goodqa#15598
- NEG-15 (AC-3): each of these ends the host's read, one named test each: key revoked, secret deleted, grantee revoked, grantee made ineligible; the minting token's revoke does not end it (stated). Source: ticket:GoodQA goodqa#15598
- NEG-16 (AC-3): the route is refused to a bound desktop session, a commander-turn grant and an org API key; a member without `org:manage_api_keys` or `org:manage_vault` is refused; a signed-in session may call it. Source: ticket:GoodQA goodqa#15598

## Risks

- Largest change: a single choke point over about thirty vault openers; mitigated by the census test and by shipping it before the route; a missed path defeats the purpose, so the census fails closed on any raw call.
- Laundering residual: the control is that the grantee was human-created and pre-existing; a human who deliberately gives the agent the grantee's secret defeats it (stated limitation). A compromised token that holds `tokens.mint_to_vault` can mint keys up to its own ceiling into a vault it cannot read: bounded by the ceiling, the grantee rule, the DB rate limit, the unmutable owner email and the audit.
- The host needs a grantee principal that satisfies A2: if none exists, one human step (create a key through a signed-in session on the host, wait an hour) is recorded as a limitation; it is not an ask at mint time.
- A mint route that writes a vault-env allow-list entry (A3) is a deliberate departure from "config writes are session-only"; limited to the exact secret id and grantee of a blind row and tested.
- Migration: additive table with cascading FKs; rollback is the platform flag, never dropping the table.
- Some Sources are inferred from review findings and main's decisions and are labelled; numbers in D7 are a proposal pending main.
