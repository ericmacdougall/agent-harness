## Outcome
`command_guard.py remove-worktree` (and `ah worktree-remove`) removes a clean, pushed, registered linked worktree on t2-dev while the user's systemd sd-pam helpers, tailscaled session helpers and the long-lived `sg docker` pgpool server keep running, instead of refusing every worktree with "N process(es) of this user cannot be inspected" (13 clean release-smoke worktrees could not be removed, the disk was at 98 percent and a production release was blocked). A process that really uses the worktree still blocks, every skipped process is named in the result, and the ignored-file refusal lists the offending paths.

## Design (read command_guard.py busy_scan and unreadable_verdict)
A same-user process whose /proc/PID/cwd cannot be read (a setgid or privilege-separation helper) cannot be inspected by lsof or fuser either, so "in use" is judged from the worktree side by what ties it to this worktree. Order: (a) the scanner's own ancestors (the caller's session; on t2-dev an ssh login's `tailscaled be-child`, whose command line carries the remove command) are skipped and reported; (b) an unreadable command line refuses; (c) a command line naming the worktree refuses; (d) shells, editors and interpreters refuse always; (e) known long-lived helpers whose name AND command line agree are skipped whatever their start time ((sd-pam), systemd --user, ssh-agent, gpg-agent, tailscaled be-child, docker with the pgpool label, `sg ... lanes/pgpool.py serve`); (f) every other program is judged by time: it cannot have been launched from the worktree before the worktree existed, so it is skipped and reported only when it started before the worktree was created (the mtime of the worktree's .git file), and refuses when it started after or when either time is unknown. A process with a readable cwd inside the worktree is still `busy` as before. The other-users rule and the same-user real-uid rules are unchanged.
