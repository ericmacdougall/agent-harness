MATERIAL
F1 Human approval contradiction. Spec: "No human approval and no approvalAlways". D-1: "the same ceiling as POST /api-keys today (... plus tokens.create_other_keys)".
  Code (lib/user-token-policy.ts ~230): POST /v1/orgs/:p/api-keys carries abilities ['tokens.create_other_keys'] AND approval 'tokens.create_other_keys' ("a token that asks first asks"). Inheriting that rule gives human approval for ask-first tokens, which main decided against; dropping `approval` is a policy change the spec never states. A1 says tokens.create_other_keys "is NOT reused", D-1 says it is: direct self-contradiction (A1 text is also garbled: "`crm`-free `api_keys.mint` family").
  Required: state the exact new USER_TOKEN_ABILITY_RULES entry, whether `approval` is set, and the allow-list entry (the allow list is a literal list, ~line 506; an unlisted route is denied to tokens). Add AC/NEG: token in ask-first mode gets no approval row (or is refused) as decided; a token lacking the ability is refused, tested through the real policy gate, not a handler stub.
F2 Grantee holder is unverifiable; the blind pin is only as strong as grantee secrecy. D4 forbids only "the minting token's own user-token-minted key" and the key being minted. It does not forbid a grantee the minting agent itself holds (its own org API key/MCP key, or a persona it runs as): the agent then reveals via vault-env/reveal with that key and "never enters the agent" fails. No NEG covers it (NEG-5/6 cover other-org and spoof only). Required: a rule and test (grantee not the principal of the request's own session/key; grantee not created via the same token), plus an honest limitation line. "Bootstrap grantee ... never one the agent can read" is an assertion with no check.
F3 Reveal-path enumeration deferred to reviewers. Risks: "the review must enumerate them; a missed path is a total failure". The spec must enumerate. From code, openSecretPlaintext consumers: modules/vault/{service,routes}, secret-requests/routes, vault-env/{service,routes}, webhooks, ahrefs, seo-connectors, deploy-connections, mailer connections-service, outreach/smtp/setup. Not covered by D3: vault grants (setVaultSecretGrant: an admin could grant a second reader), scope move/convert, export/backup, /vault/admin. Required: a table of every read/share path with disposition; a negative per path (grant to another principal refused; connectors/webhooks cannot reference a blind id); a repo-wide guard test that every openSecretPlaintext call sits behind the blind check, so a future path cannot bypass it.
F4 Outcome overclaims AC-12 of goodqa#15561. Outcome: unblocks "a desktop_signin + read + crm token minted without anyone reading it". D8: "minting user tokens (user_tokens_create stays dark)" while this route mints an ORG API key. Either the AC-12 artifact is an org key with those scopes (show desktop_signin is a valid API key scope) or the outcome is false. AC-4's last sentence ("Then use it for the AC-12 token and the people-watch keys") is a downstream action, not an observable criterion; move it out or give it a Verify by.
F5 Idempotency and rate-limit gaps that let a wrong implementation pass NEG-8/9/10.
  - Key stored "hashed with the org": scope should be (org, minting token); org-only lets another token replay a key and learn ids. No unique constraint is specified (only secret_id unique), so NEG-8 has no mechanism: check-then-insert passes a sequential test and fails concurrently. Verify by must fire truly concurrent requests (Promise.all, >=2) and require a DB unique index.
  - No retention/TTL; replay after the original key was revoked is unspecified.
  - Does a replay count against the rate limit? Does a rate-limited request consume the key? Unspecified. NEG-10 "refused requests ... are ledgered" is unclear for refusals before a token is resolved.
  - 5/hour/token, 20/day/org, 429 `api_key_mint_rate_limited`, 409 `idempotency_key_reused` are invented numbers/names not labelled ASSUMPTION. Limiter storage unspecified: an in-memory limiter resets per process/replica and would pass NEG-10 vacuously on one process.

SHOULD FIX
S1 Grantee eligibility. Code (vault-env/routes.ts ~87-88): "A user-scoped API key cannot read vault secrets", "A runner key cannot use the vault". D4 accepts any "non-revoked API key"; a runner or user-scoped grantee yields a secret nobody can read. Add NEG: grantee of kind runner or scopedToUserId refused 400. The statement "the org's vault-env allow-list names the secret, set by the same transaction" mutates shared org config: concurrent admin edits, provider-prefix rules, and not widening other principals' access are unspecified, and it is invented behavior, unlabelled.
S2 Invented behavior beyond the cited decisions, not labelled ASSUMPTION: D3(b) "a signed-in person's session can reveal" (decisions never say a human may read it); notify "org owner and admins" (decision says owner); vaultName collision handling; `scopedToUserId` accepted in body though vault-env refuses user-scoped keys; rate numbers; response headers.
S3 Atomicity: "one transaction with the vault write" but notification and ledger/audit placement unstated. A rolled-back mint must not leave an audit row claiming success; a failed notify must neither roll back nor leak. AC-1 says "abilities the minted scopes imply" and omits org:manage_vault, which D2 requires.
S4 NEG-3 "same generic not-allowed answer as a missing secret". Code returns the distinct `user_token_cannot_read_secrets` for any user token at vault-env principalOf, and the policy /reveal rule refuses tokens before the handler; existing behavior already differs from a missing-secret answer. Decide which changes. The test must compare status, body and headers byte-for-byte against a nonexistent id.
S5 NEG-1 vacuity: search for the secret portion without prefix as well as the full token; explicitly exclude only the sealed vault_secrets row and the intended grantee reveal response; name the log capture mechanism ("server logs of the test run" is not one).
S6 NEG-11 bundles five revocation events; one passing assertion satisfies it. Split or require each by name. "Revoking the minting token ends the grantee's access" (via createdByUserTokenId) was not verified by me, and is a surprising availability coupling for host-held keys; confirm it is intended.
S7 NEG-12 mixes six actors. Whether an org API key may call the route (existing POST /api-keys behavior) must be stated; "signed-in session may call it" is unsourced.
S8 Rollback is incomplete. "Reversible by dropping the table": after rows exist, dropping the table or running old code makes blind secrets revealable to anyone with vault access (fail OPEN). Rollback criteria must say revoke/delete blind secrets and keys first, or keep the table. Code must fail closed if the table is missing or the lookup errors (add NEG). Mixed-version window: old replicas have no blind check; ship migration and blind refusal before enabling the mint route (feature flag).
S9 OpenAPI/MCP surface unaddressed. Scope names "the MCP ... reveal paths" only. Decide: is mint exposed as an MCP tool or HTTP only; OpenAPI/route-schema registration, generated client, tool catalog and docs.
S10 Compensating controls are detective, not preventive, and the laundering path is open. A token holding agents.manage + tokens.create_other_keys can create key K1 via existing POST /api-keys (K1 token returned to the agent), name K1 as grantee, mint K2 to vault, then reveal K2 with K1 through vault-env. The feature then adds no confidentiality against a compromised token (only against honest agents). State this in Risks. Cheap mitigation: reject a grantee whose createdByUserTokenId is the minting token, or any user-token-created key, and add NEGs for both; D4 only names "the minting token's own user-token-minted key", confirm that covers it.
