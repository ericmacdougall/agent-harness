## What changed and why (read this first: the environment-identity model is withdrawn)
r3 F1 asked to walk the ancestor chain and require every readable ancestor to carry one identical CLAUDE_CODE_SESSION_ID. Before building it, a probe from a real Claude Code Bash tool call on this Mac, at main's request, read each ancestor's START environment and printed only counts of that variable per hop, never values: the python process 1, the tool shell 0, the claude process 0, the login shell 0, login unreadable (root), Terminal 0. The harness adds the variable to the command after the tool shell started, so no ancestor start environment carries it. The one-hop check at 8647cd2 therefore refused every legitimate call (its tests mocked or spawned parents that carry the variable), and the ancestor walk would too. The process-environment model cannot prove the session on this harness. Main chose option A.
- `ah clone-remove` takes the session only from `CLAUDE_CODE_SESSION_ID` in its own environment and calls the new `clone_remove.require_session(session, home)`: the session must match the session pattern (no `CLAUDE_SESSION_ID` fallback) and BOTH `~/.claude/wals/SESSION/` and `~/.agent-harness/work/SESSION/` must exist (not symlinks), else a CloneError; the trusted account home check stays; the parent-environment call is gone from ah.py.
- The KERN_PROCARGS2 reader (`parse_procargs2`, `process_environment`, `parent_session_env`) stays in clone_remove.py, tested and UNUSED, for the follow-up token (goodqa#15751); the docstring says so. r3 F3: an empty argv[0] cannot be told from the padding NULs after the executable path, the parse shifts by one and skips the first environment entry, which can only make a lookup miss; the limit is written in the docstring and pinned by `test_an_empty_argv0_shifts_the_parse_and_fails_safe`.

## STATED LIMITATION (for the user to accept; main registered the ask)
The session identity is CALLER-SETTABLE. The existence check is not proof of identity: a deliberately forged `CLAUDE_CODE_SESSION_ID=OTHER ah clone-remove ...`, with or without a wrapping shell, can reach the verified-clean, fully pushed `receipts/wt-*` clone of another existing session. Combined with the unimplemented live-owner refusal (spec D8) this DISRUPTS that session: it loses a local clone it may be using (recreatable by `git clone`) and an idle owner gets no warning. It LOSES NO COMMITTED OR PUSHED WORK: the removal still requires a clean tree, no stash, every ref, tracking ref and reflog commit reachable from the live remote, ignored files only as whole regenerable build directories, and no process or open file inside. What could still be lost, named: regenerable ignored build output, and a file written inside the clone after verification only if the ctime and directory-set rules miss it (they keep and report it). The fix is a hook-written per-session token that ah verifies, tracked as goodqa#15751. A test pins the limit so nobody mistakes it for a control (`test_an_untrusted_home_is_refused_and_the_forged_session_limit_is_real`).
