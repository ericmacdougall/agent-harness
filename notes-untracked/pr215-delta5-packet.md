## What changed and why (the environment-identity model is withdrawn)
r3 F1 asked to walk the ancestor chain and require every readable ancestor to carry one identical CLAUDE_CODE_SESSION_ID. Before building it, a probe from a real Claude Code Bash tool call on this Mac, at main's request, read each ancestor's START environment and printed only counts of that variable per hop, never values: the python process 1, the tool shell 0, the claude process 0, the login shell 0, login unreadable (root), Terminal 0. The harness adds the variable to the command after the tool shell started, so no ancestor start environment carries it. The one-hop check at 8647cd2 therefore refused every legitimate call (its tests mocked or spawned parents that carry the variable), and the ancestor walk would too. The process-environment model cannot prove the session on this harness. Main chose option A.
- `ah clone-remove` takes the session only from `CLAUDE_CODE_SESSION_ID` in its own environment and calls the new `clone_remove.require_session(session, home)`: the session must match the session pattern (no `CLAUDE_SESSION_ID` fallback) and BOTH `~/.claude/wals/SESSION/` and `~/.agent-harness/work/SESSION/` must exist (not symlinks), else a CloneError; the trusted account home check stays; the parent-environment call is gone from ah.py.
- The KERN_PROCARGS2 reader (`parse_procargs2`, `process_environment`, `parent_session_env`) stays in clone_remove.py, tested and UNUSED, for the follow-up token (goodqa#15751); the docstring says so. r3 F3: an empty argv[0] cannot be told from the padding NULs after the executable path, the parse shifts by one and skips the first environment entry, which can only make a lookup miss; the limit is written in the docstring and pinned by `test_an_empty_argv0_shifts_the_parse_and_fails_safe`.

## STATED LIMITATION: PENDING USER ACCEPTANCE (ask wb37184efe71), NOT ACCEPTED
The session identity is CALLER-SETTABLE. The existence check is not proof of identity: a deliberately forged `CLAUDE_CODE_SESSION_ID=OTHER ah clone-remove ...`, with or without a wrapping shell, can reach the verified-clean, fully pushed `receipts/wt-*` clone of another existing session. Main registered a user ask (wb37184efe71) to accept this residual; it is pending, NOT accepted, and main will not merge until the user accepts it or the follow-up token (goodqa#15751, a hook-written per-session token that ah verifies) lands. Combined with the unimplemented live-owner refusal (spec D8: `ah owners` rows carry no worktree or cwd) a forged call DISRUPTS the other session: it loses a local clone it may be using, recreatable by `git clone`, and an idle owner gets no warning. It LOSES NO WORK THAT A REF, A REFLOG OR THE LIVE REMOTE HOLDS (exceptions named below): the removal still requires a clean tree, no stash, every ref, tracking ref and reflog commit reachable from the live remote, ignored files only as whole presumed-regenerable build directories, and no process or open file inside.
What could still be lost, named, for any removal and so for a forged-session one (spec AC-4):
(a) commits that no ref or reflog reaches, such as a dropped stash or cruft-pack objects;
(b) local repository state outside git history: `.git/config` (upstream and remote settings, user.*), `.git/info/exclude` patterns, the COMMIT_EDITMSG draft, and the reflog messages and timestamps under `.git/logs`, all on the allowlist and none restored by a fresh `git clone`;
(c) ignored build directories, which are PRESUMED regenerable by their NAME only (dist, build, target, .venv and so on) and can hold artifacts that cannot be rebuilt;
(d) "pushed" means on the live remote at verification time, so a commit proven only by a remote branch that is later force-pushed or deleted can be lost afterwards, while a `refs/pull/*/head` proof is durable on GitHub;
(e) the real gaps of the ctime and directory-set rules (AC-6): a single file moved into the clone whole after verification keeps its old ctime and is deleted; a directory created while the directory-set walk runs can join the set; a directory that reuses a verified directory's inode after the original was deleted would be walked into (APFS does not reuse ids in practice).
A test pins the limit so nobody mistakes it for a control (`test_an_untrusted_home_is_refused_and_the_forged_session_limit_is_real`).
