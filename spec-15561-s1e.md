## Outcome

In a desktop session started from a user token (the bound desktop session of #15561), clicking a person in the CRM opens the contact record and its timeline, with no org-owner opt-in and no `userTokens.sessionActions` switch, for a token that holds `desktop_signin`, `read` and `crm`. Nothing else changes (the org CRM switch and the org opt-out `userTokens.contactTimelines` still refuse both routes): a bearer call with the same token keeps today's answers on both routes, the other session-only CRM routes stay refused, the owner's role, the token's org list, personal timeline entries and the Gmail mailbox withholding all still apply, and every request is ledgered and ends when the token is revoked, narrowed or expires.

## Design

D1. A named waiver W4 for the bound DELEGATED door only (never the host door, never bearer), pinned by test: `GET /v1/orgs/:p/crm/contacts/:p` (contact detail) and `GET /v1/orgs/:p/crm/contacts/:p/timeline` are entries of the delegated table (abilities `crm` + `read`) and members of the exact-key set `DESKTOP_SESSION_ONLY_OPENED` in `lib/desktop-token-session.ts`. HEAD maps to GET (existing `methodOf`), so a HEAD on either route is covered the same way; no other method on those paths is opened. For these routes the gate (in `auth-gate.ts`, applied after the bound door check, never touching `nonDelegable` of a future rule except by clearing it for these exact keys) treats the route as an ordinary token route: `signedInPersonOnly` is waived and the session-action refusal and the org opt-in requirement do not apply; the session-action path is never entered (no `req.userTokenSessionAction`, no `user_token.session_action` audit). Operator-kind tokens get NO W4 (an agent-held, non-expiring orchestrator), exactly as they get no host waivers. Every other gate step still runs: ability ceiling, org allow-list (404), org agent-pause, scope, ledger, rate, and the org CRM family switch (D6: it does not run for these routes by itself because they are session-only in the key-family table, so W4 applies `crm.api.enabled` explicitly, answering `crm_api_disabled` for a member org).
D2. The handlers run unchanged under the token-shaped actor (delegated door, so `req.auth` carries the token id): `requireOrgPermission(crm:read)` (owner role), `forTimelineReader` (Gmail mailbox-read entries stay withheld from a token credential) and `timelineWithSubjects` (a colleague's `personal` entries are absent; a colleague's `busy_only` entry arrives as "Busy" with no subjects, no join link). Contact detail of another org's contact is 404 (`getContact`); the contact TIMELINE handler does not check the contact, so another org's contact id yields 200 with an empty, org-scoped page and no data (no handler change; the owner's own entries are visible to their own session by design). Both responses (the detail embeds the first timeline page) get the same filtering.
D3. Not changed: bearer calls (answers identical to c81dfd8f in every switch state: contact detail `user_token_non_delegable`; the timeline keeps whichever session-action refusal the switch state gives), contact export, meetings, files, call, SMS, AI briefing and suggestions, issue-links, timeline writes, import (all stay refused to a bound session), org API keys, outreach.
D4. Audit: both routes are NOT on `DESKTOP_POLL_ROUTES`; every request is ledgered with `via: desktop_session`.
D7. Hidden-match oracle closed (red-team N1, confirmed by a live probe): withholding runs after paging, so for a desktop-session reader `q` and `pinned` on the contact timeline are refused (400 `user_token_filter_unsupported`) and `nextCursor` (and the contact detail's `timelineNextCursor`) is derived from the last entry the reader can see, null when a page shows none (a stated limit: a page that is entirely withheld ends paging). Signed-in persons and bearer session actions keep today's behaviour (the same personal/busy_only oracle exists there today and gets its own ticket). Source: ticket:GoodQA goodqa#15561
D6. Controls: (a) the org CRM family switch `crm.api.enabled` off: both routes answer 404 `crm_api_disabled` for a member of the org (same as the contact list); (b) the org opt-out `userTokens.contactTimelines` exactly false: 404 `contact_timelines_disabled` for a member (A2); both run before the handler and only reveal themselves to a member of the org the token may reach (no org-existence oracle). Source: inferred: from the review of this spec (F1, F3) and the existing `crm_api_disabled` behaviour.
D5. The invariant "reachable(bound) is a subset of reachable(bearer, same token)" has exactly one deliberate, named exception pair (D1), pinned by a test that fails on drift; the inventory snapshot changes by exactly these two entries.

## Scope

- In: `apps/api/src/lib/desktop-token-session.ts` (table entries, W4 set, `contactTimelinesOnForOrg`), `apps/api/src/modules/user-tokens/auth-gate.ts` (apply W4 for the bound delegated door, operator exclusion), `apps/api/src/plugins/auth.ts` (the gate deps: org CRM switch and org opt-out for the two routes), tests (`apps/api/test/user-token-contact-timeline-default.test.ts`, the bound-session case in `gmail-limited-use.test.ts`, the inventory snapshot and the carve-outs in the inventory and delegation tests), this spec.
- Out: bearer opening of contact detail and timeline (S1e-b), web copy for the now-working pages (S4), any change to `SESSION_ONLY_ROUTES` or `USER_TOKEN_BEYOND_API_KEY_ROUTES`, Messages, org-scope filtering.

## Negative cases

- NEG-1 (AC-1): a bound session whose token lacks `crm` gets exactly 403 `user_token_ability_missing` naming `crm` on both routes; a token without `read` cannot start a session; removing `read` or `desktop_signin` mid-session ends the session on the next request. Source: ticket:GoodQA goodqa#15561
- NEG-2 (AC-3): a contact id that belongs to org B requested under org A is 404 on the contact route and 200 with an empty page on the timeline route (no org-B entry in the body), for a token that reaches both orgs. Source: ticket:GoodQA goodqa#15561
- NEG-3 (AC-3): a token whose org list is narrowed (after the session started) to exclude the contact's org gets 404 on both routes on the next request. Source: ticket:GoodQA goodqa#15561
- NEG-4 (AC-3): a user who is not a member of the org gets 4xx with no contact data on either route (exact codes pinned in the test), and a member without `crm:read` is refused by the existing handler check (`requireOrgPermission`, unchanged and covered by the existing CRM permission suites; this slice does not rebuild a role without `crm:read`, a stated limit). Source: ticket:GoodQA goodqa#15561
- NEG-5 (AC-3): revoking the token ends the session on the very next request (exactly 401), and removing `crm` refuses it (exactly 403 `user_token_ability_missing`), on the same access token. Source: ticket:GoodQA goodqa#15561
- NEG-6 (AC-4): a colleague's `personal` timeline entry is absent from both routes' responses for the session of another member; the colleague's `busy_only` meeting arrives as Busy with no title, no subjects and no join link on both routes. (There is no GET-by-entry-id route, so "404 by id" is not claimed.) Source: ticket:GoodQA goodqa#15561
- NEG-7 (AC-4): a real Gmail mailbox-read entry (ingested through the real ingest) is absent from both routes for the bound session, with the positive control that the owner's signed-in session receives it and the hand-logged email is still received. Source: ticket:GoodQA goodqa#15561
- NEG-8 (AC-2): export, meetings, files, call, SMS, AI briefing and suggestions, issue-links, timeline create, deal and pipeline detail routes stay `user_token_non_delegable` for the bound session. Source: ticket:GoodQA goodqa#15561
- NEG-9 (AC-2): a bearer call with the same token gets `user_token_non_delegable` on contact detail and the existing session-action refusal on the timeline (unchanged), asserted with the switch off, on, and on with the org opted in; an org API key with every scope is unchanged. Source: ticket:GoodQA goodqa#15561
- NEG-10 (AC-4): each request on the two routes (allowed and refused) writes a token ledger row with `via: desktop_session` and the session id, none carries the contact payload, a body or a token value, and neither route is on the quiet poll list. Source: ticket:GoodQA goodqa#15561

- NEG-11 (AC-2): the org CRM switch `crm.api.enabled` off answers 404 `crm_api_disabled` on both routes to a member; the org opt-out `userTokens.contactTimelines` false answers 404 `contact_timelines_disabled` to a member and the contact list stays readable. Source: ticket:GoodQA goodqa#15561
- NEG-12 (AC-2): an operator-kind token's bound session gets `user_token_non_delegable` on both routes; a HEAD on either route is covered exactly like GET (200 with `crm`, 403 without), and no other method is opened by W4: DELETE on the detail path is refused, POST on the timeline path (timeline create) is refused, PATCH on the detail path remains the ordinary CRM write door (needs `write`). Source: ticket:GoodQA goodqa#15561

- NEG-13 (AC-4): for a bound session, `q` and `pinned` on the contact timeline answer 400 `user_token_filter_unsupported` and never echo a withheld entry's id; with a colleague's `personal` entry as the newest row and `limit=1`, the page has no entry, `nextCursor` is null, and neither the timeline nor the contact detail contains that entry's id or its timestamp; the colleague's own signed-in session still finds it with `q`. Source: ticket:GoodQA goodqa#15561

## Risks

- A bound session reads mail, SMS and call timelines of contacts it never could before: bounded by token revoke (the access token is renewed by refresh, so the bound is the token chain's end, infinite for a non-expiring token), the ledger, the owner's `crm:read` and the token ability; the user chose this knowingly (Source above).
- The token holder may be an agent that also started the desktop session (a session started from a token never belongs to a person at the keyboard): the same agent could read the timeline through the session while its bearer calls are refused. This is the user's choice for token sessions; the red-team must judge whether the named assumption (sessions only) should instead be bearer too, or neither.
