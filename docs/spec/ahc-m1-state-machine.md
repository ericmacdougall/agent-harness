## State machine

The tables below are the only definition of these states; text elsewhere that disagrees loses. `check_state_tables.py` checks them mechanically:
- names, class, outcome and bound;
- exits, reachability and the path to a terminal;
- actors and unique test ids;
- R1: an owner never moves a waiting state to terminal without carrying its obligation;
- R2: every failure terminal escalates;
- R3: only the Effect entity dispatches.

The checker works on one entity at a time. Cross-entity traces are covered by the tests named in AC-2, AC-5 and AC-6. The code's tables must equal these one-to-one (AC-1). Test-id mapping: the `SMTests.test_xNN` names in the tables resolve per entity to WorkItem `tests.test_ahc_runner.StateMachineTests`, Review `tests.test_ahc_contracts.ReviewTests`, Grant `tests.test_ahc_contracts.GrantTests` and Effect `tests.test_ahc_contracts.OperationTests` (builder F3).

Bounds, from design 1.1:
- B10: 3 dispatches per operation key in total.
- B7: 2 review rounds, counted only when the reviewer blocked on the PR's own content.
- B29: not used in M-1. By main's ruling, re-reviews forced by a base move are not failed rounds and spend only B33.
- B33: the model-run budget per root lineage.
- B37: one readback per 60 s, 20 at most.
- B42: 30 min.
- B47: 24 h grant expiry.
- B48: 30 days of retention after settlement, then a tombstone.
- B54: withdrawn in v2f. No time horizon settles an op (Codex v2e F2).
- B55: 2 min from dispatch to unknown.
- CAP1 (A3): 10 per repo per UTC day, counted by the UTC day of G1.

### Eligibility predicate ELIG (one definition, required at W2, W6, G1 and E2)

ELIG(item) holds when all of the following hold, each read inside the transaction (T1) or as a fresh observation (T2). Observation age is measured on a monotonic clock; wall-clock time is used only for the CAP1 UTC day and for log stamps:
- (e1) every required Review row is `passed` for H, the packet sha and the policy revision. The PR head is H, and each row's snapshot base B_r is an ancestor of, or equal to, the current default-branch tip B, so the change that lands (B..H) is within what was reviewed (B_r..H).
- (e2) the spec row is `passed` against the spec core sha currently attached to the ticket.
- (e3) there is no Finding in `open`, `repair-claimed` or `challenged`.
- (e4) the PR touches no protected path (NEG-6), and neither the commit messages in B..H nor the PR body carry a closing keyword naming another repository (L9).
- (e5) the policy record is readable at the current policy revision, and the repo is on the allowlist and enabled. Every required check in the policy is green for H under its producer binding (Required checks, below).
- (e6) the kill switch is off, the kill epoch equals the grant's epoch (G1), and the current authority epoch is not frozen (F8 restore).
- (e7) a CAP1 slot is reserved for this grant (made at G1), or one is free (checked at W2 and W6).
- (e8) the PR is open and not a draft.
- (e10) B is an ancestor of H (`compare B...H` reports `ahead`), so the update is a pure fast-forward to the reviewed and checked commit. A PR that is behind is not eligible; at the queue head it may take W21.
- (e9) CHK-CAS passed for this repo under the merge identity in use, recorded at enablement and re-run after any change of that identity, and a CAS canary younger than 24 h. The canary runs daily under the merge identity on the scratch ref `refs/ahc/canary` (never a branch; CHK-CAS also asserts, by reading the Actions runs list, that a canary update started no workflow, as chk-cas-refs-ahc observed) and repeats the four CHK-CAS cases: create from zero, a correct fast-forward, a typed non-fast-forward refusal and a stale-`beforeOid` refusal with the ref unchanged. A failed or missing canary turns the repo's merging off and escalates once. REALLY_TESTED chk-cas-refs-ahc showed `updateRefs` behaving the same way on `refs/ahc/...` as on a branch. Without it the repo cannot be enabled, and no other dispatch path exists (NEG-19).

### Required checks (Codex v2f F2)

Each repo's policy record lists its required checks. Each entry gives a name, an API type (`check-run`, `status` or `ahc-local`) and the one trusted producer: the GitHub App id for a check run, the creator login for a status, or `ahc` for a check that ahc runs itself. For each (name, producer), every attempt for H counts: e5 holds only when at least one attempt succeeded and no attempt for H is failed, cancelled, timed out or pending. A failure followed by a successful rerun fails e5, and the item goes to `waiting-dep` (W5) with the cause `check failed on this head`; only a new head clears it, or main's stamped disposition (W16). So nobody with write access can rerun a check until it turns green. These fail closed: a check with a matching name from another producer, a duplicate context, or an incomplete or failed paginated read. The policy's list may not be empty for a real repo.

Per repo, stated plainly:
- agent-harness: CI is off, and the user pays for no Actions. The required checks are `ahc-local` only: the repo's focused suites, named in its policy record, which ahc runs on the coordinator host against H. They run in a transient DynamicUser unit with no credentials, no network and a read-only snapshot of H, as the review units do (H2). The test runner and its configuration come from B, never from H: the runner command, `conftest*`, `pytest.ini`, `setup.cfg`, `tox.ini`, the test sections of `pyproject.toml`, `tests/__init__.py` and any file the policy record lists as test configuration are taken from the snapshot of B and overlaid on H. The unit runs each named suite on B and on H and records collected, executed, skipped and failed counts for both. e5 fails when H executes fewer tests than B in a suite, skips more, or collects a suite empty, unless the drop is limited to test files the PR deletes and main records a stamped disposition. Counts alone cannot catch a test body rewritten into a pass, so the unit also runs B's own test files, taken from the snapshot of B, against H's code (a third run: B's tests and configuration overlaid on H). e5 fails when any test that passed on B fails, errors or is skipped in that run, unless main records a stamped disposition naming each such test (a legitimate behavior change). A PR that modifies an existing test file also gets a `tests-changed` gate row: the review packet lists each changed test file with its diff, and each review's verdict must state, per file, whether an assertion was removed or weakened; a missing statement fails e1. A PR that changes any of those configuration files is a protected-path PR (NEG-6). The result is recorded with producer `ahc`, bound to (repo, B, H, policy revision).
- the sandbox `ahc-integration-sandbox`: one `ahc-local` smoke check bound to producer `ahc`. Its own Actions workflow `ci` is not a required check.
- any other repo: its policy record names its checks before it can be enabled (AC-14).
Fixtures: a spoofed name from another producer, an unexpected app, an earlier success superseded by a pending rerun and by a failed rerun, a failure followed by a successful rerun, an H that deletes a test function, an H that adds a skip marker, an H whose `conftest.py` turns every test into a pass, an H that replaces a test's assertions with `pass` while keeping its name and count, an H that makes a test body return early, and an H that changes the code under test together with its test so that B's version of the test fails. Each must fail e5 (`tests.test_ahc_core.RequiredCheckTests`, with a failing-first variant that keeps the latest attempt only, one that takes the runner configuration from H, and one that drops the run of B's tests against H).

Producer rules for a repo with GitHub checks: a `status` producer may never be a login any author can act as, which includes the shared user account and the merge identity itself, so with the merge identity being the user's own token a `status` check is not admissible at all. A `check-run` bound to the GitHub Actions app is admissible only while `.github/**` is a protected path (NEG-6), because a PR can otherwise rewrite the workflow that produces the check.

### Merge queue

Each repo has one merge queue: its items in `pr-gate` or `merge-ready`, ordered by lineage admission time. The head is the oldest item for which every ELIG clause except e10 holds, with one exception: while an item's W21 successor (at H') is in its checks or re-review, that successor keeps the head position, even though its e1 does not yet hold. At most one W21 update, or one successor in checks or re-review, is outstanding per repo. The head position passes on only when that successor merges, takes W22, or leaves the queue (W3, W4, W13, W16 or W20). Only the head may take W21, and only immediately before its own merge attempt. That rules out updating N items against the same B and re-reviewing them all. At most one integration is in flight per repo (T9). A base move never updates any other PR, so review spend grows with integrations, not with open PRs.

### Transaction contract (H6)

- T1. Each row executes as one SQLite `BEGIN IMMEDIATE` transaction in `ahccore`. The guard re-reads every ledger fact it names.
- T2. A GitHub or GoodQA fact used in a guard is an observation row. It is taken before the transaction, stamped with its time and its SHA or ETag, and must be under 2 min old. A missing or stale observation fails the guard.
- T3. The writes are all or nothing: the state change, the rows named in Effects, the obligation change, and one audit row (actor, peer uid, from, to, row id, observation ids).
- T4. A row marked "authority log first" commits only after its log line is appended and fsynced. A failed fsync aborts the transaction (NEG-9).
- T5. No external call happens inside a transaction. The only external calls are:
  - W21's update-branch;
  - E2's dispatch;
  - readbacks;
  - outbox notices (H5).
  Each follows the commit of the row that authorizes it, and its result enters the ledger only through a later row.
- T6. Rows are idempotent by (entity id, row id, observation ids). A replay after a crash is a no-op.
- T7. While an item has an unsettled Effect (its Effect is `dispatched`, `outcome-unknown`, `held` or `fenced`), only W8, W9 (abandoned, unmarked), W10 (held), W24, W25 and W26 and the Effect's own rows move it; W4, W5, W13, W14, W17 and W18 wait for the Effect to settle, and a head move still creates the successor at once (W24). This is what lets an E3 confirmation after a head move or closure land as `merged` at H (L7). Otherwise, when two guards hold at once, these win in order: W4, W13, W14, W18, W19, W17, G8, G9. Otherwise the lower-numbered row wins. In particular, W17 (a protected path) beats W2, and W2 also requires e4.
- T8. The authority log is a superset audit trail, and the ledger is the state. A log line written before a rolled-back transaction stays, marked by its event id. A retry with the same event id reuses its sequence number. State is never derived from the log.
- T9. Dispatch linearization (F6):
  - A dispatch is "in flight" from the moment `ahc-merge`, holding a shared `flock` on `/run/ahc/dispatch.lock`, has re-read the kill epoch and the grant state and then sends the request.
  - The send has a client deadline of 30 s while the shared lock is held; on the deadline the request is abandoned locally, the lock is released and the op settles by readback (E5), never as absent.
  - Turning the kill switch on takes the lock exclusively, writes the new kill epoch and fsyncs it, and returns only after that. So every later dispatch sees the kill. The kill waits at most 45 s for the lock. If it is still held, the kill writes the new epoch, then terminates `ahc-merge` (the only process that sends, in its own unit) with SIGKILL and confirms its cgroup is empty, which releases the lock; only then does it return `kill complete`, naming the op in flight by key. If the cgroup cannot be confirmed empty, it returns `kill-incomplete`, raises an incident and keeps retrying the stop; the timer never acknowledges on its own, so no kill is reported complete while a process that could still send exists.
  - A grant revoke (G8) and a per-repo disable take the same lock exclusively, with the same bound and the same terminate-and-confirm fallback, so they give the same "no later dispatch" guarantee.
  - The kill also stops the ahc unit slice: running review units and `ahc-local` check units stop, and their rows go to outcome-unknown (R7). The credential refresher is not stopped.
  - A request already in flight settles by readback (E3, E4, E5). It is never assumed cancelled.
- T10. Authority epoch (F8):
  - A ledger restored from backup starts a new authority epoch, with every repo's enable flag off.
  - The reconcile set is every unsettled op in the restored ledger, plus every op the authority log or the ticket mirror records after the backup point.
  - Before main may resume with a stamped command, every unsettled operation is reconciled against GitHub: whether the activity log has its (before B, after H) entry, or the tip equals H.
  - Delivery allowances and CAP1 counts are taken as the larger of the restored ledger and the authority log, so they never go down.
  - A grant from an earlier epoch never reserves or dispatches.

A reserved grant past its expiry has no transition while its Effect is unsettled (design 3.9a). A grant is never used for a second operation key. Operation records and keys are kept until settlement, then for 30 days, then as tombstones. A request whose key is tombstoned is refused. A `fenced` or `held` op is not settled: it is never tombstoned, and its key, grant and CAP1 slot stay held. Late-apply watch (L5): it runs from the repo-level poll (W18, every 10 min), not only from the item's own readbacks. While any `fenced` op exists for the repo, the watch has no expiry. For 30 days after an op settles `abandoned`, the watch also checks it. Attribution: each activity entry is identified by its id, and it is attributed to at most one op. An entry is already explained when it is the entry that confirmed an op (E3, E12, E14, E10) or the entry an E16 incident named. A confirmed op or an E16 op at the same (repo, pr, B, H, policy revision) that has no entry yet may claim exactly one later (B, H) entry, and either also explains a tip equal to its H (an E16 op raised its incident once, at E16). An entry without an id is never explained. The watch fires only on a (before B, after H) entry that is not already explained, or on a tip equal to a watched H when no such op explains it; a tip-only incident fires once per op, and an entry, once attributed, never raises again. So when generation g is abandoned and generation g+1 at the same (B, H) is confirmed, the entry that confirmed g+1 does not trip g's watch, and an E16 op's own entry is not raised twice. A second (B, H) entry needs the branch rewound to B first, which W18 already raises as an incident, and the watch still fires on that second entry. A fenced op cannot be shadowed this way, because it blocks any new generation for its (B, H). If the activity log shows an unexplained (before B, after H) update for a watched op, ahc raises an incident naming the op, turns the repo's merging off and waits for main (E14). Fixtures (`tests.test_ahc_contracts.WatchAttributionTests`): an abandoned g followed by a confirmed g+1 at the same (B, H) raises nothing; an E16 op raises once, not again on the next poll; a second, unexplained (B, H) entry after a rewind raises. A failing-first variant that watches every abandoned op without attribution must fail the first fixture, and one that drops every abandoned op once any later op is confirmed must fail the third. The watch is a detector, not a fence. A successor item on a moved base B' may still be integrated: its CAS needs the tip to be B' and the fenced op's CAS needs the tip to be B, so at most one of them can match any tip. W18 also reads the activity log: an entry of type `force_push` on the default branch is always an incident, and an entry that matches no ahc op is L1. ASSUMPTION, checked by CHK-ACT at enablement: the activity API records an applied update within 60 s (chk-ff-dispatch saw it within 1 s) and keeps entries long enough for the watch; CHK-ACT records the observed lag and the oldest entry it can still read. Because entries may lag, E13 reads the activity log no earlier than 2 min after the dispatch, and twice, 60 s apart. A (B, H) entry that appears after an op is `fenced` is handled by E14 (confirmed, with an incident), never ignored. If an activity read fails, the watch and E3 fail closed (no confirmation, merging off after 1 h of failed reads).
