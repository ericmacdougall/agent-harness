# Portable T2Scan direct Astra consent

This opt-in broker verifies a fresh operator signature for the three synthesis assignments in one T2Scan audit. It spends each assignment once immediately before the guarded native Codex launch. The regular Agent Harness installer only ships the verifier source. A protected operator manages the socket, issuer, persistent replay state and enrollment separately.

## Trust and provisioning

Use a Linux execution host whose application UID has no administrative access to the broker configuration, code, socket ancestors, service UID or replay state. The application may submit a signed scope but cannot enroll an issuer, delete consumed nonces or revoke approval. Local administrative access defeats this boundary. A sudo-enabled application account on t2-dev can be used for staging tests only until a protected trust boundary is established.

A qualified operator independently verifies the executing host's Ed25519 SSH host-key fingerprint and application UID. The audience is the lowercase host label followed by a hyphen and the first 32 hex characters of the SHA-256 of canonical JSON `[fingerprint, uid]`. Use the normal OpenSSH fingerprint format, `SHA256:` followed by 43 unpadded Base64 characters. The broker checks that pin against the root-protected `/etc/ssh/ssh_host_ed25519_key.pub` at startup. A signer provisioned separately must carry the same audience pin.

The operator enrolls a hardware-protected P-256 signer that displays the signed scope and requires fresh human presence. The broker validates a detached signature against the enrolled public key. Enrollment is the trust decision that binds that key to human presence. Associate one issuer ID with one independently verified enrollment. The normal Claude human-source check remains separate.

Provision with the following fixed paths and ownership:

- `/usr/lib/agent-harness/t2scan_consent.py` and its ancestors are root controlled. Install the reviewed source there using the protected operator's release process.
- `/etc/agent-harness/t2scan-astra-consent/settings.json` is a root-owned JSON object with exactly `issuer`, `host_label`, `ssh_ed25519_fingerprint` and `peer_uid`. The host label permits lowercase ASCII letters, digits, dots and hyphens, starts with a letter or digit and has at most 24 characters. The issuer follows the same format with at most 64 characters. `peer_uid` is the local numeric, non-root account allowed to request checks and consumes.
- `/etc/agent-harness/t2scan-astra-consent/issuer.pem` is the corresponding root-owned P-256 uncompressed SubjectPublicKeyInfo PEM public key. Protect the files and all config ancestors against group or other writes. Stop the service for issuer rotation and retain the replay ledger.
- Create a dedicated non-login `agent-harness-consent` user and group, distinct from the application UID. Provision `/var/lib/agent-harness-t2scan-astra-consent` with this owner and mode `0700` below protected ancestors. Run `/usr/bin/python3 -I /usr/lib/agent-harness/t2scan_consent.py initialize-state` once as that service UID. Initialization rejects an existing ledger and runtime rejects an absent one. Preserve this directory across updates and investigate any lost or restored state before reactivation.
- Install the supplied systemd service and socket under the protected operator's unit directory. The socket is root-owned and the system manager owns the listener shared with the service UID. Activate it only after the issuer, application UID and ledger are provisioned. The broker independently checks the local Unix credentials on each connection.

## Signed scope and consumption

Export the canonical challenge as raw UTF-8 JSON bytes and the detached signature as raw DER. The challenge has no trailing line break. The signer signs the ASCII domain separator `Agent Harness T2Scan Astra direct approval v1` followed by a single NUL byte and the exact canonical bytes. The signing algorithm is P-256 ECDSA with SHA-256. Canonical JSON uses ASCII escapes, lexicographically sorted object keys, compact separators and integer epoch seconds. All protocol field values are ASCII. The maximum lifetime is 900 seconds and future starts are rejected.

Root keys are `schema`, `issuer`, `audience`, `provider`, `model`, `mode`, `project_id`, `run_id`, `created_at`, `expires_at` and `assignments`. The schema is `agent-harness.t2scan.astra-direct.v1`, provider is `codex`, model is `gpt-6-astra` and mode is `direct`. Each of exactly three items has `assignment`, `work_item_id`, `task_key`, `packet_sha256` and `nonce`. Sort by work-item ID. Use the roles `executive-synthesis`, `assurance-synthesis` and `delivery-synthesis` once each. Nonces are distinct random 32-byte values in lowercase hex. Task keys are the prefix `t2scan-audit-`, the first 32 lowercase hex characters of the SHA-256 of canonical JSON `[project_id, run_id, work_item_id]`, and the suffix `-astra-direct`.

Connect to `/run/agent-harness/t2scan-astra-consent.sock` for one request per connection. The interface accepts a single ASCII JSON object terminated by LF, with a maximum frame of 8192 bytes including LF. The client verifies the root listener peer and protected path, sends the request and shuts down the write side of the connection. Send `action` as `check` or `consume`, padded standard Base64 `challenge_b64` and `signature_b64`, and the independently known request fields `project_id`, `run_id`, `assignment`, `work_item_id`, `task_key`, `packet_sha256` and `model`. Maximum decoded sizes are 4096 bytes for the challenge and 72 for the signature. The response is a single line with `decision` set to `allowed` or `denied`, followed by EOF. Any other response, failure or timeout requires denial. The broker never echoes the signed material.

`check` verifies the current claim without spending it. The guarded launcher uses `consume` after obtaining the provider pool slot and immediately before dispatch. Each successful consume commits before the reply. Resolve an uncertain consume with operator reconciliation rather than retrying a possibly spent scope. Consumption grants one attempt even if the native program fails to start later.

To revoke a whole batch, a protected root operator sends `{"action":"revoke","challenge_sha256":"<lowercase SHA-256 of exact challenge bytes>"}` through the same socket. Revocation and consumption are ordered by the same durable SQLite transaction lock. A committed revocation rejects any later check or consume for those exact signed bytes. A consume already committed may proceed using its confirmed approval. The broker transports only consent metadata. Assessment packets and model responses stay with the T2Scan runtime.
