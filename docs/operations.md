# Operations and safety boundaries

## Components

| Component | Role |
| --- | --- |
| `HARNESS.md` | User-wide workflow instructions installed as a marked block in `CLAUDE.md`. |
| `harness/agents/*.md` | Task owner, click tester, fixer and red-team roles. |
| `wal.py`, `wal_note.py` | Private metadata and human-readable WAL entries. |
| `peer_review.py`, `report_file.py` | Read-only Sol plan/PR review with blind Opus fallback and inode-checked private reports. |
| `rescue.py` | Main-approved Astra rescue with Fable fallback on a clean worktree. |
| `publish_feature.py` | Guarded feature branch push to `origin`. |
| `integrate_local.py` | Guarded local merge into the starting checkout. |
| `watch-tests.py` | Polling test runner for source edits. |

No background process is installed. Claude Code runs hooks, and the main agent invokes the other helpers when appropriate. The installer refuses symlinked managed files and directories, including its backup directory, before reading settings or writing files. Reinstallation preserves unrelated hooks even when they share an entry with a managed hook. The installer rejects non-regular managed files (including FIFOs) and files occupying managed directory paths. It reads all source payloads before writing, then backs up the captured original bytes in private files before replacing managed files. It keeps original directory and managed-file inodes open through installation and rollback. A missing directory is created under a random staging name, opened and checked while empty, then published under its final name; the installer does not infer that a newly opened final name is the directory it created. Each file write compares the captured parent and file identity; a replacement is refused before mutation. The published file inode is recorded before the directory `fsync`, so a later write error can still roll back that file. A descriptor for each published managed file remains open through rollback so its inode number cannot be recycled while the guard relies on it. Reads, replacements, and rollback traverse parents without following symlinks, and each replacement rechecks the visible parent after publication. A parent that moves during installation produces an error rather than a success report. On a caught write failure it attempts to restore the original bytes and permission bits of existing files and remove newly installed files. Restoration continues after an individual failure; an incomplete rollback reports affected paths and the backup directory. Backups and newly created empty directories remain. This is per-file atomic replacement with best-effort rollback, not a crash-safe transaction: power loss, process termination, or a second failure during recovery can still require manual restoration. In an eight-process disposable contention test, some installers may refuse an intervening directory creation and succeed on retry; the final installation remains coherent. Concurrent settings editors can still race over read-modify-write settings, so do not run them together.

Before replacing a managed file, both installers also compare its current bytes and permission mode with the original snapshot. If either differs, they refuse the write and leave that path untouched. Rollback acts only on files this run published and refuses to replace or remove one whose published bytes or mode were edited in place. The backup contains the preflight snapshot, not a later external edit. A noncooperating editor can still write in the narrow interval between the final comparison and atomic replacement; filesystem rename has no portable compare-and-swap guard for file contents. Coordinate installers and editors if that race matters.

## WAL behavior

The `SessionStart` hook creates a private session log. Session and agent identifiers are reduced to `[A-Za-z0-9._-]` with a reserved escaped namespace and hash suffix for cleaned, truncated, uppercase, or reserved-prefix IDs so distinct values remain distinct on case-insensitive filesystems; the names `.` and `..` stay under `~/.claude/wals`. `UserPromptSubmit` logs prompt length, and `PreToolUse` logs tool metadata and target length. Neither logs the text or an unkeyed digest that could reveal a short input by guessing. `SubagentStart` creates a separate `agent-` log so an agent named `main` cannot alias the main WAL. Concurrent writers lock the file before appending a record. Prompt and pretool hooks use `onFailure: block`; a broken hook can stop those actions. Agents add semantic entries with:

```sh
python3 ~/.claude/hooks/wal_note.py --wal ~/.claude/wals/SESSION_ID/main.jsonl --event intent --note 'Brief intent without secrets'
```

Claude Code's `--safe-mode` disables customizations, including these hooks and `CLAUDE.md`. A safe-mode session therefore has no automatic WAL gate. A fresh normal headless session was smoke-tested after installation: it created `session` and `prompt` entries in a mode `0600` WAL.

Both WAL writers refuse symlinks from `.claude` down to the log, hardlinked logs, and non-regular files such as FIFOs. They open directories without following links, enforce mode `0700` on the WAL root and session directory, and mode `0600` on new and existing log files. If a concurrent first write gets `ENOENT` while creating the log, the writer retries at most three times with short delays. It verifies the pinned `.claude`, `wals`, and session directory components through their parent descriptors before retrying, then checks those components and the log file identity before writing and after `fsync`. Under the file lock, an append removes an unterminated final suffix left by an interrupted writer, then adds the next complete JSONL record. Recovery scans at most 64 KiB; a longer suffix fails closed for manual inspection without truncating the file. A removed or replaced path fails the hook. If a path moves during a write, a record may remain in the moved file even though the hook returns an error; inspect it before retrying. Mutation after the final identity check is outside this protection. Semantic note commands reject common credential-shaped values and assignments, including compound environment variable names, before writing. This guard cannot recognize every secret. Record redacted summaries, keep `~/.claude/wals` and `~/.agent-harness/codex-wals` private, review them before sharing, and do not commit them.

For behavior changes, use matching `PENDING_REAL_TEST <id>:` and `REALLY_TESTED <id>:` notes through `wal_note.py` before editing and after observation. Use `status` for the pending note and `check` for the verified note. The latter names the command or live steps, result, and applicable commit; any unmatched pending ID stays visible in the handoff. This is a concise audit trail, not an automated Stop gate. A disposable live slug-fix trial recorded `V1` before the edit, observed the baseline test fail, reran it successfully after the edit, and recorded the matched proof. A separate Stop-hook probe showed why the global gate was rejected: it ran on a simple arithmetic answer and forced an unnecessary second turn when configured to demand a test.

## Review and rescue

```sh
python3 ~/.claude/hooks/peer_review.py plan --repo /absolute/worktree --packet /absolute/plan.md --output /absolute/plan-review.md
python3 ~/.claude/hooks/peer_review.py pr --repo /absolute/worktree --packet /absolute/pr-packet.md --output /absolute/pr-review.md --expected-head FULL_COMMITTED_SHA
```

Both plan and PR review require a clean worktree; PR also requires the full expected HEAD. Plan review judges the proposed design against the observed baseline, while PR review judges the implementation and evidence at the specified commit. The external packet is untrusted evidence, not executable instructions. Both Sol and the blind Opus fallback run from the same private, detached Git checkout of the observed commit, with ancestor history available for diffs. The source checkout's ignored files and vendor directories, local configuration, refs, hooks, and unrelated objects are not copied into that checkout. Tracked vendor files, other committed files, and reachable history are review inputs: do not commit credentials or private material to them.

Snapshot preparation uses a fresh Git repository and a local fetch of the exact commit. Inherited Git routing variables and global/system configuration are disabled for preparation, verification, and reviewer processes; templates, hooks, replace objects, and lazy fetching are disabled. Source-local Git configuration is still read by source Git operations; this is not a defense against arbitrary hostile Git metadata. Shallow/partial repositories, alternate object stores, grafts, and a reviewed tree containing symlinks or gitlinks are refused. Disabling global ignore rules can reveal previously ignored files as untracked and require cleanup before review.

The helper compares source HEAD, Git status, and tracked diff before preparation, before review, and after snapshot cleanup. It rejects index flags such as `assume-unchanged` and `skip-worktree` that can hide tracked edits from Git status and diff; the NUL-delimited index listing has a five-second, 40 MB, 250,000-entry budget and does not read tracked file contents. It also checks snapshot HEAD and cleanliness before and after review. Special-file metadata scanning skips ignored directories without opening their contents and retains limits of 250,000 entries, 64 levels, five seconds, and 1 MB of ignored-directory names. Git snapshot operations have 120-second deadlines; fetching complete reachable history has no byte or disk quota, so very large histories may need a smaller dedicated review repository. Cleanup must succeed before report publication, and reports identify the reviewed SHA and isolated input. These checks are not an OS isolation boundary: a process able to mutate the snapshot or access arbitrary external paths is outside this guarantee. Changes made and reverted between guards and changes after the final check remain outside the gate.

Report finalization reopens the published path without following symlinks, then compares its inode, bytes, size, mode, and link count with the private written report before either caller announces success. The comparison has a narrow final-check-to-announcement window; a later external edit can invalidate a previously successful report, so consumers still verify the exact reviewed SHA and report contents when using it.

Exit 0 means a reviewer returned PASS, 3 means BLOCK, and 2 means no valid review. Set `CODEX_REVIEW_MODEL` to override the Codex model used for review; the rescue model is fixed. The reviewer and rescue helper require one regular, unlinked packet file of at most 150 KB and put private reports outside the Git worktree, preferably in a private directory owned by the user. Give each attempt a fresh output path; an existing file or directory is preserved and rejected before any model call. The report writer pins its output directory, rechecks its identity before and after publication, and creates the final file atomically without replacement. It refuses a file created while a model runs or a directory moved during that run, with a nonzero exit; a rescue may already have edited or committed its worktree when report creation fails, so inspect it. If a directory moves after publication, a report may remain in the relocated directory; the helper never unlinks the public destination on failure because another writer could replace it. An old PASS report is historical evidence and must never be treated as the result of a failed new attempt; check the helper exit code and the fresh path together. Temporary-file cleanup and rescue result WAL append complete before the final directory/file identity check immediately preceding the success announcement; pinned directory and report descriptors remain open through that check. A WAL append failure also returns nonzero and directs worktree inspection. A result WAL entry describes model/worktree results, not proof that report finalization succeeded. The reviewer requires a worktree root; the rescue helper also requires a clean named branch. The reviewer reads the packet and repository. Do not include secrets or personal data in either. A PASS is advisory evidence, not proof that checks were run or that every defect was found. Reviewer and rescue model subprocesses use process-group cleanup after their deadlines; a deliberately detached child can still escape it.

The main agent can invoke `rescue.py` after repeated material findings, only in a clean rescue worktree and with a self-contained packet. A successful rescue still needs main-agent verification and final review.

## Publication and local integration

```sh
python3 ~/.claude/hooks/publish_feature.py --repo /absolute/feature-worktree --branch feat/example --original-branch main --expected-head FULL_FEATURE_SHA
python3 ~/.claude/hooks/integrate_local.py --repo /absolute/original-checkout --original-branch main --expected-head FULL_ORIGINAL_SHA --source feat/example --expected-source-head FULL_FEATURE_SHA --check 'python3 -m unittest discover -s tests -v'
```

The publication helper resolves `origin`’s effective push URL (including `pushurl` and `pushInsteadOf`) and asks that destination for its advertised default branch and refuses to push that branch, including nonstandard names such as `trunk`. If the default is unknown (for example, an empty remote) or the query fails, it returns `BLOCKED_REMOTE` (exit 4) and local integration continues. Multiple push destinations, or an effective URL that would be rewritten again during inspection, are rejected with `BLOCKED_POLICY` before any push; they cannot be checked or updated atomically across repositories. This follows Git’s [push URL semantics](https://git-scm.com/docs/git-push#REMOTES). It canonicalizes source-relative local push URLs, including paths with a colon after a slash, and preserves the source object format, then exposes the reviewed commit to a temporary bare repository through Git object alternates (without copying the project's history), then pushes that object to the inspected feature ref using a temporary remote pinned in command environment. This prevents a moving source branch, source-local URL rewrite, or source `pre-push` hook from changing the delivered object or destination. Because the isolated transport bypasses source `pre-push` hooks, publication scans bounded reachable history for [Git LFS pointer blobs](https://github.com/git-lfs/git-lfs/blob/main/docs/spec.md) and returns `BLOCKED_POLICY` if any are found; use an LFS-aware push path and let local integration continue. The LFS scan runs in that prepared transport immediately before pushing, using the same original object graph as the transfer. Source shallow boundaries and grafts cannot hide retained ancestor objects from inspection. A shallow source with complete accessible ancestry can publish if it has no pointer history; missing ancestor objects make verification fail closed with `BLOCKED_REMOTE`, even if the destination might already have them. All publication Git commands disable replacement objects. The scan conservatively rejects small blobs containing a recognized LFS version line, including CRLF, surrounding Unicode whitespace, extension records and legacy version aliases; malformed pointer-like text can therefore also require manual publication. Enumeration streams object IDs without paths and refuses more than 300,000 objects, 19,500,000 output bytes, or malformed/oversized ID records before buffering the complete enumeration. Candidate blob content is limited to 30,000,000 bytes. If the scan cannot complete within these budgets or its command deadline, it returns `BLOCKED_REMOTE` without pushing; the read-only enumeration process group is killed immediately on refusal or timeout. It does not create a PR; the main agent does that separately when available. A concurrent change to global Git URL rewrites or external DNS/transport routing remains outside this protection. Git terminal credential prompts are disabled during the push. Credential helpers and SSH can still stall; `--timeout` (default 600 seconds) bounds each Git command, including local inspection, temporary transport setup, and the push. Local inspection timeouts return `BLOCKED_REMOTE` before any push; the default-branch query has the smaller of this deadline and 30 seconds. For other Git commands, on timeout the helper terminates Git and descendants in its process group with SIGTERM, then kills anything still running after a two-second grace, before reporting. A timeout does not prove that the remote ref was unchanged: verify it before retrying.

The integration helper allows a small fixed set of test/build commands and lockfile installs, parsed as argv without a shell; an unparseable or unapproved command returns `BLOCKED_POLICY` (exit 2) before anything is touched, and `--repo` must be the root of the original worktree because checks run from that directory. It merges into a clean, unchanged original checkout. Each local Git command, dependency preparation, check, and merge-abort attempt has a `--timeout` in positive seconds (default 600 per command). A failed branch, HEAD, or cleanliness inspection blocks integration; an empty error result is not treated as a clean checkout. A timeout terminates that command’s process group with SIGTERM, so Git can remove its own lock files, then kills anything still running after a two-second grace, before attempting to abort the merge; a missing executable or nonzero exit also triggers an abort and `BLOCKED_LOCAL` (exit 3). Failure reports include the failed phase, an exit code when available, and `merge_aborted`; they omit child stdout and stderr because arbitrary test or hook output can contain secrets. Text decoding replaces invalid bytes so malformed output cannot bypass rollback. For a failed prepare or check phase, rerun the listed allowlisted command locally for diagnostics after the checkout is safe. When `merge_aborted` is false, inspect `git status`, `MERGE_HEAD`, locks, and HEAD before retrying; a commit may already exist. The helper never uses a hard reset to force rollback. Python bytecode generation is disabled during checks. On Python 3.12 and later, `unittest` exits 5 when it discovers no tests, so a repository without tests is blocked rather than integrated unverified. The command allowlist is not a sandbox: test scripts and package lifecycle hooks execute repository code. Before commit, it compares the index tree with the intended merge tree and rejects unstaged or untracked test output; after commit, it verifies both parents, the committed tree, the original branch ref, and a clean checkout. Checks or hooks that stage extra changes cannot produce `INTEGRATED`. Test and build commands may still leave artifacts after a blocked merge; inspect the checkout before retrying. It does **not** validate reviewer reports or decide whether a check command is sufficient; that belongs to the main agent. Git hooks, merge drivers and signing are covered by the enclosing Git command’s deadline. Git removes `index.lock` from its own SIGTERM handler; the helper never deletes lock files itself, so a Git process that ignores SIGTERM past the grace and is killed can still leave one. Temporary files that Git does not clean on signals, such as `.merge_file_*` from an external merge driver, can remain as untracked files and make the next run report a changed checkout. A post-commit hook can time out after HEAD has advanced, so `BLOCKED_LOCAL` and `merge_aborted: false` do not mean no commit was created. A failed final HEAD inspection also blocks a success report. Inspect HEAD, merge state, locks and changes before recovery. Deadlines are per command, not an overall workflow budget: the termination grace, pipe cleanup and an abort attempt add time. Descendants that deliberately detach into another process group are outside timeout cleanup; hooks and checks must not start detached services that depend on this helper for cleanup. It does not push the original branch. If the original checkout is dirty or changed, preserve it and resolve the conflict with the user.

## Test watcher

```sh
python3 ~/.claude/tools/watch-tests.py --root /absolute/checkout --once -- python3 -m unittest discover -s tests -v
python3 ~/.claude/tools/watch-tests.py --root /absolute/checkout -- python3 -m unittest discover -s tests -v
```

The watcher polls common source extensions plus exact dependency filenames: `pyproject.toml`, `requirements.txt`, `poetry.lock`, `uv.lock`, `go.mod`, `go.sum`, `go.work`, `go.work.sum`, `pnpm-lock.yaml`, and `yarn.lock`. These names remain watched when `--extensions` changes the suffix list. It skips common vendor/build directories, generated-output directories (`coverage`, `test-results`, `playwright-report`, `.next`), and symlinked files/directories. Other generated files with watched suffixes can still retrigger a run; move them into a skipped directory or choose a narrower `--extensions` list. It compares file metadata (device, inode, mode, size, modification time, and status-change time), without reading source contents; on macOS/Linux this detects ordinary same-size edits with restored modification times and atomic replacements. Coarse timestamps and concurrent filesystem changes remain possible, so the watcher is a best-effort local convenience, not a security boundary or CI gate.

Watcher-authored status shows run number, elapsed time, exit status, and watched-file count without printing the checkout path or command arguments. Child test output is streamed verbatim and remains the test command's responsibility. A scan error stops the watcher with exit 2 and a generic message; a missing command executable returns 127 without echoing its path. A stalled test process group is terminated after `--timeout` (600 seconds by default), with `--once` returning 124 on timeout. Stop a continuous watch with Ctrl-C. After changing this helper, run `python3 install.py --apply` from the harness checkout to update the user-wide copy; the installer retains private backups of replaced files for manual recovery.

## Design limits

The policy is intentionally risk-scaled. The small fix path skips worktrees and review loops. A normal code task gets only relevant tests and documents. The agents must not infer that the presence of a test or a reviewer PASS proves quality. Independent checks, reviewer availability, UI tool access and remote permissions vary by environment; handoffs must say exactly what ran and what did not.

Claude Code settings can change between versions. The hook structure follows the [Claude Code hooks reference](https://code.claude.com/docs/en/hooks), and worktree agents follow the [subagent](https://code.claude.com/docs/en/sub-agents) and [worktree](https://code.claude.com/docs/en/worktrees) guides. Check these references when upgrading Claude Code.
