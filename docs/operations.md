No background process is installed. Claude Code runs hooks, and the main agent invokes the other helpers when appropriate. The installer refuses symlinked managed files and directories, including its backup directory, before reading settings or writing files. Reinstallation preserves unrelated hooks even when they share an entry with a managed hook. The installer rejects non-regular managed files (including FIFOs) and files occupying managed directory paths. It reads all source payloads before writing, then backs up the captured original bytes in private files before replacing managed files. It keeps original directory and managed-file inodes open through installation and rollback. A missing directory is created under a random staging name, opened and checked while empty, then published under its final name; the installer does not infer that a newly opened final name is the directory it created. Each file write compares the captured parent and file identity; a replacement is refused before mutation. The published file inode is recorded before the directory `fsync`, so a later write error can still roll back that file. A descriptor for each published managed file remains open through rollback so its inode number cannot be recycled while the guard relies on it. Reads, replacements, and rollback traverse parents without following symlinks, and each replacement rechecks the visible parent after publication. A parent that moves during installation produces an error rather than a success report. On a caught write failure it attempts to restore the original bytes and permission bits of existing files and remove newly installed files. Restoration continues after an individual failure; an incomplete rollback reports affected paths and the backup directory. Backups and newly created empty directories remain. This is per-file atomic replacement with best-effort rollback, not a crash-safe transaction: power loss, process termination, or a second failure during recovery can still require manual restoration. In an eight-process disposable contention test, some installers may refuse an intervening directory creation and succeed on retry; the final installation remains coherent. Concurrent settings editors can still race over read-modify-write settings, so do not run them together.

Before replacing a managed file, both installers also compare its current bytes and permission mode with the original snapshot. If either differs, they refuse the write and leave that path untouched. Rollback acts only on files this run published and refuses to replace or remove one whose published bytes or mode were edited in place. The backup contains the preflight snapshot, not a later external edit. A noncooperating editor can still write in the narrow interval between the final comparison and atomic replacement; filesystem rename has no portable compare-and-swap guard for file contents. Coordinate installers and editors if that race matters.

## Kimi independent review

`kimi_review.py` lets an agent get an advisory independent opinion from Kimi through the user's Kimi subscription, replacing the manual paste of a packet into the Kimi app. It wraps the official Kimi Code CLI (`npm i -g @moonshot-ai/kimi-code`, then `kimi login`, a device-code flow); there is no API key and no HTTP in the harness. Install the CLI on the user's Mac only: the login is a subscription session, so a shared Linux host would expose it to every agent there. The script never reads, copies or prints the stored credential (the CLI keeps it under `~/.kimi-code/`).

```sh
python3 ~/.claude/hooks/kimi_review.py --packet <packet.md> [--snapshot <file-or-dir> ...] \
  --output <fresh-report.md> [--head <full-sha>] [--model kimi-code/k3.1-pro-highspeed]
python3 ~/.claude/hooks/peer_review.py pr --repo <worktree> --packet <p> --output <o> --expected-head <sha> --secondary kimi
```

- **The result is advisory, never a sign-off.** Kimi sees only the packet text (and any snapshot files you pass), never the repository, and the author controls that text. Report headers say so: `Reviewer: kimi-code/<model>`, `Reviewer-Rung: n/a`, `Review-Input: packet text only (no repository snapshot, no tools)`, `Advisory: yes`. Other headers: `Reviewed-Model`, `Reviewed-Packet-SHA256` (raw packet bytes), `Reviewed-HEAD` when given, `Tokens-In-Estimate` and `Tokens-Out-Estimate` (the CLI reports no usage, so these are bytes/3), `Cost-USD: 0 (subscription)`, `Request-Id` (the CLI session id). The verdict line is `KIMI_ADVISORY: ACCEPT|BLOCK`. Reports are created exclusively with mode 0600.
- **peer_review.py:** `--secondary kimi` makes Kimi the single authorized independent fallback in place of the other harness, so one primary plus one fallback with no same-provider loop is unchanged. Kimi runs only after the primary fails with a quota, auth or availability error. Its answer is written to the report path with the advisory headers, the receipt records reason `ADVISORY`, the run exits 4 (not 0 pass, not 3 block), a `VERDICT: PASS` line in its text is neutralised, and nothing is recorded in the task ladder. A main-agent decision is needed before any Kimi opinion counts toward a gate; it would then need to see the gated diff, not the packet alone.
- **Egress gate (fails closed, before the CLI starts):** it refuses private locations (`~/.agent-harness/scratch` task outputs, local log-backup staging, `.claude/wals`, `.claude/projects`, `.claude/shell-snapshots`, `.claude.json`, `.codex`, `.config/gh`, `.config/gcloud`, `.ssh`, `.gnupg`, `.aws`, `.kimi-code` and the other Kimi directories, harness state, the leak denylist, keychains), matched case-insensitively and by inode, plus `*.jsonl`, `.env*`, names containing `secret`, `token` or `transcript`, and key files. It refuses any file with more than one hard link and any symlink inside a snapshot directory. Content is normalised (NFKC, invisible characters dropped, common lookalike letters folded) and then refused when it matches `redact.py` shapes, other key shapes (Stripe, short keys, base32 seeds, credential URLs, split tokens), long high-entropy strings (git and sha256 digests pass; lockfiles up to 200 KB may carry integrity hashes), WAL or Claude-transcript shaped JSON, the private `~/.agent-harness/leak-denylist.txt`, or the forbidden topics (yates, apex_app_pos, Granola, interview and Solve material). Verbatim user work-instruction quotes in `Source:` lines are allowed. Emails are redacted. The cap is 1.5 MB, collection stops reading at the cap, the gate checks a 20 second limit between scan steps and scans in 64 KB chunks, and because the prompt travels in argv the CLI path also refuses payloads over 600 KB (the Mac limit; Linux limits one argument to 128 KB). A refusal names the rule and line, never the matched text, and a refused call is not counted as a launch. In `peer_review.py` the gate also checks the packet path itself.
- **Isolation:** the agent file is parsed back and must declare `tools: []`; any tool call or tool record in the output fails the review closed. The CLI runs in an empty directory outside any repository, with a minimal environment (`HOME`, `XDG_*`, `TMPDIR`, `PATH`, `LANG`, `KIMI_*` limits), a scratch `HOME`, and a scratch `KIMI_CODE_HOME` whose `config.toml` carries only the managed provider, the one model and `default_permission_mode = "manual"`. The login directories are symlinked in, never read. The user's plugins (including kimi-cu), MCP servers, hooks and permission mode therefore cannot apply. `KIMI_LOOP_MAX_STEPS_PER_TURN=1` and `KIMI_LOOP_MAX_ATTEMPTS_PER_STEP=1` bound the CLI's own loop and its internal 429 retry. The CLI version must be 2.5.x (tested range) and its path passes the same executable trust checks as codex and claude. The child runs in its own process group, which is killed on exit. The CLI writes its session records into the scratch home, which is deleted when the call ends; nothing is added to `~/.kimi-code/sessions`.
- **Fast mode and swarm:** every call defaults to K3.1 Pro fast mode, which the CLI exposes as the alias `kimi-code/k3.1-pro-highspeed` (listed as "2x usage cost" against the subscription quota). Swarm cannot be enabled: the Kimi Code docs say only the user can turn swarm mode on (`/swarm` in the TUI), swarms are unavailable in `kimi -p`, and there is no flag or config key for it (confirmed by experiment on CLI 2.5.2). Docs checked 2026-11-07: https://moonshotai.github.io/kimi-code/ (llms-full.txt, release 2.3.2 and the AgentSwarm tool entry).
- **Quota and state:** a quota or rate-limit failure is never retried by the wrapper: it exits 7 and writes a 30 minute cooldown in `~/.agent-harness/kimi/cooldown.json` so later calls refuse before launching. A local daily call cap (40) is kept in `~/.agent-harness/kimi/ledger.jsonl`. An unreadable or corrupt ledger or cooldown file fails closed. Callers cannot raise the cap or reset the cooldown: the only override is `--main-override-daily-calls N`, for the main agent, and the state-home and binary overrides exist only in test mode. Exit codes of `kimi_review.py` (not of `peer_review.py`, where 4 means advisory): 2 usage, 3 egress refusal, 4 call cap, 5 login or trusted CLI missing (run `kimi login` on the Mac and approve the device code), 6 other failure, 7 quota.
- **Known limits of the gate (heuristics, not guarantees):** only email addresses are redacted; other personal data (phone numbers, card numbers, street addresses, national ids) passes. Obfuscated project names (`Y a t e s`, leetspeak), pretty-printed multi-line WAL entries and unlabelled base64 secrets that contain `/` can pass. The gate stops a careless or cooperative author, not a hostile one. Treat every packet as possibly retained and used for training.
- **Advisory reports in other tools:** `spec_flow.py` and `review_map.py` ignore the verdict of any report whose header says `Advisory: yes`, so a Kimi opinion cannot be recorded as a spec review.
- **Argv exposure:** the packet is passed as the CLI's `--prompt` argument because the CLI has no stdin or file input. On the single-user Mac that is visible to same-user processes (which can read the packet file anyway) and to root. Do not add a tool that persists full process arguments.
- **Data handling (read before sending anything private):** the Kimi consumer privacy policy (https://www.kimi.com/user/agreement/userPrivacy?version=v2, effective 2026-11-12, updated 2026-11-05, retrieved 2026-11-07; the Chinese mainland version) names Kimi Code as a covered product and says: user inputs and outputs may be used to optimise models after encryption and de-identification, with an opt-out by contacting customer service (section 11) and no in-app toggle; personal information is kept "only as long as necessary" with no fixed retention period; data is stored in mainland China and is not provided abroad without separate consent. It has no coding-specific retention or training terms, and a separate product policy would take precedence. The Kimi Code membership guide (https://www.kimi.com/help/kimi-code/membership-guide) says nothing on retention, training or location, and the CLI uses the international endpoint `api.kimi.ai`, whose policy was not verified. Treat every packet as possibly retained, stored in China and used for training until the user opts out in writing and the international terms are confirmed. The egress gate limits what leaves, but it is not a licence to send private customer or production code.

## WAL behavior

The `SessionStart` hook creates a private session log. Session and agent identifiers are reduced to `[A-Za-z0-9._-]` with a reserved escaped namespace and hash suffix for cleaned, truncated, uppercase, or reserved-prefix IDs so distinct values remain distinct on case-insensitive filesystems; the names `.` and `..` stay under `~/.claude/wals`. `UserPromptSubmit` logs prompt length, and `PreToolUse` logs tool metadata and target length. Neither logs the text or an unkeyed digest that could reveal a short input by guessing. `SubagentStart` creates a separate `agent-` log so an agent named `main` cannot alias the main WAL. The Claude hook and semantic-note writer omit the working directory from new records. Existing WALs are not rewritten; inspect older private logs if directory names need removal. Caller-authored notes and other helper records may still contain paths. Concurrent writers lock the file before appending a record. Prompt and pretool hooks use `onFailure: block`; a broken hook can stop those actions. Agents add semantic entries with:

```sh
python3 ~/.claude/hooks/wal_note.py --wal ~/.claude/wals/SESSION_ID/main.jsonl --event intent --note 'Brief intent without secrets'
```

Claude Code's `--safe-mode` disables customizations, including these hooks and `CLAUDE.md`. A safe-mode session therefore has no automatic WAL gate. A fresh normal headless session was smoke-tested after installation: it created `session` and `prompt` entries in a mode `0600` WAL.

Both WAL writers refuse symlinks from `.claude` down to the log, hardlinked logs, and non-regular files such as FIFOs. They open directories without following links, enforce mode `0700` on the WAL root and session directory, and mode `0600` on new and existing log files. If a concurrent first write gets `ENOENT` while creating the log, the writer retries at most three times with short delays. It verifies the pinned `.claude`, `wals`, and session directory components through their parent descriptors before retrying, then checks those components and the log file identity before writing and after `fsync`. Under the file lock, an append removes an unterminated final suffix left by an interrupted writer, then adds the next complete JSONL record. Recovery scans at most 64 KiB; a longer suffix fails closed for manual inspection without truncating the file. A removed or replaced path fails the hook. If a path moves during a write, a record may remain in the moved file even though the hook returns an error; inspect it before retrying. Mutation after the final identity check is outside this protection. Semantic note commands reject common credential-shaped values and assignments, including compound environment variable names, before writing. This guard cannot recognize every secret. Record redacted summaries, keep `~/.claude/wals` and `~/.agent-harness/codex-wals` private, review them before sharing, and do not commit them.

For behavior changes, use matching `PENDING_REAL_TEST <id>:` and `REALLY_TESTED <id>:` notes through `wal_note.py` before editing and after observation. Use `status` for the pending note and `check` for the verified note. The latter names the command or live steps, result, and applicable commit; any unmatched pending ID stays visible in the handoff. This is a concise audit trail, not an automated Stop gate. A disposable live slug-fix trial recorded `V1` before the edit, observed the baseline test fail, reran it successfully after the edit, and recorded the matched proof. A separate Stop-hook probe showed why the global gate was rejected: it ran on a simple arithmetic answer and forced an unnecessary second turn when configured to demand a test.

## Usage guard

Both editions install the same standard-library helper: `~/.claude/hooks/usage_guard.py` or `~/.codex/agent-harness/usage_guard.py`. It guards commands routed through it. Direct shell commands and native agents remain workflow-governed; no daemon, global Stop gate, permission reduction or distributed account enforcement is installed. Tiny fixes need no new receipt or model call.

State defaults to `~/.agent-harness/usage`; set `AGENT_HARNESS_USAGE_DIR` or global `--state-dir` to an owned private directory outside the worktree. Directories are `0700`, records `0600`. START precedes command execution; its metadata reference is emitted on stderr before the child starts. Stdout carries one final JSON result. FINAL records the observed execution/result/reason and a separately held digest reference. Inspecting a START reference is historical/UNKNOWN, not a claim that a process is still running. A missing FINAL is unknown, including after supervisor death. A session ID, PID, log text or exit zero is not completion proof. The main agent keeps foreground ownership through completion and hands off receipt paths and the actual responsible owner.

An input manifest is a mode-`0600` private JSON file, at most 32 KiB. Declare relevant public runtime instruction/config/schema/fixture/expected-record files and opaque revisions for secret-dependent configuration. Do not include credentials or hash secret inputs. For example, replace the paths and executable digest with verified values:

```json
{
  "schema": 1,
  "complete": true,
  "deterministic": true,
  "public_arguments": true,
  "files": [{"label": "instructions", "path": "/private/runtime-instructions.md", "public": true}],
  "revisions": {"config": "reviewed-config-revision-1"},
  "toolchain": {"python": {"executable": "python3", "public": true, "sha256": "REPLACE_WITH_VERIFIED_EXECUTABLE_SHA256"}},
  "environment": {"CI": "1", "LANG": "C"},
  "target": "local"
}
```

Toolchain entries identify an absolute `path` or an `executable` resolved through PATH, with an expected SHA-256 and explicit public declaration. A bare version string cannot verify executable identity. Relevant environment declarations are bounded nonsecret values from `CI`, `LANG`, `LC_ALL`, `TZ`, `PYTHONHASHSEED` and `NODE_ENV`; never dump the environment. Known helper files are included as runtime inputs. A missing/incomplete manifest, dirty or unknown input, unverified toolchain or secret-dependent input without a safe revision prevents reuse. Fingerprints cover declared dependencies, not universal discovery. HEAD changes invalidate conservatively even when tree bytes match.

Run focused test evidence with a finite timeout:

```sh
python3 ~/.codex/agent-harness/usage_guard.py check --repo /absolute/worktree --manifest /private/inputs.json --purpose feature-focused --owner owner-a --label focused --timeout 300 --kind focused --adapter unittest -- python3 -m unittest discover -s tests -p 'test_feature.py' -v
```

Replace `test_feature.py` with the actual module for the focused change.

Adapters require a recognized terminal result and nonzero observed executed count; zero cases or ambiguous output are NO_RESULT. The supported test formats are unittest summaries, pytest summaries and Go JSON test events. A non-test command needs `--kind command --adapter command --success-exit 0`, an explicit exit predicate rather than a claim about test coverage. Assertion findings, compile/process failures, provider errors and unknown results remain distinct. Receipts omit raw argv, prompts, source/log tails and credential values.

The helper retains typed outcomes/counts and receipt references only; it does not automatically retain raw child output or offer a log-file option. Arrange repository-native reports or a separate caller-owned logging/supervision path before a run when diagnostic output is needed. Capturing only the helper's stdout/stderr captures its final JSON and START metadata, not the child's raw test logs. Inspection/reuse commands can succeed administratively while evidence is unknown or ineligible: read the typed execution/result and reuse eligibility rather than treating their exit zero as check success.

A review FINAL records its historical provider outcome and remains provisional until the review's publication and final input checks settle it. Gate and reuse checks require that settlement. A later detected finalization failure appends an immutable invalidation; the historical FINAL is preserved and cannot authorize validation or cached acceptance. Missing or inconsistent START/history references and damaged pool state require diagnosis; ordinary reconciliation does not repair corrupted evidence.

A guarded `--kind full` run additionally needs `--gate RUN_ID:final:SHA256` naming accepted current subject-matching CODE_INSPECTION evidence with no open material findings. Review and test argv differ, so this gate matches the subject; reuse requires the exact invocation. If using verified native evidence or a bounded pre-review investigation, supply an explicit `--ungated-reason` that names the evidence/reason. It remains recorded as ungated and never becomes a helper approval. This does not waive required full validation. Freeze runtime files/docs before full execution; record late results in private/PR receipts.

```sh
python3 ~/.codex/agent-harness/usage_guard.py inspect --reference RUN_ID:final:SHA256
python3 ~/.codex/agent-harness/usage_guard.py gate --repo /absolute/worktree --manifest /private/inputs.json --reference RUN_ID:final:SHA256
python3 ~/.codex/agent-harness/usage_guard.py reuse --repo /absolute/worktree --manifest /private/inputs.json --purpose feature-focused --reference RUN_ID:final:SHA256 -- python3 -m unittest discover -s tests -v
```

CLI references use the printed receipt fields as `run_id:record:sha256`. REUSED references original scope, timestamp and result. It does not execute a command, create CHECK_OK, sign off a PR, substitute a prior-head approval or replace mandatory fresh validation. Failed evidence remains historical failure. An identical completed/reserved invocation is refused before another launch. One explicit `--repeat-reason` can spend the remaining declared aggregate budget; it cannot clear an unknown active reservation.

Missing FINAL, interrupted/unknown execution and stale pool ownership require diagnosis and an explicit append-only acknowledgement:

```sh
python3 ~/.codex/agent-harness/usage_guard.py reconcile --run RUN_ID --actor owner-a --reason 'Owned process and logs reconciled' --evidence 'private-evidence-reference'
python3 ~/.codex/agent-harness/usage_guard.py ack-pool --provider codex --pool default --actor owner-a --reason 'Availability change verified' --evidence 'private-evidence-reference'
```

Every START also records who holds the reservation (`owner_process`: pid, host, boot id, a process start-time token taken with TZ=UTC, and a deadline of the run's recorded timeout plus 60 s of grace; `AGENT_HARNESS_DEADLINE_GRACE` 0..3600 shortens the grace for live tests). A supervisor records each child it spawns through `process.run(on_spawn=run.note_child)` in `children.json`; peer_review records its reviewer process. A reservation without a FINAL is reconciled automatically, on the next `begin`, `acquire_pool`, `reconcile --auto` or `sweep`, only when all of these are proven on the same host: the owner is dead (pid gone, or alive with a different start token of the same scheme, or the boot id changed), every recorded child is dead by the same rule, and the deadline has passed. The record is a `reconciled.json` of kind `automatic_reconciliation` with the liveness facts as evidence; it keeps the run UNKNOWN / NO_RESULT, releases the pools the run held with a `RECONCILED` event, and never writes a FINAL; a late `finish` on a reconciled run is refused and its result discarded. A dead owner before its deadline, an owner on another host, a live owner or child, a START without owner facts, a boot id that cannot be read, and any pool held by a FINAL that itself says TIMEOUT or UNKNOWN stay uncertain and still need the manual command above.

```sh
python3 ~/.codex/agent-harness/usage_guard.py reconcile --run RUN_ID --auto
python3 ~/.codex/agent-harness/usage_guard.py sweep
```

`sweep` prints one report per run (`reconciled`, `why`, `liveness`), probes only runs without a completion, and is safe to run on a schedule; the dead-man check uses it.

Attempt budget: an attempt is zero-launch only when its FINAL shows `provider_launches` 0 (an int), no reported usage, execution `NOT_STARTED` and reason TRANSIENT_INFRA, LOW_DISK, QUOTA or AUTH: the provider was never launched and the refusal was infrastructure. Such attempts do not spend the two-launch repeat budget and the next attempt needs no `--repeat-reason`. Launched attempts, content outcomes (CODE_FINDINGS, INPUT_CHANGED, INVALID_OUTPUT), uncertain results and reconciled runs without a FINAL still count. Zero-launch attempts are bounded to 6 per rolling hour per invocation (`ZERO_LAUNCH_CAP`, `ZERO_LAUNCH_WINDOW`) and 32 attempt slots in all (`MAX_ATTEMPTS`); the refusal is `BUDGET_EXHAUSTED` and names the infrastructure, not the packet. Every attempt's elapsed time still counts against the declared aggregate budget.

These actions retain history and record actor/reason/evidence; they never manufacture successful execution. Acknowledging availability is separate from reconciling an active owner. Quota/auth cooldowns apply only to cooperating callers sharing this state directory and the configured opaque provider/auth-pool alias. Aliases do not derive from credentials. Trusted account errors can set a cooldown; vague credit messages, model-specific availability and tool content cannot disable the whole pool. A reliable reset hint can permit a later call after its reset; otherwise availability needs recorded evidence, with no polling, purchase or automatic model-switch loop.

Before expensive commands, disk probes cover work/build, temp and receipt filesystems. Default floors are 2 GiB for compile/test work and 256 MiB otherwise, with `--minimum-free-bytes` for a declared override or known higher peak. Missing data or low space prevents launch. Floors are not predictions and are subject to concurrent consumption. No automatic cache deletion or broad process killing occurs. Process-group cleanup retains its existing detached-descendant limitations. Hashes/permissions catch accidental staleness or mutation; same-user receipts are cooperative evidence, not signed attestations.

## Model ladder

`~/.claude/hooks/model_tiers.json` is the one tier table (R0 Sonnet/Terra; R1 to R3 Opus/Sol at medium, high and xhigh; R4 Opus/Sol max and R6 Fable/Astra high are review-only; R5 Fable/Astra medium needs the user's permission). `model_tiers.py` answers deterministic questions about it:

```sh
python3 ~/.claude/hooks/model_tiers.py table
python3 ~/.claude/hooks/model_tiers.py classify --model opus --effort high        # -> R2, claude
python3 ~/.claude/hooks/model_tiers.py reviewer --author-rung R2 --author-harness claude   # -> R3 on the other harness
```

`escalation.py` keeps one locked, mode-0600 state file per task under `~/.agent-harness/escalation/`. Failure events come only from machine receipts: a usage-guard FINAL whose review verdict is BLOCK with named findings, or a guarded test FINAL that is red at a HEAD the owner claimed fixed (`claim-fix`). Zero-launch attempts, TRANSIENT_INFRA, LOW_DISK, QUOTA, AUTH, TIMEOUT and UNKNOWN never count. Each event is keyed by the receipt's sha256, so replaying it is a no-op. The rung is a pure function of the events: two failures on the same finding fingerprint advance one writing rung, a new fingerprint resets the count, review-only rungs are skipped, and the top automatic rung stays put until the user approves the next one.

```sh
python3 ~/.claude/hooks/escalation.py record --task TASK --run-id RUN_ID --kind review --source peer_review:code-inspection
python3 ~/.claude/hooks/escalation.py claim-fix --task TASK --head FULL_SHA
python3 ~/.claude/hooks/escalation.py status --task TASK
python3 ~/.claude/hooks/escalation.py digest
python3 ~/.claude/hooks/escalation.py approve-top --task TASK --ask ASK_ID --wal ~/.claude/wals/SESSION_ID/main.jsonl
```

`approve-top` records the user's permission for the top writing rung only when the WAL holds an `ask` with a user-turn source (`user:`, or the `queue:` and `answer:` variants provenance treats the same way; since 2026-11-06) naming the task and an `ask_resolved` that references it. A state file that is missing, corrupt or locked resets the task to the lowest rung with a durable reset record (reason code, prior state hash, preserved copy) and a notification in `notifications.jsonl`; a corrupt file can never raise a rung. Every escalation or reset also appends a decision entry to the WAL named by `AGENT_HARNESS_MAIN_WAL`. Ladder limits (8 failing review launches, 3 automatic climbs, $60 per task, each counted launch spending the rung's review budget until helpers report real cost) block further writer spawns until a human signs off; `escalation.py gate-digest` lists what the hook refused or would have refused. On its own errors (an unreadable table, a symlinked or unwritable state directory) the hook denies spawns and `claude`/`codex`/`rescue.py`/`peer_review.py` launch lines only and never blocks plain shell use. `python3 ~/.claude/hooks/model_tiers.py mode` shows the installed mode and `mode --set warn` is the one-command rollback after the enforce flip (the rewrite reformats the table: sorted keys, indent 1). The Bash check reads literal tokens: `$c` and `--model $M` variable indirection, `xargs` and data-driven forms are not parsed (a `claude --model $M` line is denied as an off-table model under enforce: spell the model out), and a heredoc body mentioning a launch is split like text, so under enforce write such text to a file instead of a heredoc.

`tier_gate.py` is the PreToolUse hook for Agent, Task, Workflow and Bash. Bash lines launching `claude`, `codex`, `rescue.py` or `peer_review.py` are checked segment by segment (the line is split on unquoted `;`, `&&`, `||`, `|`, `&` and newlines; any denied segment denies the line; a review line at a permission rung needs the installed ledger's permission). A spawn names its task with `[task:KEY]` in the prompt or description; without it the hook generates a key and resets to the lowest rung. The requested model and effort must match the task's rung: above it is downgraded through `updatedInput`, below it needs a `[rung-below:REASON]` token, review-only rungs never write, reviewer spawns (red-team, click-tester, reviewer) sit one rung above, and the top writing rung needs the recorded permission. `mode` in `model_tiers.json` is `warn` (the hook only adds context and logs what enforce would do to `~/.agent-harness/escalation/gate.jsonl`) or `enforce`; an unreadable table denies. SubagentStart and SubagentStop keep a per-session live-agent count under `caps.session_live_agents` (default 40).

`peer_review.py --task TASK [--author-rung R] [--author-harness claude|openai]` picks the reviewer from the table (one rung above the author, the other harness preferred, the same harness one effort up when the other is unavailable, an unknown author reviewed at Opus/Sol medium and flagged), writes a selection receipt under `~/.agent-harness/escalation/selections/`, stamps `Author-Rung`, `Reviewer-Rung` and `Reviewer-Selection` on the report, and records the FINAL receipt in the task ledger so reviews count where they are consumed. `rescue.py --task TASK` runs at the task's computed writing rung on the other harness; `--rung` overrides it; a rung that needs permission is refused before any launch unless `approve-top` recorded it.

## Review and rescue

```sh
python3 ~/.claude/hooks/peer_review.py plan --repo /absolute/worktree --packet ~/.agent-harness/work/SESSION_ID/TASK/plan.md --output ~/.agent-harness/work/SESSION_ID/TASK/plan-review.md
python3 ~/.claude/hooks/peer_review.py code-inspection --repo /absolute/worktree --packet ~/.agent-harness/work/SESSION_ID/TASK/code-packet.md --output ~/.agent-harness/work/SESSION_ID/TASK/code-review.md --expected-head FULL_COMMITTED_SHA
python3 ~/.claude/hooks/peer_review.py pr --repo /absolute/worktree --packet ~/.agent-harness/work/SESSION_ID/TASK/pr-packet.md --output ~/.agent-harness/work/SESSION_ID/TASK/pr-review.md --expected-head FULL_COMMITTED_SHA --snapshot-base FULL_MERGE_BASE_SHA
```

All three review stages require a clean worktree; code inspection and PR review bind the expected HEAD. PLAN_RESULT and CODE_INSPECTION_RESULT use ACCEPT/BLOCK, while only a fresh PR can emit its pass marker. Code inspection examines implementation with full validation explicitly pending; final PR review checks the fresh full evidence and every delta. The external packet is untrusted evidence, not executable instructions. Both Sol and the blind Opus fallback run from the same private, detached Git checkout of the observed commit. The checkout holds only that commit and one base commit (depth 1), so its size follows the reviewed trees rather than the repository's history. The base defaults to HEAD's first parent so reviewers can check the packet's diff with `git diff BASE HEAD`; pass `--snapshot-base FULL_SHA` (an ancestor of HEAD, usually the merge base) to diff a whole branch instead. Other history is absent, `HEAD^` does not resolve, and the reviewer prompt names the base. The source checkout's ignored files and vendor directories, local configuration, refs, hooks, history, and unrelated objects are not copied into that checkout. Tracked vendor files and other committed files of the reviewed commit and base are review inputs: do not commit credentials or private material to them.

Snapshot preparation uses a fresh Git repository and a local depth-1 fetch of the exact commit (and base). Fetch verifies every received object ID; the helper then requires the snapshot commit and tree IDs to equal the source's, requires every named commit that has parents to be a shallow boundary, and allows no other boundary. Inherited Git routing variables and global/system configuration are disabled for preparation, verification, and reviewer processes; templates, hooks, replace objects, and lazy fetching are disabled. Source-local Git configuration is inspected before source status: executable local/worktree filters (including conditional includes), hidden index flags, and gitlinks are refused. Source status also forces ordinary stat, executable-bit and symlink-type checks and includes all untracked files. This is a bounded guard against known execution and concealment paths, not an OS sandbox or a guarantee against source configuration changing after preflight. Shallow/partial repositories, alternate object stores, grafts, and a reviewed tree containing gitlinks are refused. Committed symlinks are checked out in the snapshot as regular files whose content is the link-target text (`core.symlinks=false` for the snapshot and the reviewer processes only), so a reviewer reads the target path but cannot follow it outside the snapshot; the snapshot state check refuses any real symlink in the snapshot worktree, including inside ignored directories, and the reviewer prompt says how symlinks are shown. Disabling global ignore rules can reveal previously ignored files as untracked and require cleanup before review.

The helper compares source HEAD, Git status, and tracked diff before preparation, before review, and after snapshot cleanup. It rejects index flags such as `assume-unchanged` and `skip-worktree` that can hide tracked edits from Git status and diff; the NUL-delimited index listing has a five-second, 40 MB, 250,000-entry budget and does not read tracked file contents. It also checks snapshot HEAD and cleanliness before and after review. Special-file metadata scanning skips ignored directories without opening their contents and retains limits of 250,000 entries, 64 levels, five seconds, and 1 MB of ignored-directory names. The base ancestry check, snapshot fetch, tree listing and checkout share one `--snapshot-timeout` deadline (default 1800 seconds, at most 7200); metadata commands keep short fixed deadlines. The snapshot is prepared before the usage reservation, so a slow or failed snapshot launches no provider and leaves no reservation to reconcile. A very large reviewed tree still costs its full checkout size, with no byte or disk quota, and the post-checkout snapshot state check keeps the fixed status and metadata-scan limits described below. Cleanup must succeed before report publication, and reports identify the reviewed SHA and isolated input. These checks are not an OS isolation boundary: a process able to mutate the snapshot or access arbitrary external paths is outside this guarantee. Changes made and reverted between guards and changes after the final check remain outside the gate.

Report finalization reopens the published path without following symlinks, then compares its inode, bytes, size, mode, and link count with the private written report before either caller announces success. The comparison has a narrow final-check-to-announcement window; a later external edit can invalidate a previously successful report, so consumers still verify the exact reviewed SHA and report contents when using it.

Peer-review reports also name `Reviewed packet SHA-256`, calculated from the raw packet file bytes before text decoding for the reviewer. The helper keeps the original packet inode open and rechecks its identity, metadata, and bytes after review, immediately before the public report link, and before announcing success. To rely on stage acceptance, require helper exit 0, verify the stage and reviewed HEAD, and compare the header with the **current packet file's raw-byte SHA-256**. Only PR acceptance is PR signoff. A report without this header predates packet binding and cannot establish which packet bytes were reviewed. There is no atomic operation joining a packet check to the report link: a packet mutation immediately after that check can leave a historical digest-bound PASS file while the helper returns 2. Preserve that file, treat the attempt as failed, and retry with a fresh output path. A transient change entirely between checks may also escape detection; coordinate other packet writers while reviewing.

Exit 0 means acceptance for the named stage, 3 means a material block, and 2 means no valid review. PLAN_RESULT/CODE_INSPECTION_RESULT acceptance never becomes a PR PASS. Set `CODEX_REVIEW_MODEL` to override the Codex model used for review; the rescue model is fixed. The reviewer and rescue helper require one regular, unlinked packet file of at most 150 KB and put private reports outside the Git worktree, preferably in a private directory owned by the user. Give each attempt a fresh output path; an existing file or directory is preserved and rejected before any model call. The report writer pins its output directory, rechecks its identity before and after publication, and creates the final file atomically without replacement. It refuses a file created while a model runs or a directory moved during that run, with a nonzero exit; a rescue may already have edited or committed its worktree when report creation fails, so inspect it. If a directory moves after publication, a report may remain in the relocated directory; the helper never unlinks the public destination on failure because another writer could replace it. An old PASS report is historical evidence and must never be treated as the result of a failed new attempt; check the helper exit code and the fresh path together. Temporary-file cleanup and rescue result WAL append complete before the final directory/file identity check immediately preceding the success announcement; pinned directory and report descriptors remain open through that check. A WAL append failure also returns nonzero and directs worktree inspection. A result WAL entry describes model/worktree results, not proof that report finalization succeeded. The reviewer requires a worktree root; the rescue helper also requires a clean named branch. The reviewer reads the packet and repository. Do not include secrets or personal data in either. A PASS is advisory evidence, not proof that checks were run or that every defect was found. Reviewer and rescue model subprocesses use process-group cleanup after their deadlines; a deliberately detached child can still escape it. The rescue helper reads Astra's optional handoff only from a regular, singly linked file of at most 1 MB, opened without following symlinks or blocking on pipes. An unsafe or oversized handoff blocks report readiness and leaves the worktree for main inspection.

The review helper normalizes supported Codex JSONL and Claude JSON/JSONL terminal envelopes before extracting a verdict; structured errors, unsuccessful completion, malformed output and nonzero exit cannot sign off despite embedded pass text. Legacy plaintext uses strict stage/verdict markers. A wrong-stage marker is invalid output. It launches at most one primary and one authorized independent-provider fallback, with `--timeout` between 1 and 720 seconds per call and at most 1,440 seconds of provider execution; a fallback receives only the remaining budget. Invalid output and code findings do not spend a fallback call. Codex `Reconnecting... N/M` error records are treated as progress, and a plain `error` record repeated verbatim by the final `turn.failed` is classified by that final record. The final Codex error record of a transcript with no completion or agent message, carrying no structured code, type, subtype or scope, counts as an auth failure, which may use the fallback, only when its own message carries an explicit `401`, `unauthorized` or `revoked` signal (for example a revoked refresh token); that prose-derived classification never places an account-pool cooldown, and model or tool output is never inspected for it. Without a cooldown, later runs on a revoked token still spend Codex's reconnect attempts from the shared provider budget before falling back. Use `--input-manifest` for declared runtime identity and `--pool`/`--fallback-pool` for opaque auth-pool aliases; a model override cannot bypass same-pool cooldown. One explicit `--repeat-reason` may spend the remaining immutable-purpose budget. Token/money usage is recorded only if reported by the provider; no dollar/token cap or zero charge on early cancellation is promised. `--packet-budget-bytes` can tighten the 150,000-byte ceiling; 32 KiB and exact duplicate fenced-block warnings are advisory and never rewrite signed bytes.

The main agent can invoke `rescue.py` after repeated material findings, only in a clean rescue worktree and with a self-contained packet. A successful rescue still needs main-agent verification and final review.

The rescue wrapper does not stage or commit leftover model edits. It always exits 3 after a valid model attempt, including a clean committed descendant reported as `needs-main-verification`; exit 0 is never a rescue success signal. The isolated worktree and its existing Git index remain in place. Main must independently inspect the preserved worktree, branch, commit ancestry, file types and contents, and test evidence, then obtain final review before integration. If the model leaves a dirty worktree, the report says `needs-main-commit`; main must test and commit the preserved work. Any failed Astra invocation preserves the worktree for main inspection instead of triggering Fable. Fable is used only when the Astra executable is unavailable and the worktree remains unchanged under Git inspection; the main agent must give this worktree exclusive ownership. The wrapper compares `.git/info/attributes`, `.git/info/exclude`, and repository-local configuration values for their alternate paths while selecting fallback and reporting status. It does not pin the alternate files' contents or worktree-scoped configuration, nor attest to raw file bytes under every pre-existing attribute or stat-cache combination; a `needs-main-verification` report is only a handoff. Keep the report's `exit` field distinct from the helper exit: it records the model's exit code.

## Review helper reliability

`peer_review.py` never fails silently. An author on a review-only rung is refused with its own message, because no reviewer is needed and no CLI is at fault. Every other failed review prints a `REVIEW_DIAGNOSTIC code=<CODE> reason=<usage-guard reason>` block with the cause, numbered next steps, a `wal_note.py --event blocker` command to record the blocker, and a fixed disclosure: a native review you run instead is **native evidence only, it is disclosed, it is not a helper receipt**, and it never carries the PR pass marker. The helper never suggests skipping review. The budget is unchanged: one primary and at most one authorized independent fallback, 720 seconds per provider and 1,440 in total, and no same-provider retry after any diagnostic.

**Executable discovery.** Codex and Claude are looked up on `PATH` (absolute entries only; relative and empty entries are ignored) and then in `known_install_locations` of `harness/hooks/review_policy.json` (the ChatGPT app bundle, `/usr/bin/codex`, Homebrew and `~/.local/bin` by default). Set `AGENT_HARNESS_REVIEW_POLICY` to a private copy to change locations (a provider's list in the copy replaces the default list, so copy the defaults you still want); it is ignored with a warning unless you or root own it and it is not group/world-writable. Policy entries are candidates only: every candidate must resolve outside the repository, snapshot and working directory (compared case-insensitively and after Unicode normalization, and by device and inode of each ancestor, so a differently spelled path to the same folder is still refused), be a regular executable owned by you or root, not be group/world-writable, and have no world-writable ancestor (a root-owned sticky directory such as `/tmp` is accepted). The helper runs the resolved absolute path, once per provider, and records `usage.executables[provider] = {path, source}` (`PATH` or `policy`) in the run record's `final.json`; the invocation identity also holds the path digest and a digest of the effective policy. The reviewer process gets a PATH without empty, relative, repository, snapshot or working-directory entries, so a `#!/usr/bin/env node` reviewer script cannot pick up an interpreter committed in the reviewed repository. An override policy is ignored unless its directories, too, are owned by you or root and writable by no other user. Limits: the executable is checked at selection, before the snapshot, which decides the reviewer tier and availability, and again after the snapshot is built and before the provider runs, so it could be swapped in between (its sha256 is recorded in the invocation identity); group-writable ancestor directories (for example a root:admin 775 `/Applications`) are accepted; system temp directories are not refused as reviewer locations. When no reviewer CLI is usable, the refusal comes before any provider budget is reserved: it prints one diagnostic per provider and writes no run or ladder record.

**Snapshot deadline.** Without `--snapshot-timeout`, the deadline is `base_seconds + per_gib_seconds x pack GiB` from `git count-objects -v` (30 second probe cap), clamped to 7,200 seconds. A failed, hanging or zero probe uses the base. An explicit `--snapshot-timeout` (1 to 7,200) wins. The deadline is separate from the 720/1,440 provider budget.

**Usage-limit prose.** In a terminal Codex or Claude error record, or in the stderr of a Codex run that exits non-zero with no stdout, text such as "You've hit your usage limit" is classified `QUOTA` and unlocks the one independent fallback. Because it is unstructured text it writes no account-pool cooldown and sets no reset time; only structured provider codes do that.

**Packet lint.** For `code-inspection` and `pr` stages the packet must contain the full `--expected-head` SHA and at least one command line (`$ ...`, `Command:`, `Testing:` or a backtick span) with, in the same fenced block within 12 lines, an exit status of 0 and a positive count (`Ran N tests`, `N passed`, `N tests`, `N checks`). A command written just above a fence may have its output in that fence. A non-zero exit is not passing evidence. Each line is inspected up to 2,048 characters and the lint stops and rejects the packet after 5 seconds, so a hostile packet cannot hang the helper. This is a format guard: a count and an exit status in the same block are not proven to come from the same command, and reviewers still verify. The packet is never rewritten and the 150,000-byte ceiling still applies. Plan packets are not linted.

## Delivery workflow

Both editions install the same delivery implementation and dependencies. Claude uses `~/.claude/hooks/deliver.py`; Codex uses `~/.codex/agent-harness/deliver.py` and needs no Claude installation. Remote delivery also needs an authenticated Git transport and GitHub CLI (`gh`). The helper never merges a remote PR. Repository review, authorization and scope checks remain the main agent's responsibility.

Create private mode-0600 input files outside the worktree, in the durable session work directory the hooks announce (`~/.agent-harness/work/SESSION_ID/`) rather than `/tmp` or the scratchpad, so a reboot cannot destroy a run kit that a later `finish --resume` must reproduce byte for byte. A run kit records real commands; its text is validated but never executed by this helper. For example, replace these with the repository's actual verified instructions:

```json
{"run":"python3 -m app","test":"python3 -m unittest discover -s tests -v","watch":"python3 ~/.codex/agent-harness/watch-tests.py --root /absolute/original -- python3 -m unittest discover -s tests -v","logs":"Read the terminal test output","stop":"Ctrl-C"}
```

After final source review and tests, prepare the feature and draft PR:

```sh
python3 ~/.codex/agent-harness/deliver.py prepare --task OWNER_TASK --source /absolute/feature --original /absolute/original --original-branch main --expected-source-head FULL_REVIEWED_SHA --expected-original-head FULL_CAPTURED_SHA --kit-file ~/.agent-harness/work/SESSION_ID/TASK/kit.json --pr-title 'Reviewed scope' --pr-body-file ~/.agent-harness/work/SESSION_ID/TASK/pr-body.md
```

The effective fetch and push identities of both checkouts must be the same supported GitHub repository. Publication binds that identity inside the publisher before network effects; a policy refusal cannot become local fallback. `PR_READY` records the reviewed source, run-kit digest, PR number, generation and state path. It leaves the original checkout unchanged. Once the normal repository process has merged the PR:

```sh
python3 ~/.codex/agent-harness/deliver.py finish --task OWNER_TASK --generation GENERATION --original /absolute/original --original-branch main --mode remote --check 'python3 -m unittest discover -s tests -v'
```

Finish checks get their own deadline: `--check-timeout` (default 1800 seconds, at most 7200) bounds each preparation and check command, while `--timeout` (default 120) keeps bounding Git and GitHub commands. A bare `python` or `python3` check resolves through `PATH` to an absolute interpreter that must be Python 3.10 or newer. Finish checks this before any checkout effect and refuses an older or missing interpreter with `BLOCKED_POLICY`, naming the version found and asking for a supported `python3` first on `PATH`; each check run resolves and verifies the interpreter again. Remote finish, resume and `--resolve-baseline` stream check output to an owner-only log of at most 32 MiB under the generation's `checks/` directory, keeping the newest five logs (an older `check_log` path reported by an earlier attempt can therefore disappear). A failed or timed-out check there reports `check_log`, `check_status`, `check_log_truncated` and a 2000-character `check_tail`, with best-effort redaction of URL credentials, authorization headers, bearer and provider tokens, private-key blocks, cookies, and `KEY=value`, quoted JSON and `--flag value` secrets, and omits lines over 4000 characters; recovery responses carry the same fields. `integrate_local.py --resolve-journal` logs its checks under the journal's `checks/` directory the same way. Local-mode scratch and delivered checks still discard output. `integrate_local.py` accepts `--check-timeout` (default: its `--timeout`), which finish passes for local delivery. The full log is not redacted; treat it as private.

Remote finish verifies the PR's repository, branch, source SHA and merge commit. It fetches the exact advertised target through private bare transport, using the original object store without reading source-local routing configuration. The borrowed-store context explicitly disables automatic maintenance/GC and fetch commit-graph writing, and advertises available original/baseline/source negotiation tips. A real-Git regression uses aggressive maintenance and split packs to verify all prior objects survive; another verifies incremental object transfer, including cached feature history. It accepts only clean original history between the captured baseline and pinned target, reserves a shared recovery barrier and target ref, then uses hook-disabled `--ff-only --no-overwrite-ignore --no-autostash`. After exact merged-PR proof, the feature worktree may be removed or reused. Checks run in the actual original checkout. Concurrent remote advancement is accepted only after fetching the observed tip and proving the pinned target is its ancestor. The checkout and receipt stay at the pinned tested target; `remote_observed_head` identifies the later observation without claiming its code was delivered. Failed commands report observed HEAD even if Git advanced before returning an error; recovery evidence remains and blocks other tools on that original scope.

A saved `REMOTE_BLOCKED` generation permits `finish --mode local`; not every network-error response settles the generation. Explicit local-only work uses `prepare --local-only` (PR title/body are then optional) before local finish. Local delivery requires worktrees of the same repository, uses the scratch helper below, and leaves remote publication outstanding. `REMOTE_UNCERTAIN`, unsupported origins and policy refusals cannot silently unlock fallback. Missing origin is a definite remote blocker. Continue independent local work when remote access is unavailable.

Publication/create intents survive process loss. Query-only `prepare --reconcile-only --task OWNER_TASK --original /absolute/original --original-branch main` verifies an exact remote outcome without push, PR creation or checkout mutation, even when the source checkout has moved. Known PR numbers are queried exactly; inaccessible/ambiguous outcomes stay uncertain. A possible create is never disproved by a temporary empty list, malformed response or missing feature ref: it needs positive matching PR evidence. Durable `PUBLISHING` and `PR_LOOKUP` phases distinguish a push from a not-yet-attempted PR create. Explicit preflight failure before any push can settle `REMOTE_BLOCKED`; a definite push rejection or pre-create policy refusal settles `POLICY_BLOCKED`, permitting a new reviewed generation without local fallback. Fork/foreign PRs with the same branch name are excluded from owned matches. PR enumeration is capped at 101 records, rejecting more than 100, with bounded output and API deadlines. Publisher parent time is bounded to cover its fixed sequential per-command budgets; its deadline test uses a synthetic two-stage elapsed-time model, separate from real Git behavior tests. New reviewed source/run-kit inputs use `--new-generation` only after the prior generation is settled; older generations are stale and cannot mutate the current task.

Workflow state is private metadata beneath `<git-common-dir>/agent-harness/delivery-workflows`, separated from scratch journals and independent of HOME/session. One task lock serializes workflow receipt changes; the existing original-checkout lock serializes actual applies across tools. The local child owns that original lock itself so parent/child do not deadlock. A fresh local generation can retry a previously resolved identical baseline/source tuple; the child preserves the prior attempt in archive history. Only the guard API's explicit `reservation_started is False` proof permits returning a failed pre-reservation attempt to `PR_READY`; unknown or partially written own attempts retain recovery. A remote target remains reachable through an owned ref. Successful receipts are immutable and written only after checks; `ALREADY_DELIVERED` validates the historical delivered commit in a clean current original without silently syncing newer remote work. Full run-kit/body text and check-command text are not persisted in workflow receipts.

A moved, copied or restored checkout can have a different filesystem identity even when its path or files look unchanged. A saved generation/guard from another identity is not permission to rewrite scope identifiers or reset state. Stop, preserve the original records and diagnose the mismatch. A fresh owned checkout and fresh reviewed transaction may be appropriate; the helper does not migrate safety journals automatically.

An interrupted remote finish can be resumed explicitly when its known pending guard belongs to the exact current generation and the original is already clean at that guard's pinned target:

```sh
python3 ~/.codex/agent-harness/deliver.py finish --task OWNER_TASK --generation GENERATION --original /absolute/original --original-branch main --mode remote --resume --resume-reason 'Checks interrupted after sync' --kit-file ~/.agent-harness/work/SESSION_ID/TASK/kit.json --check 'python3 -m unittest discover -s tests -v'
```

Supply the same run kit and ordered preparation/check commands. Verify the project's interpreter and dependency prerequisites first and stop on a failed prerequisite; an unchanged command digest does not prove toolchain readiness. Declared `--prepare` commands run before checks, and a failing preparation prevents the test child from starting. Resume holds one original-checkout lock throughout read-only guard validation, fresh merged-PR/remote proof, fresh checks and durable completion. It never moves the checkout, selects a newer target, creates another guard or treats an earlier check as fresh success. Other recovery barriers, dirty/non-target state, changed bindings and resolved guards are refused before checks. Ordinary pending refusal remains unchanged.

Private per-attempt records beneath the workflow generation's `resumes` directory identify the followup executor revision/helper digests separately from the historical reviewed source and kit. Keep the reason free of secrets. A start without a final result, or a guard resolved before its workflow receipt completed, requires diagnosis; it is not delivery evidence. A reviewed followup helper can be invoked from its checkout before a global installation.

A failed apply that is not eligible for explicit resume requires inspection. Resolve actual shared journals using the lower-level helper's explicit `--resolve-journal KEY` below, at a full confirmed clean HEAD with real passing checks. `RESOLVED` accepts a baseline while retaining artifacts and actual pin-state facts; it proves no delivery. If the workflow stopped before binding its child/guard result, after all actual barriers are resolved use:

```sh
python3 ~/.codex/agent-harness/deliver.py finish --task OWNER_TASK --original /absolute/original --original-branch main --resolve-baseline FULL_CONFIRMED_SHA --check 'python3 -m unittest discover -s tests -v'
```

Only known interrupted apply phases can make this transition. Exact clean HEAD, passing nonvacuous checks, unchanged generation/state and no shared unresolved barriers are required. `RESOLVED_BASELINE` preserves every record/ref and writes no delivery receipt; start a new reviewed generation and finish with fresh proof. It cannot settle unknown push/PR outcomes.

No global Stop hook claims these steps occurred or blocks ordinary questions/background work. The main agent must call the helper and inspect the actual result. The run kit also needs useful user-facing instructions: verify a repository-native watcher or the installed dependency-free watcher (`~/.codex/agent-harness/watch-tests.py` or `~/.claude/tools/watch-tests.py`). Use `--once` to verify setup, omit it for continuous testing and Ctrl-C to stop. The helper cannot judge whether those commands are useful. Local scratch and remote checks execute repository code and are not an OS sandbox; same-user external mutations and changes reverted entirely between guards remain outside the guarantee.

### Prepare preflights and failure verdicts

`deliver.py prepare` refuses early, with a `reason` and a `hint` in its JSON, instead of failing late or generically:

- **Target sanity (`TARGET_POLICY` in deliver.py):** the original checkout is refused (`BLOCKED_POLICY`, reasons `HUGE_STAGED`, `HUGE_UNTRACKED`, `ORIGINAL_BEHIND`, `TARGET_UNREADABLE`) when it has more than 5000 staged or 5000 untracked paths, or is more than 1000 commits behind its local `origin/<branch>` tracking ref. Counts are bounded reads; a listing that exceeds the output or time bound counts as too many, and a git error in the listing is refused as `TARGET_UNREADABLE`. Limits are inclusive. Pass `prepare --target-policy warn --wal <session WAL>` to print a warning and continue to the strict clean check instead. Warn applies to that run only (it cannot come from the run kit or the environment) and is never silent: it is refused without a usable `--wal`, and each warn run, with the checks it bypassed, is appended to the WAL (a `risk` event), kept beside the generation journal in `target-policy-overrides.json`, and shown as `target_policy_overrides` in every later output of that generation. Behind-counts use the last fetched tracking ref, so fetch first for an accurate answer; when that ref is missing, prepare prints a warning that the behind check was skipped. To resume an in-flight generation while behind, do not move the original checkout (its HEAD is pinned); use `--reconcile-only` or `--target-policy warn`.
- **Remote base branch:** before any push, `--original-branch` must exist on the remote (exact `refs/heads/<name>`); otherwise `BASE_BRANCH_MISSING` and nothing is pushed. `BASE_BRANCH_MISSING` is not settled: push the base and re-run the same prepare. A remote that cannot be queried gives `REMOTE_BLOCKED` with reason `BASE_CHECK_UNAVAILABLE`; nothing was pushed, so, like any `REMOTE_BLOCKED`, it is settled and `finish --mode local` is available (or retry with `--new-generation`).
- **`gh pr create` failures:** a non-zero exit is classified from bounded, redacted stderr. Authentication, access, missing base, missing repository and validation errors, recognised only at the start of a gh message line and only when the follow-up lookup succeeds and shows no PR, become `REMOTE_BLOCKED` with a hint (re-run with `--new-generation` once fixed). If a PR exists anyway, it is adopted. gh's authentication exit code 4 counts as definite even without stderr. When the follow-up lookup fails too (usual for authentication or repository errors), the result stays `REMOTE_UNCERTAIN` and the hint names the likely cause. Any transient phrase anywhere in stderr, including gh's echoed `Creating ... for <branch>` line, keeps the outcome uncertain, so a branch name containing words such as `timeout` or `eof` always gives `REMOTE_UNCERTAIN` (the safe direction). Timeouts, killed processes, gateway or network errors, "already exists", a failed lookup, and unrecognised failures stay `REMOTE_UNCERTAIN` and are never a local-fallback licence. Output carries `gh_exit` and a sanitised one-line `gh_error` (escapes and control characters stripped, secrets redacted, at most 300 characters).
- **Waivers:** `commit_policy_waivers` in the prepare output lists every commit-policy waiver (kind, subject, id, WAL) the checked range used (at most 50, with `commit_policy_waivers_total` when there are more; fields sanitised, WAL as a basename). A waiver record that exists but cannot be read, or holds a malformed item, sets `commit_policy_waivers_unreadable` instead of looking like no waivers. Finish output does not repeat the list.

## Commit message policy

Every agent commit uses one structured format, and the commits in ticket-tracked repositories must reference a ticket that was updated after the commit. The rules live in one file, `commit_policy.json`, installed beside the hooks: `~/.claude/hooks` for Claude Code and `~/.codex/agent-harness` for Codex. Edit that file to change the types, the sections, the boilerplate lists, the tracked repositories or the ticket systems.

```text
fix(deliver): refuse non-compliant commit ranges before publication

Why: an agent reverted two production auth fixes with no recorded reason.
What: prepare checks the owner's commit range and blocks violations.
Testing: `python3 -m unittest tests.test_commit_policy` -> 42 passed
Refs: GoodQA #14151
Risk: optional; migrations, rollback

Co-Authored-By: ...
```

### Message rules

- **Subject.** Write `<type>(<scope>): <imperative summary>`, at most 72 characters, with no trailing period.
  - Allowed types: `feat fix refactor perf test docs build ci chore revert security`.
  - Summaries in the boilerplate list are rejected, such as `wip`, `update` and `various fixes`.
- **Body sections.** After a blank line, write `Why:`, `What:`, `Testing:` and `Refs:` in that order. `Risk:` is optional.
  - A section is rejected if it is empty, holds a placeholder, or is too short.
- **Testing.** Name the exact command and its result. Bare text like "tests pass" is rejected. If you didn't test, write `not run: <reason>`.
- **Refs.** Reference a GoodQA ticket as `GoodQA #N` (project `goodqa`) or `GoodQA <project-slug>#N`.
  - PR references and `R-NNNNNN` coordinator records are recognized. They do not count as a ticket, because they cannot be verified.
  - A repository is tracked when the `url` or `pushurl` of any remote, raw or rewritten by `insteadOf`, matches `ticket_systems.*.repos` (each URL is also matched in a normalized form: lowercase host without a trailing dot or port, scp-style or URL syntax, percent-decoding, `.`/`..` and doubled slashes resolved, `.git` dropped; SSH host aliases from `~/.ssh/config` are not visible). This applies to the GoodQA rule too. Renaming `origin`, pointing it at a fork with a tracked `pushurl`, or tracking only a second remote does not shed the rule. `check-range --push-url <url>` also counts the push destination.
  - In tracked repositories only `chore` and `docs` may write `Refs: none (<reason>)`. Every other type needs a GoodQA ticket.
  - Other repositories accept `none (<reason>)` for any type.
  - **Local ledger refs** (`Refs: Ledger <slug>#<8+ hex>`, the `ledger` system) count only in untracked repositories that have a remote, or in remote-less repositories whose absolute top-level path fully matches a regex in `ticket_systems.ledger.allowed_repos` (empty by default). They never satisfy a tracked repository's rule. Each one is resolved through `harness tickets show --json --min-version --as-of --slug`, with a 5-second deadline; a missing, old, hanging or malformed binary rejects the commit as "could not verify". GoodQA verification and delivery comments ignore them. See [the local ledger](ledger.md#commit-policy).
- **Reverts.** A revert uses type `revert` and includes `Reason:` and `Authorized-by:` lines. In tracked repositories, `Authorized-by:` must cite the GoodQA ticket that records the authorization.
  - A commit is treated as a revert if its body says "This reverts commit", even when its subject uses another type.
  - The policy enforces a recorded and verifiable citation. It cannot prove that a human approved the revert.
- **Trailers** such as Co-Authored-By and Signed-off-by come last, after a blank line.
- **Repeats.** A message identical to the previous commit's message is rejected.
- **Exemptions.**
  - Only real merges are exempt: a merge in progress (`MERGE_HEAD`), or a commit with more than one parent in a range. A single-parent commit whose subject starts with "Merge" is judged like any other, and so is a `gh pr merge --squash` message.
  - `fixup!`, `squash!` and `amend!` commits are allowed only on an unpublished branch. The publication check always rejects them.

### Enforcement points

1. **PreToolUse hook** (`commit_policy.py hook`). It runs before each Claude Code Bash call and each Codex tool call.
   - It reads the message from the forms it can check without running anything:
     - `-m` (repeated) and `-am`;
     - `--message=`;
     - `-F <file>` and `-F -` with a quoted heredoc;
     - `-m "$(cat <<'EOF' ... EOF)"`;
     - `--amend --no-edit`, which checks HEAD's message;
     - `-C <commit>`;
     - `--fixup` and `--squash`;
     - `gh pr merge --squash --subject --body`.
   - It fails closed with an explanation when it cannot know the message:
     - the message comes from `$VAR`, another `$()`, or an unquoted heredoc containing `$`;
     - the commit would open an editor;
     - `-F` names a file that does not exist yet;
     - the command is a bare `git revert`, `git commit-tree`, `eval`, or `gh pr merge --squash` without a subject and body;
     - git commit runs through another program (`xargs`, `find -exec`, `parallel`, `watch`, `sudo`, `env -S`), through a pipe into a shell (`echo ... | bash`), or under a command name computed at run time (`$G commit`);
     - a command that commits also runs a git subcommand that is not built in. That subcommand may be an alias, and the same command can define one (`git config alias...`, `GIT_CONFIG_*`);
     - another program in the same command touches the `-F` message file (`sed -i`, `python3 -c`, `truncate`, `>|`; reading with `cat`, `grep` or `git add` is fine);
     - the message could change after the check: `-e`/`--edit`, `--cleanup=strip|scissors`, or a `-F` file that the same command writes (redirect, `tee`, `cp`/`mv`/`install`, or a write to an unknown path);
     - git commit runs inside `$(...)` or backticks (for example `OUT=$(git commit ...)`), or `git history` rewrites messages;
     - an unknown git subcommand (possibly an alias) runs where the repository configuration is not visible: an unknown working directory, or over ssh.

   Shell keywords (`if`/`then`/`else`/`for`/`do`/`while`/`{ }`/`!`) and the wrappers `timeout`, `nice`, `ionice`, `stdbuf` and `caffeinate` (including their value flags) are unwrapped and checked. Shell options that take a value (`bash -o pipefail -c`, `--rcfile`, `-O`, `+o`) are understood. An alias call in a command that never contains the word `commit` (for example `git ci -m x`, locally or over ssh) is not analyzed. The git backstop catches it in tracked repositories on Git 2.54+, and the publication checks catch it everywhere. The same applies to deliberately obfuscated command names (for example `gi''t` inside a substitution). The hook guards against careless commits, not adversarial ones. A script file (`bash deploy.sh`) or a program such as `python3 -c` that commits is not visible to the hook. Outside dev2/T2 the git backstop covers those cases, and the publication checks cover them everywhere.

   It also analyzes `ssh <host> '<remote command>'`, `ssh <host> bash -s <<'EOF'` and nested `bash -lc` strings, which is where most dev2/T2 commits run. A remote host's files, HEAD and repository are not visible, so a remote `-F <file>`, `--amend --no-edit` or `-C` fails closed. Pass the message inline instead: `ssh host 'cd repo && git commit -F - <<"EOF" ... EOF'`. Remote commits are held to the ticket rule (`remote_tickets_required`).

   When it blocks, it lists the problems and prints a template that starts from your subject line.
2. **Git `commit-msg` backstop** (`commit_policy.py git-hook`). It is a Git 2.54+ config-based hook registered as `hook.agent-harness-commit-policy` (Claude) and `hook.agent-harness-commit-policy-codex` (Codex) in `~/.gitconfig`.
   - It runs alongside each repository's own hooks and never changes `core.hooksPath`.
   - It enforces only when both of these hold:
     - an agent marker is present (`CLAUDECODE`, `CODEX_THREAD_ID`, `CODEX_TOOL_CALL_ID`, `CODEX_SANDBOX` or `AI_AGENT`);
     - any remote URL of the repository matches `backstop_repos`.
   - Everywhere else it stays silent: human commits, test fixtures, and other repositories that agents run.
   - The installer reports "backstop inactive" when Git is older than 2.54.
   - If the script is removed, the hook command exits 0.
   - Not verified live: that Codex shells carry a `CODEX_*` marker (Codex quota was exhausted while this was built). For Codex, the PreToolUse hook is the primary gate.
   - dev2 and T2 run git 2.43, which has no backstop. A user-local git was not installed there, because the hosts are shared and a source-built git on agent PATHs risks breaking https push, LFS and credential helpers. On those hosts the protection is the ssh-aware PreToolUse hook plus the publication checks (`deliver.py prepare`, `gh pr create`, `peer_review.py pr`).
3. **Publication check in `deliver.py prepare`.** It runs only when prepare is about to create a new generation. Re-entering an existing generation never repeats it.
   - **Range checked:** commits reachable from the reviewed head, excluding the baseline and `refs/remotes/origin/<branch>`, so upstream commits written by others are never judged. If upstream moved, run `git fetch origin` first.
   - **Ticket check:** each referenced GoodQA ticket must exist and must have a comment that names one of these:
     - The commit SHA (7+ hex characters). Such a comment necessarily postdates the commit.
     - The branch. This comment must be newer than the commit time minus `clock_skew_seconds`.
   - **PR text:** prepare also checks the PR title (at most 64 characters, so `title (#N)` fits) and the PR body (the same sections), because GitHub squash uses them as the final message.
   - **Results.** Neither failure creates delivery state.
     - `BLOCKED_COMMIT_POLICY` (exit 2) lists each failing commit and stale ticket, with the fix.
     - `TICKETS_UNVERIFIED` (exit 6) means GoodQA was unreachable or answered unexpectedly. The check fails closed.
   - **Projects the credential cannot see.** The key reaches one GoodQA org only (`org_id` is pinned to it), so GoodQA answers `project_not_found` for refs in other orgs such as `GoodQA solve#7`.
     - Only projects listed in `ticket_systems.goodqa.unreachable_projects` (shipped: `solve`, `ai-course`, `harness`) are reported as `OUT_OF_SCOPE`. The ref still has to be well formed. The range passes with a warning naming `unreachable_reason`. `deliver.py prepare` and the PR-review gate print it; the `gh pr create` hook passes silently. Each warning is recorded once per ticket and head in `~/.agent-harness/commit-policy/warnings.jsonl`. finish skips the ticket's comment and lists it as not verified on the other tickets' comments.
     - Any other `project_not_found` fails closed as `TICKETS_UNVERIFIED`. That covers a typo, an invented slug, another org's project not yet listed, and the default project `goodqa`, which is never treated as out of scope. A missing ticket in a project the key can see is still `MISSING` and blocks.
     - Adding a confirmed slug is a config change. Empty the list once durable cross-org access lands.
   - Local-only delivery verifies tickets too.
   - **Credentials.** The member key file `~/.claude/goodqa-hive/member.key` (mode 600) is used first and keeps full access: verification, plus the finish and `notify` comments. Never copy it to another host.
     - A host without that file (dev2) reads `key_secret` (a Secret Manager secret named in your local profile) in-process through `gcloud secrets versions access`. The value is never passed in argv or the environment, and never written to disk.
     - That credential is **read-only** in code: only `list_orgs`, `list_projects`, `get_issue_by_number` and `get_issue_comments` are allowed. Any write (a comment, a status change) is refused before a request is sent. On dev2, `prepare` and PR review therefore verify tickets, but finish's ticket comment stays pending (exit 5). Post it from the Mac with the printed `notify` command.
     - If gcloud cannot read the secret, verification fails closed (`TICKETS_UNVERIFIED`).
   - **Project-qualified refs.** `GoodQA #N` means the default project `goodqa`. Tickets in another project need its slug, for example `GoodQA work-tracker-automatic#35633`. A `MISSING` result says so.
   - **Legacy commits:** commits authored before `enforce_after` are reported as legacy and do not block.
4. **Delivery comments in `deliver.py finish`.**
   - After `DELIVERED`, `LOCAL_DELIVERED` or a repeat `ALREADY_DELIVERED`, finish comments on each referenced ticket once, with an idempotent operation id.
   - The comment opens with the stage, "Merged (not yet deployed or live)" or "Delivered to the local checkout only". It then lists the delivered SHA, the PR, the checks that passed, and any waivers used.
   - Exit 5 means the delivery succeeded but a ticket comment is still pending. Do not start recovery; re-run the same finish command or the printed `notify` command.
   - Deployment happens outside `deliver.py`. After a deploy, post the evidence:

     ```sh
     python3 ~/.claude/hooks/commit_policy.py notify --repo <checkout> --base <baseline> --head <source-head> \
       --seed <generation> --stage deployed --evidence '<where and how it was verified live>'
     ```

   - Status changes are off by default (`on_delivered_status` / `on_deployed_status`), because GoodQA's done states need independent acceptance.

### Checks, waivers and audit

- **Check a draft:** `python3 ~/.claude/hooks/commit_policy.py check-message --file msg.txt` (add `--repo <checkout>` to apply that repository's tracked-repo rule and resolve `Ledger` refs)
- **Check a range:** `python3 ~/.claude/hooks/commit_policy.py check-range --repo . --base origin/main --head HEAD --branch <branch> --verify-tickets` (exit 0 pass, 2 blocked, 4 tickets unverified; `deliver.py prepare` reports the last case as exit 6 `TICKETS_UNVERIFIED`)
- **Waivers.** A waiver is the only exception path. There is no environment-variable bypass.

  ```sh
  python3 ~/.claude/hooks/commit_policy.py waive --wal <your WAL> --kind message|commit|tickets --subject <digest-or-sha> --reason '<why and who authorized it>'
  ```

  - The waiver is appended to your WAL and indexed in `~/.agent-harness/commit-policy/waivers.jsonl`. A waiver counts only when both records exist. It expires after `max_age_hours`.
  - A `message` waiver applies only in the session that recorded it. A `tickets` waiver applies to one range head, which is the offline delivery path.
  - Waivers are self-attested. The threat model is careless or hurried agents, not adversarial ones: an agent can edit the installed hooks anyway. The `waive` command is not on the permission allow list, but Codex with `approval_policy = "never"` and Claude in bypass or broad-allow modes will not prompt.
  - Every waiver that gets used is listed in the reports and in the delivery ticket comment.
- **Audit:** `commit_policy.py report --since 2026-11-04` lists the waivers and flags any whose WAL record is missing. It also lists out-of-scope ticket warnings (`warnings`, `warning_count`).

### Rollout and rollback

- A malformed `commit_policy.json` blocks only commit-like commands, with an explanation. Every other tool call runs before the file is read. The PreToolUse handler's timeout is 60 seconds, because `gh pr create` consults GitHub and GoodQA (internal budget: 10 + 15 + 25 seconds).
- `enforcement` in `commit_policy.json` takes three values:
  - `enforce` (the default) blocks.
  - `warn` prints the problems and allows.
  - `off` turns every enforcement point off.
- **Remove the git backstop:** `python3 ~/.claude/hooks/commit_policy.py uninstall-git-hook`. For the Codex key, use `git config --global --remove-section hook.agent-harness-commit-policy-codex`.
- **Remove the PreToolUse hook:**
  - Claude Code: delete the `commit_policy.py hook` handler from `~/.claude/settings.json`.
  - Codex: delete it from `~/.codex/hooks.json`.

## Command guard

`command_guard.py` (GoodQA #14471) is a PreToolUse guard for shell commands. It blocks two kinds of command before they run: commands that delete, move or empty the harness's own logs and state, and commands that print secrets or configuration into a transcript. It exists because an agent once fed test strings through a heredoc, and the real shell then deleted `~/.claude/projects` and `~/.claude/wals` and printed rclone OAuth tokens. The guard is stdlib-only and runs on Python 3.9 to 3.13.

### What it protects

| Tier | Paths | Refused |
| --- | --- | --- |
| A (logs and state) | Claude transcripts (`~/.claude/projects`, history), Codex sessions and history, WALs (any `wals` directory, `main.jsonl`, `*.wal.jsonl`, and under a work dir on any home `wal`, `wal-*`, `wal_*` and `wal.*`), the approval state in `~/.agent-harness/state`, credential files, and the guard's own installed files | every destructive form: delete, move, truncate, overwrite, `find -delete`, `rsync --delete`, `rclone move/sync/delete/purge`, interpreter one-liners, `git clean` |
| B (harness roots) | everything else under `~/.claude`, `~/.codex` and `~/.agent-harness`, for the local home and for `/home/*`, `/Users/*`, `/root` paths on ssh or container targets | delete, move, truncation, and replacing an existing file's content through a shell redirect (`>`, `>|`, `&>`, zsh `>!`, `1<>`, a `N<>` that a `>&N` dup or `exec` writes, every target of a zsh multios brace, and the existing files a redirect glob matches) or `tee`. `cat >! f`, `echo >! f`, `printf >! f` and a bare `>! f`, `&>! f` or `>&! f` empty the file in zsh, so they count as truncations, as `cat > f` does (see the note on `>!` below). Under `~/.agent-harness/work/<session>/...` a redirect may still replace a plain file (owners rerun `cmd > <task>/x.log`), except `*.json` receipts, `*.jsonl`, files in a folder named `state`, files directly in the work or scratch dir, and files in a directory marked with `.keep`. The same exception applies to a fully literal `/home/<user>/.agent-harness/{work,scratch}/...` path on another host, where the `.keep` and symlink checks cannot run; a `..`, variable or glob in such a path is refused. New files, `>>` appends and editor-tool edits are allowed; `cp` over an existing file here is not refused yet (GoodQA #14594) |

A command that names an ancestor of a protected path (`rm -rf ~`), or a path the guard cannot resolve but that points at one (a variable, glob or `cd -` it cannot follow), is refused too.

Exceptions, none of which applies to Tier A:

- Under `~/.agent-harness/work`, deletes are allowed only inside the git repository the agent is working in. That is the working tree whose top level holds the effective working directory: the payload `cwd`, or Codex `tool_input.workdir`, updated by a `cd` or `pushd` earlier in the same command. The tree must have a real `.git` (a directory holding `HEAD`, or a `gitdir:` file) that existed before the command, and it must lie strictly below a task folder. The top level itself, its `.git` and `git worktree remove` stay refused. A wildcard that could reach `.git`, `.` or `..` (one starting with `.`, `?` or `[`) voids the exception. A `tmp/` folder directly in a task folder is also deletable, by literal path only, so `rm -rf tmp/*` is refused and the message suggests per-item deletes. `kit.json`, `*.jsonl` and `state` directories are never deletable by name anywhere under `~/.agent-harness`. Session folders, task folders and sibling task folders are cleaned up with `workdir.py prune --apply`. When the guard cannot tell where the agent is working, the delete is refused.
- A command's own temp file (goodqa#15122): `"$T"` or `"$T/name"` may be removed or overwritten when the same command (or the script it runs) set `T=$(mktemp ...)` once with a plain `mktemp [-dqu] [-t prefix] [-p dir] [template]`, and the directory mktemp creates in is not a protected log, WAL or transcript location. The guard does not see the command's TMPDIR, so the default and `$TMPDIR` are checked against both the hook's TMPDIR (or `/tmp`) and `CLAUDE_CODE_TMPDIR`, symlinks resolved; a TMPDIR relocated under the harness is fine. The exemption is dropped (normal rules apply) when T is assigned, read, exported or looped over anywhere else, passed to a command other than plain readers, writers and rm (mv, cp, an interpreter or a function could make it a symlink), the command makes a symlink or sets TMPDIR, the path has `..`, a glob or more than one name after `$T`.
- Literal paths in `~/.agent-harness/scratch/<a>/<b>/<c>/...` are deletable, except WAL-shaped files, `kit.json`, anything in a `tasks` folder, and `*.output` and `*.log` files. Agent task output falls under the log-retention rule and is never deleted without a verified backup.
- Under `~/.claude` and `~/.codex`, literal paths are deletable inside a git working tree whose top level sits two or more levels below the root and whose `.git` existed before the command.
- In temp directories and inside git working trees outside the harness roots, WAL-shaped names (`wals/`, `main.jsonl`) are test data, not WALs.

**Residual risks.** These are recorded, not hidden:

- "Own worktree" means only "the repository the agent is working in". Any agent can `cd` into another agent's worktree, so the rule guards against mistakes; it is not an ownership boundary.
- `git clean` is allowed inside the worktree and can remove untracked `*.jsonl` or WAL-shaped files there.
- A `git init` run in an earlier command makes a folder count as a repository. That is outside the threat model, which covers careless or hurried agents, not an adversary.
- Name-based refusals have false positives: `*.jsonl` results and `state` directories under `~/.agent-harness` cannot be deleted by name.
- A script or program file that already exists when the command runs (`bin/dev2`, `./run.sh`, `python3 tool.py`) is the repository's own tooling. Only its deletions of protected logs count, and a Python file's source is not scanned. A script written earlier in the same command is judged in full.
- Inside the own worktree, a wildcard below the top level (`rm -rf build/*`) is judged by what it matches on disk when the guard runs. Hidden entries count, as if `dotglob` were set. A wildcard directly in the top level, one that can match a dot-name, or one behind a symlinked directory is judged by the pattern rule instead: it is refused when it could match a protected name. Above 2,000 matches in one command, the pattern rule also applies. A path whose `..` follows a symlink is judged where the shell really resolves it.
- `find` with `-delete`, `-exec rm` or `-exec mv` is judged by its start directories, whatever `-name` filters it has. The guard skips leading options such as `-P`, `-D`, `-O3` and `--`. Start directories read with `-files0-from` are unknown and refused. The operands of the `-exec` command other than `{}` are judged too. So `find build -name '*.o' -delete` is allowed. `find . -name '*.pyc' -delete` from the worktree top is refused, because the walk reaches `.git`. This is a known false positive: run it from a subdirectory instead. Two attempts to relax it by its filters both opened bypasses.
- `find -L` or `-follow` combined with a deleting action is refused.
- Known gaps, unchanged since earlier rounds:
  - an xargs here-string or heredoc line holding several paths is judged as one path;
  - a pnpm or yarn global flag before the bin (`pnpm --silent rimraf`) hides the bin;
  - a `-exec` operand that embeds `{}` (`{}/../x`) is not judged;
  - the POSIX classes `[^x]` and `[[:lower:]]` in a worktree glob are matched literally;
  - `cd -P` through a symlink is tracked logically.
- A nested repository below the worktree (`src/vendor/.git`) is not the worktree's own `.git` and is not protected. A script written with `tee` and then run in the same command gets only the heredoc advisory, not the written-then-run analysis.
- Not detected (tracked for a later round): `rsync` or `scp` of a whole credential directory such as `~/.ssh/` (single key files are caught); a PowerShell `Get-ChildItem ... | Remove-Item` pipeline whose `Remove-Item` has no path; macOS `ditto` over a protected directory; and a protected directory mounted into a container (`docker run -v ~/.claude:/c ... rm -rf /c/...`). The in-process `approve_delete` verifier can be replaced by code running in the same process. That is outside the threat model.
- Variables the guard cannot resolve fail closed. A positional parameter (`$1`, `$@`, `$0`), a loop variable over a glob or a substitution, a `read` variable, or an `export`/`declare`/`local` value that names a protected path refuses a destructive command whenever the same command names a protected location anywhere. That includes, for example, `ls ~/.claude/projects; for f in $(...); do rm "$f"; done`.

**Policy file.** `command_guard_policy.json` is optional and can only add protection. Its protective lists are merged into the built-in ones, and `broad_kill` may be set to `enforce`. Every other key is ignored, including allow-lists, regexes, temp roots and limits. The guard's own files (`command_guard*`, `redact.py`, `safe_input.py` in both hook directories) are refused for writes even when they do not exist yet, so an agent cannot create a policy file or a replacement module beside the hook. Block messages do not name the file.

### Secret and configuration dumps

Blocked: `rclone config show|dump|file|redacted|reconnect|paste`, a bare `rclone config`, `rclone config create|update|password` with values, `rclone authorize|reveal`, `--dump auth|headers|bodies`; `gh auth status --show-token`; and `gh auth token` in every shape except `VAR=$(gh auth token) gh <subcommand>`, where the subcommand is not `auth`, `config`, `extension`, `alias` or `secret`, with no other assignment, wrapper, redirect, pipe or further command. Also blocked: environment dumps (`env`, `printenv`, `set`, `export -p`, `declare -p|-x`, `compgen -v` with values, `${!name}`, and interpreter dumps such as `os.environ.items()`, `process.env`, `%ENV`, awk `ENVIRON` loops) and printing secret-named variables. `env | grep '^NAME='` or `grep -w NAME` with exact non-secret names is allowed. A prefix or substring filter (`env | grep -i GITHUB`) is still blocked, because it also matches `GITHUB_TOKEN`. Also blocked: `kubectl config view --raw`, `gh config get oauth_token`, `aws configure export-credentials`, `docker-credential-* get`, and `xargs cat` over paths listed from a credential directory. Reading credential files (ssh private keys, AWS, Codex `auth.json`, Claude `.credentials.json`, `rclone.conf`, `gh` `hosts.yml`, `.netrc`, `.npmrc`, `~/.env`, the approval key) with a printing reader or a network sender is blocked, and so is the same read through a copy made earlier in the command. So are recursive greps for secret words above a credential directory, Keychain password reads, `/proc/*/environ` and `ps e`. A project `.env` can still be sourced or added to git.

`rclone config file` is blocked too. It prints only a path, but it is the first step of the incident, and `doctor` reports where the config lives.

**Credential scripts and pinned routes (GoodQA goodqa#14518).** An existing script is otherwise judged only for log deletion. A script run by a shell or Python, or by its own path when its suffix or shebang says it is one, is also refused when its text outside comment lines names the rclone config directory or file, dumps the config with `rclone config show` or `dump`, or names the `GOODQA_CLOUDFLARE_API_TOKEN` secret. In Python the dump must open a string or be an argument list, so a table or a rule's wording that mentions the command is not refused, and neither is a real dump inside a longer string such as `"sudo rclone config show"`. `.json`, `.jsonl` and `.md` files, binaries, `bash -n`, `test_*.py` directly in a folder named `tests`, and the guard's own files are skipped. This check only adds refusals. It runs as a separate pass after the rest of the analysis has finished, with its own 1.5-second cap, and only when nothing else already blocks the command. The rest of the analysis is unchanged and keeps its whole time limit, so a slow read cannot turn any other refusal into a warning. A stop in this pass, including a read that stalls until the hook's alarm, ends the pass with what it found so far, and the rest of the verdict stands. Each file is read once per command. Commands inside a script already on disk are not checked, since they are judged only for log deletion. A command can take up to 1.5 seconds longer to judge. Its reads never wait on a FIFO or other non-regular file.

This is a text match with stated gaps. It does not catch a script that builds the name at runtime or calls another script, a name past the first 1 MiB, scripts reached after the pass's 1.5 seconds, a path the guard cannot resolve (`"$PWD/x"`, a glob, an exported variable), a runner it does not unwrap (`uv run`, `tmux`, `python3 -m cProfile`, `cat x | python3`), or a file run by another language (`node`, `perl`, `ruby`). A file on another host cannot be read. Copying the config as a command, such as `cp -r ~/.config/rclone /backup/x` or `cp` of the file itself, is not refused yet (GoodQA goodqa#14762).

Two one-off routes are the only exceptions: a fixed table in `command_guard.py`, for the pve evacuation. The Dropbox route allows one exact command string, `/bin/bash -p` and the script's path: in privileged mode bash runs no `BASH_ENV` or `ENV` file and imports no exported function first, and the script sets its own `PATH`. The DNS route allows that tool's pinned family of argument shapes (`list`, `set-ttl` and `set-content` with bounded names and values). Each needs a regular file at one path with one SHA-256, until 2026-11-09T00:00:00Z. Any other argument shape, pipe, prefix or byte in the file gets no route. Only the file itself must not be a symlink: a symlinked parent directory, or a hard link, still routes when the hash matches. No policy file, flag or environment variable can add one, and a later change removes the table. The hash is read when the guard decides, so a file changed after that still runs.

### How it decides

The command is lexed like a shell before any rule runs. The lexer handles quotes, `$'..'`, escapes, line continuations, heredocs (the body ends at its delimiter and the rest of the text is commands again), `$(..)`, backticks, pipes, redirects, brace expansion, prefix assignments, wrappers (`sudo`, `env`, `nice -n`, `timeout`, `xargs` including its here-string, heredoc, `< <(..)` and `-a` input, package runners `npx`, `bunx`, `pnpm dlx`, `yarn dlx`, `npm exec`, `uvx`, `pipx run`, `yarn`/`pnpm` (and `yarn run`) with a deleter bin, `shx`, `cross-env` and `cross-env-shell`, `eval "$(..)"`, `flock`, `script -c`, `tmux send-keys`, `osascript`, `at`), `sh -c` strings, `ssh` and `docker exec` commands, scripts written and then run in the same command, `$(which rm)`, absolute binary paths, and case and Unicode lookalikes. An unterminated quote or substitution, nesting that is too deep, or input over the analysis budget is blocked when the raw text names a protected location, a secret source, or a code-execution step (a pipe into a shell, `eval`, `-c` or `-e` code, a decoder) together with a destructive verb. Otherwise it is a warning. Block messages are passed through `redact.py` and never echo a secret.

zsh and bash read `>!` differently, and the guard cannot tell which shell will run the text. zsh takes `>! w`, `>>! w`, `&>! w`, `>&! w`, `&>>! w` and `>>&! w` as a single clobber or append operator with `w` as its target. bash stops the operator before the `!`, so it writes a file named `!` and `w` is a command word; it rejects `>>&!` as a syntax error. A script containing one of these operators, quoted forms excepted, is analysed once under each reading, each starting from the same state, and refused if either reading refuses. This happens at every parse, including `bash -c`, `eval`, `ssh` and `$(..)` text, because a nested shell can read the operator differently from its parent.

At the top level each reading sees its own later commands, so nothing has to be reconciled. Nested text (`eval`, `bash -c`, `ssh`, `$(..)`) has commands after it in the outer script. If its two readings end with different variables, aliases, links or working directories, or different text for one file other than bash's file named `!`, the command counts as unanalysable, because no single state describes both, even when nothing follows. An existing script is treated the same way although its state does not carry over. This can warn on harmless nested text, such as `bash -c 'echo a > out.log; echo b >>! out.log'`, and refuse it if the command's text or directory reads as sensitive. A file only one reading wrote is judged by what is on disk and then by its recorded text, because that reading may be the wrong one. When reading the disk text stops the analysis, the recorded text goes only to the raw-text check. For the commands that follow, a variable they disagree on is treated as unknown with its values as hints, which protects a path operand but not a command name, an option or a script path. A directory they disagree on is treated as unknown, and as protected if either names a protected location.

A script with these operators forks at most three times around any one parse, whatever the nesting, because plain levels do not count. Past that, or when a script is too large for two parses inside the analysis budget, it gets one reading (zsh's). The command then counts as unanalysable: refused if its text names a protected location or secret, or pairs `eval`, `sh -c` or similar with a destructive verb, otherwise a warning. This also applies inside an existing script, where only the command line that runs it is read for protected text, so `bash deep.sh` gets a warning. Anything already refused stays refused through a budget stop, a nesting error or the hook's alarm. Text the guard has not reached when it stops goes to the raw-text check only (GoodQA #14634), and forks spend the same budget, so a later command in very large text (about 240 KB in one measured case) can go unread and the command only warns. A one-sided file's recorded text and the commands after it can go unread the same way, and the disk file that stops the read can be small: a 27-byte script that calls itself is enough. The guard reads at most eight script files and does not warn past that. A one-sided file's disk read counts toward the eight, so a script its recorded text runs can go unread and the command is allowed.

A relative `cd` under a directory the guard could not resolve is judged by its text, as `cd "$X/.claude"` already was, with or without these operators: `cd "$D"; cd .claude; rm -f stale.txt` is refused.

dash also reads `&>` as `&` followed by `>`, whatever follows it, and rejects `>&!`. The guard does not model dash's reading.

For a script written earlier in the same command and then run by an interpreter the guard knows (`python3 run.py`, `node`, `perl`, `ruby`, `php` and others), one line naming a harness root under a real home spelling (`~`, an absolute home, `$HOME`, `os.environ`, `getenv`, or `.home` on any object), outside work and scratch, together with a call that can delete or write a file is refused. This matches text on that line, not the call's real target, so a comment, a dry-run print, a table of command strings used as test data, a copy out to `/tmp` or a new file under `~/.claude` on such a line is refused too, as are names like `~/.claude.bak`, `self.home`, perl's or php's own `$home` variable, and a read-only line where a later bare `w` follows `open`. Write such a script with the editor's file-writing tool instead. The rule does not follow a path held in a variable (including one named `home`), node's `os.homedir()`, ruby's `ENV['HOME']`, perl's `$ENV{HOME}`, `Path.home().joinpath(..)`, `os.chdir`, `shutil.move`, `shutil.copy`, `os.replace`, `os.rename`, `Path.rename`, `wb+` modes or `./run.py`, and it does not apply to existing scripts, `python3 -c` or an interpreter heredoc, which keep the log-only rule.

A heredoc whose body contains a deletion of a protected location gets an advisory warning even when the heredoc only prints the text or writes it to a file, such as test data or a commit message. Heredoc text passes through the shell, which is how the incident happened. The warning points to the editor's file-writing tool and does not block. Interpreter heredocs are scanned as code, and a deletion of a log still blocks.

The guard never emits an explicit allow, so the host's own permission flow still applies.

### Fail closed

The registered command is the launcher `command_guard_hook.py`, not the analyser. Claude Code allows a command when a hook crashes or times out unless the entry sets `onFailure: block` (Claude Code 2.1.295 and later), and Codex always allows. The launcher therefore runs the analyser in a child process with a 10 s watchdog. If the child crashes, cannot start, prints invalid output or runs out of time, the launcher decides from the raw text with the same probe and exits 2 for sensitive input. Non-shell tools return at once. The Claude Code entry matches `Bash|PowerShell` with a 30 s timeout and `onFailure: block`. Both entries pass the verb `hook`, which the launcher ignores; `cmd/harness/gates.json` lists `command-guard hook` as a fail-closed gate, so the Go front door blocks rather than allows when it cannot run the guard. The Codex entry has no matcher, because the host does not re-check `write_stdin` text typed into a running shell, and the guard analyses that text as shell input. It is the last `PreToolUse` group: Codex keys hook trust by position (`[hooks.state."<hooks.json>:pre_tool_use:<group>:<handler>"]` in `config.toml`), so appending it keeps the existing hooks' trusted hashes valid, and only the new guard entry needs trusting with `/hooks` in a new Codex session (GoodQA #14590). Upgrading from an install that placed the guard first moves every later group back one position, so hooks trusted under that layout need one re-trust. A command split across several `write_stdin` calls is a residual risk.

### Deleting logs on purpose

The agent may approve a delete itself, but only after a backup that the approval command verifies in the same run:

```bash
python3 ~/.claude/hooks/command_guard.py approve-delete --path <literal path> --remote dropbox:<mirror dir> --wal <WAL path>
```

`approve-delete` refuses in these cases:

- a glob or variable path;
- a whole root, or a whole `projects`, `wals`, `sessions` or other top-level log directory, or one of their parents;
- more than 20,000 files;
- anything changed in the last 10 minutes;
- a remote that is not a named remote of type `dropbox` (checked with `rclone listremotes --long`);
- a remote copy that is missing a file, differs in size or hash, or offers sizes only.

A tree of many small files cannot be mirrored file by file in reasonable time at the account write rate (the pp407 trees ran at about 22 KiB/s). Back it up as one archive instead (goodqa#15068): run `tar -cf - <dir>` from the directory's parent so every member starts with `<dir>/`, optionally compress with `zstd` or gzip, stream it with `rclone rcat`, and upload a `.sha256` file (`<64-hex>  <archive name>`) and a `tar -tvf` listing beside it. Then:

```bash
python3 ~/.claude/hooks/command_guard.py approve-delete --path <literal dir> --archive dropbox:<dir>.tar.zst \
  --archive-sha256 dropbox:<dir>.tar.zst.sha256 --archive-listing dropbox:<dir>.tar.listing.txt --wal <WAL path>
```

The guard streams the archive with `rclone cat`, never to disk. The proof is the member comparison: every regular file in the archive (path, size and content sha256) must equal the local tree, with nothing missing and nothing extra. The `.sha256` file and the listing are written by the same uploader, so they are consistency checks that catch a broken upload run, not extra safeguards: the archive's sha256 must equal the `.sha256` file (which must not hold the digest of empty input), and the listing's (path, size) set must equal the archive's.

It refuses on any of these:

- a truncated or corrupt stream, or a `zstd` error; every gzip member is read, as `gzip -dc` and bsdtar read them, and anything but zero padding after the end of the tar refuses;
- a failed download, or a `.sha256` file or listing larger than its limit;
- an absolute member path, a member path containing `..`, or a path named twice by members of any type (compared after Unicode NFC and case folding);
- a symlink, hardlink or special member, or a symlink in the local tree (only regular files and directories are compared);
- more than 4 members per local file plus 1000, decompressed data larger than twice the tree plus 256 MiB, or a read longer than the timeout;
- a local file that changed between hashing and the end of verification;
- `--no-backup` given with the archive flags;
- any of the three remotes not being a named `dropbox` remote.

macOS bsdtar stores extended attributes as AppleDouble `._name` companions that its own `tar -tvf` does not list. Such a member is ignored when it is not a local file, starts with the AppleDouble magic `00 05 16 07`, and its sibling is in the archive.

The approval and its use in the audit log record the archive URL and its sha256. Verifying takes one full download and a hash of the local tree.

The approval is single use, signed with a local key and bound to the exact realpath, device, inode and a stat manifest. The hook consumes it under a lock, so of two commands racing for one approval exactly one runs. Every approval, refusal and use goes to `~/.agent-harness/state/log-delete-audit.jsonl` and to the WAL; report it in the ticket status. `revoke-delete` removes every approval.

### Deleting disposable copies without a backup (goodqa#14911)

When the user approves deleting something without a backup, ask with AskUserQuestion: one question per path, in a call that asks only that question, naming the exact literal path, with the predefined option "Delete, no backup" (optionally "Delete, no backup (Recommended)"). That exact label is the only approval: "Delete after backing up" and similar labels never approve. Then cite the answer:

```bash
python3 ~/.claude/hooks/command_guard.py approve-delete --path <literal path> --no-backup \
  --user-source answer:<session>/<uuid> --wal ~/.claude/wals/<same session>/main.jsonl [--ttl S]
```

The source must be exactly `answer:<session>/<uuid>`: no `user:` turn and no quoted excerpt. It must resolve, from the account's pinned `~/.claude`, to an AskUserQuestion answer that:

- is at most 24 hours old;
- answers a call with exactly one single-choice question, and that question is the key of the one answer;
- is a predefined option, never "Other" free text, whose label is exactly "Delete, no backup" or "Delete, no backup (Recommended)";
- answers a question that names the literal path as a whole path (`.../mirror-old` does not name `.../mirror`), and names no other path except ancestors of it given as context;
- comes from a real transcript: no symlinked `projects` folder, project folder or transcript, and the session id must be the file's exact name (case included);
- is from the same session as the `--wal`, which must already exist as a real file (no symlink) and hold a hook-written `pretool` entry dated before the answer. Give the session's `main.jsonl`.

The account home comes from the password database. The route refuses to run when `HOME` or `CLAUDE_CONFIG_DIR` points elsewhere. The hook blocks any `approve-delete` command that sets `HOME`, `CLAUDE_CONFIG_DIR`, `PATH`, a `GIT_*`, `LD_*`, `DYLD_*` or `PYTHON*` variable, or goes through `env`. Every git command the route runs uses a system git by absolute path (`/usr/bin/git`, then Homebrew's) with a constructed environment: `PATH=/usr/bin:/bin`, the pinned `HOME`, `GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_GLOBAL=/dev/null`, no other caller variable but `SSH_AUTH_SOCK`, and `ssh` as `/usr/bin/ssh`. A PATH shim or `GIT_EXEC_PATH` helper cannot answer for git. Bash commands that write, copy or link into `~/.claude/projects` (outside `projects/<dir>/memory/`), or make a symlink to it, are blocked as transcript forgery. This is best effort: `rsync`, `tar -C`, `unzip -d`, `ditto`, `git clone`, and interpreter code such as `node -e` or `sqlite3 .output` can still write there, with the same power as the Write and Edit tools (disclosed below).

Only two kinds of target qualify, and only when deleting them loses nothing:

- **The top of a git working tree.** Every file must be committed, with no changed, untracked or ignored file. No index entry may be assume-unchanged, and no skip-worktree file may be present on disk (absent sparse-checkout files are fine). The tree must have no stash, no linked worktree, no submodule or gitlink, no replace ref or graft, no filter driver in its config, no `.git/info/attributes` and no LFS store (`.git/lfs`). These are checked before `git status` runs, because status would run a filter. Every remote whose URL is a network URL (`https://`, `ssh://` or `git@host:`) on an allowlisted host (`marker.no_backup_remote_hosts`: `github.com` and `t2-dev` by default) is listed once with `git ls-remote <url> refs/heads/* refs/tags/*`, run outside the repository. Every commit reachable from HEAD or any ref, including remote-tracking refs, must be reachable from those live shas. Tracking refs are never proof, because they can be stale or hand-set; a commit that only a stale tracking ref holds is refused (run `git fetch --prune`, or push it). A local path, a `file://` URL or the repository itself never counts. Live shas this clone lacks are left out, which can only refuse more; if the remote has moved on, run `git fetch` first.
- **A disk image** (`.sparseimage`, `.dmg` or `.sparsebundle`) under `~/.agent-harness/work` that `hdiutil info` does not list as attached. Its size is recorded in the approval. Its contents are not inspected.

The route also refuses in these cases:

- the same answer (compared as `answer:<session>/<lower-case uuid>`) has already approved 4 paths. The count is taken under the marker lock, from the audit log, and an approval whose audit record cannot be written is not stored;
- the path is a log, WAL, transcript or approval state (always refused, with no override), a harness root or one of its parents, or a top-level directory;
- the path uses a glob or variable, is relative, or goes through a symlink or `..`;
- the TTL is above 3600 s.

Repository config cannot run anything or hide an edit during the checks: fsmonitor, hooks, the ext and file transports, ssh command, credential helper, pager and attributes file are all switched off, `core.checkStat`, `core.trustctime` and `core.ignoreStat` are forced to their defaults, filters are refused, and replace objects are ignored.

The approval is single use and MAC-signed. It is bound to the exact path and its inode, and is recorded in the audit log and the WAL with the user source and expiry. At delete time the hook checks every local fact again. For a git tree that means status, index flags, submodules, replace refs, stash, worktrees, unpushed refs, HEAD and a digest of every ref. For an image it means size, mtime and attach state. A change in between voids the approval. The `ls-remote` proof is made at approval time only; at delete time the digest of every ref must be unchanged. A no-backup approval is used only by a command that is just `rm [-rRfv] [--] <approved path>`: any other segment, substitution, redirect, background job or second line is blocked, because an earlier segment could create work that exists nowhere else.

Residuals, disclosed:
- The check proves that the user answered a question naming the path and chose a "delete" answer. It does not read the question's wording beyond the path.
- A same-user process can read the marker key, so the approval resists hand-edited markers, not an agent that sets out to forge one. This is the same as for the backup route.
- Commits that only the reflog holds, and repositories that borrow this one's objects through alternates, are not checked.
- The transcript store is agent-writable through the Write and Edit tools, which no hook judges, and through scripts run by name. A forged answer under a fresh project folder is therefore still possible; the route only refuses symlinks, Bash writes, case variants and a WAL that did not exist before the answer. The WAL check also trusts that `pretool` entries were written by the hook.
- ssh still reads the user's `~/.ssh/config` (needed for `t2-dev`). An agent that can edit that file could route the `t2-dev` listing elsewhere (for example with `ProxyCommand`) and so forge the proof. Listings from every allowlisted remote are pooled, so a GitHub remote next to a t2-dev remote does not help: if t2-dev's ssh route is not trusted, set `marker.no_backup_remote_hosts` to `github.com` only. The approval records every host that answered.
- A writer started in an earlier tool call can change the tree between the hook's recheck and the `rm` (the same holds for the backup route). Disk image contents are not inspected; only size, mtime and attach state are.
- An allowlisted host constrains the host, not the repository path: `t2-dev` accepts any path, including a disposable worktree that may be cleaned up later. Prefer a GitHub remote as the proof.
- The backup route does not have the sole-segment rule; there the backup was verified first.

### Removing an archive-backed tree on another host

Use this when a tree on another host (`dev2`, `t2-dev`, `ah-mac-mini`) has a verified Dropbox tar.gz, and a bundle if it has unpushed commits. That host's own guard has no user transcript, so it refuses relayed approvals. This route checks the approval on the Mac and then deletes over ssh, the way `ah kill --host` does (goodqa#15251):

```
python3 ~/.claude/hooks/remote_delete.py --host t2-dev --path /home/eric/wt/<name> \
    --archive-dir dropbox:<dir holding <name>.tar.gz, .tar.gz.sha256, .tar.gz.listing, .bundle> \
    --user-source answer:<session>/<uuid> --wal <that session's WAL>
```

- **The answer:** a predefined option at most 24 h old that approves every named path as a whole, such as "Yes, remove all 11 (Recommended)", "Delete them" or "Remove it". "Delete only X", "Remove all except Y" and any decline word are refused. A number in the answer must equal the number of paths the question names. The session's WAL must hold a hook entry older than the answer.
- **The question:** it must name the host, say the trees are backed up, and name the path, either absolute or as `~/...` under the remote home. One question may name several paths. An answer approves no more deletions than its question names paths, and never more than `archive_remote_max_paths_per_source` (16), counted from the audit log.
- **On the remote host:** the tree is checked twice, at the check and at the delete. Each time the archive is downloaded first and the tree is compared after it, so nothing written during the download goes unseen. The tree must be:
  - a plain directory at least two levels below home, outside the harness and credential folders (`.claude`, `.codex`, `.agent-harness`, `.ssh`, `.config`, `.gnupg`, `.aws`, `.kube`, `.docker`, `.local`, `.cache`, `Dropbox`);
  - on one filesystem, with no mount point inside;
  - when it is a git tree, a clean linked worktree. A checkout with its own `.git` directory is refused, because its branches and stash would go with it;
  - equal to the archive: the archive streams to its recorded sha256, holds the same entries, and every file has the same size and mtime and every symlink the same target. The listing has one line per member;
  - covered by a bundle that verifies and holds HEAD, when HEAD has unpushed commits;
  - the same directory (dev:inode) at the delete as at the check.
- **The delete:** a worktree is removed with `git worktree remove --force` plus prune, and its branch stays. Any other tree is removed as a directory. Both hosts write an audit line.

`remote_delete_agent.py` is the lower-level remote half that this route sends over ssh. Never run it directly: run by hand, it skips every approval check above and keeps only the remote archive checks.

## Kill guard

**Remote spawn (2026-11-06, GoodQA goodqa#14927).** `python3 ~/.claude/hooks/kill_guard.py spawn --host HOST [--log REMOTE_FILE] -- CMD ARGS...` starts CMD detached on HOST over ssh (BatchMode, words single-quoted, never re-parsed) and records the host, remote PID and the start time the host reports in a per-host ledger (`remote:HOST` root, HMAC-signed like the local one). From then on `ssh HOST kill [-SIG] PID` is allowed for exactly that PID, and only while a bounded probe (`ssh HOST ps -o lstart= -p PID`, 5 s) still reports the recorded start time, so a reused PID or a dead process is refused. Everything else stays refused: another host, a PID not in that host's ledger, a mixed PID list, a container, a nested hop (`ssh gw ssh HOST ...`), a variable host, a pid finder, every broad verb, and any ssh option that could reroute the connection (`-o HostName=`, `-J`/`ProxyJump`, `ProxyCommand`, `-F`, `-W`, `-S`, or anything not in the small plain set: `-p N`, `-l user`, `-q`, `-T`, `-n`, `-t`, `-4`, `-6`, `-o BatchMode|ConnectTimeout|LogLevel|ServerAlive*|ConnectionAttempts`; and, because OpenSSH keeps reading options after the destination, any option word right after the host other than `--`). `--log` takes a plain remote path (no `~`: it is single-quoted on the host). This is the route for an agent that must stop its own remote wait loop; it never makes a foreign remote process killable.

`kill_guard.py` (GoodQA #14506, matrix X05) is a PreToolUse guard that stops an agent from killing processes it does not own. It exists because an owner piped `pgrep -f` into `xargs kill`, and another ran `pkill -f`, and both stopped other owners' test runs on a shared host. It is separate from the command guard and reuses its parser, so wrappers (`sudo`, `env`, `nohup`, `timeout`, `sh -c`, `eval`, here-documents, aliases, script files) are followed. Threat model: careless agents and common obfuscation, not an agent that edits its own hooks.

### How ownership is proven

A PID is yours when it is not PID 1, not the hook process or any ancestor of it (the agent CLI and its shell), not a protected program (`claude`, `codex`, `sshd`, `launchd`, `systemd`, `init`, `tmux`, `screen`, `netwatch`), has your uid, and one of these holds:

1. its cwd (Linux `/proc/PID/cwd`, macOS `lsof -a -d cwd -p PID`) is inside your git worktree;
2. its program (`argv[0]`) is a path inside your worktree, or `argv[0]` is an interpreter or shell and `argv[1]` is a path inside your worktree (a `tail` or editor that merely names a file there does not count);
3. it is in this worktree's spawn ledger with the same start time.

Your worktree is the git toplevel of the tool call's working directory, not of a `cd` inside the command, so a `cd` into another owner's worktree proves nothing. Worktrees nested inside yours are excluded, and `/`, HOME and its ancestors are never used. Anything that cannot be read, times out (2 s per probe) or does not parse is unprovable and blocked. The probes run only after a kill verb is found, so ordinary commands cost nothing extra.

Process ancestry is deliberately not a proof: subagents share the CLI process, so another owner's processes are descendants of it too.

### Kill grammar

Once the shared command parser has handed the guard a `kill` command, the guard accepts it only if every word fits a closed grammar, checked against the word's exact source text so a form the lexer does not understand cannot pass as a literal (`kill_guard.py`, `parse_kill_words`). This covers the kill words only. A kill the parser never presents to the guard is not judged at all; those gaps are listed under Known limits below and tracked in goodqa#14654 (items 1-14) and goodqa#14677 (item 16):

- option, first word only and unquoted: `-SIG`, `-s SIG`, `-n SIG`, `--signal SIG`, `--signal=SIG`, then an optional `--`; or `-l`, `-L`, `--list`, `-t`, `--table` with plain signal values;
- target: a literal integer, a job spec `%N`, `%%`, `%+`, `%-` or `%name` matching `[A-Za-z_][A-Za-z0-9_.-]*`, unquoted or wholly inside one pair of quotes;
- `kill -0` only: one target that is exactly `"$NAME"` or `"${NAME}"`.

Everything else fails closed, whatever it would expand to: `$!`, `PID=4001; kill $PID`, `{4001,4016}`, `\\4001`, `$'4001'`, `$x""`, `%a$=x`, `%?str`, and a parenthesis in a command that holds a kill (`kill 4001(N) 4004`, where zsh drops the first word). The shell may read such words again as code, so the parenthesis rule judges the command up to the parenthesis with its variables resolved, whatever the command is called: `gkill`, `K=kil; ${K}l`, `$(...)`, `K=kill; eval $K 4001(N) 4004` and `eval "kill 4001" 4001(N) 4004` all count, as do `env -S` with a separate value, `watch`, `sh -c`, and a wrapper with the parenthesis word directly before the kill (`timeout 5 x(N) kill 4004`). A parenthesis word among a wrapper's own options is not seen (Known limits, row 26). When a value is unknown, a shell, `eval`, `source`, `trap`, a listed wrapper or remote tool, or a command whose name holds an expansion is refused if the input names a kill anywhere. Other commands that run text are not, such as `cmd /c` and `pnpm exec` (row 26). A command that only prints or searches its words (`echo`, `print`, `printf`, `ls`, `cat`, `head`, `tail`, `wc`, `grep`, `rg`, `ag`, `ack`) leaves them as data unless it is piped into a shell. A parenthesis in another command does not count (`[[ "$s" =~ ^(a|b)$ ]] && kill 4001`, `case "$x" in (a) kill 4001;; esac`), and neither does the definition `kill() { ...; }` or the parenthesis of an array literal. An array assigns its variable like any other, so `K=(kill); $K 4004` and `a=(kill 4001); $a 4004` are judged as the kills they run; in bash `$a` is only the first element, and the guard judges all of them. The words of a literal are also still read as a command, so `K=(kill stop)` is refused on its own and `K=(kill)` is not (Known limits, row 24). After a background job use `kill %1`, or start it with `kill_guard.py spawn` and use the printed PID.

### Starting processes you will need to stop

`python3 ~/.claude/hooks/kill_guard.py spawn [--log FILE] -- CMD ARGS...` starts the command detached from inside a git worktree, records its PID and start time in `~/.agent-harness/state/kill-guard/ledger-<hash>.jsonl` with an HMAC under a 0600 key in a 0700 directory, and prints the PID. `spawn` takes a command, never a PID, and the guard judges the spawned command as if you had typed it. The ledger protects against accident: anyone who can read the key can forge a line. A later call's `kill "$SERVER_PID"` is blocked by design; use the printed PID literally, or `netwatch orphans --kill --pid N`.

### Remote kills

Ownership cannot be checked on another machine, so every kill verb and every kill with a numeric PID inside `ssh`, `mosh`, `docker exec` or `kubectl exec` is blocked, as is the code of `ssh -o ProxyCommand=` and `-o LocalCommand=`. Remote listing and `kill -0` are allowed. The only remote kill is `ssh HOST netwatch orphans --kill --pid N[,N...]` (digits only; flags `--json` allowed). netwatch signals only processes it lists as orphans, and the guard recognises it by name. A local `netwatch orphans --kill --pid N` is allowed without the ownership proof, so an orphan of another owner can still be named by PID; that trust is accepted.

### Block messages and audit

Every block is one line and names `netwatch orphans --kill --pid <pid>`. It carries a rule code and PIDs, never the command, a secret or another process's command line. Each block appends a redacted line (time, rule, PIDs, a 16-character hash of the command) to `~/.agent-harness/state/kill-guard/audit.jsonl`.

### Fail closed

The registered command is `kill_guard.py hook`, a launcher that runs the analysis in a child process with a 10 s limit (8 s watchdog inside). If the child crashes, cannot start, times out, prints garbage, the launcher blocks when the normalised command text (the whole text, with quotes, backslashes and `$` removed) contains `kill`, `fuser`, `Stop-Process` or an indirection marker (ANSI-C quote, `eval`, `base64`, `xxd`), and otherwise allows with a note. Input above 8 MiB is always blocked. A harmless `eval` is therefore blocked while the analyser is broken. The Claude Code entry matches `Bash|PowerShell` with `onFailure: block`; the Codex entry has no matcher. The guard never blocks reading or editing its own files. Policy is `kill_guard_policy.json` (`mode`: `enforce`, `warn` or `off`; the file is human-edited, there is no override variable).

zsh and bash read `>!` differently, so the shared analyzer judges a script under both readings, and a kill either one runs is blocked (see the command guard's section on this operator). `>! kill 4004` is a kill only under bash, and `>! y kill 4004` only under zsh. A shell string sent over `ssh` is read both ways too, so `echo "kill 4004" | ssh h '>! bash -s'` is blocked. When a reading cannot be judged (too deeply nested, too large for the budget, or the readings disagree on what a later command uses), the guard blocks with rule `readings-capped`, whatever the text says, because a kill can be spelled without the word (`K=ki; K+=ll; $K 4004`). The size limit depends on time, so it moves with load. Harmless commands are refused in that case too, for example a nested `bash -c 'echo a > out.log; echo b >>! out.log'; grep -c killed out.log`, or `A=1; bash -c '>! y A=2'; echo $A`. The command guard only warns on these. Running an existing repository script that holds such a line (`bash disp.sh`) is refused too. Likewise, when the analysis stops on a command containing a clobber operator, the guard blocks even without a kill word, because the stop can come before the reading that holds the kill (a script written with `>!` is judged on disk first). A kill found before the analysis stops stays found. Without a clobber operator, a stop still allows text that has no kill word or indirection (see Known limits).

"Known" is the guard's reading of the last assignment in the text: it does not follow a subshell, a branch or a function body, so `K=(kill); (K=()); "${K[@]}" 4004` is allowed, as it is by the earlier rule (goodqa#14896, high). Further low gaps are listed in goodqa#14713.

The guard therefore does not close the incident class. It closes the kill words it is shown.

**A budget stop allows a kill with no kill word (goodqa#14764, high).** When the analysis stops (size, time or nesting) before it reaches a kill spelled without the word, and the text has no kill word, indirection or clobber operator, the guard allows. The time limit moves with load (goodqa#14763), so a command that is judged on a quiet host can stop on a busy one.

Not verified: busybox and util-linux `kill` option parsing, live `docker exec` and `kubectl exec` kills, and interactive zsh with Claude Code's shell snapshot (the zsh-only forms are refused by the closed grammar; only `kill A(N) B` and the `#` comment form were run, on macOS zsh 5.9 against sleepers). `sleep N; kill PID` is judged when the hook runs, not when the kill runs, so a PID reused in between is a residual risk. ## Production-delete guard

`prod_delete_guard.py` is a PreToolUse hook. It refuses destructive SQL aimed at a production database unless a recorded, user-sourced grant covers it. It is a port of Hawkeye's `hawkeye-prod-delete-guard.py`, which ran on dev2 only (goodqa#14908, rule S28). The detection starts from Hawkeye's rules and closes the bypasses a native review found on 2026-11-06. The grant store is the harness's own, and it is signed.

### What it matches

A call matches only when it carries a destructive statement together with an identifiable production target. The destructive statements are `DELETE FROM`, `DROP TABLE|DATABASE|INDEX|SCHEMA`, `TRUNCATE`, `UPDATE ... SET` with no `WHERE` in the same statement, `dropdb` and `mysqladmin ... drop`. They are matched after `/* */` comments, backslashes (with `\x20`, `\t` and `\n` escapes read as whitespace) and shell quote characters are removed, and again with `--` line comments removed, so `DEL""ETE`, `DELETE/**/FROM`, `DELETE\ FROM` and `DELETE--x` + newline + `FROM` still match.

Each production target yields the exact name a grant must give:

| Target | Grant names |
|---|---|
| `wrangler d1 execute <db> ... --remote` (value-taking flags such as `--env production`, `-c <config>`, `--persist-to`, `--command` and `--file` are skipped with their values) | `<db>` |
| a connection string (`postgres://`, `mysql://`, `mongodb://`, `redis://`, and similar) naming `prod` or `production` as a name segment | its host when the host names prod; otherwise its host or its database (either covers it) |
| a database client (`psql`, `mysql`, `mongosh`, `sqlite3`, and others) whose `-h`, `--host`, `-d`, `--dbname`, `--database` or `--db` value names one (attached forms such as `-hprod-db` included), or whose positional database argument names one | that value |
| `PGHOST=`, `PGDATABASE=`, `DATABASE_URL=` or `MYSQL_HOST=` in the command, or the same variable in the hook's environment when the command references it or relies on it (no `-h` for `PGHOST`, no `-d` for `PGDATABASE`) | the host, or the connection string's host or database |
| `ssh <prod-host>` running a database client or `wrangler` | the host |
| `docker exec <prod-container>` running a database client | the container |
| a tool that is production by construction: `mcp__*__d1_database_query` or `mcp__*__hyperdrive_*` | its `database_id` (or similar) field; with no such field the call is denied, because no grant can name it |

The guard also reads the SQL in these inputs, up to 200,000 bytes each and only as regular files (a FIFO cannot hang it):
- `--file`, and `psql -f` including grouped short flags (`-1f`, `-Xf`) and `--fi=`/`--fil=` prefixes;
- `< file` and `$(< file)`;
- every `cat` argument anywhere in a command that has a client: `cat file | client`, the same through `ssh`, `docker exec`, `sudo`, `env` or `timeout`, `$(cat a b)` and backticks, after `-c`, `--command=` or anywhere else;
- psql `\i`, `\ir`, `\include` and `\include_relative`, mysql `source` and `\.`, sqlite `.read` and `-init`, with or without quotes around the file.

A client fed through a pipe by anything other than `cat`, `echo` or `printf` (for example `head`, `sed` or `curl`) reads SQL the guard cannot see, unless its own flag replaces stdin (psql `-c`/`-f`/`--command`/`--file`, mysql or mariadb `-e`/`--execute`, mongosh `--eval`/`--file`) or a `<` redirect does. The flag must be its own shell word, or a short cluster of that client's boolean letters (`-Xc`, `-Be`); an attached option value such as mysql `-pchangeme` or `-Dstore`, psql `-Usvc`, or a value such as `-v x=-f` does not count. Flags such as psql `-e` (echo), mysql `-f` (force) and sqlite3 `-cmd`/`-init` do not. A `$(...)` or backtick substitution after the client that is not a `cat` or `< file` read is unjudgeable in the same way. This includes harmless substitutions: `psql -h prod-db -c "SELECT '$(date)'"` is denied, and no grant can lift it; compute the value in an earlier command. A prod-targeted command is denied when it has such a pipe or substitution, or when one of its SQL files cannot be judged at hook time: the file is missing, is not a regular file, is unreadable or is larger than 200,000 bytes. It is also denied when the command has any other step besides a plain pipeline (`;`, `&&`, `||`, `&`, a newline, `cd`, `pushd`, `xargs`, `<(...)`, `>(...)`, or a substitution that is not a `cat` or `< file` read): another step could write or swap the file first, and no list of writers is complete. `&>` and `2>&1` are redirects, not steps. Because every `cat` counts as input, a read-only prod command that also cats a file it writes (`psql ... > out.txt && cat out.txt`) or a missing file is denied; split it into two commands. Write the file in an earlier command, then run it. Relative paths resolve against the event's cwd, and `~` is expanded.

Commands over 64 KiB are split on whitespace instead of shlex. Every word naming prod after a client then counts as a target. Every client scan is bounded (at most 512 characters per scan, 256 words after a client and 64 clients), and a command too long to judge its database is denied when it carries a destructive statement. Adversarial 100 KB shapes decide in under 1 s on the Mac.

Out of scope, disclosed:
- SQL built at run time (`base64 -d | psql`, a variable holding the statement, a script run by name);
- a default host that is not in the hook's environment, and `PGSERVICE`;
- deletes that are not SQL (API calls, removing a data directory);
- statements the destructive list does not cover: MySQL multi-table `DELETE t FROM t`, mongosh `deleteMany` or `drop`, and redis-cli `FLUSHALL`, `FLUSHDB` or `DEL`;
- database MCP tools such as `mcp__*__execute_sql` whose text does not name prod;
- a libpq conninfo string (`psql "host=prod-db dbname=app"`), long-option prefixes for the host (`--hos=prod-db`), unlisted clients (`usql`, inline Python drivers), and other `$'...'` escapes than `\x20`, `\t` and `\n`;
- a statement past the first 200,000 bytes of a command's own text is still read, but a file over that size is denied rather than read in part.

It judges `Bash` commands, the fields of `mcp__hawkeye__run`, and the `sql`, `query` and `statement` fields of database MCP tools.

Prose that only mentions these words is ignored. A heredoc that also names a client and a prod host still matches, because shell text cannot be proven inert; Hawkeye accepted this limitation after three review rounds. A grant lifts it.

### Fail direction

- Before a match, any error allows.
- After a match, any error denies. That includes a grant file that cannot be read or parsed, a missing or short key, and an unsigned or tampered grant.
- If there is no grant file, there is no grant, and the call is denied.
- The guard only allows or denies; it never returns `ask`.

Register the hook without `onFailure`.

### Granting

When the user approves a production delete through AskUserQuestion, record the approval:

```
python3 ~/.claude/hooks/prod_delete_guard.py grant --user-source answer:<session>/<uuid> \
    --target <host-or-db literal> --wal <session WAL> [--ttl 900] [--note TEXT]
python3 ~/.claude/hooks/prod_delete_guard.py list
```

- `--user-source` must be an `answer:` id: an AskUserQuestion answer. A typed `user:` turn is refused, because "do NOT touch prod-db" cannot be told apart from an approval. `ah user-msg` finds the id.
- `provenance.py` must resolve the source to a real answer at most 1 hour old when the grant is made. At check time the bound is on `granted - source`, so a grant made near the end of that hour works for its TTL after it.
- The user's own selected answer must name the target as a whole name: ask with an option label such as "Approve DELETE on <target>", then cite the answer. The agent's question text never counts. An answer that names the target inside a host, port or path (`prod-db.example.com:5432`, `/srv/prod-db/x`) does not name `prod-db`, and an answer with a decline word outside the target name funds nothing: no, nope, nah, not, don't (either apostrophe), never, keep, kept, cancel, skip, stop, leave, hold, wait, later, instead, abort, reject, deny, denied, untouched, preserve(d), spare or "only after". The list is a deny-list: an agent-written label that mentions a second target without such a word ("Delete on staging-db, then prod-db") still names prod-db, so write one target per option.
- The source is resolved from the pinned `~/.claude` of the guard's home. `CLAUDE_CONFIG_DIR` is ignored.
- `--target` must equal, case-folded, a target name the guard extracts from the command. It is never a substring match. SQL keywords, client names, bare `prod` and `production`, names starting with `-`, and names with spaces, quotes or wildcards are refused. A command with several production targets needs a grant for each. A connection string to a prod host is covered only by a grant naming that host; a database-only grant (`app`) covers a connection string only when its host does not name prod.
- The TTL defaults to 900 seconds and cannot exceed 3600. A grant can be reused until it expires.
- The grant is written to the WAL first, through `wal_note.py`. Then it is stored, HMAC-signed, in `~/.agent-harness/state/prod-delete-grants.json` (mode 0600). The key is `~/.agent-harness/state/prod-delete.key` (32 random bytes, mode 0600, created on first use). Writes run under a lock, and expired or unsigned grants are pruned on each write.
- Each check verifies the signature, the scope, the expiry, the TTL bound and the source-age bound again, and resolves the grant's source again. A grant whose turn no longer resolves, or whose timestamp has changed, stops working.
- `command_guard` refuses shell writes to the grant file and the key, as it does for the log-delete marker.

Residuals, disclosed:
- Provenance proves that the cited answer is a real AskUserQuestion answer, and the guard checks that the selected answer names the target and does not decline. It cannot prove what the user believed the option meant; the WAL record and the exact-target binding keep that claim narrow and auditable.
- The key is used only when it is a regular file with mode 0600, owned by the caller, with one link, and it is opened without following a symlink. The store is replaced through an `O_EXCL|O_NOFOLLOW` temp file.
- A same-user process, or the Write and Edit tools (command_guard judges Bash only), can read or plant the key and so sign a grant. That skips only the WAL record, because the `grant` command is itself agent-runnable. The key protects the audit trail against hand-edited JSON, not against an agent that sets out to forge one.

### Commands and rollout

- `install.py --apply` copies the hook and registers it with the matcher `Bash|mcp__hawkeye__run|.*d1_database_query|mcp__.*__(execute_sql|run_sql|query|sql)|mcp__.*__hyperdrive_.*`.
- `doctor.py` runs two canaries: an allow for `ls`, and a deny for a `psql --host=prod-db... TRUNCATE`.
- Tests: `python3 -m unittest tests.test_prod_delete_guard`. They judge text only and never run SQL.
- Rollback: revert the commit and reinstall.

## WAL cadence

`wal_cadence.py` is a Stop and SubagentStop hook for rule W04. It nudges once when real work has piled up without a human-readable WAL entry. It is a port of Hawkeye's `hawkeye-wal-cadence.py`, which ran on dev2 only (goodqa#14908).

The hook blocks the stop once (exit 2) when all of these hold:

- The agent's worktree has at least 40 uncommitted source lines, tracked or untracked. Changes under `docs/`, `plans/`, `devstate/` and `audit/`, and `README.md` and `CONTRIBUTING.md`, do not count.
- That agent's WAL has no `wal_note.py` entry with a note from the last 20 minutes. Hook metadata rows do not count.

Which worktree and which WAL it checks depends on the event:

| Event | Worktree checked | WAL checked |
|---|---|---|
| `Stop` | the cwd, only when it is a linked worktree (the primary checkout belongs to the user) | `main.jsonl` |
| `SubagentStop` | only worktrees directly under `~/.agent-harness/work/<session>/agent-<id>/`, never the cwd (a subagent's cwd is often main's checkout or another owner's tree). An owner working in a tree elsewhere is not nudged. | `agent-<id>.jsonl` |

The nudge names the files and gives the exact `wal_note.py` command.

The nudge is bounded:

- It fires once per agent per distinct diff fingerprint. The state is kept in `~/.agent-harness/state/wal-cadence/<session>.json`.
- It never fires on a repeated stop (`stop_hook_active`).
- `HARNESS_WAL_CADENCE=off` turns it off.
- Every internal error fails open, so the hook is registered without `onFailure`.

Hawkeye's knowledge-net replication is not ported.

Tests: `python3 -m unittest tests.test_wal_cadence`. They use temporary git repositories and linked worktrees only.

## Worktree hygiene

`worktree_hygiene.py` is a Stop and SubagentStop hook for rule S18. It stops a turn from ending while a worktree the agent created or worked in holds work that exists only on this disk. It is vendored from Hawkeye's `hawkeye-worktree-hygiene.py` (ericmacdougall/hawkeye 831ea85), which ran on dev2 only (goodqa#14908). Hawkeye's transcript reader, shell lexer, ownership hand-off, time budget and fail-open rules are unchanged.

### How it works

1. It reads the agent's transcript and collects the linked worktrees that the agent created (`git worktree add`) or worked in. Working in a tree means an `Edit` or `Write` under it, or a mutating `git -C <tree>` or `cd <tree> && git ...` command. Only worktrees of repos under the repos dirs count. Those default to `~/repos` and `~/.agent-harness/work`.
2. It skips any worktree that another transcript touched more recently, because that owner answers for it.
3. It blocks once per distinct state (exit 2) when a remaining worktree has uncommitted changes, or has commits on a detached HEAD that no local branch or tag holds (git gc can drop those once the tree moves). A detached review or rescue tree at a branch's commit is only reported. The message lists the paths and the commit commands, with the message checked by `commit_policy.py check-message`, and for a detached HEAD the `git switch -c` that names the work.
4. Without blocking, it reports:
   - committed work on a named branch that is on no remote branch (`UNPUSHED`), to be published through `deliver.py prepare` or `publish_feature.py` once reviewed;
   - merged worktrees that are still on disk;
   - duplicate worktrees;
   - leftover detached worktrees.

   Each report comes with its cleanup commands.

Unpushed commits are reported, not blocked, because harness owners commit locally and publication goes through the identity-checked delivery helpers. To get Hawkeye's original behaviour, where unpushed commits also block, set `{"block_unpushed": true}` in `~/.agent-harness/state/worktree-hygiene.json`, or set `HARNESS_WORKTREE_HYGIENE_BLOCK_UNPUSHED=1`.

### Settings

| Setting | Effect |
|---|---|
| `HARNESS_WORKTREE_HYGIENE_REPOS_DIRS` (path list) | Overrides the repos dirs. |
| `{"repos_dirs": [...]}` in the same config file | Overrides the repos dirs. |
| `HARNESS_WORKTREE_HYGIENE_BUDGET_S` | Sets the time budget: 12 s by default, 15 s at most. |
| `HARNESS_WORKTREE_GATE=off` | Disables the hook. |

Hawkeye's `HAWKEYE_*` names for these settings are still accepted.

### Guarantees

- It never blocks on a repeated stop.
- It fails open on any error or timeout.
- It only reads: `GIT_OPTIONAL_LOCKS=0`, no fsmonitor, and no fetch, commit or remove.
- Its state is kept in `~/.agent-harness/state/worktree-hygiene/` and pruned after 14 days.

### Tests

Run `python3 -m unittest tests.test_worktree_hygiene`. This runs Hawkeye's 108-check scenario suite (`tests/worktree_hygiene_scenarios.py`) and the harness-default cases. Both use temporary homes, bare origins and real worktrees.

## Spec-driven tickets

Every want, need, finding or bug is a GoodQA ticket. When an agent picks one up, it writes a spec, gets the spec reviewed and attaches it to the ticket. As it works, it attaches proof for each acceptance criterion. After deploy, it attaches the click-test record. Once signed off, the ticket can be marked done.

The ticket is the record of truth. Each step posts one comment containing a readable summary and a fenced `harness-spec-record` JSON block, with its files attached. Attaching costs four calls: `file_upload_start` (project surface), a presigned `PUT`, `file_upload_complete` with the sha256, then `comment_on_issue` with `attachmentIds`. The done gate trusts a file only when `issue_attachments_list` shows it completed, on that comment, with the server-computed sha256 that the record names. Retries are idempotent: a record whose content key is already on the ticket is reported `ALREADY_RECORDED`, and the comment `operationId` is derived from that key.

```sh
S=~/.claude/hooks/spec_flow.py
python3 $S new --ticket 'GoodQA harness#168' --out ~/specs/168.md --author 'agent:<id> (<model>)'
python3 $S lint ~/specs/168.md
python3 $S packet ~/specs/168.md --out ~/specs/168.packet.md      # exact bytes a helper review must see
python3 ~/.claude/hooks/peer_review.py plan --repo <clean worktree> --packet ~/specs/168.packet.md --output ~/specs/168.adv.md
python3 $S review ~/specs/168.md --role adversarial --report ~/specs/168.adv.md
python3 $S review ~/specs/168.md --role acceptance --agent <red-team|task-owner|fixer id> --wal <main WAL> --verdict ACCEPT --report-file <its report>
python3 $S attach ~/specs/168.md --actor 'agent:<id>'
python3 $S evidence --ticket 'GoodQA harness#168' --actor 'agent:<id>' --ac AC-1 --really-tested RT1 --wal <WAL> [--commit <sha> --repo <checkout> --target origin/main] [--log run.log]
python3 $S click-test --ticket 'GoodQA harness#168' --actor 'agent:<id>' --agent-id <click-tester id> --wal-dir ~/.claude/wals/<session> --url <url> --deployed-commit <sha> --repo <checkout> --result pass --report <its report> [--log f] [--screenshot f.png]
python3 $S signoff --ticket 'GoodQA harness#168' --actor 'agent:<main id>' --by <main id> --kind agent --source '<where it was given>'
python3 $S done --ticket 'GoodQA harness#168' [--apply]          # status: same report, never writes
```

### Spec document

- **Header lines:**
  - `Ticket: GoodQA <project>#<n>`. The project slug is required; a bare `GoodQA #N` is rejected.
  - `Author: agent:<id> (<model>)`, `human:<name>` or `model:<name>`.
  - `Click-test: required` or `not-applicable (<reason>)`.
  - `Sign-off: main` or `human`.
- **Sections:** `## Outcome`, `## Scope`, `## Acceptance criteria`, `## Negative cases` and `## Risks`.
  - Each criterion is written `- AC-n: <observable result>. Verify by: <check>.`
  - Each negative case is written `- NEG-n (AC-n): ...`.
  - `lint` rejects a spec that has no criteria, duplicate ids, a criterion without `Verify by:`, a negative case that names an unknown criterion, an unedited `<placeholder>`, or an unrecognized bullet.
- **Reviews section:** `## Reviews` is generated from the sidecar `<spec>.reviews.json`. The *spec core* is everything above it, normalized to NFC and LF with trailing spaces trimmed. Reviews bind to the core's sha256. Editing the spec after review therefore makes its reviews stale, while regenerating the reviews table does not. Keep `## Reviews` last: `attach` refuses a spec with a section after it, since that section would be lost.

### Reviews

- **Two roles, distinct reviewers.** The `adversarial` and `acceptance` roles each need an `ACCEPT` on the current core.
  - The two reviewers must differ in model, agent or person. Two runs of the same helper model count as one reviewer.
  - Neither reviewer may be the spec author.
  - A later `BLOCK` for a role replaces an earlier `ACCEPT`.
- **Review sources:**
  - **Helper report.** A `peer_review.py plan` report. It must have `Stage: plan`, a body verdict `PLAN_RESULT: ...`, and `Reviewed packet SHA-256` equal to the core sha.
  - **Native agent.** A native agent id recorded by SubagentStart in the main WAL, plus its report file. Every agent type is logged by SubagentStart; only `task-owner`, `click-tester`, `fixer` and `red-team` agents may record a review (other types are refused). An adversarial review from a native agent requires `red-team`.
  - **Human.** A human name with `--source`. This is self-attested.
- **What `attach` uploads:** the spec, the reviews JSON and each review report. A report that changed since its review is refused.

### Evidence, click-tests and sign-off

- **Evidence** must name criteria of the attached spec. Proof is any of these; a note alone is not proof:
  - a `REALLY_TESTED <id>:` WAL note newer than its `PENDING_REAL_TEST`;
  - a log;
  - a commit plus a note naming the check.
- **Commits** must exist. With `--target`, they must also be reachable from that ref.
- **Logs:**
  - They are regular files; symlinks are refused.
  - A log longer than `max_log_bytes` (2 MB) is cut to its tail.
  - The text is redacted with `integrate_local.redact_output` (tokens, cookies, bearer, URL userinfo, keys).
  - A log is refused if private-key material remains, or if the cut lands in what looks like a key.
  - Screenshots and recordings (`png jpg gif webm mp4`, up to 15 MB) are checked by magic number and are not redacted.
- **Click-tests:**
  - Logs or a report are mandatory.
  - `--deployed-commit` names the commit that was deployed and tested. Every commit cited by evidence on the current spec must be reachable from it, or the record is refused. Evidence commits added later make `done` NOT READY until a new click-test covers them. This is a membership check, so it also applies when the later commit was already inside the deployed commit; rerun the click-test. The deployed commit is declared by whoever records the click-test and is not read back from the deployment, so `done` lists it under Self-attested.
  - The tester must be independent: a click-test whose tester is the spec author, a spec reviewer or anyone who posted evidence does not count toward READY.
  - **Agent click-tester:**
    - The agent must be recorded as `click-tester` in the session's `main.jsonl`.
    - The start time is its SubagentStart record. The end time is its first `subagent_stop` record (from the SubagentStop hook). If there is none, `ended_at` is null and `last_activity_at` is recorded.
    - A pass counts only if it comes from the click-tester: its report (first line `CLICK_TEST_RESULT: PASS|FAIL`, matching `--result`) has its sha256 noted in the agent's own WAL, or `--really-tested <id>` is found there.
  - **Human click-tests** are self-attested.
- **Sign-off:**
  - It must come from someone other than the spec author, either spec reviewer, a click-tester, or anyone who posted spec, evidence or click-test records. By default this is the main agent. When the main agent directed the work, its independence is nominal; ask for `Sign-off: human` when that matters.
  - It must be `--kind human` when the spec says `Sign-off: human` or the ticket text says "human sign-off".
  - The sign-off identity is self-declared.
  - GoodQA labels agent comments made through a user token as human, so comment authorship never proves a human.

### Done gate

`done` reports READY only when all of the following hold:

- a verified spec is attached: its record carries the spec file (matching `spec_file_sha`), the reviews file and at least one criterion;
- both reviews `ACCEPT` that spec's core;
- every criterion has evidence on that core;
- the evidence on that core cites at least one commit and attaches at least one execution log (this applies to every ticket, including documentation-only work: cite the docs commit and a check log);
- the latest click-test on that core passed with logs, by an independent tester, on the live deployment (not a loopback URL), at a deployed commit containing every evidence commit; when the spec says not-applicable, an evidence record must cite a REALLY_TESTED run whose note names the deployed or installed sha or version and the live target it ran on, and does not say it was staging, pre-prod, local or not yet live (done means deployed to live and tested); a click-test of an older spec version is stale;
- a valid sign-off exists on that core.

Otherwise it lists each missing item with the command that fixes it. Under "Self-attested" it lists every check that rests on a name the helper cannot verify.

**Exit codes:**

| Code | Meaning |
|---|---|
| 0 | READY, or `--apply` on a ticket that is already done (`ALREADY_DONE`, safe to retry) |
| 2 | Missing items, a refused record, a `lint` failure, or a command-line error from the argument parser |
| 3 | Spec or input error found after parsing (for example a stale review, a refused log file, an unknown criterion) |
| 4 | GoodQA unreachable, or the page budget ran out (fail closed) |
| 5 | `--apply` was refused by GoodQA (`TRACKER_REFUSED`); the ticket is left unchanged |

GoodQA's own independent-acceptance rule for done transitions still applies.

### Gates

1. **Ticket at plan review.** In tracked repositories (origin matches `ticket_systems.*.repos`), `peer_review.py plan` needs a `Ticket: GoodQA <project>#<n>` line naming a ticket that exists. The check is controlled by `plan_ticket_gate` in `spec_policy.json`:
   - `warn` (the shipped default) prints the problem and continues.
   - `enforce` stops before any reviewer launches, with exit 2.
   - An unreachable GoodQA gives `TICKETS_UNVERIFIED` (exit 6 in enforce mode). A commit-policy `tickets` waiver for subject `plan-<packet sha256[:20]>` covers that case.
   - Commits are already held to `Refs:` by the commit policy.
2. **Done at the tracker call (Claude Code).** A PreToolUse hook (`spec_flow.py hook`, timeout 60 s, `onFailure: block`, internal budget `hook_deadline_seconds` = 40) watches `close_issue_done`, `close_issue_wont_fix`, `update_issue`, `bulk_update_issues`, `archive_issue`, `reassign_issue` and `call_api`.
   - **Allowed without a network call:** open statuses (triage through `on_production`, which GoodQA documents as nonterminal) and `update_issue` without a status.
   - **Gated by the spec:** `done`.
   - **Need a reason:** `wont_fix` and `duplicate` need one of at least 20 characters.
   - **Warn mode:** the hook allows the call and returns its findings as `additionalContext`, which Claude Code shows the agent next to the tool result (plain stderr from an allowing hook is never shown to the agent). It makes no permission decision, so normal permission rules still apply.
   - **Blocked:** an unknown status, archiving an open ticket, a project, pipeline or stage move (`reassign_issue`, or `projectId`, `pipelineId` or `stageId` in an `update_issue` patch), and a `call_api` DELETE on an issue.
   - **`call_api` writes:** every non-GET `call_api` call is unchecked unless the hook recognises it, and an unchecked call warns, or blocks while any project is enforced. The path is lowercased first, so a mixed-case path is gated like the canonical one; a path without a leading `/`, or with a query, fragment, `%` escape, backslash, or empty or dot segment, is unchecked. Recognised shapes: an exact `/issues/<uuid>` path with an object body whose fields are all known (`status` and `patch.status` are gated like `update_issue`, and two different values or an explicit null are an unknown status, `projectId`/`pipelineId`/`stageId` as a move, and descriptive fields such as `title`, `priority` and `labels` pass; any other field, such as `archivedAt` or `action`, is unchecked); the exact `/comments`, `/attachments` and `/time-entries` sub-paths (allowed unless the body carries a status); a collection write with an `items` list (checked like `bulk_update_issues`); and a plain create (`POST /v1/issues` or `/v1/projects/<uuid>/issues` with no status, patch, items, id or filter keys), which blocks only when the path names an enforced project. Routes that do not name issues (projects, stages, other resources) are unchecked too, because the hook cannot tell whether they move or close issues.
   - **Bulk calls:** every item in a bulk call is checked, and one failing item blocks the call.
   - **Where it blocks:** only in `mode: enforce`, and only for `enforced_projects`. Everywhere else it prints what is missing and allows the call.
   - **Unreachable GoodQA:** a transport failure blocks only in enforce mode when enforced projects are configured. The status write goes to the same service, so blocking it costs little.
   - **Refused key:** if any routed key gets `forbidden` reading the issue (a revoked or rotated key, or lost membership), the hook blocks in enforce mode while any project is enforced, and names `doctor`. Re-run `doctor` for each enforced project after any key or membership change.
   - **Non-uuid issue id:** a missing or non-uuid `issueId` blocks while any project is enforced. Only `update_issue` and `reassign_issue` declare `issueId` as a uuid; the other tools only describe it as one.
   - **Issue not found:** GoodQA also answers `not_found` to a key without membership. So when every routed key reports `not_found`, the hook first checks that each enforced project's key can still read its own project (`get_project`). If any cannot, it blocks and names `doctor`. If all can, the issue is outside every enforced project and the hook only warns.
   - **Bulk calls while enforced:** one unresolvable item (a non-uuid id, or a not-found id while an enforced key is dead) blocks the whole call, including items in projects that are not enforced.
   - **Out of reach:** the GoodQA UI, REST calls made with curl or scripts, Codex and Cursor. Codex has no SubagentStop or MCP PreToolUse hook here, and Cursor is not wired, so on Codex and Cursor the commands are run by hand and `done` is advisory. Parity is tracked in GoodQA work-tracker-automatic#35670, to be absorbed by the harness Go port.

### Blockchain domain gates

When a repo shows blockchain work, the spec flow and the reviewers get a data-driven checklist. All text lives in `domain_checklists.json`; `domain_gates.py` only detects and renders.

- **Detection** reads file names from a capped `git ls-files` (signal paths only, up to 20,000; vendored `node_modules`, `vendor`, `third_party`, fixtures and top-level `lib/` are skipped) and at most 200 manifests of at most 256 KiB each (4 MiB total). It never follows symlinks and never runs repo code. JSON deeper than 100 levels is rejected before parsing (`domain_gates.safe_json_loads`; deep nesting can abort CPython 3.9), which counts as a failed scan. Hitting any scan cap (file list, manifest count or size, read budget, proto count) is also reported as a failure, and enforce mode fails closed on either (a skipped symlinked or unreadable manifest counts as well; a proto cap counts only when NATS is present without a ledger signal). If spec_policy.json cannot be loaded, `peer_review` warns loudly that enforce refusals are off (fail-closed is a follow-up). In enforce mode a very large repo (or one with oversized or deeply nested manifests) needs `allow_truncated` before reviews can run: `lint`, `attach` and `peer_review` behave the same: each refuses whenever a signal-hiding limit was hit (truncation or a too-deep manifest), even if some other domain was detected, and says how to proceed. With `allow_truncated`, or in warn mode, the review continues and an incomplete-scan notice goes into the reviewer prompt and the new spec block. `allow_truncated`, `mode` and `disabled` come only from the installed spec_policy.json; the repo file, environment and CLI cannot set them, and an attempt is reported as an ignored warning. A monorepo that legitimately exceeds the caps can set `"allow_truncated": true` under `domain_gates` in `spec_policy.json`, which downgrades truncation and too-deep manifests to a visible warning. Signals: `.sol`, `foundry.toml`, `hardhat.config.*` and ethers/viem/web3 (`evm`); `Anchor.toml`, `anchor-lang`, `solana-program` (`solana`); `frame-support`, `sp-runtime`, `polkadot-sdk` (`substrate`); `xrpl`, `xrpl-py`, `ripple-lib` (`xrpl`); a `.proto` file plus a NATS dependency plus a ledger, journal, posting or balance signal in a path or proto file (`ledger-messaging`). Untracked (not yet added) files count; paths changed by a diff count too. Review prompts are built from the committed snapshot, and a diff that touches the opt-out file, or an unknown base, ignores that file.
- **Checklist items** per domain: reentrancy, access control, precision, replay and chain id, nonce and idempotency, finality and reorgs, key custody, gas and DoS, upgradeability, oracle trust. Each has a NEG-case sentence and a `Verify by` hint, plus scaffolds (anvil fork, forge invariant, Echidna, `anchor test`, standalone rippled, `try-runtime`, NATS JetStream) and prompts for the review map (`domain_gates.suggested_prompts(domains)`).
- **`spec_flow.py new --repo R`** appends a `## Domain checklist` block (with a `Domains:` line) when something is detected; nothing changes otherwise. **`spec_flow.py lint --repo R`** warns, without failing, for each item that no `## Negative cases` bullet names and that has no line `Domain-gate: <item-id> waived (<reason, 10+ chars>)`. Set `"domain_gates": {"mode": "enforce"}` in `spec_policy.json` to make `lint` and `attach` (`--repo R`) fail, and in enforce mode `peer_review` refuses to review when the reviewer checklist cannot be built (broken data, truncated scan). NEG matching counts only `- NEG-n (AC-n):` bullets in `## Negative cases` and chain-specific keywords (placeholders, code fences and generic words do not count); waivers need a 10+ character reason of at least three words, one item per line; NEG text inside code fences or HTML comments does not count. `packet` and `done` are unchanged. When `--repo` is not a git checkout lint says so instead of passing silently, and an opt-out in a repo with detected blockchain work is reported as a warning.
- **`peer_review.py`** adds a bounded checklist (9,000 bytes) to the reviewer prompt for plan, code-inspection and PR stages. It is not part of the packet, so the packet hash and byte budget are unchanged; the report notes the section's SHA-256.
- **Opt out:** `HARNESS_DOMAIN_GATES=off` (ignored with a warning when the policy mode is `enforce`: environment variables only tighten), `"domain_gates": {"disabled": true}`, or `.harness/domain-gates.json` with `{"disabled": true}`. The repo file may also carry `extra_checklists` (`items`, `domains`) that add items, never replace built-in ones. A diff that touches anything under `.harness/` (compared case-insensitively) cannot disable its own review or add checklist text, and the repo file can never switch off a policy-level `enforce` (use the policy file or the environment). In enforce mode a broken checklist file or an internal error fails closed. The repo file is repo-controlled, so treat a PR that adds it as a review finding.
- **CLI:** `python3 domain_gates.py detect --repo R [--json]`, `checklist --domain D`, `scaffold --domain D` (prints commands, never runs them).

## Merge gate

Why: an owner merged netwatch PR #1 while its CI was red (staticcheck and Windows vet failing). `harness/hooks/merge_gate.py` is a PreToolUse hook (Claude Code: Bash and the write tools, `onFailure: block`; Codex: PreToolUse, command ends in `|| exit 2`) that blocks a PR merge unless every required and every reported check run and commit status on the exact head SHA concluded success. GoodQA #14502, matrix D11. The rule is in `docs/rules/merge-gate.json` for the rules registry.

What counts as a merge: `gh pr merge` (also `--auto` and `--admin`), `gh api` REST `pulls/<n>/merge`, GraphQL `mergePullRequest` and `enablePullRequestAutoMerge`, curl or an interpreter one-liner calling those endpoints, wrapped in `sh -c`, `bash -c`, `ssh`, `eval`, `xargs`, `env`, `timeout`, `sudo`, subshells, backticks, here-documents and pipes into a shell. Shapes that cannot be tied to one PR block with no waiver possible: the branch merge endpoint and `mergeBranch`, a GraphQL query read from a file or stdin that the hook cannot see, a target built at runtime, `xargs gh pr merge`, a repository that a `cd`, `ssh`, `GH_REPO` or `GH_HOST` could change (pass `-R owner/repo` or a PR URL). `gh pr merge --disable-auto` is not a merge.

What it checks, with a fake-gh-tested read of `gh pr view --json statusCheckRollup`, the check-runs and combined-status endpoints, branch protection on the base branch, rulesets and `gh pr checks --required`:

- Every check run and status must be `success`. Pending, queued, in progress, failed, cancelled, timed out, action required, stale, startup failure and any unknown value block. The latest run per check name wins when every run has a timestamp.
- **Neutral and skipped policy:** accepted only for checks that are not required. A required check must be `success`; a required check that is neutral or skipped blocks. This is stricter than GitHub, which treats a skipped required check as passing; use a waiver when a path filter legitimately skips one.
- The required set is the union of branch protection, rulesets and `gh pr checks --required`, and it must be known. When `gh pr checks --required` is the only readable source (protection returns 403), the PR must also report `mergeStateStatus` CLEAN or HAS_HOOKS, because that source lists only checks that already reported. A required check that has not reported blocks.
- Zero reported checks block unless the repository has no active workflow that can run on a PR head (GitHub CI switched off). Only `state == active` workflows count (`disabled_manually`, `disabled_inactivity`, `disabled_fork` do not). An active workflow is inert only when its `on:` holds nothing but `workflow_dispatch`, `schedule`, `release`, `workflow_call`, `repository_dispatch` or `push` limited to `tags`; any other, unparseable or unreadable trigger, an unreadable workflow list or file, or a truncated list blocks (fail closed). Accepted risk: a same-user agent can switch CI off (`gh workflow disable`) or push a commit that no workflow reports on, and then merge with zero checks; the gate treats that as no-CI by design (the rule is no GitHub CI here), so use branch protection or the command guard if that must be prevented. Simple `workflow_dispatch` or `workflow_call` workflows with `inputs:`/`secrets:` blocks, a leading `---`, tabs or `*` in scripts are read as unknown and block (fail closed). Each active workflow file is read at the PR base and at the verified head and is inert only if both versions are (a PR cannot switch off its own CI by editing the workflow), workflow files that exist only at the head are classified too, an unknown workflow state blocks, a `deleted` workflow is classified wherever its file exists (it counts as gone only when absent at both refs), the workflow directory is listed at both refs, only a real `(HTTP 404)` means a missing file or directory (any other failure blocks), and `push` counts as tag-only only with a non-empty `tags` filter and nothing else.
- The merge command must carry the verified full head SHA as a real flag or field: `--match-head-commit <sha>`, REST `-f sha=<sha>`, GraphQL `expectedHeadOid`. GitHub then refuses a head that moved after the check, and the gate also re-reads the head at the end. A short or different SHA blocks.
- Unknown state (required checks unreadable, truncated lists) is a waivable reason: the main agent may override it with a waiver, which is recorded. Fail closed: a gh failure, timeout (8 s per call, 40 s total, output capped at 4 MB), non-JSON, truncated check list, closed PR or unreadable input blocks (exit 2).
- `--auto`: the gate needs green now, so arming auto-merge on pending checks needs a waiver or a later plain merge.

Waiver: `python3 ~/.claude/hooks/merge_gate.py waive --repo owner/name --pr N --head <full sha> --ticket 'GoodQA #N' --reason '<10+ characters>'`. It is bound to repo, PR and head, single use, expires after 24 hours and a waived merge still needs the head flag. The main agent runs it; the hook stamps the approver from the session. **Main approval is not authenticated.** The hook refuses `waive` and shell or write-tool access to the state files when the payload carries `agent_id` (a Claude Code subagent). Since goodqa#15122 a subagent command that names merge_gate and a waiver word is allowed only when every simple command in it is a known free-text form: print and search commands (`echo`, `printf` without `-v`, `grep`, `cat`, a stored heredoc), `cd`, git `log`/`show`/`diff`/`status`/`add`/`grep`/`rev-parse`/`branch`/`tag` with only the options on a per-subcommand allow-list (`GIT_OPTIONS`; abbreviated long options are refused), `commit`, `add`, `status`, `branch` and `tag` only with `-c core.hooksPath=/dev/null` (they can run hooks; any other `-c` and `-C` are refused; `--no-pager` is allowed), no git or gh argument built at run time (a word starting with `$`, except a quoted `"$( )"` body after `--body`/`-m`, and no unquoted `$`, glob or brace in a command that runs git or gh), the text verbs of `gh issue`/`gh pr` and `gh api`/`search` without `--web` (also joined, `-cw`), and the harness helpers `~/.claude/hooks/{wal_note,ah,commit_policy,provenance,spec_flow}.py` named by `~` or the literal home; every `$( )` inside it must be free text too. Such a command is still blocked when it assigns `HOME`, `PATH`, `PYTHON*`, `GIT_*` or a similar variable, uses process substitution, or writes a file (redirect or `tee`) while it also runs git or python. Known limit: git and gh can still start a program from configuration that already exists (a pager, `core.fsmonitor`, diff or textconv drivers, clean filters, a signing program, the editor, the browser), chosen by the repository the command runs in (`cd`); a file written by an earlier command or the Write tool and run later is not linked to this check. Anything else (an interpreter, a shell, `awk`, `sed`, `rg`, `pytest`, `find -exec`, `make`, a git alias, a wrapper such as `env` or `sudo`, a variable as command word) keeps the old text rule and blocks. It normalizes quotes, `$` and globs first, but this is best-effort and only inspects the command text: a subagent that writes a script with the Write tool and then runs it, or builds the command at runtime (base64), can evade it, and Codex sends no `agent_id`, so there every caller counts as main. Without a stamp the caller passes `--approved-by main:<agent-id>` and the record is marked `asserted`; anyone with shell access can type that. The hash chain is unkeyed: it catches accidental edits and truncation (a corrupt, truncated or edited log honours no waiver) but not a deliberate forger who knows the format. Treat the waiver as an audited honesty control against careless agents, not as proof that the main agent approved; the report shows who and how. State lives in `~/.agent-harness/state/` (`merge-gate-waivers.jsonl`, `merge-gate-audit.jsonl` with command hashes only). `merge_gate.py report` lists waivers (used, unused, expired, approval source) and recent decisions; `merge_gate.py check --repo owner/name --pr N` runs the check without a merge. A waiver is consumed when the hook allows the command, so a merge that then fails burns it.

Known limits: merge queues (the PR head is checked, not the queue branch), MCP GitHub tools and browser merges (the Bash matcher never sees them), aliases defined outside the command, scripts that hide a merge in a file, and the check state changing in the seconds after the check. Commands that merely print or search text are not merges (`git commit -m`, `echo`, `grep`, `pytest -k`, a `cat` or `git commit -F -` heredoc body), but a merge string inside any other command that is not a plain gh call (a variable, `awk`, `xh`, an unreadable script) blocks. `gh pr merge --help` and `--disable-auto` are not merges. A command word that is only a variable or substitution (`$A $B $C 5`, `$'gh' ...`, `eval $A`), a gh subcommand word built at run time (backticks, braces, `${IFS}`) and a write to a `gh api` endpoint whose last path part is built at run time block when the command mentions gh or a merge. A command word or gh subcommand word taken from a variable assigned once from a literal by a top-level statement earlier in the same command (`SUB=view; gh pr $SUB 5`, `GH=gh; $GH pr view 5`) is read as that word: reads pass, and a merge reached that way still blocks; an assignment inside a group, loop, branch, function, pipeline or `&&`/`||` list, a prefix assignment, or any builtin that can assign anywhere in the command (`eval`, `source`, `read`, `mapfile`, `declare`/`typeset`/`local` (also `-n` namerefs), `printf -v`, `trap`, `unset`, `export`, `let`, `getopts`) leaves every variable unknown (goodqa#15122). A token named `gh` inside `git push`, `fetch`, `remote` and other git subcommands that run no program is a remote or branch, not a gh call. A `git push` whose destination is main or master (`origin main`, `x:refs/heads/main`, `x:heads/main`, `+x:master`, `--delete main`), `--all`, `--mirror`, a destination built at run time, refspecs appended by `xargs`/`parallel`, or a git command given `-c alias.*`, `-c push.*`, `-c remote.*.push`, `-c branch.*.merge` or `--config-env` blocks as a merge without a pull request; a push with no refspec or to `HEAD` is not resolved against the current branch, and only main and master count as default branches; this is a best-effort net, not a proof against every obfuscation. The hook never executes the command text. Fail-closed wiring: on Claude Code the hook entry uses `onFailure: block` (the convention this installer uses for its other gates; the hook also exits 2 itself if its helper module cannot be imported); on Codex the command ends in `|| exit 2`. A missing `python3` binary is a spawn failure that only `onFailure` can turn into a block. To uninstall, remove the `merge_gate.py` hook entries from `settings.json` (Claude Code) or `hooks.json` (Codex).

## PR review map

`review_map.py` builds one self-contained HTML page for pair-programming a pull request:

```sh
python3 ~/.claude/hooks/review_map.py generate --repo <checkout> --pr <N>      # or --branch <name> --no-gh
python3 ~/.claude/hooks/review_map.py attach --map <file.html> --yes           # tickets come from the PR's commits

```

The page has a grouped change map (tile area follows changed lines), reasoning per commit (Why, What, Testing, Risk), known edges with diff snippets (spec NEG cases, spec risks, commit Risk lines and review findings), the refinements reviews caught (finding, fix commit, test file), suggested next steps and prompts to run next. It loads nothing from the network, escapes every string, pins its single script with a CSP hash and is written with mode 0600 to `~/.agent-harness/work/review-maps/` (override with `HARNESS_REVIEW_WORK`).

Specs and reports are found under `~/.agent-harness/work`, WAL notes under `~/.claude/wals`. Refinement links (finding to fix commit) are inferred and labeled so. Text is redacted with the harness redactor plus e-mail, JWT and home-directory patterns before it is truncated, and generation refuses to write a page that an independent detector still finds token-shaped text in. Ticket references come only from the PR's commit messages, never from PR comments, and `attach` needs `--yes`. The console lists the selected session repository's pull requests; selecting one and pressing **Open review map** builds the page and shows it in a sandboxed frame (no access to the console token or API). **Attach to GoodQA tickets** asks you to confirm the ticket list first. ## Lower-level publication and local integration

```sh
python3 ~/.claude/hooks/publish_feature.py --repo /absolute/feature-worktree --branch feat/example --original-branch main --expected-head FULL_FEATURE_SHA
```

If publication succeeds, create a draft PR for that exact feature commit and treat it as `PR_READY`. Keep the original checkout unchanged until the repository's review and merge authorization are complete. After GitHub merges it, verify the PR and pin the remote branch target before a hook-disabled, protected fast-forward into a clean original checkout; run checks there before reporting delivery. The remote-phase command is still coordinated by the main agent; this local helper does not merge a GitHub PR.

Use the local helper when publication is genuinely blocked or the user chose local-only delivery:

```sh
python3 ~/.claude/hooks/integrate_local.py --repo /absolute/original-checkout --original-branch main --expected-head FULL_ORIGINAL_SHA --source feat/example --expected-source-head FULL_FEATURE_SHA --check 'python3 -m unittest discover -s tests -v'
```

Local-only delivery leaves publication outstanding. A later GitHub merge may have different history even if its file tree matches, so reconcile deliberately instead of assuming it will fast-forward onto the local merge.

The publication helper requires `--repo` to resolve to the feature worktree root before inspecting the branch or remote; a nested directory returns `BLOCKED_POLICY` (exit 2), because a directory-scoped index scan could miss hidden root entries. It resolves `origin`’s effective push URL (including `pushurl` and `pushInsteadOf`) and asks that destination for its advertised default branch and refuses to push that branch, including nonstandard names such as `trunk`. If the default is unknown (for example, an empty remote) or the query fails, it returns `BLOCKED_REMOTE` (exit 4) and local integration continues. Multiple push destinations, or an effective URL that would be rewritten again during inspection, are rejected with `BLOCKED_POLICY` before any push; they cannot be checked or updated atomically across repositories. This follows Git’s [push URL semantics](https://git-scm.com/docs/git-push#REMOTES). It canonicalizes source-relative local push URLs, including paths with a colon after a slash, and preserves the source object format, then exposes the reviewed commit to a temporary bare repository through Git object alternates (without copying the project's history), then pushes that object to the inspected feature ref using a temporary remote pinned in command environment. This prevents a moving source branch, source-local URL rewrite, or source `pre-push` hook from changing the delivered object or destination. Because the isolated transport bypasses source `pre-push` hooks, publication scans the commits the push can add for [Git LFS pointer blobs](https://github.com/git-lfs/git-lfs/blob/main/docs/spec.md) and returns `BLOCKED_POLICY` if any are found; use an LFS-aware push path or make an explicit local-only delivery decision; a policy refusal is not a remote outage. The LFS scan runs in that prepared transport immediately before pushing, using the same original object graph as the transfer. It asks the pinned destination for its `refs/heads/*` and `refs/tags/*` tips, peels those present locally to commits, and scans every commit reachable from the feature head but not from those tips. Local remote-tracking refs are never trusted to shrink the range. Each such commit is diffed against every parent (or as a root), so the scan covers new blobs and older blobs a new commit adds at a changed path, as the Git LFS pre-push hook does. Pointers only in history the destination already advertises do not block publication. If a destination ref disappears between this listing and the push, Git may send objects that already existed on the destination without this scan; those objects were not introduced by the feature commits. Source shallow boundaries and grafts cannot hide retained ancestor objects from inspection. A shallow source can publish when the unpublished range is complete locally and adds no pointer; missing objects inside the unpublished range make verification fail closed with `BLOCKED_REMOTE`, even if the destination might already have them. All publication Git commands disable replacement objects. The scan conservatively rejects small blobs containing a recognized LFS version line, including CRLF, surrounding Unicode whitespace, extension records and legacy version aliases; malformed pointer-like text can therefore also require manual publication. Enumeration streams commit IDs and raw diff records without retaining paths and refuses more than 200,000 destination refs or 64,000,000 ref-listing bytes, 100,000 unpublished commits, 300,000 candidate blobs, 19,500,000 commit-list bytes, 256,000,000 diff bytes, or malformed/oversized records before buffering the complete enumeration. Candidate blob content is limited to 30,000,000 bytes. The whole scan shares one `--timeout` deadline. If the scan cannot complete within these budgets or that deadline, it returns `BLOCKED_REMOTE` with a fixed `reason` (for example `LFS scan commit budget exceeded`) without pushing; the read-only enumeration process group is killed immediately on refusal or timeout. It does not create a PR; the main agent does that separately when available. A concurrent change to global Git URL rewrites or external DNS/transport routing remains outside this protection. Git terminal credential prompts are disabled during the push. Credential helpers and SSH can still stall; `--timeout` (default 600 seconds) bounds each Git command, including local inspection, temporary transport setup, and the push. Local inspection timeouts return `BLOCKED_REMOTE` before any push; the default-branch query has the smaller of this deadline and 30 seconds. For other Git commands, on timeout the helper terminates Git and descendants in its process group with SIGTERM, then kills anything still running after a two-second grace, before reporting. A timeout does not prove that the remote ref was unchanged: verify it before retrying.

The integration helper accepts a small fixed set of test/build commands and lockfile installs, parsed as argv without a shell. Besides the full-suite forms it accepts exactly one focused form, `python3 -m unittest discover -s tests -p test_<name>.py` (`python` is accepted too), where the name is one literal ASCII file name (no glob, path separator, `..`, option or extra argument; discovery matches that file name in `tests/` and its subpackages, so a same-named file in a subpackage runs as well); it is shared by `finish --check`, `finish --resolve-baseline` and `integrate_local.py --resolve-journal`; like every `unittest discover` check it fails when the pattern runs no tests or only skipped tests (GoodQA #14729). An unparseable or unapproved command returns `BLOCKED_POLICY` (exit 2) before integration. `--repo` must be the root of the original worktree, and the named original branch and HEAD and reviewed source branch and commit must still match. The original checkout must be clean. The helper refuses inherited `GIT_*` routing, index, and configuration overrides before Git inspection; identity variables, `GIT_CONFIG_GLOBAL`/`GIT_CONFIG_NOSYSTEM`, `GIT_TERMINAL_PROMPT`, `GIT_PAGER`, and (since 2026-11-06) `GIT_EDITOR`/`GIT_SEQUENCE_EDITOR`, which the non-interactive helpers never consult, are allowed. Helper-owned Git commands strip `GIT_PAGER`. A blocked or changed original checkout is preserved; do not reset it to make delivery pass.

Before the scratch merge can run merge drivers, hooks, or checks, the helper reserves an owner-only journal under the repository Git common directory at `agent-harness/delivery-scratch`. This state is independent of `HOME` and shared by linked worktrees. A private lock serializes integration for one original checkout inode and branch. Each original checkout and branch has its own `scopes/<scope>/active` namespace. A scan of at most 4096 active or legacy journals shares a deadline of the smaller of `--timeout` and 30 seconds; an unsafe or over-budget set requires recovery before new merge/check effects. Unresolved attempts block across changed baseline or feature inputs. Completed and explicitly resolved metadata moves to `scopes/<scope>/archive`; a new feature never rescans archived history or depends on old candidate ancestry. An exact completed repeat checks that candidate, current clean checkout, and remaining artifacts before returning `ALREADY_INTEGRATED`; natural completion of retained-artifact cleanup is accepted. An unfinished reservation in another linked worktree does not block this scope. The scratch worktree is created in a separate owner-only temporary container outside `.git`, `.hg`, and `.sl` path components so VCS-ignoring test tools can see its files. The journal binds its absolute path and container device/inode; changing `HOME` does not move recovery state. The scratch worktree shares the repository's objects, refs, and local Git configuration. It lets the helper validate the candidate before deliberately changing the original HEAD, **not** sandbox repository code: merge drivers, hooks, package lifecycle scripts, and tests can execute and can affect external paths or shared Git metadata. Use trusted repositories and inspect a retained scratch worktree before recovery.

In scratch, the helper runs `git merge --no-ff --no-commit` against the exact reviewed feature commit. It records the actual merge tree, runs approved preparations and checks there, and rejects a changed index tree, unstaged edit, or untracked test output before committing. It then verifies the candidate merge commit's two exact parents and tree and pins it under a private `refs/agent-harness/delivery/<tuple-key>-<attempt>` ref. The attempt identity is recorded before repository code runs, so a resolved retry can preserve the old pin and create a distinct new pin, including when a legacy flat tuple-key ref exists. A custom merge driver may produce a tree different from a default Git merge prediction; the checked and pinned candidate is the one offered to the original checkout. The helper rechecks original branch, HEAD, cleanliness, source ref, candidate ref, and scratch identity before applying it. It uses `git merge --ff-only --no-overwrite-ignore --no-autostash <candidate>` with hooks disabled in the original checkout, then reruns approved preparations and checks **in that checkout** and verifies the final HEAD and cleanliness. Scratch merge and commit hooks still run; original fast-forward hooks are suppressed because a post-merge hook can delete ignored user data after Git's overwrite guard. A green scratch run alone is not `INTEGRATED`. With `merge.autostash=true`, the explicit no-autostash flag prevents this step from silently stashing a concurrent user edit. The ignored-file overwrite guard covers tested flat, nested, and relocated destinations, but external filesystem or Git configuration changes after a check remain a race.

On a failed scratch merge or check, the helper has not intentionally applied the candidate to the original checkout. Inspect the original anyway: repository code can change its files or shared refs before the protected fast-forward. The helper attempts `git merge --abort` **in scratch** only after rechecking scratch Git state. If that state cannot be verified, it leaves the merge for inspection. A failure at or after candidate application can leave the original checkout at the candidate commit even when the helper returns a failure; delivered-check failures report `DELIVERED_CHECK_FAILED` with the observed HEAD. Once a journal exists, failed or interrupted attempts retain it, plus any scratch worktree and candidate ref already created. Recovery state and retained payload paths are reported separately; the journal directory is not the scratch worktree. Inspect the reported journal, scratch worktree if present, original HEAD/status, merge state, candidate ref if present, and any ignored artifacts before manual recovery. Never infer success from a changed HEAD, delete an uncertain worktree, or automatically retry the same inputs. The helper does not hard-reset the original checkout or delete Git lock files. After the protected fast-forward and original checks, it marks the journal as finalizing, attempts cleanup with hooks disabled for its own candidate-ref operations, rechecks the original, then marks the journal delivered. Cleanup removes scratch only if its identity still matches and it has no hidden, untracked, or ignored data. `cleanup_pending` means a scratch worktree, candidate ref, or both remain; inspect which artifact remains. Terminal journal metadata remains in the archive. Archive growth does not add work to a new feature scan. The fixed schema-1 legacy namespace is inspected fail-closed and can be explicitly resolved without moving its nested worktree.

## Explicit recovery resolution

First inspect the reported journal, actual original `HEAD` and status, scratch data, and candidate ref. Preserve anything uncertain. Choose the current clean original commit as the baseline you intend to keep, then run:

```sh
python3 ~/.claude/hooks/integrate_local.py --repo /absolute/original-checkout --original-branch main --expected-head <confirmed-current-SHA> --resolve-journal <64-character-journal-key> --check 'python3 -m unittest discover -s tests'
```

Resolution takes the same per-checkout lock, verifies the selected journal belongs to this checkout and branch, and runs the approved nonempty checks in the original checkout. It rechecks the exact confirmed HEAD, cleanliness, and repository identity afterward. Only then does it emit `RESOLVED` and archive the metadata. This accepts the tested current checkout as a new baseline; it does not assert that the failed candidate was delivered. It deletes no scratch files or refs, including ignored output or dependencies. A failed check, changed checkout, symlinked/hardlinked journal, or journal from another scope remains blocked. A scoped reservation interrupted before its first journal write can be resolved explicitly, with `artifacts_unknown: true`; a legacy reservation whose scope cannot be established stays blocked for manual inspection.

After `RESOLVED`, a corrected feature can be attempted as a new delivery. If the source and baseline are unchanged because an external failure was fixed, the helper preserves the prior resolution under `archive/history/<attempt>/<key>` before reusing that tuple; it never overwrites the earlier record. Retained worktrees and candidate refs still need deliberate inspection and cleanup; use a normal non-forced `git worktree remove` only after preserving all needed ignored/untracked data, and use an exact compare-and-swap ref deletion for the recorded candidate. The resolver intentionally does not automate that deletion.

Git cleanliness inspections disable fsmonitor and untracked caches, force normal stat, executable-bit, and symlink-type checks, include untracked files and dirty submodules despite user configuration, and reject gitlinks and hidden `assume-unchanged` or `skip-worktree` index entries. The NUL-delimited index scan reads no file contents or paths into reports and refuses more than 40 MB, 250,000 entries, a 1 MB path record, or 30 seconds. Sparse checkouts with skip-worktree entries and submodule gitlinks need a separate delivery path; do not clear flags automatically. These checks are not byte-for-byte filesystem attestation: forged stat metadata, concurrent edits, and changes after final verification remain limits. A repository's `.gitattributes` may select a user-global clean filter during status, and scratch integration retains merge drivers and Git hooks for its merge and commit. Source checks constrain known execution and concealment paths but cannot isolate or pin all repository code and shared configuration.

Each Git command, preparation, check, and abort attempt has a positive `--timeout` in seconds (default 600 **per command**, not for the whole workflow). The helper terminates a timed-out command's process group with SIGTERM, then SIGKILL after a bounded grace. Detached descendants remain outside that cleanup. Failure reports give a phase, status, and available exit code without child stdout or stderr, which might contain secrets; `merge_aborted` describes the scratch merge only. Approved `unittest discover` checks require at least one non-skipped test invocation, but a test can still lack meaningful assertions; other allowlisted runners retain their own exit-status semantics. The main agent must judge test sufficiency and review evidence. The helper does not publish the original branch.

## Integration command output

Approved preparation and check commands merge stdout and stderr into one pipe and drain it in fixed 64 KiB chunks without retaining the bytes. The helper keeps their exit status, not their output, and prints only its structured status report. It waits for pipe EOF, including same-group children that inherited the descriptors, and then waits for the command leader within the original deadline. On timeout, it continues bounded draining during the two-second TERM grace, kills the process group, then bounds final pipe cleanup before attempting a safe scratch merge abort. If cleanup itself fails, it reports `BLOCKED_LOCAL` with `merge_aborted: false` and retains the scratch worktree and journal because a child might still be active. A child that closes or redirects both descriptors, or detaches from the process group, can still outlive this check; do not rely on the helper to supervise detached services. Inspect the reported phase and scratch worktree before rerunning a command for diagnostics. If the phase reached original checkout checks, first inspect the actual original HEAD and user files. Merge, commit, and fast-forward hook output is discarded. Metadata Git inspections still capture output needed to verify branch, tree, and checkout state without a hard overall memory bound; an unusually large untracked set can stress memory or time.

## Background jobs and chains (bg_job.py)

Rule (`docs/rules/bg-launch.json`, GoodQA #14513 and #14472): a launch is reported only after `bg_job.py launch` prints `STARTED`; chains use `&&`, never `;` or `&`, before a success echo; a wait returns the job's real exit status. Incidents: `cmd1; nohup suite & echo started` printed "started" after `cmd1` failed and two reruns never ran (1.5 h lost); a wait loop exited 0 because its last command was `ls`; a garbage-collected systemd transient unit reports `Result=success` after failing; `PIPESTATUS` read after `X=$(a | b | c)` holds only the assignment's status, so a per-stage check written that way can never fail.

```sh
python3 ~/.claude/hooks/bg_job.py launch --name suite --log /abs/suite.log --deadline 30 --dir /abs/task/bg-jobs -- ./run-suite
python3 ~/.claude/hooks/bg_job.py status --name suite --dir /abs/task/bg-jobs
python3 ~/.claude/hooks/bg_job.py wait --name suite --timeout 3600 --dir /abs/task/bg-jobs
```

- `launch` takes an argv list (no shell string), detaches into its own session behind a wrapper, and prints `STARTED name= pid= ...` with exit 0 only when the PID is alive, the log exists and the log has grown within `--deadline` seconds. Otherwise it prints `FAILED_TO_START reason=...`, exits 3 and stops the process group it started. A job that is silent for the whole deadline therefore fails to start; make it print a first line. The job record (PID, start, log, status path, argv hash, nonce) goes in `--dir`, else `$BG_JOB_DIR`, else `$AGENT_HARNESS_TASK_DIR/bg-jobs`, else `./.bg-jobs`. Argv is stored in the record: never pass secrets as arguments.
- `wait` exit codes: 0 the status file says exit 0; 1 the job ran and failed (`EXIT_STATUS=n`); 2 no trustworthy status (missing, garbled, belongs to another job, or the process is gone without a status, including a reused PID); 3 timeout while still running. PID liveness is proven by the wrapper nonce in the process command line, never by `kill -0` alone, and the status file is written atomically by the wrapper. Never use the last command of a loop, or a systemd unit `Result` alone, as the outcome.
- Per-stage pipeline status: use `set -o pipefail`, or read `PIPESTATUS` immediately after the pipeline itself (not after `X=$(...)`), or write each stage's status to its own file.
- `bg_lint.py` is an advisory PreToolUse hook (Claude Code only; Codex ships `bg_job.py` as a helper but has no lint hook). It warns, never blocks, and names `bg_job.py` for: a success echo after `;` or `&`; a wait/poll loop whose last command is `ls`, `cat` or `tail`; `PIPESTATUS` after a command-substitution assignment; a while/until loop polling `pgrep -f PATTERN` or `ps | grep PATTERN` (without `grep -v grep`) where the pattern also occurs in the loop's own shell command line, so it never exits (one ran 12 h on dev2 on 2026-11-06; use `pgrep -f "[t]sc ..."`, a PID wait or an exit file). It is a heuristic over a shell string, so it can miss wrapped or generated commands; the helper itself is opt-in.

## Test watcher

```sh
python3 ~/.claude/tools/watch-tests.py --root /absolute/checkout --once -- python3 -m unittest discover -s tests -v
python3 ~/.claude/tools/watch-tests.py --root /absolute/checkout -- python3 -m unittest discover -s tests -v
```

The watcher polls common source extensions plus exact dependency filenames: `pyproject.toml`, `requirements.txt`, `poetry.lock`, `uv.lock`, `go.mod`, `go.sum`, `go.work`, `go.work.sum`, `pnpm-lock.yaml`, and `yarn.lock`. These names remain watched when `--extensions` changes the suffix list. It skips common vendor/build directories, generated-output directories (`coverage`, `test-results`, `playwright-report`, `.next`), and symlinked files/directories. Other generated files with watched suffixes can still retrigger a run; move them into a skipped directory or choose a narrower `--extensions` list. It compares file metadata (device, inode, mode, size, modification time, and status-change time), without reading source contents; on macOS/Linux this detects ordinary same-size edits with restored modification times and atomic replacements. Coarse timestamps and concurrent filesystem changes remain possible, so the watcher is a best-effort local convenience, not a security boundary or CI gate.

Watcher-authored status shows run number, elapsed time, exit status, and watched-file count without printing the checkout path or command arguments. Child test output is streamed verbatim and remains the test command's responsibility. Root-resolution and scan errors stop the watcher with exit 2 and generic messages; a missing command executable returns 127 without echoing its path. A child directory removed during scanning is skipped, while a missing root fails. A stalled test process group is terminated after `--timeout` (600 seconds by default), with `--once` returning 124 on timeout. Stop a continuous watch with Ctrl-C. After changing this helper, run `python3 install.py --apply` from the harness checkout to update the user-wide copy; the installer retains private backups of replaced files for manual recovery.

## netwatch monitor

`install.py --apply` and `install_codex.py --apply` also install [netwatch](https://github.com/ericmacdougall/netwatch), a small public Go binary that records gateway and internet latency, apps that start using the network, and orphaned or runaway developer processes. `harness/netwatch.json` pins the version, the SHA-256 of each platform archive and the SHA-256 of the binary inside it. The installer:

1. hashes any existing `~/.agent-harness/bin/netwatch` (`netwatch.exe` on Windows) and, if it matches the pinned binary, downloads nothing;
2. otherwise downloads only `https://github.com/ericmacdougall/netwatch/releases/download/<version>/...`, refuses an archive or binary whose digest differs, reads only the expected binary member, places it atomically and checks that it reports the pinned version. Any binary that differs from the pin is replaced without being run, so a hand-installed build there is overwritten; keep custom builds elsewhere;
3. runs `netwatch install` to register a per-user service (a LaunchAgent on macOS, a `systemd --user` unit on Linux, a logon Scheduled Task on Windows; no root or administrator rights) unless the binary is unchanged and `netwatch status` already reports it running. That check does not compare the registered program path, so a same-label service started from another binary is left until the next upgrade or a manual `netwatch install`. On Windows the shortcut recognises only an English `Running` Scheduled Task status, so with the Run-key fallback or a localized Task Scheduler every `--apply` re-registers and restarts netwatch.

- The service belongs to whoever runs the installer, so it is registered only when the target is your real home. With a non-default `--home`, as in tests, netwatch is skipped; `--netwatch` places the binary but still leaves the service alone.
- A download, digest or service failure is reported as one `netwatch:` status line and never fails the harness install. Before an upgrade, the installer retains the previous executable and restores it if the replacement reports the wrong version, the upgrade raises an error, or service registration fails. If restoration also fails, the status says `RECOVERY REQUIRED` and names the retained backup and destination for manual recovery. A pinned binary that lost its execute bit (a plain copy or restore) is made executable again instead of being re-registered.
- `--no-netwatch` skips netwatch and is remembered in `~/.agent-harness/netwatch-state.json`; `--netwatch` turns it back on. `AGENT_HARNESS_NETWATCH=0` skips it for one run. Opting out does not remove an installed service; run `~/.agent-harness/bin/netwatch uninstall` for that, and pass `--no-netwatch` to later installs or they register it again.
- An upgrade re-registers the service, which keeps a custom config or log directory only when it is set through `NETWATCH_CONFIG` / `NETWATCH_LOG_DIR` in the installer's environment.
- To upgrade the pin, copy the version and digests from the release's `SHA256SUMS` and the extracted binaries into `harness/netwatch.json`, then rerun the installer.

Agents read it with `netwatch orphans --json` and `netwatch report --since 1h --json`. `orphans --kill` is opt-in, needs `--pid`, `--match` or `--all`, re-checks each process immediately before signalling and sends only `SIGTERM` on macOS and Linux. Logs stay on the machine (`~/Library/Logs/netwatch`, `~/.local/state/netwatch` or `%LOCALAPPDATA%\netwatch\logs`), are owner-only, and have secrets in command lines masked.

## Agent log backup

`install.py --apply --log-backup` installs a scheduled, copy-only backup of agent logs to Dropbox (GoodQA #14471). It is opt-in: a host without the component gets nothing from a routine `install.py --apply` (uploads are plaintext until #14522), the choice is remembered in `~/.agent-harness/log-backup-choice.json`, and where the component is already installed (`log-backup.excludes` next to the script; a hand-installed script alone does not count) later installs keep it up to date. `--no-log-backup` remembers the opposite and stops the scheduler job persistently (deferred while a run is active): on Linux `systemctl --user disable --now`, on macOS `launchctl disable` plus `bootout`, so the plist that stays in `~/Library/LaunchAgents` is not loaded again at the next login or reboot (`--log-backup` always re-enables it, see the scheduler state machine below). The SessionStart alert stays registered where the component is installed, so a backup switched off on purpose still shows as stale instead of silently missing; files, logs and the remote copies stay. Files: `~/.agent-harness/bin/log-backup.sh`, `log-backup.excludes` and `log-backup.work-excludes`, plus a LaunchAgent `com.ericmacdougall.log-backup` (macOS, every 15 min) or the systemd user units `log-backup.service` and `log-backup.timer` (Linux). A second install changes nothing and reloads nothing; a differing hand-installed file is first saved as `NAME.bak-STAMP`; the scheduler is reloaded only when a unit changed, never while a run holds the lock, and never with a non-default `--home`. On Linux the timer needs systemd user linger (`loginctl enable-linger $USER`) to run without a login.

What it copies: `.claude/{projects,wals,history.jsonl}`, `.codex/{sessions,archived_sessions,history.jsonl}`, `.agent-harness/work` and the work-ledger files, to `<remote>/<host>/...`. It runs only `rclone copy` (and `listremotes`): a local deletion never reaches the remote, and an overwritten file is kept under `versions/STAMP/` (`LOG_BACKUP_VERSIONS=0` turns that off and logs a warning; versions of actively appended transcripts grow without bound until a pruning follow-up exists). Live sources (`.claude/*`, `.codex/sessions`, history and ledger files) are first snapshotted with rsync into `~/.agent-harness/backup-stage` (mode 0700, not deleted by the script, so it grows with the sources; credential-named files are excluded from the snapshot as well as the upload) and uploaded from the snapshot, because transcripts change mid-upload and Dropbox then rejects the hash; static sources (`.codex/archived_sessions`, `.agent-harness/work`) upload in place and skip files younger than 2 minutes. Credential-named files are excluded by `log-backup.excludes` (a filter file, never shell globs). Secrets pasted into transcripts cannot be found by name: **the remote copy is plaintext at rest until encryption is added** (open decision). Selecting a crypt overlay later needs only `LOG_BACKUP_REMOTE`.

Bulk tier timing (goodqa#15062): the bulk tier runs after tier 1 in the same run and uses only the time left. When no time is left it is deferred (logged as `bulk tier deferred`), which is not an attempt and does not fail the run; a bulk pass stopped by the run budget clears `log-backup.bulk-last-try`, so the next run continues it instead of waiting `LOG_BACKUP_BULK_EVERY_SECONDS`. A pass that finished, or in which any source really failed (even if another then hit the budget), starts the hourly gap. While a backlog lasts, a budget-stopped bulk tier therefore runs every 15 minutes instead of hourly: about four times the listing and checksum work, and up to `LOG_BACKUP_WORK_MAX_TRANSFER` (5G) per run, all inside each run's own time budget. The work-tree git scan is not time-bounded, so it starts only when its last measured duration (`log-backup.work-scan-seconds`, 60 s when unknown) plus one copy slice still fits. `log-backup.last-run` shows `bulk=0` for a deferred tier; the log line `bulk tier deferred` and the 6 hour bulk alert are what surface a tier that never gets time.

Bulk checkpoint (goodqa#15062): a bulk pass resumes where the last run stopped instead of starting over. Before this, every run started a fresh `rclone copy` of the whole source, so with a large work tree each run spent its few minutes re-checking the same first files and the pass never finished. Each bulk source now has a checkpoint in `~/.agent-harness/logs/log-backup.bulk.d/<source>/`. When a pass starts, `rclone lsf` lists the local source once, with the credential excludes and the source's own filters (`--min-age`, the work excludes, the git-tree excludes and `--max-size`). Files already verified by an earlier pass with the same size and modification time are left out, and the rest go to `pending`. The copy then sends `pending` in chunks of `LOG_BACKUP_BULK_CHUNK` files (default 1000 in the bulk lane, 100 in a run that shares its 13 minutes with tier 1; never more than fit the time left at about 2 rate-limited operations a file, because a chunk cut short is sent again whole) with `--files-from-raw` and `--no-traverse`. rclone refuses other filter flags with a file list, which is why the filters are applied by the listing. A chunk that exits 0 advances `cursor`. A chunk stopped by the budget is sent again whole next run, and rclone skips the files that already arrived. When the cursor reaches the end, the pass's listing becomes `done`, which drops deleted files, and the source counts as complete. The work-tree git scan runs only when a new pass is listed. Checkpoints are tied to the destination (`remote`) and start over if it changes. Two limits apply. A path containing a tab or a newline cannot be checkpointed; it is counted in the log. And a file removed from the remote by hand is not sent again until its local size or modification time changes.

Expected bulk backlog: the Mac's work tree listed 619,746 files on 2026-11-07 (bulk_measure, goodqa#15062); the earlier 70,218-file figure predates the agent worktrees now under it. The Mac runs at `LOG_BACKUP_TPSLIMIT=2`, and a pass cut short by the run budget continues on the next 15-minute run from its checkpoint, so the first pass still takes many runs (with 100-file chunks each chunk is one rclone start and one Dropbox batch commit; real files per run are measured in the live check before the chunk default is changed). Until it finishes, `log-backup.bulk-last-ok` can stay missing past its 6 hour limit and the session notice says the bulk tier "has not completed its first full pass yet". That is accurate, not an error: transcripts, WALs and ledgers (tier 1) are covered by `log-backup.last-ok` and are not waiting on the bulk tier. A pass is closed by removing `pending` before `listing` becomes `done`, so a crash while closing makes the next run list again rather than report a finished pass forever (PR #123 review L1). Excludes are judged on names when a pass is listed. Each checkpoint records a checksum of the two exclude lists (`filters`); when either list changes, the pass in progress is listed again, keeping `done`. The lists are read again before every chunk: a change during a run stops the pass after the chunk in flight, and the next run lists it again, so at most one chunk is sent from the old listing. A checkpoint written before this marker existed is listed again once.

Bulk lane (goodqa#15062, Mac only): tier 1 used about 9 of every run's 13 minutes, so the bulk tier moved about 400 files an hour. With `LOG_BACKUP_BULK_LANE=1` each scheduled run starts a detached lane run (`LOG_BACKUP_TIER=bulk`, set by the script itself) that copies tier 2. The launchd plist ships it off (`0`): it is turned on by hand only after three tier-1 runs in a row finish inside the budget with the lane running (goodqa#15147). The lane yields to tier 1 instead of splitting the write budget: the first split (1/s each) made tier 1 overrun its 13 minutes in 2 of 3 live runs. The lane never starts a copy while a live tier-1 run holds `log-backup.lock.d`; a lock with no pid file counts as held until it is stale (24 h), exactly as tier 1's own lock check treats it. During a copy it checks every `LOG_BACKUP_LANE_POLL_SECONDS` (default 2); when a tier-1 run starts, it sends its copy SIGTERM, then SIGKILL after `LOG_BACKUP_KILL_GRACE_SECONDS`, and sends the same chunk again whole after tier 1 releases the lock. A cut chunk never advances the cursor, so no file is skipped. The lane copies at `LOG_BACKUP_BULK_TPS` (default `TPSLIMIT`, never above it), and tier 1 always copies at the full `TPSLIMIT`. The lane writes `log-backup.lane.state`: `copying PID` before every copy, and only then checks the lock; `idle PID` while it waits. A tier-1 run takes the lock first and then waits, at most poll + kill grace + 5 s, while that file says `copying`; past that it logs a warning and copies anyway. Lane chunks are 300 files, so a cut chunk is cheap to resend. A scheduled run starts a lane only when the bulk tier is due (`log-backup.bulk-last-try` is older than the hourly gap, or was cleared by a pass stopped on the budget). A live lane started by the pre-#15147 script has no state file and does not yield: beside it, tier 1 copies at `TPSLIMIT - 1` until it ends. The lane holds `log-backup.lane.lock.d` and runs for at most `LOG_BACKUP_LANE_BUDGET_SECONDS` (default 10800, at most 43200 so a live lane's lock never looks stale); a scheduled run that finds it still going leaves it alone. Any run that copies tier 2 holds that lock, so a hand run with the lane off never shares a checkpoint with the lane. The lane writes `bulk-last-ok`, its own `log-backup.lane.last-run` and its own log, `log-backup.lane.log` (lines prefixed `[lane]`, rclone output included, rotated on its own); the scheduled run's `last-run` then reads `bulk=lane`. It never touches the stage or tier 1's watchdog markers. The plist sets `AbandonProcessGroup` so launchd does not stop the lane when the scheduled run exits. On SIGTERM every run, lane or not, stops its own rclone copy and watchdog before it exits, so no orphan copy keeps uploading. `install.py --no-log-backup` also sends SIGTERM to a running lane (only a pid running `log-backup.sh`). `log_backup.py status` shows the lane lock and the last lane run. A holder whose command line `ps` cannot read (a sandboxed shell) counts as alive, so its lock is never taken over. To turn it on, set `LOG_BACKUP_BULK_LANE` to `1` in the installed plist (`~/Library/LaunchAgents/com.ericmacdougall.log-backup.plist`, any plist layout) and run `install.py --apply`; later applies keep `1` and say `keeps the bulk lane on`. The installer records the value launchd last loaded in `log-backup.lane-loaded` and reloads the job whenever the plist's value differs, so the loaded job always matches the file. To turn it off, set it to `0` in the installed plist and run `install.py --apply`. A lane run still going finishes within its own budget; until then a run with the lane off skips tier 2 (logged as `bulk tier skipped`). Before rolling the script back to a version without the lane, stop the lane first: send SIGTERM to the pid in `log-backup.lane.lock.d/pid` (check that it runs `log-backup.sh`) and wait until that directory is gone. An older script does not know the lane lock and would share the checkpoint with it. Linux units do not set it.

Excluded `.lanes` copies: five `.lanes` directories in the Mac's work tree (about 230k files, 9.2 GB) are excluded in `log-backup.work-excludes`. Every file matched commit 9cbdd16 of the bugtracker repository by git blob id, that commit is pinned on GitHub by the tag `backup-pin/lanes-9cbdd16`, and the path, size and sha256 of every excluded file are in `lanes-exclude-manifest.tsv.gz` (with a `.keep` file, so work-directory pruning leaves it) under the work tree, uploaded directly before the excludes were installed. The fifth pattern (`repo2`) is already covered by the git-tree exclude, so the pending list dropped by about 184k files, not 230k. `pgdata` and `t2-course` stay included.

Write-rate budget: Dropbox limits write operations per account, and every host that backs up (Mac, dev2, T2) draws on the same budget, so each host runs at `LOG_BACKUP_TPSLIMIT=1` and `LOG_BACKUP_TRANSFERS=2` by default (whole numbers 1 to 99; raise them only on a quiet account). Hosts are staggered: the systemd timer adds `RandomizedDelaySec=120` and the launchd plist sets `LOG_BACKUP_JITTER_SECONDS=120` (a random start delay, since launchd cannot offset an interval). The Mac plist also sets `LOG_BACKUP_TPSLIMIT=2` (2026-11-07, goodqa#15062): the Mac carried a multi-hour transcript backlog while dev2 was being retired, so it takes a larger share; dev2 and T2 keep the default 1, which puts all three hosts together near 4/s rather than 3/s. Revisit it (back to 1) when T2 starts uploading after the move or when the log shows `too_many_write_operations` again. The setting lives in the plist so a reinstall keeps it (`launchctl setenv` is lost at logout or reboot); to change it, edit `harness/schedulers/com.ericmacdougall.log-backup.plist` and run `install.py --apply`. The bulk tier (archived sessions and the narrowed work tree) runs at most once per `LOG_BACKUP_BULK_EVERY_SECONDS` (default 3600); transcripts run on every pass, and a skipped bulk tier neither fails the run nor writes `bulk-last-ok` (its alert limit is 6 hours). Other bulk copies to the same account (such as a decommission backup) count against the same budget: give them a low `--tpslimit` as well.

Rollback: run `install.py --apply --no-log-backup` (or by hand: macOS `launchctl disable gui/$(id -u)/com.ericmacdougall.log-backup` and then `launchctl bootout gui/$(id -u)/com.ericmacdougall.log-backup` (bootout alone is undone at the next login by RunAtLoad); Linux `systemctl --user disable --now log-backup.timer`), then restore the `NAME.bak-STAMP` copies the installer saved next to the script, plist or units to go back to the hand-installed version. The remote copy is never touched. A scheduler reload that fails or raises leaves `~/.agent-harness/logs/log-backup.reload-pending`, and the next install retries it. `log-backup.log` is renamed to `log-backup.log.1` once it passes 10 MB (one generation); the launchd `.out`/`.err` files stay tiny and are not rotated.

Encryption at rest is deliberately not part of this component; it is tracked as follow-up GoodQA #14522. Until it lands, treat everything under `Backups/agent-logs/` as readable by anyone with access to the Dropbox account. The dev2 host retires on 2026-11-09 and its work moves to T2: reinstall the component there with `install.py --apply` (the remote there may be named `dropbox:` or `lessons-dropbox:`; selection is automatic) and keep the old dev2 backup path, because the remote copy outlives the host.

Remote selection: `LOG_BACKUP_REMOTE=NAME:path` (NAME must be a configured dropbox or crypt remote), else the first of `lessons-dropbox`, `dropbox`. The name is pinned in `~/.agent-harness/logs/log-backup.remote`; a change fails the run (exit 4) until you remove the pin. Exit codes: 0 ok or skipped, 1 a source failed or no primary source copied, 2 bad excludes, host, numeric or size setting, or stage path, 3 remote problem, 4 pin mismatch, 127 rclone or rsync missing, 1 the stage directory could not be created. rclone runs in Dropbox batch mode with 2 transfers, tpslimit 1 (the per-host default, see the write-rate budget above) and its own 10 retries (30 s apart), and the script retries a failed source twice more, because Dropbox rate-limits (too_many_write_operations); a source that still fails keeps the run non-fresh. Build outputs, VM and disk images are excluded; the build, dist, target and .cache exclusions match at any depth, including inside durable task folders under `.agent-harness/work`. The stage must be an absolute, private directory that is not a symlink and not inside or around any source; a stage that still holds deleted files never makes an empty live tree count as a backup. `last-ok` means every source copied without error, not that every file was uploaded: files younger than 2 minutes in static sources wait for the next run. A partial snapshot (rsync exit 23) uploads what was staged but withholds `last-ok`.

Two tiers, two markers (as in the reviewed live script): tier 1 (transcripts, WALs, ledgers) writes `log-backup.last-ok`, tier 2 (bulk: `.codex/archived_sessions` and the narrowed `.agent-harness/work`) writes `log-backup.bulk-last-ok`, so a slow bulk pass can never hide a gap in the transcripts. The run exit code is non-zero if either tier failed. `check` exits 0 when both are fresh, 1 transcripts stale, 2 transcripts missing or invalid, 3 transcripts fresh but the bulk marker is older than 6 hours (or never appeared although the backup was installed over 6 hours ago; `log-backup.first-run` records the install time); the session alert reports either. Uploads compare by checksum (`--checksum`) because staged files keep their modification times. On a remote with no hash in common with local files (a crypt overlay added later) rclone falls back to size-only, so re-check this flag before adopting one. Directories whose names contain backslashes, braces, glob characters or newlines cannot be excluded safely and are uploaded; `log-backup.log` counts them each run. A `.git` deeper than 12 levels under `work/` is not detected.

Freshness: `~/.agent-harness/logs/log-backup.last-ok` holds the run start time and is written, atomically, only after every source copied and at least one primary source (`.claude/projects` or `.codex/sessions`) was copied. A run skipped because another holds the lock writes `log-backup.last-skip` and never counts as success. `python3 ~/.claude/hooks/log_backup.py check` exits 0 fresh (1 hour or less), 1 stale, 2 missing or invalid (garbage or future); `status` prints the success, run, skip and lock state; a SessionStart hook prints a visible alert when the backup is not fresh (a very long session will not see staleness arrive).

Shared Dropbox write budget (goodqa#15218): `~/.claude/hooks/dropbox_budget.conf` holds the account's write budget in operations per second and each uploader's share: `account 6` (an ASSUMPTION: Dropbox does not publish the limit; throttling appeared at about 7/s on 2026-11-07, so the total sits below that), `log-backup.Mac-2 2`, `log-backup.t2-dev 1`, `agent-bulk 2` and `reserve 1`. log-backup.sh uses the share named `log-backup.<host>` as its `--tpslimit` when LOG_BACKUP_TPSLIMIT is unset (the systemd unit) and otherwise only lowers that setting; heavy_job_guard caps the agent upload lane at `agent-bulk` (never above its built-in 4). Both readers apply one line rule (CRLF accepted; anything odd, a symlink or a file over 64 KiB makes the file invalid). A missing or invalid file, or one without a share for the reader, leaves today's values (LOG_BACKUP_TPSLIMIT or 1; 4). The agent-bulk share is enforced per host (one agent upload at a time on each host), not yet across hosts. A run whose copy fails or is cut short on the rate limit stops copying (the transcripts, `.claude/projects` and `.codex/sessions`, still get their own copy), writes `log-backup.throttled` and withholds last-ok; status and the backup alert name it.

Machine-readable status: `python3 ~/.claude/hooks/log_backup.py status --json` prints one JSON object, `{"schema": 1, "transcripts": {"state", "age_seconds", "max_age_seconds", "marker"}, "bulk": {same}, "last_run", "last_skip", "last_throttled", "lock", "ok"}`, and exits 0 when `ok` (transcripts fresh and bulk fresh or pending), 1 otherwise. States are fresh, stale, missing, invalid or (bulk only) pending. Other tools should read the marker names and limits from `log_backup.py` (`LAST_OK`, `BULK_OK`, `MAX_AGE_SECONDS` = 3600, `BULK_MAX_AGE_SECONDS` = 21600) and keep these names stable.

Restore test: `python3 ~/.claude/hooks/log_backup.py restore --src .claude/wals --into /an/empty/scratch/dir` copies the source from the remote, verifies it against the remote with `rclone check --download`, and compares it with the live files (identical, grown = restored is a byte prefix of the longer live file, differing, or no-live). It exits non-zero on zero files, a differing file or a failed check, and refuses relative, `..`, symlinked or non-empty targets and anything inside `~/.claude`, `~/.codex` or `~/.agent-harness`. A real disaster restore copies from the remote into the new home by hand with `rclone copy`.

Work tree and run budget: `.agent-harness/work` can hold hundreds of GB of git worktrees, checkouts, screenshots and mutation trees, which no 15-minute run can upload under Dropbox rate limits. The component therefore backs up only small durable state from it: every directory that has a `.git` entry is excluded (found on each run; paths with glob characters cannot be excluded safely and are still uploaded), media and archive files (`log-backup.work-excludes`) are skipped, files over 25M are skipped (`LOG_BACKUP_WORK_MAX_SIZE`) and a 5G transfer cap applies (`LOG_BACKUP_WORK_MAX_TRANSFER`). Each run has a 13 minute budget (`LOG_BACKUP_BUDGET_SECONDS`) passed to rclone as `--max-duration`; when the budget or transfer cap stops a source, progress is kept, `last-ok` is withheld and the next run continues, so a large backlog shows as a stale backup rather than a hung job. The freshness alert does not depend on the lock: a run that has been going for over an hour still alerts, and the alert says that a run holds the lock.

Scheduler state machine (`log_backup_install.py`, one owner: `status()` decides, `reload_scheduler()` enables, `disable_scheduler()` disables). Inputs: the remembered choice (`~/.agent-harness/log-backup-choice.json`), whether the installed files differ from the repo, and whether a backup run or a hand-installed run is active. Recorded state: `~/.agent-harness/logs/log-backup.scheduler` holds `enabled` or `disabled`, written only after the matching command SUCCEEDED; `log-backup.reload-pending` marks a deferred, failed or raised attempt. Transitions: choice on and (files changed or state is not `enabled` or a retry is pending) leads to enable (macOS `launchctl enable`, `bootout`, `bootstrap`; Linux `daemon-reload`, `enable --now`, `restart`) and, on success, state `enabled`; choice off and the component is installed and (state is not `disabled` or a retry is pending) leads to disable (macOS `launchctl disable` then `bootout`; Linux `disable --now`) and, on success, state `disabled`; choice on, files unchanged, state `enabled`, nothing pending: no scheduler call and the message says up to date; choice off and state `disabled`: no call, "nothing changed"; a run in progress defers either direction (marker kept); a failed or raising command keeps the marker and leaves the state unchanged, so the next install retries; a non-default `--home` never touches the scheduler. Preview (no `--apply`) and apply share one plan (`plan()`), so the preview says `would (re)load and enable` (with the reason: a unit file changed, a retry is pending, or the recorded state is `disabled`/unknown) exactly when apply would call the scheduler, and `up to date` appears in neither while the installer has the job disabled. Limits, not built for: the recorded state is what the installer last did, so a `launchctl disable` or `systemctl --user disable` run by hand afterwards is not noticed (re-run `install.py --apply --log-backup` after changing it by hand, or remove `log-backup.scheduler` to force a re-enable); two installs run at the same time are not serialised, so do not run them concurrently. On Linux, if the timer unit file has been deleted, an opt-out stops whatever is still loaded and counts as done instead of failing on every install.

Coexistence with the hand-installed script: it keeps its own lock directories (`log-backup.lock.d` without a pid, `log-backup.transcripts.lock.d` stale after 1 hour, `log-backup.bulk.lock.d` stale after 6 hours). A young one means its run is still going, so the component skips (recording `last-skip`) and the installer defers the scheduler reload instead of killing that run; an unreadable modification time counts as a live run, and a time in the future counts as live only within the stale limit. A hand-installed lock left behind by a crash or a killed run therefore pauses every component run, including the transcripts tier, for up to 6 hours (1 hour for the transcripts lock); only `last-skip` and the stale-marker alert show it, so remove such a lock by hand once you know its run is gone. The component itself uses one lock. Its 13 minute budget is passed to every rclone call as `--max-duration` and stops new copies once used up, but it is a target, not a hard cap: rsync has no timeout and rclone's retry sleeps can run past it, so a run can end later than 15 minutes (the lock and the timer still prevent overlap). A lock holder only counts as a live backup run when its command line is a shell running a path that ends in `log-backup.sh` (a path with spaces is fine), in both the script and the installer.

Behaviour changes from the hand-installed script: lock takeover by rename (and only for a dead or non-log-backup holder or a lock over 24 h old), skip marker, primary-source rule, anchored excludes check, remote type check and pin, extended excludes, retries, rclone timeouts, `RCLONE_*` environment stripped except `RCLONE_CONFIG`.

## Design limits

The policy is intentionally risk-scaled. The small fix path skips worktrees and review loops. A normal code task gets only relevant tests and documents. The agents must not infer that the presence of a test or a reviewer PASS proves quality. Independent checks, reviewer availability, UI tool access and remote permissions vary by environment; handoffs must say exactly what ran and what did not.

Claude Code settings can change between versions. The hook structure follows the [Claude Code hooks reference](https://code.claude.com/docs/en/hooks), and worktree agents follow the [subagent](https://code.claude.com/docs/en/sub-agents) and [worktree](https://code.claude.com/docs/en/worktrees) guides. Check these references when upgrading Claude Code.
