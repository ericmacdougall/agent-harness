# Spec: Self-host production cannot start any dispatcher job (scan, transcode, intelligence-worker, suggest-fix-worker): job images never built or loaded, guard refuses DO-registry pins (since ~2026-10-14)

## Outcome

After the next release through the release runner, every dispatcher job kind (scan, transcode, intelligence-worker and suggest-fix-worker) starts and completes on the self-host production stack. Users get repo scan results, playable recordings and transcripts, new project intelligence and Suggest Fix proposals again. A release whose compose file names an image the host does not have is refused before the switch, never left half-broken.

## Scope

- In:
  - harness `config/goodqa-release/bin/rw-ship.sh`, the self-host IMAGES section: build, transfer, id-verify and deploy-record the four job images.
  - The one `vmctl pin` call, which gains `--job-image` arguments.
  - harness `config/goodqa-release/bin/selfhost-ctl.py`:
    - `pin --job-image KEY=REF`, which rewrites the four `JOB_IMAGE_*` lines of the `&job-images` anchor on the create-guard block (the dispatcher inherits them through `<<: *job-images`)
    - an image-presence check over every image named in the prepared compose
    - `state` reports the job pins
  - harness `config/goodqa-release/bin/test_rw_ship_selfhost.py`: the tests.
- Out:
  - `ship.sh` and the staging-gate lines of rw-ship.sh (owned by the goodqa#16130 part 2 owner a65f3103; ranges agreed, no overlap).
  - The bugtracker product code: the guard and dispatcher are unchanged, and AUD-031 digest pinning is kept as is.
  - Worker runtime env gaps. GITHUB_APP_ID and GITHUB_APP_PRIVATE_KEY are not in the self-host job env for intelligence-worker; this gets a follow-up ticket if the live proof shows it.
  - Any production database read or write (forbidden by programme rule, by any route).
  - Bulk re-running of failed user jobs.

## Risks

- Seven images per release add build time, possibly 10-20 minutes, against the 60-minute unit timeout. Mitigation: measure one real job image build on t2-dev, record it in the packet, and raise TimeoutStartSec in ship.sh only through its owner if needed.
- The jobs have never run on self-host, so having the images present is necessary, not sufficient. Per-job env (GITHUB_APP_ID and GITHUB_APP_PRIVATE_KEY are absent for intelligence), network or guard HostConfig limits may still fail a job. Mitigation: AC-5 to AC-8 prove one real job of each kind, and any failure gets its own ticket with the job log. The staging gate (goodqa#16130) is used first if it is ready. Otherwise the ship is labelled TARGET_MISMATCH: no staging rehearsal of the job kinds.
- A job image's tag is per release (`goodqa-JOB:SHA12-STAMP`) and old ones pile up on the host disk. Mitigation: the same retention as the existing api, web and dispatcher tags, with no new pruning in this change.
- If the presence check read the live compose, the first deploy of the fix would refuse itself. Mitigation: AC-3 checks the prepared text, with a test.
- rw-ship.sh is also edited by the goodqa#16130 part 2 owner. Mitigation: disjoint line ranges are agreed, and whoever merges second rebases.
