# Spec: P0: internal parallel headed agent browser, off the user's screen, with Chrome cookie import

Ticket: GoodQA goodqa#15745

## Outcome

An agent (MCP or REST, through a granted org agent key) leases several parallel headed Chrome sessions in seconds on a GoodQA fleet virtual display, never touching the user's screen or the GoodQA desktop app window, controls them (navigate, click, type, read, screenshot, tabs), can be watched live on demand in the GoodQA web app, and can open one with the user's own imported Chrome cookies so a signed-in site shows the user signed in. The user's only human step is answering the native macOS prompts of one helper command that the agent starts.

"GoodQA main screen" means the GoodQA desktop app window (and the user's display). The desktop Electron lane (modules/machines/agent-browser.ts, browser_* tools) is the lane that can take that over; this change never routes to it.

## Scope

- In: headed Chrome on Xvfb in the Agent Browsers worker; a worker that runs leases concurrently; multi-tab control with a popup policy; on-demand live view (worker-to-API relay) and screenshots; per-user encrypted cookie profiles; a native macOS export helper; owner-only use, revoke, audit; automated grant and key issuance through the user token; concurrency and time-to-ready measurement.
- Out: the desktop Electron lane (untouched, never a default); CAPTCHA solving; account creation; password typing (credentialRef rules unchanged); letting the user token open a lease directly (NOT approved by main, goodqa#15746 keeps the step-up credential); production deploy by the owner (main directs it); encryption key rotation (documented only).
- Assumption labels: every numeric latency, size and cap in this spec is an ASSUMPTION (inferred), not a user-stated number.

## Transport and custody (cookies)

- Path: Mac helper -> HTTPS (TLS) to goodqa.app API only (pinned host, no redirects) -> Postgres (sealed blob, unchanged) -> worker host (infra/do/agent-browsers droplet) which alone holds the unsealing private key and unseals at lease start. No third-party service, no logging of values.
- In transit: TLS plus the sealed box (defense in depth). The sealed plaintext carries userId, orgId, idempotency key, issuedAt and the upload ticket.
- At rest: the sealed blob only. Metadata in clear is domains, count, timestamps, userId, orgId, version.
- Who can decrypt: the worker lease path for the owning user's lease only. The API, admins and other members cannot. Stated trust assumptions: whoever operates the worker host and holds its private key can decrypt (single-operator system, accepted); the worker already holds the vault KEK (co-resident risk accepted and noted).
- Retention and deletion: default max age 14 days then purged by an idempotent scheduled job; owner delete removes the blob immediately and ends live leases; database backups age out on their normal retention window (stated in days in the release notes from the existing backup policy). Key rotation is out of scope; the blob carries a key id so rotation can be added; profiles are at most 14 days old so an old key can be retired after 14 days.

## Release (deploy route, health, rollback; main directs the deploy)

- Deploy route: existing infra/do/agent-browsers deploy flow after the API migration and API deploy; API first, then the worker image (Xvfb, headed Chromium, profile private key as a worker-only secret); migrations additive only.
- Live worker sizing: stated in the release notes before deploy (worker count and droplet size must support the 32 fleet cap or the cap is lowered to match; compose currently mem_limit 3g, cpus 2, 512 MB /browser-tmp which holds about 4 headed leases, so the release plans for at least 8 workers or lowers the fleet cap to the measured capacity, and /browser-tmp headroom for 4 Chrome profiles is part of the AC-4 measurement).
- Health check: worker readiness reports headed true and Xvfb up; scripted lease open, navigate and screenshot on the live worker; 4-lease parallel probe; live view fps probe.
- Capability gate: the API refuses profileId and tab requests until the worker reports the new capability (agent_browsers.capabilities heartbeat); the capability flag is disabled, so the API refuses profile and tab requests, before any worker rollback so a profile lease is never run anonymously by an old worker.
- Rollback: AGENT_BROWSER_HEADED=0 returns to headless without an API redeploy; previous worker image tag kept; new tables and columns are unused when no profile is created; agent_browser_close always available. When the fleet is full new opens wait then return browser_capacity with Retry-After.

## Risks

- Cookie bundle leaks through logging or error messages: values wrapped in a type whose toString and JSON are redacted, third-party exceptions that stringify CDP params are caught and replaced, sentinel and mutation tests (AC-10).
- Headed Chrome in a container needs a display and shared memory: Xvfb per worker, --disable-dev-shm-usage fallback; crash recovery AC-19.
- Injecting cookies lets a lease act as the user: owner-only, origin and domain filtered, 14-day TTL, audited, revocable, grant required, 15 s revoke bound. The agent controlling the lease sees signed-in pages by design (accepted trust boundary; the user's request to have agents use their signed-in sessions is the consent).
- Live view and screenshots show private signed-in content: owner-only ACL, no-store, caps, profile-lease artifacts expire in 1 day.
- Worker-held private key and operator trust: stated assumption; no key rotation in this slice.
- Helper trust on the Mac: Keychain prompt is the human gate; helper built from the repo, SHA-256 in the build log compared by the agent before running; compiled-in host, no redirects, token never printed.
- Chrome cookie encryption format changes: macOS v10 supported, unknown versions fail closed.
- Worker concurrency refactor could regress existing lease behavior: existing agent-browsers tests run before and after.
- Replaying the user's cookies from a datacenter IP with a different fingerprint can trigger security alerts or revoke the session in the user's own Chrome (notably Google): the user is told before the first real import and the live check uses a lower-risk site.
- Worker headed fingerprint can trip bot detection: no evasion work is done; this is not a CAPTCHA bypass.
- Prompt injection from page content: existing untrusted-content notice and origin allowlist unchanged.
