# Spec: Sanctioned audited remote hook install: ah install-files --host

Ticket: GoodQA goodqa#15742
Author: agent:af9e33704216a1ea1 (Sonnet 5.5)
Click-test: required
Sign-off: main
Review-policy: standard

## Outcome

A merged hook file can be installed on a remote host (t2-dev, ah-mac-mini) through one audited command, `ah install-files --host HOST --from-ref SHA --file NAME [--file NAME ...] --ticket GoodQA project#N [--dry-run]` (with `--resume RUN_ID` to finish an interrupted run and `--rollback RUN_ID` to undo one), that takes the bytes from a git commit proven to be on the live remote main, backs up what is there, uploads and verifies every file before replacing any, replaces them atomically with command_guard.py last, reads each sha256 back, compares the host's own self-test (allow and deny probes plus the doctor findings) before and after, rolls back automatically when the result is worse, and writes an audit row on both ends, so a remote install no longer needs a hand-typed `cp`, `mv` or `scp` into a guarded path (the 2026-11-11 t2-dev install of command_guard.py was blocked as `cp` and then done with `scp`, a second route around a guard). The Mac guard allows the command only in its exact literal form and only for main.

## Scope

- In: a new module `harness/hooks/ah_install.py`, an `ah install-files` subcommand in `ah.py`, the module added to both installer file lists, a literal-form rule in `command_guard.py` (AC-9); nothing is read from any repository the caller names: the tool fetches `refs/heads/main` of the canonical harness repository URL (a constant in the module, ASSUMPTION A4: that repository is readable without credentials) into its OWN bare repository `~/.agent-harness/install-cache` (mode 0700, `transfer.fsckObjects=true`, so every object arrives hash-verified), and the bytes come from `git cat-file blob SHA:harness/hooks/NAME` in that repository, SHA a full 40-hex commit that is an ancestor of the fetched main; names only from the installer's `HOOKS` tuple at that (proven merged) commit, read with `ast`, never imported; hosts only from the allowlist `t2-dev` and `ah-mac-mini` (ASSUMPTION A1: dev2 is gone after the pve shutdown; the ticket text also lists dev2); the remote home is `~/.claude/hooks` on the host; transport is `ssh -o BatchMode=yes -o ClearAllForwardings=yes` running a constant, fixed remote program whose text is part of this module (`python3 -I -c SCRIPT OP ARGS`, one shell-quoted command string, never caller-supplied), with file bytes on stdin; `--dry-run`; `--resume`; `--rollback`; JSON on stdout.
- Out: the Mac itself (`install.py` and the selective installers stay the route there); the Codex home on remote hosts and the `DELIVERY_HELPERS` names of `install_codex.py` (ASSUMPTION A5: the ticket allows those names too, this spec narrows to `HOOKS` for the Claude-style home because the Codex home has another path and another self-test; a follow-up widens it); `settings.json` and `CLAUDE.md` edits; any caller-chosen path or bytes; any automatic run from a hook; Windows hosts.
- Decisions (owner assumptions, none is a user decision; main confirms A2 with a source): A1 host allowlist; A2 the command is main-only, applied by the guard rule in AC-9 (which is accident prevention, not an access control: see its stated limit) (the ticket says a human or main decides whether sub-agents may use it, so the default is no); A3 the self-test is the guard's allow and deny probes plus the failing checks of `doctor.py check --json --no-canary` on the host; A4 the canonical harness repository is public; A5 `HOOKS` only; A6 a stale lock is 30 minutes judged by the host's clock (a run has a 20 minute budget); A7 the Mac copy of the old bytes lives in `~/.agent-harness/install-backups/RUN_ID/` (durable, shared by sessions) rather than in an owner work directory, which the ticket names, because a work directory belongs to one session and is not a stable place for a rollback to find; the ticket's wording is narrowed on purpose.

## Acceptance criteria

- AC-1: Only these inputs are accepted, all checked before any ssh call: `--host` in the allowlist; `--from-ref` a full 40-hex lowercase sha; each `--file` a bare name (letters, digits, `_`, `-`, `.`, no slash, no dot segment, no leading dot) listed in `HOOKS` at that commit and present as a blob at `harness/hooks/NAME`; no duplicate name; between 1 and 20 names; each blob at most 4 MiB; `--ticket` of the form `GoodQA project#N` REQUIRED for a real run, a resume and a rollback (optional for `--dry-run`); `--resume` and `--rollback` take a run id of the form `ins-` plus 12 hex and no `--file` or `--from-ref`; `--force-file NAME` is accepted only with `--rollback` and only for a name in that run's file list; `--allow-older` is accepted only with a new install and is audited in the start row. Everything else refuses with exit 2 and a named reason. Verify by: `python3 -B -m unittest tests.test_ah_install` (one subtest per bad input). Source: ticket:GoodQA goodqa#15742
- AC-2: The bytes are proven merged from a repository the tool owns, never from one the caller names: the tool fetches `refs/heads/main` of the constant canonical URL (never a configured remote) into a FRESH temporary bare repository created for this run only (a new directory 0700 under `~/.agent-harness/install-cache/`, created exclusively, deleted by its own fixed name after the run and when a run starts with a leftover older than one hour) with `transfer.fsckObjects=true`, so every object arrives through the fetch's own verification in this run and nothing planted beforehand can exist in it, then checks that SHA is an ancestor of the fetched main with `merge-base --is-ancestor`; every git call there runs with `GIT_NO_REPLACE_OBJECTS=1`, `-c core.commitGraph=false`, the global and system config off, `core.fsmonitor=false`, `core.hooksPath=/dev/null`, and the cache must have no `info/grafts`, no `shallow` file and an empty `refs/replace`; each blob's tree mode must be `100644` or `100755` (a symlink or other mode refuses); the git blob id is recorded in the audit; an ancestor of main is NOT enough to install: when a newer merged commit changed a requested file (`git log REF..main -- harness/hooks/NAME` is not empty) the run is refused as a DOWNGRADE (code `older_ref`, naming the latest commit) unless `--allow-older` is given, which the start row audits; an installer list at that commit that is not a plain literal refuses; a failed fetch or a failed proof refuses the run before any ssh call. Because git does not hash-check objects on plain reads, the tool also re-computes the hash of every object it relies on (the commit, each tree on the path and the blob) with `git hash-object` and refuses on any difference, so an object written into the repository after the fetch under a real id is caught too; because the repository is created fresh for each run, nothing planted beforehand (an object, a pack, a commit-graph file, a replace ref) can exist in it, and every object, including every commit the ancestry walk reads, arrived through the fetch's own verification in this run. STATED LIMIT: a same-user process that writes into that repository during the few seconds of the run is outside the threat model. A fork URL, a moved or forged ref, a replace ref, a graft, a shallow cache, a forged commit-graph, a planted pack holding a forged blob under a real id, a symlink-mode blob and a ref that adds a new name to `HOOKS` without being on the fetched main all refuse. Verify by: the same suite with fixtures for each (a local bare repository standing in for the canonical URL through a test-only constant, a replace ref, a planted pack with a forged blob, a forged commit-graph file, a symlink blob). Source: ticket:GoodQA goodqa#15742
- AC-3: Install in two phases. Phase 1 (nothing live changes): for every file read the host's current sha256 (absent is allowed), copy an existing live file to `~/.claude/hooks/.ah-install/backups/RUN_ID/NAME` on the host (created 0700, files 0600) and keep a copy in the caller's `~/.agent-harness/install-backups/RUN_ID/` with its sha256 checked against what the host reported, upload the new bytes to `.NAME.ah-install-tmp` in the same directory as the target (created exclusively, mode 0600, over ssh stdin), and compare the sha256 of every temporary file with the sha256 of the git blob; a symlink or directory at a target or at a temporary name, a temporary name that exists as anything but a regular file (replaced by the run's own fixed name), or a mismatch refuses the whole run before any rename. Phase 2: for every file in a fixed order with `command_guard.py` LAST, set the mode (the old file's, else 0644), rename atomically over the live name, fsync the directory, then read each live sha256 back; the run reports per file old sha, new sha, backup path and the blob id. Keep the last 10 backup runs under `.ah-install/backups` (older ones are pruned by that fixed path only). Verify by: the same suite plus a real ssh-to-localhost run on a disposable HOME (skipped when the machine does not accept ssh to localhost), with a bad file 2 while file 1 is command_guard.py: nothing live changes. Source: ticket:GoodQA goodqa#15742
- AC-4: The host self-test runs before any write and again after the last rename, in the same fixed way, and the result is recorded: the verdict (allow or deny plus rule id) and exit code of `python3 -I ~/.claude/hooks/command_guard.py check` for one allow probe (`ls -la`) and for fixed deny probes that must stay denied with the same rule id (a recursive delete of the harness WAL directory and an ssh-wrapped `cp` into `~/.claude/hooks/command_guard.py`; measured against the real guard: an `scp` into that path is NOT denied today, so it is not a probe), and the SET of failing check ids of `doctor.py check --json --no-canary` (a check whose `state` is neither WIRED nor PENDING fails) (only the ids are stored and audited, never doctor's text; a timeout of 120 seconds for doctor and 60 seconds per guard probe, all inside a TOTAL deadline of 200 seconds enforced by the remote script itself (a probe that has no time left reports an error, not a pass) and under a local timeout of 330 seconds, so a local timeout is a lost link and not a slow self-test; an after-install self-test that does not answer in time is treated as a worse result and triggers the automatic rollback, guard first; when the host's doctor predates those flags the self-test uses the guard probes only and says so). After the install every probe verdict must be unchanged and the failing set a subset of the failing set before; anything else (a changed verdict, a new failing check, a non-zero exit, a self-test that cannot run) rolls EVERY file of this run back from its backup in the reverse order with command_guard.py restored FIRST (a file that did not exist before is removed by its live name only when its sha256 equals this run's new sha256), reads the shas back, reports ROLLED_BACK with the reason and runs the self-test once more; a self-test that cannot run BEFORE any write refuses the run, and so does a host whose guard already fails open: the baseline must show the `rm -rf ~/.claude/wals` probe BLOCKED and `ls -la` allowed (a guard that allows everything before the install would let any replacement pass the comparison); the deny probe for the ssh-wrapped `cp` is compared for an unchanged verdict only, because an older guard may lack that rule. Verify by: the same suite with a fake host whose `~/.claude/hooks` holds the REAL command_guard.py and doctor.py, installing a GENUINELY broken command_guard.py from a test commit (an allow-all guard, a guard that crashes), one that already fails some doctor checks (the baseline), one whose doctor timeout fires, and one that cannot run. Source: ticket:GoodQA goodqa#15742
- AC-5: Audit and unknown outcome. An audit row is appended to the Mac's `~/.agent-harness/install-audit.jsonl` (mode 0600, `O_NOFOLLOW`, fsynced) BEFORE the first remote write (start: run id, host, the canonical URL, the fetched main sha, ref, files, blob ids, new and old shas, the self-test baseline, caller session and agent, the sha256 of the constant remote script) and after the run (result: installed, already_current, rolled_back, refused, dry_run, restored or unknown, per file old and new sha and backup path); a failed Mac audit write stops the run before any ssh write and exits non-zero; one row is appended to `~/.agent-harness/install-audit.jsonl` on the host (created 0700 and 0600 on the first install, best effort: a failure is reported, never fatal) with the run id, files, shas, the script sha256 and the caller agent; with `--ticket` one comment is posted naming the ref, the files and the shas (a failure to post is reported). The result is `unknown` whenever the outcome of a remote step cannot be known (a lost answer after the first remote write, an interrupted automatic rollback, reported as "rollback incomplete"), never installed or refused, with the host named. A host with an UNFINISHED run (an install, resume or rollback ATTEMPT whose start row has no definite result) refuses every new install and rollback of another run; only a definite result clears an attempt (installed, rolled_back, restored, already_current, or `refused` of a NEW install, where nothing live changed), while `unknown` and `attempt_refused` never clear: a resume or a rollback that is refused (the lock held by another run, no answer at the lock, a stage that fails) is recorded as `attempt_refused`, because the host is still in whatever state the earlier attempt left it, and a resume always counts as started, so its failures are `unknown` or a rollback and never a clean refusal; a failure before the lock is taken touches nothing on the host; `--resume RUN_ID` finishes it reusing the ORIGINAL self-test baseline from the start row, or `--rollback RUN_ID` undoes it. STATED LIMIT: when neither can ever succeed (both backup copies missing or tampered, a rebuilt host) the host keeps refusing new installs until an operator edits the audit file by hand; a main-only `--resolve RUN_ID` that records a definite row only when every live sha matches that run's old or new sha is tracked as a follow-up ticket. Exit codes: 0 installed, already_current, dry_run or restored; 2 refused for input or a precondition; 3 the Mac audit write failed; 4 rolled_back; 5 unknown. Output is one JSON object. Verify by: the same suite (a kill after the first rename then a plain rerun refuses, then a resume finishes with the original baseline). Source: ticket:GoodQA goodqa#15742
- AC-6: Unattended safety: a rerun with the same ref and files is a no-op per file (the live sha equals the new sha: already_current, no backup, no write); two runs on the same host cannot interleave (a lock directory `~/.claude/hooks/.ah-install/lock` created with `mkdir`, holding the run id and taken by every install, resume and rollback; one older than 30 minutes by the HOST's clock is taken over atomically by renaming it aside under a unique name and creating a new one, with a note in the result; released only by its own run id and in every path; the same run id takes its own leftover lock back, as a resume does, and the lock's time is renewed by every stage, commit and restore so a slow run does not look stale; renamed stale locks are pruned; the remote hooks directory must be a real directory owned by the connecting user, a symlink or another owner refuses every operation, and its realpath is reported by the probe); an interrupted upload leaves only the fixed temporary name which the next run replaces; the remote program is run as one command string built with `shlex.quote` per argument, passed to `ssh -o BatchMode=yes -o ClearAllForwardings=yes -- HOST CMD`, and runs on the oldest `python3` of the allowed hosts (3.9: no newer syntax or library). Verify by: the same suite (rerun, two runs racing, fresh and stale lock, interrupted upload, the real argv run through `sh -c` with a minimal PATH reaching python unchanged, the script compiled and run by python 3.9 semantics). Source: ticket:GoodQA goodqa#15742
- AC-7: `--dry-run` validates every input exactly as a real run (including AC-2), reads the host's current sha256 of each file and the self-test baseline over ssh (read-only operations only), prints the plan per file (new, replaced or already_current, old sha, new sha, backup path it would use), writes only a `dry_run` audit row on the Mac, takes no lock and changes nothing on the host (the hooks directory listing, sizes, mtimes and inodes are identical before and after). Verify by: the same suite. Source: ticket:GoodQA goodqa#15742
- AC-8: `--rollback RUN_ID` takes the lock and, for every file of that run in the Mac audit row, restores the backup onto the live name by the same upload, sha-check and atomic-rename steps with command_guard.py first, only when (a) the backup's sha256 (the host copy, or the Mac copy when the host copy is missing or differs) equals the old sha the row recorded and (b) the LIVE file's sha256 still equals the run's recorded new sha (else that file is refused and the later run named, unless `--force-file NAME` is given and audited); a file the run created is removed by its live name only when its sha256 equals the new sha; it then runs the self-test and writes its own audit rows; it is never blocked by a failing self-test (it reports the result); the restore step returns the REAL state of every file it was asked to remove or restore and the read-back checks it, so a file that could not be removed (its sha256 is not the run's new one) makes the result `unknown`, never `restored`, and is refused only for an unknown run id, another host's run, an already rolled back run or another unfinished run. Verify by: the same suite (rollback after a good install, after a degraded one, with a tampered host backup falling back to the Mac copy, with a tampered Mac and host copy refused, after a later install changed the file). Source: ticket:GoodQA goodqa#15742
- AC-9: The Mac guard allows `ah install-files` only in its exact literal form and only for main: the installed copy (`python3 -I ~/.claude/hooks/ah.py install-files ...` or the installed `ah`) with flags matching the AC-1 grammar, when the caller is main (`caller_identity.is_main`, decided from the hook payload and its transcript proof, never from an environment variable the caller sets); a bare `ah` is resolved to its real path and passes only when that is the installed copy (a script named `ah` earlier on PATH does not); it refuses a repository or worktree copy of `ah.py` or `ah_install.py`, a `python3 -c` or `-m` import of `ah_install`, any other path to those files, and any caller that is not main, each with a refusal that names the sanctioned form. The match is made on the command with quotes removed (`install-file""s` is the command), the body of a `bash`, `sh` or `zsh -c` is inspected, wrappers such as `env` and `sudo` are looked through, a heredoc or `python -c` import of `ah_install` (also by concatenation or importlib) is refused for every caller, redirections (`> out.json`, `2>&1`) are allowed after the grammar, and programs that only VIEW the name (grep, rg, cat, git, sed and similar) pass. STATED LIMIT: this rule is ACCIDENT PREVENTION, NOT AN ACCESS CONTROL: the guard sees command text only, so a script that imports `ah_install` through `sys.path`, or any program that speaks ssh itself, is invisible to it; the controls that hold are the merged-code proof (AC-2), the allowlists and the audit (AC-5). A hand-typed `cp` or `mv` into `~/.claude/hooks` over ssh stays refused by the existing rule (its text is not changed by this work; an `scp` is not refused today, which is a known gap outside this spec, tracked as goodqa#15759). Verify by: `python3 -B -m unittest tests.test_command_guard_install_files` driving `command_guard.py check` and the hook entry with main and sub-agent payloads for every form. Source: ticket:GoodQA goodqa#15742
- AC-10: Real proof by main: a real ssh-to-localhost run on the Mac with a disposable HOME (the AC-3 suite part, run where `ssh localhost` works); `--dry-run` on t2-dev and on ah-mac-mini; the real install on t2-dev of the files of a merged PR, then `--rollback RUN_ID` of that run, then a second real install of the same ref, each with its saved output, the before and after shas, the self-test results, the audit rows on both ends and the ticket comment kept under the work directory; the live hooks directory ends at the new shas. The owner types no scp, cp or mv. Verify by: the saved outputs. Source: ticket:GoodQA goodqa#15742

## Negative cases

- NEG-1 (AC-1): a host outside the allowlist, a shell metacharacter or a leading dash in the host, a ref that is a branch name, an abbreviated or uppercase sha, a name with a slash or `..` or a leading dot, a name not in the installer list at that ref, a duplicate name, more than 20 names, an empty list, an oversized blob, a missing or malformed ticket on a real run, a malformed run id, and `--resume` combined with `--file` must all refuse before any ssh call. Source: ticket:GoodQA goodqa#15742
- NEG-2 (AC-2): a canonical URL that is a fork or another repository, a replace ref that swaps a blob, a graft or shallow file in the cache, a forged commit-graph file claiming ancestry, a pack, a forged parent commit or a commit-graph file planted in the install-cache directory beforehand (it has no effect on a run, which fetches into a fresh repository), a repository object overwritten with a forged blob (tree or commit) under a real id after the fetch, a blob with mode 120000, and a ref that adds a name to HOOKS and is not an ancestor of the fetched main must all refuse before any remote write; there is no `--repo` flag to point at another repository. Source: ticket:GoodQA goodqa#15742
- NEG-3 (AC-3): a wrong upload (the remote sha256 differs from the blob) leaves every live file untouched and removes the temporary files; a bad file 2 when file 1 is command_guard.py changes nothing live; the target or the temporary name is a symlink or directory; the backup of this run already holds different bytes: each refuses the whole run before any rename. A read-back sha that differs after a rename rolls the run back. Source: ticket:GoodQA goodqa#15742
- NEG-4 (AC-4): an allow-all command_guard.py, a command_guard.py that crashes, one that stops denying the scp probe, a doctor that gains a failing check, and a self-test that cannot run all end ROLLED_BACK or refused with every live sha equal to its old sha; a baseline that already fails some doctor checks only counts NEW failures; the host's old doctor without the flags falls back to the guard probes only. Source: ticket:GoodQA goodqa#15742
- NEG-5 (AC-4): after a rollback the live sha equals the old sha for every file of the run, including files already replaced earlier in the same run, command_guard.py was restored first and the lock is released. Source: ticket:GoodQA goodqa#15742
- NEG-6 (AC-5): a lost ssh answer after the first remote write is recorded as unknown with the host named; a lost answer before any write is recorded as refused; an automatic rollback that loses its connection is unknown with "rollback incomplete"; the Mac audit write failing stops the run before any ssh write with exit 3; a kill after the first rename and a plain rerun is refused while the unfinished run exists; `--resume` reuses the original baseline. Source: ticket:GoodQA goodqa#15742
- NEG-7 (AC-6): a lock younger than 30 minutes refuses the run; an older one is taken over atomically and said so, and two runs that both see the stale lock cannot both proceed; nothing is ever deleted but this lock by its fixed path and run id and the pruned backups by their fixed path. Source: ticket:GoodQA goodqa#15742
- NEG-8 (AC-7): a dry run changes nothing on the host (listing, sizes, mtimes, inodes) and creates no lock and no backup. Source: ticket:GoodQA goodqa#15742
- NEG-9 (AC-8): a rollback of run 1 after run 2 replaced a file refuses that file and names run 2 (and `--force-file NAME` restores it, audited); a backup whose sha256 differs from the recorded old sha, on the host and on the Mac, is refused; an unknown run id, another host's run and an already rolled back run refuse. Source: ticket:GoodQA goodqa#15742
- NEG-10 (AC-3): the bytes never come from a caller path: a worktree edit of the same name, an unmerged commit and a name outside the list change nothing about what is uploaded or refuse. Source: ticket:GoodQA goodqa#15742
- NEG-11 (AC-9): `python3 harness/hooks/ah.py install-files ...` from a worktree, a script named `ah` earlier on PATH, `--force-file` outside a rollback, a `--repo` flag, `python3 -c "import ah_install"`, a sub-agent caller of the installed form, and a flag outside the grammar are refused by the guard; the installed literal form from main passes. Source: ticket:GoodQA goodqa#15742
- NEG-12 (AC-10): no scp, cp or mv is typed for this install and no file outside the installer list is written on the host. Source: ticket:GoodQA goodqa#15742

## Resource budget

Host: mac
Fan-out: agents=2 jobs=1 processes=4 browser_pages=0 test_workers=1
Peak memory: 0.3 GB (method: unit tests with a fake ssh runner on temporary directories)
CPU: 2 cores (method: the suite takes about a minute)
Disk: 0.05 GB (method: temporary directories; a real install writes a few hook files and their backups of about 0.4 MB each)
Network: 5 MB (method: ssh with the file bytes on stdin, a handful of short calls, one ls-remote and a possible fetch of the canonical repository)
Wall time: 240 min
Cap and kill: foreground; each ssh call has a timeout and a failure after the first remote write is recorded as unknown, never retried silently
Checkpoint: not required (under 10 min per step); every step is idempotent (a rerun with the same ref is a no-op per file, an unfinished run is resumed) with the audit rows as the record

## Risks

- A remote overwrite of a guard or hook file can break the host guard: mitigation, two-phase install with command_guard.py last, backup first, atomic rename, sha read-back, the host's own allow and deny probes and doctor findings compared with the baseline, automatic rollback with the guard restored first, names only from the installer list, merged code only.
- The command becomes a way around the Mac guard that protects hook paths: mitigation, only bytes from a commit proven to be on the live remote main, only listed names, only the installed copy of ah in its literal form and only for main (AC-9), a required ticket, audited on both ends with the caller recorded; the Mac guard still refuses hand-typed cp, mv and scp.
- A lost connection leaves a half state: mitigation, the outcome is unknown and named, the host refuses new installs until the run is resumed or rolled back with its original baseline, and the backups and fixed temporary names are recoverable.
- The constant remote script is code that runs on the host: mitigation, it is part of this module (reviewed, its sha256 in every audit row), never built from caller input, takes only validated arguments, runs with `python3 -I` and compatible with python 3.9.
- The merged-code proof needs the network and the canonical repository to be readable without credentials (A4): mitigation, a failure refuses the run; nothing is installed from an unproven commit; the proof uses a repository the tool owns, so no caller-controlled object store can supply bytes.
- The Mac guard rule (AC-9) is accident prevention, not an access control (a script importing `ah_install` or a program speaking ssh itself is invisible to a command-text guard): mitigation, the controls that hold are the merged-code proof, the allowlists and the audit; main is identified from the hook payload.
- When doctor.py is part of a run the after-test runs the newly installed doctor: limit, accepted because the fixed guard probes cover the main failure mode (a fail-open guard).
- A guard that fails open could pass a self-test of allow probes only: mitigation, fixed deny probes must stay denied with the same rule id; limit, the new code judges itself, so the audit keeps the shas and the backups for a human review of a passing run.
