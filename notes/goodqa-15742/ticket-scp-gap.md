Follow-up to goodqa#15742 (ah install-files). Measured against the real command_guard.py on the Mac on 2026-11-12: `command_guard.py check "scp x t2-dev:~/.claude/hooks/command_guard.py"` returns allow, while the same copy written as `cp` or `mv` (also wrapped in `ssh HOST "cp ..."`) is blocked by the log_delete rule. That asymmetry is exactly the route of the 2026-11-11 incident: the remote cp was blocked and the owner then used scp, a second route around a guard.

Proposal: make the guard refuse an scp, rsync or sftp whose destination is a harness hooks path on any host (`~/.claude/hooks`, `~/.codex/agent-harness`), with a refusal text that names the sanctioned route `ah install-files` (goodqa#15742). Acceptance: the same four spellings as cp (`scp`, `rsync`, `scp -r`, host:path with `~` and with an absolute home path) are blocked with the same rule id; a download from a host (`scp host:~/.claude/hooks/x .`) stays allowed; tests drive `command_guard.py check` and the hook entry for each form; a failing-first mutant removes the rule.

Why not in goodqa#15742: that ticket adds the sanctioned command and its literal-form guard rule; widening the existing destructive-path rule to scp touches a rule used by every session and needs its own review. Until then the sanctioned route exists but the old route is still open.
