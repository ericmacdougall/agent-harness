# Spec: Verified-clean primary clone removal: ah clone-remove

Ticket: GoodQA goodqa#15743
Author: agent:af9e (Sonnet 5.5)
Click-test: required
Sign-off: main
Review-policy: standard

## Outcome

A clean, fully pushed PRIMARY clone under the harness work directory on this machine (a full clone or a partial clone made with `--filter=blob:none`) can be removed through one audited command, `ah clone-remove --path P --reason R [--remote-auth] [--verify-only]` (with `--resume AUDIT_ID` to finish an interrupted removal), so that a receipts directory over its budget no longer deadlocks (ParentProof PR 773 cannot get a full clone while `receipts/wt-pp768` cannot be removed by `verify-worktree`, `rm` or any other route). The tool exists to unblock that deadlock and stays small: it is not a general deleter.

## Scope

- In: `command_guard.py verify-clone` and `remove-clone` (JSON out, like `verify-worktree`), and `ah_worktree.py` plus `ah clone-remove`, host `local` only. Verification runs the same checks as `reproducible_clone_refusal`, parametrised with the injected runner of AC-2 (clean tree, no stash, every ref reachable from a live remote ref, no linked worktrees, no submodules, no hooks, config whitelist) and adds the refusals listed in AC-3 to AC-5. Removal is a quarantine rename followed by an in-process descriptor-based walk (AC-6, AC-8).
- Out: `--host t2-dev` (the receipts deadlock is on the Mac; a remote run needs the git 2.44 lazy-fetch gate and a remote audit design and gets its own ticket); linked worktrees (`ah worktree-remove` stays their route); any path outside the work directory; the hook-form `rm` exemption (still refuses a partial clone, now by its promisor and filter keys, see D4); network clones; the owner removes nothing under receipts while this is built, main uses the tool after merge and install.
- Decisions: (D1) host local only, because git 2.43 on t2-dev ignores GIT_NO_LAZY_FETCH (the second review confirms protocol denial as the control); (D2) targets are limited to `~/.agent-harness/work/CALLER_SESSION/receipts/wt-*` (the second review showed cross-session targets are unneeded and unsafe, and the receipts deadlock is in main's own session; this replaces the earlier cross-session assumption); (D3) only `blob:none` partial clones are accepted (no `tree:0`, `blob:limit`, `combine:`, `sparse:`); (D4, amended in v4) the shared `_config_refusal` is NOT widened to accept partial clones; it is TIGHTENED to refuse any `remote.*.promisor` whose value is not plainly false (git reads any non-zero integer as true) or any `remote.*.partialclonefilter` key unless the caller opts in (only clone-remove does); BEHAVIOUR CHANGE TO AN EXISTING ROUTE, accepted by main as a safety fix: `ah worktree-remove` shares this check, so a linked worktree whose primary is a partial clone is now refused (it was accepted before, with a lazy-fetch exposure), and a test pins it, because git 2.54 writes a partial clone without an extensions section and the old refusal came only from that section, so the hook-form rm exemption keeps refusing partial clones by those keys; (D5) the live proof set for AC-3 is the full `ls-remote` listing (heads, tags and GitHub `refs/pull/*/head`), because a squash merge or force push can leave a reflog commit reachable only from a pull ref. Sources: ticket:GoodQA goodqa#15743 (both spec reviews). v4 amendments, all ASSUMPTIONS made by the owner while building and disclosed to main, none is a user decision: (D6) directories judged by membership in a recorded verified directory set, not by a timestamp, rationale: the first-run test showed an interrupted run could not be resumed under the ctime rule, birth time on resume was then shown by receipt r1b to delete a directory moved in after verification, and a recorded set is portable (no st_birthtime); (D7) a partial clone is accepted without extensions.partialClone, rationale: git 2.54 does not write the key, still exactly one remote, format version 1, filter exactly blob:none, no other extension; (D8) the live-owner refusal is dropped and AC-4 is weaker for it, rationale: the data to build it does not exist in `ah owners`, the code reviewer accepted it as a disclosed limit, the process cwd scan and the lsof scan remain. Also added in the build: any stop after the intent row restores the clone and writes a result row, and `--resume` restores a quarantine that has no marker row (AC-8).

## Acceptance criteria

- AC-1: A clean, fully pushed full clone under the work directory is judged removable; `remove-clone` deletes the whole directory (clone, `.git`, whole regenerable ignored build directories), reports `removed`, `directory_removed` and an estimate of bytes freed (block count at verification, hard links counted once; APFS clones and snapshots can make it an over-estimate), and writes the audit rows. Verify by: `python3 -B -m unittest tests.test_ah_clone_remove` (real temporary repositories, fake network). Source: ticket:GoodQA goodqa#15743
- AC-2: A `blob:none` partial clone (`remote.origin.promisor=true`, `remote.origin.partialclonefilter=blob:none`, objects missing) that is otherwise clean and pushed is judged removable. Verification never fetches on any git version: it uses its own injected git runner (not `_git_out`) whose calls carry `-c protocol.allow=never`, no `protocol.*.allow` key at all, and `GIT_NO_LAZY_FETCH=1` (plus `--no-lazy-fetch` where supported); only the one `ls-remote` call (authenticated with `--remote-auth`, anonymous without) gets the protocol it needs, run by a separate runner. A verification that needs a missing object refuses. Verify by: the same suite with a real `--filter=blob:none` clone: an argv spy over the whole verify path asserts the runner flags on every call and no override key anywhere; the runner is tested directly against a `file://` promisor remote with a `remote.origin.uploadpack` canary that records contact (zero contacts expected while a missing-object read is forced; failing first: contact appears once the flags are removed); a hook-form rm of a partial clone still refuses, by the promisor and filter keys, with the network patched to fail the test if reached. Source: ticket:GoodQA goodqa#15743
- AC-3: Every unsafe state refuses with its own reason and removes nothing: refs: every ref `for-each-ref` lists in any namespace (heads, tags, `refs/remotes/*` except the symbolic HEAD, notes, bisect, rewritten, replace) and the shas in ORIG_HEAD, FETCH_HEAD, `logs/HEAD` and every file under `.git/logs` (read directly) must be reachable from a sha in the live remote listing (heads, tags, `refs/pull/*/head`; authenticated when `--remote-auth`); a stale tracking ref whose commits exist nowhere else refuses; working tree: stash, modified, staged or untracked file; an ignored file that is not a whole regenerable build directory, where each accepted ignored directory must be matched (by `git check-ignore -v`) by a tracked `.gitignore`, never by `.git/info/exclude` or a global ignore; structure: any entry under `.git/worktrees`, a submodule, `.git/commondir`, a `rev-parse --git-common-dir` other than TARGET/.git, `.git/lfs`, `.git/info/attributes`, replace refs or grafts, installed hooks, an `objects/info/alternates` or `http-alternates` entry naming a missing path; any top-level `.git` entry outside an allowlist (HEAD, config, description, index, info with only `exclude`, logs, objects, packed-refs, refs, shallow, FETCH_HEAD, ORIG_HEAD, COMMIT_EDITMSG, empty `branches`, hooks holding only `*.sample`) refuses; state files: MERGE_HEAD, CHERRY_PICK_HEAD, REVERT_HEAD, REBASE_HEAD, AUTO_MERGE, `rebase-merge/`, `rebase-apply/`, `sequencer/`, BISECT_LOG refuse (ORIG_HEAD and FETCH_HEAD shas join the pushed set instead); remote: a remote not on a known hosting service, a remote URL that carries a password (refused without echoing the URL), a remote that does not answer. Shallow clones are allowed. A bounded scan of the caller's session work directory (pruning `node_modules`, `.git/objects` and build directories, budget 60 s, refusing when the budget is exceeded) finds no `objects/info/alternates` entry resolving into the target; borrowers outside the session work directory are a stated limit. Verify by: the same suite, one subtest per state. Source: ticket:GoodQA goodqa#15743
- AC-4: Scope: the target is `~/.agent-harness/work/CALLER_SESSION/receipts/wt-*` exactly (one directory level under receipts, name starting `wt-`), a real `.git` directory (not a file), no symlink in the path or at the target, not the caller's current directory or an ancestor of it, and with no same-user process working inside it or holding an open file or mapping inside it (exact invocation one `lsof -w -Fpn` listing filtered by path prefix (the target exactly, or the target followed by a slash), not `+D`, with a 60 s timeout, fail closed when lsof is unavailable or times out, names compared in both the realpath and the `/System/Volumes/Data` spelling), same rule and service skip list as `ah worktree-remove` for the working-directory part. Containment and ancestry are judged by (device, inode) along the ancestor chain AND each path component must equal its entry in the parent directory listing byte for byte (so case variants, Unicode normalization variants and Data-volume spellings refuse). CALLER_SESSION comes from the same hook-provided session identity `ah` already trusts, never from a caller-settable environment variable (a NEG sets a spoofed session variable). The command also takes the session only from CLAUDE_CODE_SESSION_ID (not the CLAUDE_SESSION_ID fallback), refuses when that differs from the calling shell's session or when the calling shell's session cannot be read, and refuses any AH_HOME or HOME that is not the account's real home. LIVE-OWNER REFUSAL DROPPED (v4, ASSUMPTION D8, see Decisions): v3 asked to refuse while another live owner works in the target, but `ah owners` rows expose no worktree or working directory, so the control cannot be built; this WEAKENS AC-4: an owner that is alive but idle between commands, and whose clone is clean and fully pushed, can lose that clone. The live-use controls that remain are the process working-directory scan and the lsof open-file scan above; agent shells reset their cwd between commands, so neither sees an idle owner. A literal absolute path only. Verify by: the same suite. Source: ticket:GoodQA goodqa#15743
- AC-5: Partial-clone acceptance is exact and done by a separate check in the new verifier: the clone has exactly one remote, a known host, and it is the promisor remote: `remote.NAME.promisor` is true (v4, ASSUMPTION D7: `extensions.partialClone` is no longer required, because git 2.54 writes a partial clone without it; when the key is present it must name that same remote), `remote.NAME.partialclonefilter` equals `blob:none`, `core.repositoryformatversion` is 1, no other `extensions.*` key is accepted (`worktreeConfig` is not accepted for a clone), and any other promisor remote, a missing promisor key, the legacy `core.partialclonefilter` or any other filter spec refuses. Verify by: the same suite, one subtest per variant. Source: ticket:GoodQA goodqa#15743
- AC-6: The walk is done by the tool with descriptors: open the quarantine root with `O_NOFOLLOW|O_DIRECTORY` and require `fstat` to equal the verified (device, inode); every descent uses `os.open(name, O_NOFOLLOW|O_DIRECTORY, dir_fd=fd)` and compares `fstat` with the earlier `lstat`; each directory listing is collected and its descriptor closed before descending (a tree 300 levels deep works under the default descriptor limit of 256); entries are removed with `os.unlink` and `os.rmdir` taking `dir_fd`, and an entry already gone (ENOENT) counts as removed; a symlink is unlinked as a link, never traversed; the walk never crosses a different `st_dev` and the tool refuses up front when the mount table (`mount` on macOS) lists a mount at or under the target; a read-only directory gets its owner write bit through `os.fchmod` on its own descriptor only; `uchg`, `schg` and ACLs are never cleared and what they leave is reported. Entries newer than the cutoff (the verification start time) are never deleted by this tool: each entry's ctime is judged from its first `lstat`, before the walk modifies anything in it, a DIRECTORY is judged by membership in the verified set instead (v4, ASSUMPTION D6, replacing the v3 ctime rule for directories on the first run and on resume): the (device, inode) of the target and of every directory below it is read right after the cutoff, before git status and the long scans (so a directory created or moved in whole during verification is outside the set; only one created while that single walk runs can join it), and written, fsynced, to a sidecar file `~/.agent-harness/clone-remove/AUDITID.dirs` before the intent row, whose hash and count the intent row holds; the walk enters only directories in that set (on the first run and on every resume, which re-reads and re-checks the sidecar against the row), and a directory not in the set, created or moved in whole after verification, is kept whole and reported; a directory ctime is never used, because it moves when a child is removed, and a directory moved in keeps its old birth time and its files' old ctimes; the remaining gap is a single FILE moved in whole, which is judged by its own ctime only, and a directory that reuses a verified directory's inode after that one was deleted), and only the quarantine root (touched by the rename) is exempt, its entries still judged one by one; kept entries are reported for a human. A partial deletion is reported as `removed: null` with `directory_removed` and what is left, never a definite false. A second process holding the same quarantine is refused by `flock` on the quarantine root descriptor. Verify by: the same suite (swapped directory, symlink inside, a second device simulated with a patched `st_dev`, failing unlink, a file that appears mid-walk, a 300-level tree, concurrent resume, and a directory of old files moved in whole after verification began, at two moments, after verification and before the rename and between git status and the end of verification, each followed by a resume, and in both the directory survives; a directory moved in between an interrupted run and its resume is outside the recorded set too, so it survives by the same rule). Source: ticket:GoodQA goodqa#15743
- AC-7: Real proof: on the Mac, `ah clone-remove --verify-only` then the real run, with `--remote-auth`, on a disposable full clone and a disposable blob:none clone created by the tester inside the work directory, remove both and free their bytes; real-environment negatives (a disposable clone with an unpushed commit, one with a stale tracking ref, one with a non-build ignored file) each refuse and nothing is deleted; before building the real run, main compares the reflog shas of `receipts/wt-pp768` with a full `ls-remote` listing (read-only) to show the clone is reachable-from-remote at all (otherwise AC-3 would refuse it), and verify-only output for it is saved first; main then runs the real removal on it (confirming first that it is a primary clone with a real `.git` directory and a partial filter) and the result and bytes freed are recorded (REALLY_TESTED) with the installed commit. The owner removes nothing under receipts. Verify by: the saved outputs under the work directory. Source: ticket:GoodQA goodqa#15743
- AC-8: The audit INTENT row (audit id, caller session, TARGET path, parent (device, inode), target (device, inode), full ref and sha snapshot, cutoff time) is written and fsynced BEFORE the rename, and the removal refuses if that write fails. The tool then opens the parent with `O_NOFOLLOW`, checks its identity, renames with `os.rename(name, quarantine, src_dir_fd=pfd, dst_dir_fd=pfd)` to PARENT/.clone-remove-AUDITID on the same device (refusing when the destination exists), checks that the quarantine's `fstat` equals the verified inode (otherwise renames it back and refuses), re-reads refs, reflogs, stash and `.git/worktrees` inside it and compares them with the snapshot (a difference renames the directory back and refuses; no marker exists yet, so the clone is left exactly as found), and only then writes a marker file holding the audit id and the snapshot sha256 into the quarantine, records its inode in a second audit row that is fsynced before any deletion (the removal refuses if that write fails), and deletes. The AC-6 ctime rule exempts the marker by exact name and inode only, and it is deleted just before the quarantine root. The live `ls-remote` lists all refs including `refs/pull/*/head` and excludes `refs/pull/*/merge` from the proof set; entries kept by the cutoff are reported as leftovers for a human, a recorded limitation. Any stop after the intent row and before any deletion (a refusal, an unwritable marker, a failed marker row) renames the clone back; every such stop writes a result row with removed false except the failed-marker-row path, which restores the clone and raises without one (a known gap, filed as a follow-up, so that stop reads as unknown in the audit until a human looks). Separately, `--resume AUDITID` on a quarantine that has an intent row but NO marker row only restores it: it requires the intent row, the exact quarantine name, the recorded parent and directory identity, and an original name that is a `wt-*` path under the same receipts directory that is free; nothing was deleted, and no marker conditions apply to that restore. An intent row with no result row means unknown. `ah clone-remove --resume AUDITID` is explicit only (a retry with `--path` never resumes on its own) and refuses unless: the quarantine path is exactly the recorded PARENT/.clone-remove-AUDITID and equals `~/.agent-harness/work/CALLER_SESSION/receipts/.clone-remove-AUDITID` (the rest of AC-4 applies; only the `wt-*` name rule is replaced by this exact name), the parent's (device, inode) matches the recorded parent, the quarantine's (device, inode) matches the row, the marker matches, the refs still present are a subset of the recorded snapshot, the recorded directory set is present and matches its hash and count, and the original cutoff is applied to files (a file newer than it survives and is reported; a directory outside the set survives whole). A failed walk therefore never leaves a half-deleted clone that nothing can remove, and resume is not usable on any other directory. Threat model: careless or hurried agents, not an adversary editing the audit file. Verify by: the same suite (injected failure halfway then resume, intent-write failure refuses, rename-destination exists refuses). Source: ticket:GoodQA goodqa#15743
- AC-9: `--verify-only` prints the verdict, every ref and the proof shas, the top-level entries and ignored directories that would be deleted and their size, and deletes nothing and changes no file in the clone (`GIT_OPTIONAL_LOCKS=0`; a listing of `.git` names, sizes, mtimes and inodes is identical before and after). The audit row for either mode holds every ref and sha, the live remote shas used as proof, the (device, inode), the size, git and verifier versions, and remote URLs with credentials removed (M5). The CLI always uses the policy from code: no policy file or argument widens the known hosts or the ignored-directory names (L5). Verify by: the same suite. Source: ticket:GoodQA goodqa#15743

## Resource budget

Host: mac
Fan-out: agents=2 jobs=1 processes=4 browser_pages=0 test_workers=1
Peak memory: 0.5 GB (method: unit tests with real temporary repositories)
CPU: 2 cores (method: the suite takes about a minute)
Disk: 0.2 GB (method: temporary repositories; the real run frees several GiB under receipts)
Network: 1 MB (method: one authenticated ls-remote per verification)
Wall time: 180 min
Cap and kill: foreground; each git call has a timeout; the deletion is bounded by REMOVE_SECONDS and a partial deletion is reported, never retried silently
Checkpoint: not required (under 10 min per step); every step is idempotent: verification changes nothing and a removal resumes through AC-8 --resume with the audit rows as the record

## Risks

- Deleting a clone with unique work is irreversible: mitigation, AC-3 (every ref, tracking ref, reflog tip and stash reachable from a live remote sha), AC-8 quarantine rename and re-verification, audit with every ref and sha.
- A failed partial deletion strands an unremovable directory (the original deadlock): mitigation, AC-8 quarantine and `--resume`.
- Walk races and symlink or mount traversal: mitigation, AC-6 descriptor walk with identity checks, no cross-device descent, up-front mount refusal.
- Another repository borrows this clone's objects: mitigation, AC-3 alternates scan and commondir refusal, NEG-11.
- A lazy fetch changes the clone or leaks a credential: mitigation, AC-2 protocol denial plus lazy-fetch off, canary test, no credential in output.
- The tool becomes a general rm: mitigation, scope strictly inside the work directory, a real .git directory, host local only, policy from code, literal path, audit on both ends, hook-form rm exemption tightened, not widened (D4).
- Known limits: dangling and cruft-pack objects that no ref or reflog reaches are not protected; notes and refs that the full ls-remote listing (heads, tags, pull heads) does not list always refuse (clear message).
