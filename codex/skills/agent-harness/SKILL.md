# Substantive software work

Use native Codex subagents when available. The main agent remains accountable for scope, integration, proof, and the user-facing result. Work with the user's sparse request as a starting point, not a complete product specification. Keep the smallest viable scope that achieves the intended outcome, while covering material security, reliability, accessibility, migration, and operations risks. Push back on a shortcut that would break an essential invariant. Ask the user about consequential unresolved choices after checking the repo and available sources; record assumptions and decisions in the WAL.

## Scope and ownership

Before delegation, record the original checkout path, branch, HEAD, dirty state, and remote. Write a concise scope brief and owner ledger in the session WAL: outcome and flows; explicit requirements versus assumptions; interfaces and likely files; domain invariants and adversarial angles; acceptance and negative cases; owner, branch, worktree, dependencies, and next checkpoint. For related follow-ups, send the delta to the same owner. Use a separate owner only for genuinely independent work. Avoid overlapping edits. Keep the user informed at assignment, review, live test, blocker, and handoff.

Preflight native dispatch against the current chat rather than assuming every chat has the same model or authentication capabilities. Inspect the active mode, the spawn surface's model choices and override rules, and the current client/runtime model catalog when available. Spawn metadata may omit a supported model, so absence there is not a conclusive denial. When Daybreak is enabled and a current runtime catalog entry agrees with the parent's active mode, explicitly select that compatible model for the new owner or replacement and attempt dispatch once. Do not hardcode a catalog entry, trust a stale cache without active-mode corroboration, violate the tool's inheritance/override rules, or degrade silently to a non-Daybreak model. A rejection before a child starts is a dispatch failure with no child effects; it is not evidence that the assigned task failed. Do not repeat an unsupported model or retry through the same stale authentication context.

When the parent has entered a newly authenticated or model-enabled context, a fresh agent may take over the same owner assignment. First check the owner ledger and active agents. If the rejected child never started, dispatch exactly one replacement with the same scope, branch, worktree, WAL handoff, and acceptance checks. Parent reauthentication does not rebind an already-running child whose authentication expires. A `resumable=true` flag is lifecycle evidence, not proof that inherited model, network, browser, filesystem, or other permission boundaries survived an auth/session/mode transition. Before resuming, use a bounded, side-effect-free probe of the capabilities the task requires in the child's context. If that probe is unavailable or fails, quarantine the child as stale. Preserve the original failure evidence; inspect messages, WAL, branch/worktree, processes, receipts, and unknown in-flight effects; then quiesce the old writer before dispatching one fresh replacement in the parent's current context. Never automatically replay an operation with uncertain effects. Retain the same owner scope and branch instead of splitting ownership, and keep implementation and independent review roles separate. Do not ask the user to disable the parent's mode or grant permissions through a workaround. WAL and user updates may name the redacted failure class and capability source, but must omit account IDs, tokens, raw auth payloads, and other secrets. If the current spawn surface cannot express a compatible selection, report a dispatch blocker and continue safe independent work instead of fabricating task progress.

Give the owner the scope brief and require it to challenge likely edge cases before implementation. For external-tool wrappers or borrowed storage, include implicit/background effects, uncertain completion versus absence, cross-generation retries, branch reuse and concurrent advancement. Require doubles to preserve the risky cwd/environment/protocol details, plus a real-tool control when those details are the risk; skip irrelevant angles. See [owner-workflow.md](references/owner-workflow.md) for worktree, plan, commit, review, and rescue mechanics. A custom `harness_owner` agent is available; if native delegation is unavailable, follow the same workflow in the main thread and state that limitation.

## Plan, proof, and review

For nontrivial code changes, have an independent `harness_reviewer` (Sol) challenge the plan before implementation and reconcile concrete objections. Implement with meaningful failing controls, run focused checks, then obtain independent CODE_INSPECTION while full validation is explicitly pending. Repair findings and run affected checks. Freeze code, runtime instructions, config, fixtures and docs before one stable full validation, then obtain fresh exact-HEAD PR evidence review. Preserve required repository/live gates. Native reviews state stage, HEAD and limits; helper PLAN/CODE_INSPECTION acceptance is never PR signoff. A review is advisory to the main agent's scope and evidence judgment. Keep late results in private/PR receipts to avoid reporting-induced reruns. Run proportionate adversarial review; after two actual code-repair rounds on the same material finding, main may assign a clean-worktree rescue. Provider/resource failures never count as code-repair rounds.

Right-size expensive work and follow [owner-workflow.md](references/owner-workflow.md): compact snapshot-based packets, finite attempts, no unchanged paid retry, and explicit unknown receipts. The opt-in `~/.codex/agent-harness/usage_guard.py` records guarded executions and subject/invocation identities, with full-run code-inspection gates and advisory historical reuse. Native evidence uses an explicit ungated/native reference, not a fabricated helper receipt. Missing, secret-dependent, dirty or incompletely declared inputs prevent reuse; no cached PR PASS is created. These helpers do not intercept arbitrary shell/native model calls. Keep the tiny-fix fast path free of mandatory receipts and models, preserve current permissions, and never restore disabled integrations.

Pick tests that could falsify the changed behavior. Demonstrate a failure against the prior implementation or a controlled broken variant where practical; require nonempty assertions and fixtures. Add deterministic edge cases, integration, contract, migration, and end-to-end checks as applicable. For a runnable UI or service, assign `harness_click_tester` before PR, use disposable local or staging accounts, route failures to the owner or `harness_fixer`, and retest. Use the [testing-and-evals.md](references/testing-and-evals.md) guide for delayed responses, chaos, stochastic systems, and production gates. Stop optional testing once the material risk is resolved; never call a simulation a live test.

## Delivery

The main agent checks the final branch HEAD, scope, tests, live evidence, independent findings, security, and affected docs. Use the installed `python3 ~/.codex/agent-harness/deliver.py` prepare/finish workflow described in [delivery.md](references/delivery.md). Prepare binds reviewed source and original commits plus a private run kit before publishing a feature and draft PR. `PR_READY` leaves the original checkout pending an authorized remote merge. Finish verifies that merge, pins/fetches its target, protects the original fast-forward, checks the actual original checkout and records delivery. Definite remote failure or an explicit local-only choice permits guarded local integration; policy refusals and uncertain publication cannot become fallback. Preserve user changes and recovery barriers. Report a blocker while continuing independent work, tell dependent owners when to rebase, and give useful actual run/test/watch/log/stop instructions. Small fixes still use the fast path. Before dispatching, arm the main session's explicit continuation checkpoint. Keep it active across worker and test waits. Reconcile the next authorized step instead of treating a running check as a terminal result. See [delivery.md](references/delivery.md) for checkpoint commands and the bounded Stop hook.
