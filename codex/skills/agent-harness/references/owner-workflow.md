# Owner workflow

## Dispatch admission and replacement

Before assigning an owner, inspect the active chat mode, the spawn tool's advertised models and inheritance/override constraints, and the current client/runtime model catalog when available. Model catalogs and slugs change, but spawn metadata can also be incomplete: a missing model in that metadata is not by itself a denial. If Daybreak is enabled and a current runtime catalog entry is corroborated by the parent's active mode, explicitly select that compatible model and attempt dispatch once. Never hardcode its slug or trust a stale cache alone. If the one attempt is rejected before start, record no child effects and stop rather than trying a non-Daybreak model or repeatedly submitting the selection.

Classify the dispatch result before changing the ledger:

- A pre-dispatch HTTP, authentication, or model-admission rejection means no child started. Record a redacted `dispatch failure`, leave the task outcome open, and do not infer branch or worktree effects.
- A returned child identity, start event, message, or uncertain start means the child may have effects. If authentication expires after start, fresh parent authentication does not rebind that child. Treat `resumable=true` only as lifecycle evidence. After an auth, session, mode, model, network, browser, filesystem, or permission transition, run a bounded, side-effect-free probe of the task's required capability in the child's context before resuming. If the probe is unavailable or fails, quarantine the child as stale. Preserve its failure evidence and inspect its messages, WAL, branch/worktree state, processes, receipts, and unknown in-flight effects before deciding whether replacement is safe.

Do not retry an old agent authentication context. When the parent is newly authenticated or newly model-enabled, create at most one fresh replacement in that context and hand it the existing owner entry: the same scope, branch, worktree, WAL location, decisions, pending checks, and next checkpoint. For a post-start failure, quiesce the old writer before replacement and never automatically replay a command or external operation whose completion is unknown. Preserve the original WAL and receipts as evidence. Do not create a second branch or concurrent owner for the same scope. A replacement reviewer must remain independent of implementation, and an owner replacement must not be reused as its own reviewer. Do not ask the user to turn off the parent's active mode or bypass a denied capability by broadening permissions or switching command surfaces. Record only redacted error categories and capability evidence; account identifiers, credentials, tokens, and raw authentication responses do not belong in prompts, WAL notes, receipts, or logs.

## Scope and plan

The main agent gives one owner a branch and isolated Git worktree for a coherent feature. Keep vendor directories, virtual environments, build output, credentials, and caches out of copies and commits. Use shared package-manager content caches; install from the lockfile in the worktree when needed. Reuse the owner for related follow-ups. The owner records a WAL intent, assumptions, risk table, planned checks, and rollback before editing.

For plan review, use a clean feature worktree and give `harness_reviewer` the brief, relevant snapshot paths, design, negative cases and an exact question. Keep private notes outside the worktree. Reconcile scope/failure-mode objections; another round needs changed evidence or a concrete disputed choice. Do not resend unchanged packets or ask a reviewer to supply missing live evidence.

## Implementation and handoff

Commit recoverable increments on the feature branch. Keep the WAL current with decisions, commands/results, review findings, commits, and next steps; omit private values. For behavior claims, note `PENDING_REAL_TEST <id>` before editing and `REALLY_TESTED <id>` only after observing the named check. At handoff, list unmatched IDs and their effect on readiness.

After implementation and meaningful failing controls, run focused checks and request independent CODE_INSPECTION with full validation explicitly pending. Repair concrete findings and run affected checks. Freeze code, runtime instructions/config, fixtures and docs before required full validation once. Final PR review examines that fresh full evidence, the prior inspection and every delta against exact current HEAD; prior approval is not copied. Keep late result summaries in private/PR receipts rather than changing HEAD solely to record them. Preserve repository-required full/live checks; a targeted-only choice needs its scope and rationale.

Use compact packets: scope/base/head, changed paths, finding IDs, concise commands/toolchains/nonzero counts/results, live evidence, risks/rollback and snapshot paths. Read snapshot files instead of pasting them together with their diff. `peer_review.py` warns above 32 KiB and rejects above 150,000 bytes or a tighter explicit packet budget. Exact duplicate fenced blocks are advisory only. A delta review needs verified prior exact approval, ancestry, complete new diff/evidence, unresolved findings and full snapshot access; it remains a fresh decision.

For helper reports, require exit 0, the correct stage, `Reviewed HEAD` equal to current HEAD and `Reviewed packet SHA-256` equal to raw packet bytes. PLAN_RESULT and CODE_INSPECTION_RESULT acceptance are not PR signoff; only a fresh PR result may carry the PR pass marker. Native reviews state their actual stage/HEAD and limits, and cannot be imported as invented helper receipts. A mismatch means no current approval: repair the evidence before spending another call.

## Finite execution and evidence

Paid external review or a check expected to exceed five minutes is expensive; full-suite/TUI runs always are. Opt into `usage_guard.py` for finite command supervision and receipts. A guarded full run requires current subject-matching accepted code-inspection evidence with no open material findings, or an explicit finite investigation/native-evidence reason recorded as ungated. Different review/test argv may share a subject; reuse requires the exact invocation. Missing, dirty, unknown or secret-dependent inputs prevent reuse unless safely represented by declared opaque revisions. A bare version string is not executable verification: declare the actual executable and expected digest. REUSED points to original scope/time/result and never creates a new CHECK_OK or PR PASS.

One review allows at most one primary and one authorized independent-provider fallback, 720 seconds each and 1,440 seconds of total provider execution. Invalid output and code findings never cause paid fallback. Shared private pool state blocks automatic quota/auth retries; ambiguous credit/model/tool text is not account quota. Pool scope is the configured opaque alias and common private state directory, not a distributed/native account guard. At most one reasoned repeat can spend remaining budget; unknown or interrupted attempts require recorded reconciliation first. The main agent owns the foreground supervisor until completion; hand off receipt paths and the responsible owner, not an exec handle assumed portable between agents. Append-only reconcile/availability acknowledgements record actor/reason/evidence and never mint success or remove history. Do not change permissions or buy credits to clear a guard.

Before expensive execution, check free space on work/build, temp and receipt filesystems. Default floors are 2 GiB for compile/tests and 256 MiB for other guarded work; set a higher known peak or a justified declaration override. Missing disk data or a low floor prevents launch. Floors are not capacity guarantees. Never delete shared caches or broadly kill processes. Tiny fixes retain the direct WAL/focused-check/diff path without new receipts or models.

If two real repair rounds fail on the same material finding, main may pause the owner and assign `harness_rescue` a fresh worktree from a clean committed branch. Give it the failing review, exact acceptance check, and remaining scope. Main inspects any rescue commit, reruns affected checks, obtains a fresh review, and keeps the user updated. Use an available independent model fallback only before rescue edits; do not have two agents edit the same checkout.
