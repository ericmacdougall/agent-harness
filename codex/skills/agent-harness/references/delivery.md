# Delivery and handoff

Before delivery, main checks the branch diff against the original scope, final HEAD, reviewer findings, actual tests and live evidence, and touched documentation. If the original checkout changed or has user edits, preserve it and ask about a consequential conflict; do not reset.

Attempt a normal feature-branch push and draft PR when a configured remote is reachable. A verified PR is `PR_READY`, an intermediate state: keep the original checkout unchanged while the PR awaits review and an authorized remote merge. After that merge, verify the PR and pinned remote target, then fast-forward a clean original checkout with `git -c core.hooksPath=/dev/null merge --ff-only --no-overwrite-ignore --no-autostash <pinned-target-SHA>`, rerun relevant checks there, and tell dependent owners what to rebase onto. A remote failure does not stop feature-worktree verification. Report the safe error; do not force-push, try another remote, or loop on credentials.

If publication is genuinely blocked or the user explicitly chooses local-only delivery, use a reviewed scratch integration path that preserves ignored user files and recovery evidence. If that path is unavailable, keep the verified work on its feature branch, provide usable run/test instructions for that checkout, and report the original-checkout delivery blocker. Do not run an unguarded non-FF merge in the original checkout. Local-only integration leaves remote publication outstanding; a later GitHub merge can have different history and needs deliberate reconciliation. Separate PR status, original-checkout delivery, and feature-worktree readiness in the handoff.

The handoff should let the user try the result immediately: original checkout path and current HEAD, delivered commit when applicable, and feature checkout plus verified commit while `PR_READY` or locally blocked. Give one start or preview path/URL where applicable, safe seed/test-account instructions, exact test and watch commands for the named checkout, result/log location, and stop command. For CLI/API work, provide a runnable request or sample instead of inventing a UI. Explain uncovered risks and pending checks plainly.

Update affected docs with verified facts: README and how it works, contributing/standards, architecture, ERD, service/deployment map, OpenAPI/MCP, and developer/customer docs as relevant. Skip unrelated documents and empty boilerplate. Record source, date, and confidence for unstable external facts; use current official sources when APIs, security guidance, or dependencies may have changed. Redact personal data and secrets from logs, docs, PR packets, and traces.
