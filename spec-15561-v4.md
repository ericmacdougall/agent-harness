## Outcome

A desktop session started from a user token (`goodqa-agentd ctl sign-in --key-file`) can use exactly the product surfaces that token's abilities cover, intersected with the owner's live org role and the token's org list, and nothing else. With a token that carries `read` + `crm` the desktop app window renders the CRM people list (saved view 757da781, showing the view's current count, 1,415 at 2026-11-09). With a token that lacks `crm` the user sees a refusal that names the missing token ability and the page to fix it, not the misleading "ask an organization owner" text. The user mints that token through the normal token-creation flow (#15382); no agent can start or widen an ability upgrade.

## Findings (where the refusal comes from)

F1. Both live errors are ONE API refusal, not two permission failures. The token-bound session branch in `apps/api/src/plugins/auth.ts:6718-6729` calls `desktopTokenSessionMayUse(method, routeKey)` (`apps/api/src/lib/desktop-token-session.ts`, `ALLOWED` + `ALLOWED_SUBTREES`, about 25 host-side routes: `/v1/me`, `/v1/orgs`, notifications, `/v1/machines/*`, machine enrollments, remote-session host routes). Any route not on that list returns `403 desktop_token_session_scope` "This desktop session was started from a user token and can only do what the desktop app needs." Every `/v1/orgs/:orgId/crm/**` and `/v1/chat/**` route is off the list. Messages shows that text verbatim.
F2. The CRM card is a mis-rendering of the same 403. `apps/web/src/lib/query-state.ts:49` `isForbiddenError` is "status === 403", and `apps/web/src/app/o/[orgSlug]/crm/page-content.tsx:235,559-563` (also `crm/records/page.tsx:208`, `crm/[contactId]/page.tsx:216`, `crm/records/[kind]/[recordId]/page.tsx:82`) turns any 403 on `GET /v1/orgs/:orgId/crm/contacts` into "You don't have access to the CRM ... Ask an organization owner or admin". The CRM handlers' own check (`requireOrgPermission(..., 'crm:read')`, `modules/crm/routes.ts:581` and others) was never reached. The owner's org role is irrelevant to this failure.
F3. A raw user token on `/v1/orgs/:orgId/crm/**` needs ability `crm` (`lib/user-token-policy.ts:291`, pattern `^/v1/orgs/ID/(crm|outreach(?!/sender-identity$))(/|$)|^/v1/outreach`) plus `read` (GET) or `write` (other methods). The same rule also covers outreach, so `crm` reaches outreach too. A session never goes through this policy today: the bound session is checked only by the host allow-list and, per request, by `DESKTOP_SESSION_REQUIRED_ABILITIES = desktop_signin, machines, read, write, tokens.create_other_keys` (`desktop-token-session.ts`, `desktopBindingState`). So a token without `crm` and a token with `crm` behave identically on CRM today: both refused.
F4. `crm` is already selectable. `apps/web/src/components/account/user-tokens/UserTokensManager.tsx:227` renders a checkbox for every `USER_TOKEN_ABILITIES` entry (only `platform.admin` and `machines` are conditional); the create dialog defaults to `['read']` (line 262); the label is `USER_TOKEN_ABILITY_LABELS.crm` ("People, companies, deals and the rest of the CRM") in `packages/shared/src/user-tokens.ts`. MCP OAuth also supports it: `OAUTH_ABILITIES` includes `crm` (`modules/mcp-oauth/policy.ts:21`) but `DEFAULT_SCOPES` (line 20) does not, and consent offers it only when requested. The agent's MCP token lacks `goodqa:crm` because nobody asked for it, not because it is impossible. Minting needs the signed-in human plus a fresh step-up (`modules/user-tokens/routes.ts:215`, `spendStepUp`), and a user-token actor can never mint (policy rule `token_mint`).
F6. (adversarial review M2, confirmed in code) The CRM outcome has two more gates the first draft missed. (a) Through any token, CRM is dark per org unless entitlement `crm.api.enabled` is on (DEFAULT ON for every plan since batch4, off only by an explicit org override of `false`; `plugins/auth.ts` around 1034 and the token switch near 6235 answer 404); once the session goes through the token gate it inherits that switch, so the live org behind saved view 757da781 must not carry a `false` override (the click-test records the value; the delegated door answers `crm_api_disabled`). (b) Many CRM routes are `SESSION_ONLY_ROUTES` and refuse every token as `user_token_non_delegable`: contact detail, timeline, meetings, export, import, AI briefing, call and SMS, `DELETE` of a contact. The saved-view list can render the saved view's current count (1,415 at 2026-11-09) while clicking a person is refused in v1 (Q7). (c) The CRM page also calls non-CRM routes (`/v1/orgs/:p/entitlements`, `/v1/orgs/:p/members`) that the v1 table does not delegate; the S0 inventory decides each.
F7. (adversarial review B1, B2, confirmed) Today a bound session ignores the platform switch `userTokens.enabled` (checked only in the bearer credential step, `auth-gate.ts:263`), the host door checks no per-route ability, `GET /v1/me/remote-control/catalog` is session-only for a bearer token but host-listed, `POST /v1/me/machine-enrollments` asks approval for a bearer token (`user-token-policy.ts:359-365`) but not for the session, and only the token gate sets `setUserTokenScope` so org lists are unscoped. D1-D3 and D7 close these.
F5. Facts the design must also fix: (a) a bound session ignores the token's org allow-list (it only requires `orgIds === null` at mint, `routes.ts:165`); narrowing `orgIds` afterwards leaves `GET /v1/orgs` and the host routes unscoped. (b) Mint (via `createSession` calling `desktopBindingState`, `auth/service.ts:210-212`), refresh (`:677-678`) and per-request liveness all require all five abilities, so a CRM-view token would need `tokens.create_other_keys` (mint org API keys) and `write` just to open the app, and dropping any one 401s and revokes the whole session instead of narrowing it. (c) The policy line for `POST /v1/me/desktop-session` (`user-token-policy.ts:349`) lists four of the five, a drift the new design removes. (d) Bound-session requests write no per-token ledger row (the `onSend` ledger hook keys on `req.userTokenLedger`, set only by the token gate).

## Design

D1. One gate, two credentials, TWO doors. Extract the part of `authenticateUserTokenRequest` (`modules/user-tokens/auth-gate.ts`) that starts after `authenticateUserTokenCredential` into `applyUserTokenRoutePolicy(req, reply, {token, user, effectiveExpiresAt}, deps, via)` with `via` of `'bearer'` or `'desktop_session'`. The bearer path calls it unchanged (behavior-preserving; the existing `user-token*` suites are the regression net). The bound-session branch in `plugins/auth.ts` calls it for EVERY bound request that is not refused at route class, host door and delegated door alike (adversarial review B2: a host door that checks abilities only is a second, weaker gate). Ability rules, non-delegable rules, governance sign-off, org allow-list, org agent-pause, org API-access switches (`crm.api.enabled`), approval asking, scope setting, ledger and rate bucket are therefore the token gate's, not a second copy. Two things stay in the credential step and are NOT lost by the extraction (adversarial review B1): the platform kill switch `userTokens.enabled` (`auth-gate.ts:263`) and the credential-kind checks. Both move into a shared `assertUserTokenUsable(token)` that the bearer credential step and the bound-session load both call.
D2. Per-request token load. For a bound session, each request loads the full minting `UserTokenRow` fresh (owner, id, secret fingerprint, abilities, `orgIds`, `projectIds`, `conversationScope`, `requireHumanApproval`, `createdVia`, chain-live, effective end) in one query, then runs `assertUserTokenUsable`: platform switch `userTokens.enabled` on, token neither revoked nor expired nor under a revoked parent, secret generation matches, `desktop_signin` held, and `createdVia` is allowed: the schema has six values; `session` and `user_token` are allowed, `oauth` and `commander_turn` are refused, and `pairing` are refused; `operator` is ADMITTED (the Q9 deviation in the decisions block, which is the one statement of this rule: the operator script mints it with `desktop_signin`, and refusing it could end the live desktop's session) (an `oauth` or `commander_turn` token can never be the bound token, and the extracted gate's commander-grant, continuation and session-action branches are asserted unreachable for `via='desktop_session'`). Any failure is 401 and the session row is revoked (`user_token_ended`), as today. No cache of abilities, orgIds or liveness anywhere in the path. Any other narrowing applies on the next request because the gate reads the live row, including `projectIds` and `conversationScope`. The shared mechanism to change is `desktopBindingState` (`lib/desktop-token-session.ts`), which `createSession` (mint and every rotation, `auth/service.ts:210-212`), refresh (`:677-678`) and every authenticated request all call; D6 changes it there, not at the policy line.
D3. Three-way intersection for a bound session, evaluated in this order after the liveness load (so a refusal at route class is still ledgered, see D9). (1) Route class: the host door (existing `ALLOWED` list, contents unchanged), or the delegated door (new default-deny `DESKTOP_DELEGATED_SURFACES` table, D4), or refuse. A route on neither door is `403 desktop_token_session_scope`, except on a surface the app has pages for (CRM): a route NO credential can reach (session-only, non-delegable, governance sign-off) answers the policy's own `user_token_non_delegable`, so the app can say "not available in a desktop session started from a token" (NEG-25; this is deliberate and must not be "fixed" back). (2) Token ceiling: the D1 gate for the matched route, host and delegated alike. The only host-door exceptions are an ENUMERATED waiver set kept in `desktop-token-session.ts` and pinned by test: W1 the `machines` non-delegable rule is waived on the allow-listed machine routes (the allow-list is their reason to exist; the route still needs the `machines` ability); W2 `signedInPersonOnly` is waived for exactly the set of host-door routes that are session-only for every credential today, COMPUTED from the code and pinned by a test that fails on drift: every route in `ALLOWED` and `ALLOWED_SUBTREES` for which `isApiKeyReachableRoute` is false and that is not in `USER_TOKEN_BEYOND_API_KEY_ROUTES` (per the code reading today: `GET /v1/me/remote-control/catalog`, `POST /v1/machines/:p/presence-challenge`, `POST /v1/machines/:p/browser-setup`, `GET /v1/orgs/:p/machines/remote-sessions`, its `availability` and `:p` reads, `:p/stop`, `:p/renew`, and the agent-browser and browser-pairing subtrees; S0 confirms the set with the real function), and each of those also requires the `machines` ability, so a token without `machines` is refused them exactly as a bearer call is; W3 approval is waived for the machine-enrollment host routes only, because the session's own mint already asked under `approval: 'desktop_signin'` (this preserves today's behavior and needs main's confirmation, Q6; without W3 an Ask-me-first token's enrollment returns 409 and the desktop cannot retry with the header). Every other host route is gated like any token route, so `GET /v1/me/remote-control/catalog` for a `desktop_signin`+`read` token without `machines` is refused, not served. (3) Owner role: the route handler's own `requireOrgPermission`/RBAC, untouched. A route is reachable only if all three pass. Because delegated routes are normal routes under the same handlers, `reachable(bound) is a subset of reachable(owner browser session)` holds by construction; the testable invariant is `reachable(bound) is a subset of reachable(bearer call with the same token)` plus the three named waivers (AC-6).
D4. Delegated surfaces (v1, default-deny table, spelled with `desktopRouteKey` like the host list), generated from the S0 route inventory below, never from a prefix alone. `crm` = the token-reachable routes under `/v1/orgs/:p/crm/**` that the CRM list, saved-view (segments) and record-read pages call; NOT outreach and NOT `/v1/outreach/**` even though the `crm` ability covers them (outreach send is out of scope and its approval UX does not exist in the desktop UI). Many CRM routes are session-only for every token today (`SESSION_ONLY_ROUTES`: contact detail `GET .../crm/contacts/:p`, timeline, meetings, export, import, AI briefing and suggestions, call and SMS, `DELETE .../crm/contacts/:p`); they stay refused (D5) and the UI says so honestly (D10); Q7 was decided by the user (open them as slice S1e, AC-14..AC-16); on the #1319 build they stay refused. `messages` = the token-reachable `/v1/chat/**`, `/v1/orgs/:p/chat/**` and `/v1/orgs/:p/dm/:p` routes the Messages page calls, and exactly `POST /v1/notifications/read`, `POST /v1/notifications/read-all`, `POST /v1/notifications/:p/archive` and `POST /v1/notifications/:p/unarchive`; notification preferences, `dnd` and `unsubscribe` stay `desktop_token_session_scope` (a stolen session must not silence the owner's security notices). Messages routes outside this table that the page calls (attachments `/v1/uploads/:p/content`, AI threads, agent chat, assistant, notes-to-self, vault and secret-request composer routes) are classified in the S0 inventory: secrets and vault stay out by design (NEG-23), the rest are named product decisions for main (Q8), not silently added. Each entry names the token abilities it expects; a unit test pins `policy.abilities` of every registered route under each entry to the declared set. A route-inventory snapshot test lists, per route in or beside a delegated prefix, `host | delegated | refused:RULE` so any new route is a deliberate classification. No stream or hijacked route may enter the table without a per-message liveness re-check (a revoke must end a stream).
D5. Non-delegable, not widened. Everything the token policy marks `nonDelegable` or `signedInPersonOnly` (auth, account, passkeys, password, account delete/export, secret reveal including `messages/:id/secure/reveal`, approval approve/deny, revoke-all, device pairing, channel members, commander admission, token mint, session-action grants) stays refused to a bound session even when it sits under a delegated prefix; the delegated door asserts `policy.nonDelegable === null && !policy.signedInPersonOnly` per route. `/v1/auth/**` and `/v1/account/**` are never on any list. The bound session is never "a person signed in": no step-up, no recent-auth proof (the existing recent-auth case in `user-token-desktop-session-bound.test.ts` is kept; its test title is confirmed in S1). The host door keeps its consent and presence-mode logic (`isConsentRoute`, `presenceModeOn`) unchanged.
D6. Host-door abilities (Q2 answered yes by main). Replace the blanket five-ability requirement, which lives in `DESKTOP_SESSION_REQUIRED_ABILITIES` and `desktopBindingState` (not in the policy line), with: mint and every refresh require `desktop_signin` + `read`; per-request liveness requires `desktop_signin` only; each host route requires what the D1 gate computes for it plus the `machines` ability except for the base reads `GET /v1/me`, `GET /v1/orgs`, `GET /v1/notifications*` and `GET /v1/desktop/update-status`. Policy line 349 is aligned to the same set. Tokens that hold all five behave as today. A token without `machines` keeps a working app for delegated surfaces and gets `403 user_token_ability_missing` on machine routes. Had Q2 been answered "keep all five", the presets tick all five, AC-9 becomes "unchanged", and D6 is dropped; note the `machines` checkbox is hidden in `UserTokensManager.tsx:225-227` until its UI is approved, so that alternative adds an unapproved product control or forces the user onto "Everything", which is far more privileged than a CRM preset.
D7. Org scope. Mint stays refused for an org-scoped token in v1 (`user_token_org_scoped`, unchanged: the desktop app is org-agnostic). After mint, `orgIds` narrowing applies per request through the same gate on both doors: routes naming an org outside the list answer 404 (the gate's tenancy-hiding answer), and the org lists (`GET /v1/orgs` at `orgs/routes.ts:401`, `GET /v1/me`, `GET /v1/orgs/:p/machines`, notifications) are filtered through the request scope (`setUserTokenScope`), which the gate sets for the bound session on both doors. A test confirms `GET /v1/orgs` honors `userTokenOrgIds`; if it does not, S1d adds the filter. Cross-org: a token never reaches an org the owner is not a member of (handler RBAC) and, with a list, never one outside it.
D8. Approval. A delegated route whose policy has an `approvalReason`, while the token has `requireHumanApproval`, is answered exactly as the token gate answers: `409 human_approval_required` with an approval request the owner approves in the web app; the handler does not run. The desktop web client has no retry-with-`x-goodqa-approval-id` step, so in v1 those actions (`data.delete` and the other listed reasons) are effectively blocked in the desktop session with an honest message; a follow-up ticket may add the retry. Minting the session itself still asks when the token asks (`approval: 'desktop_signin'`, unchanged).
D9. Audit and request shape, per door. Every bound request after the token loads, allowed or refused (including a refusal at route class, so a stolen session probing `desktop_token_session_scope` leaves a trail; the liveness load keeps running first, as today), writes the ledger row the bearer path writes (exception, ledger-load measurement: a polling read of the app on `DESKTOP_POLL_ROUTES` in `lib/desktop-token-session.ts` is THROTTLED: it stays unwritten only while the same session, address and user agent already wrote within five minutes and it answers 2xx, so a first poll, a new address or agent (a stolen session) and any non-2xx write the row and the last-use update; a REFUSED poll is always written; the chat unread polls join the list when Messages is delegated) (`recordUserTokenEvent`, `request` or `refused`) with `detail.via = 'desktop_session'` and `detail.sessionId`; `recordUserTokenUse` updates last-use. The `req.auth` shape differs by door, because host handlers bind to the real session: the HOST door keeps `sessionId = claims.sid` (the presence proof in `modules/machines/agent-browser.ts` and `auditBoundConsent` cast the id as a session uuid; a `usertoken:` id would silently drop the consent audit row and break presence proofs) and gains the token scope (`setUserTokenScope`), the ledger, and, for the credential-minting host routes only (`POST /v1/me/machine-enrollments` and the machine-token routes, `modules/machines/enroll/routes.ts` `enrollActor`), the token facts `userTokenId`, `userTokenOrgIds` and `userTokenExpiresAt` (a separate `req.boundUserToken` read by `enrollActor`, so `sessionId` and the session-shaped checks stay intact). Without this a machine credential enrolled through a bound session would not be capped at the token chain's end, not limited to the token's `orgIds`, not linked to the token and would outlive a revoke (adversarial review N2; the bearer path gets the cap today); the DELEGATED door gets the token shape (`userTokenId`, `userTokenAbilities`, `userTokenOrgIds`, `userTokenExpiresAt`, `sessionId` in the `usertoken:` prefix form) so every downstream token ceiling applies. The `x-goodqa-recovery-actor` check (`plugins/auth.ts:6733-6736`) runs for both doors (the bound branch must not return before it). Attribution: a human typing in the desktop app appears as "via token X" in the ledger and actor labels; this is intended and stated in the token page copy. The rate bucket (600/min per instance) is shared with any agent using the same token by bearer; a 429 in the desktop shows its own copy (D10). Existing `auth.desktop_session_from_user_token` and `agent_browser.consent_changed_via_user_token` audit rows are unchanged.
D10. UI honesty (the F2 fix). A pure helper `tokenSessionRefusal(error)` next to `isForbiddenError` in `apps/web/src/lib/query-state.ts` maps an `ApiError` (status, `code`, `missing`; S4 confirms `ApiError` carries `code` and `missing`) to copy: `desktop_token_session_scope`, `user_token_ability_missing` (names the missing ability), `user_token_non_delegable`, `human_approval_required` (a 409, not a 403, so the helper takes it too), the `crm.api.enabled` dark state (the server returns a distinct code `crm_api_disabled` on the delegated door only, so the helper can say "CRM is switched off for sessions in this organization"; a plain 404 with `not_found` keeps its ordinary not-found copy, so a deleted contact is never mislabelled), and 429 from the shared rate bucket. For CRM the ability copy reads "This desktop session's token does not have the CRM ability. Open Account > User tokens, add CRM to the token (or create one with the Desktop CRM preset), then sign the desktop app in again." A role 403 with no token code keeps today's "ask an organization owner" copy, and the session-only CRM detail routes (Q7) get their own honest copy ("This view is not available in a desktop session started from a token"). A 401 is signed-out, never "no CRM access". Every consumer of `isForbiddenError` on a CRM or Messages query uses the helper (about 16 sites: the CRM list, records, record detail, deals, companies, follow-ups, graph, `contact-attribute-rail.tsx`, `customers-affected-panel.tsx`, and the Messages page; the S4 grep lists them). Never prints a token value. No new server permission endpoint in this change (a page may still show create buttons the API will refuse with that message; a `/v1/me` ceiling field is a follow-up). After S1e (AC-14, AC-15) contact detail and timeline no longer show the not-available copy.
D11. #15382 product change (user-minted, no agent-startable upgrade). Verified: `crm` is selectable at `/account/user-tokens` today. (b) Copy: the `crm` description says it covers viewing and changing the CRM and outreach in API use, and that a desktop session can use the CRM only with this ability; the `write` description notes it also covers messages. Both strings are user-visible product claims and need main's wording approval (Q8). (c) `docs/design/USER-TOKENS.md` "Desktop sign-in" gets the ability matrix and the refusal codes. ## Risks

- The web UI may call session-only routes the token policy refuses (so CRM or Messages partially render): the click-test and an inventory of the routes the CRM and Messages pages call (from `useCrmContacts` and the chat hooks) are part of S0; any such route is reported to main as a classification decision, never silently added to the delegated table.
- The extraction touches the token gate every agent uses: the parity suite and the 30-route parity test are the control; S1 lands the extraction as its own green commit before any behavior change.
- Messages delegation lets a stolen desktop session send messages as the owner: this is the token's own `write` power, bounded by token revoke, the 15-minute access token and the ledger; the user chooses `write` knowingly (copy in D11b).
- `GET /v1/orgs` may not honor the org scope today: the S0 check decides, and the fix is part of S1d.
- The live proof depends on the mini and an independent tester; if unavailable it is reported as not click-tested.
