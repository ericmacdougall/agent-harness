M1 [MEDIUM, a claim the code does not support] Live-proof prerequisites, line 1:
  "(no agent mints, no token can mint: rule `token_mint`)"
  The token_mint non-delegable rule applies only while userTokens.sessionActions is ON (user-token-policy.ts:663: `(sessionActionsOn || rule.code !== 'token_mint')`). mintUserToken refuses a token actor only when sessionActionsEnabled (service.ts:582). The switch defaults OFF (DARK-FEATURES.md:206), and in that state a token with tokens.create_user_tokens can mint a legacy child (created_via 'user_token').
  The spec's own Q9 finding says the same: "a legacy child minted by a parent token is `user_token` whatever its root, while `userTokens.sessionActions` is off".
  Fix: "no agent mints; a token can mint a legacy child while userTokens.sessionActions is off, so the live proof records the token's created_via and created_by_token_id (non-secret metadata) and requires created_via = session with no parent."

M2 [MEDIUM, the live-proof oracle can be met vacuously] Live-proof prerequisites, line 2:
  "the production live proof reuses an existing token the owner supplies as a token file on the mini"
  AC-12 requires "a user-minted CRM-view token". An "existing token" may be the operator/orchestrator token with every ability, or an "Everything" token. A proof run with such a token says nothing about the least-privilege path (D6, AC-9), which is the point of the CRM-view preset.
  Fix: the reused token must have exactly the abilities desktop_signin, read and crm (the D11a "Desktop app: view CRM" preset) and created_via = session. The click-tester records both from token metadata, never from the secret. Otherwise the owner mints a fresh preset token.

L1 [LOW, factual error in AC-3]
  "A token without `read` or `write` cannot start a session (AC-9)"
  AC-9 and D6 require desktop_signin + read only (desktop-token-session.ts:50; policy line 351 `abilities: ['desktop_signin', 'read']`). A token without write CAN start a session. Fix: "without `read` cannot start a session; the missing-read case is made by a PATCH after the session starts, and the missing-write case needs no PATCH".

L2 [LOW, availability consequence not routed] Q9:
  "if the live desktop is bound to an operator token, its machine and remote-session routes need a re-sign-in with a non-operator token after deploy"

So the deploy may cut the live mini's remote control until the owner mints such a token with step-up. Register this as a named human step (ask) and a rollback criterion before deploy. Do not leave it as a consequence line only.
