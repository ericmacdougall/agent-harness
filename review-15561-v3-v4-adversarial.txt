F1 [MATERIAL, confirmed]: the Q9 finding states a false code claim, and main's acceptance rests on it.
  The v4 text says: "operator is not produced by any code path (operator tokens are written as session)" and "(nothing that can start a session today is refused)".
  Evidence: apps/api/scripts/operator-mint-user-token.ts:157 calls mintUserToken with actor {kind:'operator'}. service.ts:641 then writes createdVia = actor.kind = 'operator'. The script mints "with every ability, no expiry" (its header; it is the orchestrator's token), so the token holds desktop_signin through 'all'. The v4 claim only holds for qa-commander-directives/operator-tokens.ts, which writes 'session'.
  Effect: POST /v1/me/desktop-session (routes.ts ~157-186) has no created_via check. An operator token therefore still MINTS a session, and the bound door then answers 401 and revokes it on the first request (reason 'kind'). There are three problems:
  (a) If the mini's live desktop is bound to an operator-minted token, the deploy kills it. AC-12 then fails, or someone is tempted to "fix" it by admitting operator. The statement "the mini's token is session or user_token" was inferred from code. Nobody observed it.
  (b) Mint and door disagree, and no test covers the mint path for operator.
  (c) Main accepted Q9 on a false premise.
  Fix:
  - Correct the S0 Q9 text.
  - Read created_via of the token bound to the mini's current session. This is non-secret metadata (select created_via from user_tokens where id = <bound id>).
  - Re-present Q9 to main if that value is 'operator'.
  - Add the same BOUND_ALLOWED_CREATED_VIA check to the mint route, and name that mint case in NEG-19 with an exact code (today NEG-19 names only oauth and commander_turn).

F6 [HYPOTHESIS, not exploited]: refusing 'operator' is not a boundary while userTokens.sessionActions is off (the default, DARK-FEATURES.md:206).
  The token_mint non-delegable rule is skipped when session actions are off (user-token-policy.ts:663). An operator token with tokens.create_user_tokens can therefore mint a child with created_via 'user_token' that carries desktop_signin, and the bound door admits that child. The comment "the bound token is a human-minted token" (auth-gate.ts:358) does not hold for legacy children.
  Not exploitable beyond the parent's own power, because a child never exceeds its parent. But the Q9 rationale should be chain-root based, or should say plainly that it is defense in depth only.
  Related pre-existing text (outside the delta): F4 says "a user-token actor can never mint", which is only true while session actions are on.
