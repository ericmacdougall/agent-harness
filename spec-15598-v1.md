# Spec: P0 product gap: no route to mint an org API key whose value is delivered to a host without passing through the agent

Ticket: GoodQA goodqa#15598
Author: agent:aaef3bc78b40c0c22 (sonnet)
Click-test: required
Sign-off: main
Review-policy: standard
Baseline: bugtracker origin/main 26d95f46ada7 (paths relative to that tree)

## Outcome

With the user token (never the user's clicks), an agent can mint a new org API key whose value never enters the agent: the server seals the key into an org vault secret pinned to one named grantee principal, and answers only the key id, the key prefix and the vault secret id. A host that holds the grantee principal reads the value with the existing `vault-env/reveal` into a mode-600 file. Every other agent credential, including the minting token and an org admin acting through a user token, an API key or an MCP call, is refused the value. This unblocks moving people-watch to t2-dev (goodqa#14518) and the AC-12 live proof of goodqa#15561 (a `desktop_signin` + `read` + `crm` token minted without anyone reading it).

## Decisions (sources)

- Destination is design A: mint-to-vault, blind-pinned to a named grantee. Source: ticket:GoodQA goodqa#15598 (Expected: "mint into the org vault ... returning only id and prefix") and main decision 2026-11-10 "go with A (mint-to-vault, blind-pinned to a named grantee)".
- No human approval and no `approvalAlways`: key and token creation runs on the user token and is never surfaced to the user as an ask. Compensating controls: a scope ceiling (the minted key never broader than the caller's token), an explicit grantee plus `org:manage_api_keys`, a per-token rate limit and audit, an alert to the org owner on each mint, and the token never in any response, log or agent context. Source: main decision 2026-11-10 (feedback "Use user token for GoodQA"; CLAUDE.md section 4.1).
- Bootstrap grantee: an existing key or persona the host already holds, never one the agent can read. Source: main decision 2026-11-10.
- ASSUMPTION A1 (label): the new route is a token-reachable beyond-API-key route for user tokens only through the ordinary token gate (ability `tokens.create_other_keys` is NOT reused; it needs a new narrow ability or the existing `crm`-free `api_keys.mint` family; see Open design choice D-1 below). Source: inferred: from the existing `POST /v1/orgs/:orgId/api-keys` policy.

## Design

D1. New route `POST /v1/orgs/:orgId/api-keys/mint-to-vault` in `modules/api-keys/routes.ts`. Body: the existing mint fields (`name`, `scopes`, `maxOrgRole`, `canCreateIssues`, `expiresAt`, `scopedToUserId`) plus `delivery: { vaultName, grantee: { principalType: 'persona' | 'api_key', principalId } }` and a required `idempotencyKey` (client UUID). Response: `{ apiKey: { id, prefix, name, scopes, expiresAt }, vaultSecretId, vaultName }` and nothing else; never the token, never the sealed fields, headers `cache-control: no-store`.
D2. The mint runs `mintOrgApiKey` inside one transaction with the vault write: `requireOrgPermission(org:manage_api_keys)` and `org:manage_vault`, the existing scope and role ceilings, `assertApiKeyWithinUserToken` (the minted key is never broader than the caller's token), then `sealSecretPlaintext` of the token into `createVaultSecret` (scope org, kind `api_key`, name `vaultName`). The token string lives in memory only between mint and seal and is never logged (error paths included: the handler maps every failure to a message without the token).
D3. Blind pin: a new table `vault_blind_mints` (secret_id unique, org_id, key_id, grantee_principal_type, grantee_principal_id, minted_by_user_id, minted_via_user_token_id, idempotency_key hash, created_at). A secret with a row is "blind": `POST /vault/secrets/:id/reveal`, `vault-env/reveal`, `read_requested_secret`, MCP `get_secret` and every other reveal path refuse it for EVERY caller except (a) the grantee principal on `vault-env/reveal` (and only when the org's vault-env allow-list names the secret, set by the same transaction), and (b) a signed-in person's session (not a user token, API key, MCP dispatch, or a desktop session bound to a token). Unlike the secret-request pin, an org admin or owner acting through an agent credential is NOT exempt.
D4. Grantee validation: `grantee` must be an active persona or non-revoked API key of the same org, and must not be the minting token's own user-token-minted key and not the key being minted (no self-grant); the minter must be allowed to see it (`org:manage_api_keys`). A grantee that is later revoked or rotated leaves the secret unreadable (fail closed).
D5. Idempotency: `idempotencyKey` is stored hashed with the org; a repeat with the same key and the same body hash returns the original `{ id, prefix, vaultSecretId }` and mints nothing new; the same key with a different body is 409 `idempotency_key_reused`. Lost response and retry never creates a second key; a half-failed transaction rolls back (no key without its secret).
D6. Controls (replacing human approval): per-token and per-org mint rate limit (default 5 per hour per token, 20 per day per org; 429 `api_key_mint_rate_limited`), a `user_token_events` ledger row and an `audit_events` row (`api_key.mint_to_vault`: key id, prefix, grantee ref, vault name, scopes, via token id; never the value), and a notification to the org owner and admins on every mint (`createNotifications`, with the key prefix and grantee, never the value).
D7. Rotation and revoke: revoking the minted API key or the vault secret, or revoking the minting user token (the key's `createdByUserTokenId` already ties them), ends the grantee's access; deleting the secret deletes the blind row; rotating the value (PATCH rotate) stays human-session only.
D8. Out of scope: host-file delivery through the machine agent (design B), a settings UI, minting user tokens (`user_tokens_create` stays dark), changing the existing `POST /api-keys` (it keeps returning the token once).

## Open design choice (stated, not blocking)

D-1: the token ability for the route. Recommended: the same ceiling as `POST /api-keys` today (the user token needs the abilities the minted scopes imply plus `tokens.create_other_keys`), so a narrow token cannot mint; no new ability. Source: inferred: from `lib/user-token-policy.ts` for `POST /v1/orgs/:p/api-keys`.

## Scope

## Risk table

| Invariant | Failure mode | Control | Negative case |

## Acceptance criteria

- AC-1: Through a user token holding the abilities the minted scopes imply, `POST /v1/orgs/:orgId/api-keys/mint-to-vault` creates the org API key and a vault secret pinned to the named grantee in one transaction, and the response carries only the key id, prefix and the vault secret id: no token, no sealed field, anywhere in the response, headers, ledger, audit or notification text. Verify by: new test `apps/api/test/api-key-mint-to-vault.test.ts` (from `apps/api` on t2-dev: `pnpm exec vitest run test/api-key-mint-to-vault.test.ts`), failing first on origin/main (route absent, 404), asserting by byte search that the minted token (read in the test from the DB seal) appears nowhere in any response or stored text. Source: ticket:GoodQA goodqa#15598
- AC-2: The grantee principal reads the value through `POST /v1/orgs/:orgId/vault-env/reveal` and the key authenticates; no other principal can: the minting user token, another user token of the same user, the org owner through a user token, a non-grantee API key and persona, an MCP dispatch, `POST /vault/secrets/:id/reveal` by any of them, and a desktop session bound to a token are refused; a signed-in person's session can. Verify by: same test file plus the existing `vault`, `vault-env` and `secret-requests` suites for regressions. Source: ticket:GoodQA goodqa#15598
- AC-3: Safety controls hold: the minted key is never broader than the caller's token and role; an explicit valid grantee of the same org is required; a per-token and per-org rate limit refuses the burst; each mint writes a ledger row and an audit row without the value and notifies the org owner and admins; a repeat with the same idempotency key and body returns the original ids and mints nothing; revoking the key, the secret or the minting token ends the grantee's access. Verify by: same test file. Source: ticket:GoodQA goodqa#15598
- AC-4: Live proof after deploy: with the user token, mint a disposable key to the click-tester host's bootstrap grantee, read it on that host with the existing CLI into a mode-600 file (never printed; the file mode and the key id are the recorded evidence), and the key authenticates (a read of `/v1/me` or an org list returns 200 using the file without the agent reading it); the same call by the minting token and by a non-grantee returns refused. Then use it for the AC-12 token and the people-watch keys. Verify by: independent click-tester on the deployed build with `spec_flow.py click-test`. Source: ticket:GoodQA goodqa#15598

## Negative cases

- NEG-1 (AC-1): the minted token string is not found in any response body or header, `user_token_events`, `audit_events`, notifications, server logs of the test run, or error responses (including a forced seal failure and a forced DB failure). Source: ticket:GoodQA goodqa#15598
- NEG-2 (AC-1): a failure after the key insert but before the vault write rolls back both; no key without its secret and no secret without its key. Source: ticket:GoodQA goodqa#15598
- NEG-3 (AC-2): the minting user token, a second token of the same user, and the owner acting through any user token are refused on both reveal routes with the same generic not-allowed answer as a missing secret (no oracle that it exists and is blind). Source: ticket:GoodQA goodqa#15598
- NEG-4 (AC-2): an org API key or persona that is not the grantee, an MCP `get_secret` and `read_requested_secret`, and a desktop session bound to a token are refused. Source: ticket:GoodQA goodqa#15598
- NEG-5 (AC-2): grantee spoofing: a caller cannot become the grantee by name, header or body; the match is on the authenticated principal id only; a persona or key of another org with the same id string is refused. Source: ticket:GoodQA goodqa#15598
- NEG-6 (AC-3): a grantee that is another org's principal, a revoked key, a non-existent id, or the key being minted is refused with 400/404 before anything is minted. Source: ticket:GoodQA goodqa#15598
- NEG-7 (AC-3): scope escalation: requesting scopes or `maxOrgRole` above the caller's token or role, `machines`, launch-family scopes while dark, or a runner kind with wrong scopes is refused; a token with only `read` cannot mint a `write` key. Source: ticket:GoodQA goodqa#15598
- NEG-8 (AC-3): double submit: two concurrent requests with the same idempotency key produce exactly one key and one secret, both responses carry the same ids. Source: ticket:GoodQA goodqa#15598
- NEG-9 (AC-3): replay and reuse: the same key with a different body is 409 and mints nothing; a missing or malformed idempotency key is 400; a retry after a lost response returns the original ids without a second key. Source: ticket:GoodQA goodqa#15598
- NEG-10 (AC-3): the rate limit refuses the sixth mint in an hour for one token (429, retry-after) and the twenty-first in a day for the org; refused requests mint nothing and are ledgered. Source: ticket:GoodQA goodqa#15598
- NEG-11 (AC-3): revoking the minted API key, deleting the vault secret, revoking the minting token, or revoking or rotating the grantee each ends the grantee's read; a revoked grantee never reads; deleting the secret removes the blind row. Source: ticket:GoodQA goodqa#15598
- NEG-12 (AC-3): the route is refused to a bound desktop session, a commander-turn grant and an org API key (only a user token with the right abilities, or a signed-in session, may call it); an org member without `org:manage_api_keys` or `org:manage_vault` is refused. Source: ticket:GoodQA goodqa#15598

## Risks

- The grantee host must already hold a principal: bootstrap uses an existing key or persona the click-tester host holds (never one the agent can read); a host with none needs a one-time human step, recorded as a limitation.
- No human approval means a compromised user token can mint keys up to its own ceiling into a vault it cannot read: bounded by the ceiling, the grantee, the rate limit, the owner alert and the audit; the key is usable only by whoever holds the grantee.
- The blind pin must cover every reveal path (vault reveal, vault-env, requested-secret, MCP get_secret, any export or backup read): the review must enumerate them; a missed path is a total failure of the purpose.
- A secret request pin exempts org admins; this pin must not, and the two must not interfere: tested.
- Migration: additive table; rollback is dropping it (existing secrets are untouched).
