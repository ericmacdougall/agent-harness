VERDICT: BLOCK

One HIGH finding, confirmed by a live probe: through the newly opened bound-session timeline, the free-text `q` search
works as a content oracle over Gmail mailbox-read mail, a colleague's `personal` entries and a colleague's `busy_only`
titles. The cause is that withholding happens after the SQL LIMIT, while `nextCursor` and the match set are computed
before it. One MEDIUM finding: the org "off switch" (A2) cannot be operated by an org admin, and the spec's claim that it
is set "through the existing entitlement-override mechanism" is false for that mechanism. F1..F14 are otherwise
closed or reduced to LOW.

N1 HIGH (CONFIRMED by probe P1): `q` + pre-filter `nextCursor` = content oracle over withheld entries
  Code:
   - modules/crm/routes.ts:119-132: the contact timeline accepts `q`, `pinned`, `fieldChanges`, `cursor` and `limit`.
   - modules/crm/service.ts:105-108: `q` becomes `search_document @@ websearch_to_tsquery(...)`. search_document is
     generated from title (A) + body (B). For a Gmail ingest, title = subject and body = snippet.
   - service.ts contactTimeline: `.limit(limit)`, then
       const nextCursor = entries.length === limit && last ? `${last.occursAt.toISOString()}|${last.id}` : null;
     Both lines run BEFORE the route's `timelineWithSubjects` (removes others' `personal` entries, turns `busy_only`
     into "Busy") and `forTimelineReader` (drops Gmail mailbox-read entries for an agent credential).
  Live result: probe P1 on t2-dev, commit 7fa436767c8, bound session from a desktop_signin+read+crm token,
  GET .../crm/contacts/:id/timeline?limit=1&q=<word>.
   Gmail (subject "Acquisition zebracorn terms", snippet "we accept the quokkaprice offer", real ingestInboxMessage):
     q=zebracorn     -> {"timeline":[], "nextCursor":"2026-08-12T10:00:00.000Z|78280710-...(the Gmail entry id)"}
     q=quokkaprice   -> {"timeline":[], "nextCursor":"2026-08-12T10:00:00.000Z|78280710-..."}
     q=platypusword  -> {"timeline":[], "nextCursor":null}
     control: the owner's signed-in session sees the message (200, contains "zebracorn").
   Colleague `personal` task "Personal wombatsecret note" (member session of another member):
     q=wombatsecret  -> {"timeline":[], "nextCursor":"2026-08-11T14:05:00.000Z|1e202db6-...(the personal entry id)"}
   Colleague `busy_only` meeting "Layoff narwhalplan briefing":
     q=narwhalplan   -> one row {"title":"Busy", visibility busy_only, ...} ; q=platypusword -> [] / null
  Consequence: an agent holding a desktop_signin+read+crm token starts a bound session (A1 accepts that it can). With
  q, it learns word by word whether a withheld Gmail message (Google restricted-scope data; the privacy page promises
  that this content "never reaches a model or an agent", lib/gmail-limited-use.ts:1) or a colleague's private note
  contains a given term. It also gets each hidden entry's id and exact timestamp. A busy_only row appears only when its
  hidden title matches. The ledger records `q=…` with the value stripped (user-tokens/service.ts:323), so the terms
  searched are not auditable. Until now, an agent could reach this route only through a session action, which needs
  the platform switch, the org owner's opt-in and an explicit `session:crm_timeline` grant. W4 opens it by default.
  (Signed-in humans have the same personal/busy_only oracle today; that is pre-existing and should get its own ticket.)
  The contact detail route has the same root cause, at lower severity. It takes no `q`, but `timelineNextCursor`
  names the last raw row, which can be a withheld entry's id and timestamp, when the first page is full.
  Why the tests miss it: NEG-6 and NEG-7, and their tests, assert only that withheld content is absent from the body.
  No test sends `q`, `pinned` or a small `limit`.
  Proportionate fix (any one, plus the NEG):
   (a) Preferred: push the reader filters into SQL before LIMIT, for every caller. For an agent reader, exclude
       `gmailMailboxReadEntry(db)`. Exclude other members' `personal` rows. Never let `q`/`pinned` match a
       `busy_only` row the reader cannot see in detail. Then `nextCursor` and the match set cover only visible rows.
   (b) Minimum for this slice: on W4 (bound door), refuse `q` and `pinned` with 400 or ignore them, and build
       `nextCursor` so it never names a withheld row. Do the same for `timelineNextCursor` on detail.
  NEG to add: for a bound session, `q` (and `pinned`) matching only a withheld Gmail, personal or busy_only entry gives
  a response byte-identical to `q` matching nothing, and no response contains a withheld entry's id.

N2 MEDIUM (CONFIRMED by code reading): no org admin can set the A2 opt-out, so F3 is closed only on paper
  Spec A2: "the override is set through the existing entitlement-override mechanism". Code comment
  (desktop-token-session.ts:219): "on unless an org admin sets the entitlement override ...".
  Code:
   - PATCH /v1/orgs/:orgId/entitlements (modules/billing/routes.ts:292-337) requires `requireVerifiedPlatformAdmin`
     AND org owner, and rejects any key outside FEATURE_KEYS ("Unknown entitlement keys"). 'userTokens.contactTimelines'
     is not in FEATURE_KEYS (lib/entitlements.ts), and grep finds no writer anywhere in apps/ or packages/.
   - The org opt-in for session actions has its own route (modules/user-tokens/routes.ts:141). The opt-out has none.
   - The platform-admin org PATCH (modules/admin/routes.ts:141, z.record(z.string(), boolean|number)) probably
     accepts the key. Not executed.
  Consequence: a customer org admin has no way to turn W4 off. Only a GoodQA platform operator can, through the admin
  route or a DB write. The "default with an org-level off switch" reading of "Yes, on by default" is therefore not
  delivered as written. The test sets it by direct DB update, so it passes anyway.
  Fix: either add an org-admin route that mirrors the session-actions opt-in (org admin, audited, step-up as that route
  has it), or correct A2 and the code comment to "a platform-operator switch; org-admin control is ticket #N", labelled
  TARGET_MISMATCH against the F3 ask. Add a NEG for whichever path is the real control.

N3 LOW: the operator exclusion is not applied in the switch branch, so the refusal code depends on order.
  plugins/auth.ts w4Route (`!!opts.delegated && isSessionOnlyOpened(...)`) does not check createdVia. In an org that has
  opted out or turned CRM off, an operator token's bound session therefore gets 404 contact_timelines_disabled or
  crm_api_disabled, not the 403 user_token_non_delegable that NEG-12 pins. Every outcome is a refusal and no data
  leaks; the refusal code just depends on order. The fix is to add the same createdVia !== 'operator' check, or to
  accept this behaviour and say so.

REQUESTED ANGLES (answers)
===================================================================================================
- W4 outside the two exact keys or on a non-bound door: no (F8 above).
- Any path to req.userTokenSessionAction: no (F4 above).
- An org-existence oracle in the w4Route branch: the distinct codes are thrown only when `opts.userId` is a member AND
  the org is in the token's orgIds; a non-member falls through to the handler's requireOrgPermission, as on every other
  CRM route (pre-existing). A hypothesis only: the non-member path does one extra org-row read before the membership
  check, a negligible timing difference.
- Does clearing nonDelegable/signedInPersonOnly hide a future rule: nonDelegable no, because the pin catches it
  (F8). signedInPersonOnly is cleared by design. Later re-imposers (membership, org-admin, webhook, browser-grant sets)
  do not cover these keys.
- Opt-out default with entitlementOverrides null: correct (on). See N2 for operability.
- q / limit / cursor on the timeline: N1 (HIGH). The cursor is parsed with split('|'), and only the reader's own org and
  contact are in the WHERE, so a forged cursor cannot cross tenants.
- Tenant mixing by contactId from another org: none. Detail gives 404 (getContact); the timeline gives 200 with an
  empty page, because the query is scoped by orgId on both the entry and the link. Probed by the owner's test, and
  consistent with the code.
- Rate limit and ledger for refused requests: enforceTokenRate runs before the switches. Switch and opt-out refusals go
  through `refusal(...)`, which writes a ledger row. The test checks one refused row (the ability case). The rate
  values were not examined. They bound N1's speed but do not prevent it.
