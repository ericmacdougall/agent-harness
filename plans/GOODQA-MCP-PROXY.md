# GoodQA tool allowlist proxy

> **Unreleased baseline.** This plan describes the console kept on `main` as the base for the event-log rebuild. That console is not released, packaged or installed; see `console/README.md`.

Settings owner owns `console/settings_goodqa_proxy*.go` and, after review admission, `console/mcp.go`. The console checkpoint helper remains core-owned. Opt-in metadata snapshots identify a fixed validated endpoint, settings revision, exact discovered allowed tool names and opaque OS-vault credential reference. No upstream bearer enters provider environment, MCP JSON, arguments or logs. The helper loads the scoped credential itself from the native vault. It never receives the GUI bearer.

The executable's stdio helper mode permits initialize, ping, lifecycle notifications, filtered tools/list and exact allowlisted tools/call. Reject all other methods and tool names. Forward only to the fixed configured origin with redirects disabled, bounded response/frame sizes, deadlines, protocol/session headers and explicit lost/unknown state. A changed endpoint, tool list, vault generation or policy revision requires a new admitted helper configuration. Foreign/stale configuration cannot broaden access. Browser/desktop/hive capabilities remain disabled unless their actual discovered names were explicitly selected; no disabled bridge/old Hive workflow is revived.

Both Codex and Claude receive the same stdio proxy metadata and ordinary local tool discovery. The helper enforces the allowlist, independently of provider approval flags. Provider-specific configuration controls do not substitute for this filter. Same-user processes are not isolated from OS credentials or local files, and the app makes no such claim.

Required deterministic controls cover filtered discovery, denied tool never reaching upstream, unknown method, foreign endpoint redirect, oversized/invalid output, timeout after an accepted request, stale settings revision, malformed vault reference, missing credential and two concurrent sessions. Native Codex and Claude proof must each discover/call an allowed harmless tool and be unable to invoke a denied tool through normal MCP. A local controlled upstream proves exact allow/deny routing; real GoodQA discovery is reported separately. Do not label a capability enabled until these paths are proved. Root owns final policy review, native proof and publication.

## Review reconciliation: helper authority and output safety

The helper loads its own upstream bearer and constructs a helper-local redactor before opening upstream. Every downstream result, protocol error and diagnostic is checked with that redactor; streamed upstream data is buffered until a complete bounded JSON response, so split network-chunk echoes cannot bypass matching. No raw upstream body is logged or returned on parsing/status failure. Diagnostics carry fixed categories and request IDs only. Oversized, incomplete or malformed output fails closed.

The helper terminates upstream MCP itself rather than forwarding arbitrary JSON-RPC. It owns monotonically unique upstream IDs, validates each response ID, negotiates a supported protocol version at initialize, and retains only validated MCP session headers for that fixed origin. It advertises exactly initialize, ping and the filtered tools surface. Sampling, elicitation, roots, authorization negotiation and any unsolicited server-initiated request are unsupported and receive protocol rejection without reaching the model or user. Unknown notifications are ignored with bounded fixed diagnostics; they cannot become tools or change authority.

Each helper admission binds the exact saved revision, configured origin and discovered allowlist. The active request retains that immutable admission snapshot, matching the console policy contract. Before each new tools/call, the helper reads current metadata under the settings read lock and refuses dispatch if its profile/adapter is disabled, removed, origin changed, or the tool was revoked; it never expands its original allowlist without a new process/policy resolution. A revocation does not replay or pretend to cancel an upstream call already sent. That call may finish under its admitted snapshot; subsequent calls are refused. Tests cover both cases and report unknown if a transport failure prevents knowing its result.
