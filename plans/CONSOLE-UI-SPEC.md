# Spec: Console conversational UI and settings (K12+), over the event-log kernel

Ticket: GoodQA work-tracker-automatic#35574
Author: agent:console-platform
Click-test: required

## Outcome

The user runs one cross-platform console that looks and feels like Claude Code CLI or Codex CLI. It shows a realtime chat with the main agent, supervises owner agents and their sub-agent trees, shows worktrees and branches, and has a settings menu for keys, profiles, limits, permissions, ladders, memory files, hooks, environment and GoodQA integration. Every piece of authority state it shows is a projection of the kernel event log (K1a, K2); the UI owns no authority.

Provenance note: the layout and settings text below was relayed verbatim by the main agent in the owner brief. The original user transcript was lost in incident #14471, so every user-derived item carries an `inferred:` source and counts as an assumption until main attaches a sourced WAL entry.

## Scope

- In: slices K12 to K20 below, in the order listed, each its own branch and PR on top of the kernel slices they depend on.
- In: the decision of UI technology (see "UI technology decision"), the realtime delegation loop view, and a keychain interface with a fake store for tests.
- In: folding the architecture research (ARCH-RESEARCH.md, adopt table and gaps G1 to G8) into the design review and plan.
- Out: new provider adapters, the Go Hermes engine, owner auto-dispatch beyond what the kernel plan already admits (CONSOLE-KERNEL.md "Out of scope"), Electron packaging unless the decision below is reversed, native Windows qualification (compile-only, as the kernel plan states).
- Out: reading or writing the real OS Keychain from any agent, test or CI run. Only the interface and an in-memory fake exist before the user installs and runs the console themselves.

## UI technology decision

Decision: the primary UI is the existing embedded web UI served by the single Go binary on 127.0.0.1 (console/web, about 4,500 lines, already carrying settings, repo controls, file picker, launch buttons and agent sidebar), rebuilt as a read model over the kernel API. A terminal client (a thin Go TUI over the same HTTP and event-stream API) is K19, a secondary front end. No Electron.

Evidence:
- Selection requirement. A terminal paints one rectangular grid, and a mouse drag across several lines selects across the full row, including sidebar columns. Fixing that means capturing the mouse and re-implementing selection and copy, which breaks native terminal copy and varies by emulator. In the browser the sidebar is a separate scroll container with `user-select: none`, so a multi-line drag in the chat cannot select it. This is testable in a real browser (AC-4).
- Existing asset. console/web already implements most requested panels (baseline README: Settings panel, repo controls, file picker, Codex and Claude launch buttons, agent sidebar with selectable transcripts). The Go TUI in harness-example PR #13 (operator/tui.go, conversation.go, 19 files, +2,355 lines, open) is a conversation operator for the fleet worker, not a layout with panes, settings forms or a file picker.
- Install. A Go binary with `go:embed` assets has no Node or Electron runtime, installs with one download, and is already what CI builds on Linux, macOS and Windows. Electron adds a 100+ MB runtime, a signing and update path, and a second process model.
- Look and feel. CLI feel comes from design (monospace, dense, keyboard-first, streaming text, slash commands, no mouse needed), which a web page can deliver. The TUI client (K19) covers users who want it inside a terminal, so both are served by one API and one projection.
- Reversal trigger: if the click-test shows the browser cannot meet AC-5 (keyboard-only operation) or AC-4 on a supported browser, or users need OS tray or global hotkeys, wrap the same page in a webview shell (Wails or similar) as K20b. The API does not change.

## Layout requirements

Verbatim layout, as relayed: [Top bar: tabs of sessions with a + to start a new one] [main chat section] [sidebar showing active owner agents with expandable trees of their sub agents, the tasks they are working on - the model/harness and last ping:last write -- tab/arrow between them to pull their transcript or pause/resume/kill... below in the sidebar a section toggling between active worktrees and active branches with local vs remote sync state indicators and a star for what is on my cwd, with shortcuts to force a sync and force remove local copy] [main chat input bar with integrated file picker] [useful stats bar] [cwd changer] [shortcut list including one that launches codex to the cwd and one that launches claude code to the cwd in a new window]. It should constantly self-loop/check/manage delegation between main agent instances and owner instances, a realtime chat system. Highlighting multiple lines in the main window must not highlight the sidebar. Feel like Claude Code CLI or Codex CLI; may be GUI/Electron if better but cross-platform and easy to install.

## Settings requirements

Verbatim, as relayed: settings menu: add anthropic keys, gpt keys, gpt device-key signed-in profiles, multiple anthropic profiles with usage, remaining limits/balances and reset timers, check off which may be used/rotated, default harness permission modes, default harness/model/cascade and cross-review ladder orders, update agent.md/claude.md/memory files, see all hooks and enable/disable them, env vars/secrets/creds available to agents, turn on goodqa integration (desktop/browser/remote control/knowledge net/hive/ticket+project tracking/decision tracking), and anything else useful.

Useful additions chosen by the owner (assumptions, each removable): a read-only audit view of settings changes (facts, no values); a dry-run "test this profile" button that makes no provider call unless the user presses it; export and import of settings without secrets; per-profile cost ceiling with a visible stop; data directory, log quota and rollover status (G2).

## Risks

- Scope size: nine slices on top of K4 to K11. Mitigation: each slice has its own branch and inspection, K12 and K13 start only after the kernel slices they need are accepted; UI slices that need unlanded kernel facts (K14, K17) stay behind K1b and K1d.
- Vocabulary drift with the QAC loop owner: mitigation is the name review described above; kernel-plan names win.
- Browser-only selection checks differ across engines: mitigation is the three-engine Playwright run on dev2.
- Hooks editor can weaken harness safety: typed confirmation, backup, fact record, fixtures only in tests.
- Provider usage endpoints are undocumented or change: usage is shown only when the provider reports it, else explicit unavailable.
- Model of the user's intent is assumed from relayed text: mitigation is the provenance note and the review of the text by two independent reviewers.
