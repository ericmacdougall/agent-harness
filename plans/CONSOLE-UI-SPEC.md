# Spec: Console conversational UI and settings (K12+), over the event-log kernel

Ticket: GoodQA work-tracker-automatic#35574
Author: agent:console-platform
Click-test: required

## Outcome

The user runs one cross-platform console that looks and feels like Claude Code CLI or Codex CLI. It shows a realtime chat with the main agent, supervises owner agents and their sub-agent trees, shows worktrees and branches, and has a settings menu for keys, profiles, limits, permissions, ladders, memory files, hooks, environment and GoodQA integration. Every piece of authority state it shows is a projection of the kernel event log (K1a, K2); the UI owns no authority.

Provenance note: the layout and settings text below was relayed verbatim by the main agent in the owner brief. The original user transcript was lost in incident #14471, so every user-derived item carries an `inferred:` source and counts as an assumption until main attaches a sourced WAL entry.

## Scope

- In: slices K12 to K20 below, in the order listed, each its own branch and PR on top of the kernel slices they depend on.
- In: the decision of UI technology (see "UI technology decision"), the realtime delegation loop view, and a keychain interface with a fake store for tests.
- In: folding the architecture research (ARCH-RESEARCH.md, adopt table and gaps G1 to G8) into the design review and plan.
- Out: new provider adapters, the Go Hermes engine, owner auto-dispatch beyond what the kernel plan already admits (CONSOLE-KERNEL.md "Out of scope"), Electron packaging unless the decision below is reversed, native Windows qualification (compile-only, as the kernel plan states).
- Out: reading or writing the real OS Keychain from any agent, test or CI run. Only the interface and an in-memory fake exist before the user installs and runs the console themselves.

## UI technology decision

Decision: the primary UI is the existing embedded web UI served by the single Go binary on 127.0.0.1 (console/web, about 4,500 lines, already carrying settings, repo controls, file picker, launch buttons and agent sidebar), rebuilt as a read model over the kernel API. A terminal client (a thin Go TUI over the same HTTP and event-stream API) is K19, a secondary front end. No Electron.

Evidence:
- Selection requirement. A terminal paints one rectangular grid, and a mouse drag across several lines selects across the full row, including sidebar columns. Fixing that means capturing the mouse and re-implementing selection and copy, which breaks native terminal copy and varies by emulator. In the browser the sidebar is a separate scroll container with `user-select: none`, so a multi-line drag in the chat cannot select it. This is testable in a real browser (AC-4).
- Existing asset. console/web (1,275-line app.js, 512-line settings.js, 528-line index.html, 1,971-line style.css, measured on main) already has a Settings panel, repo controls, file picker, Codex and Claude launch buttons and an agent sidebar (baseline README). Reuse is of design, CSS and the DOM structure; the data layer is rewritten as a read model over the K12 API, so expect most of app.js to be replaced. Only web/composer.test.mjs exists as a browser test today, so layout, selection and keyboard tests are new work. The Go TUI in harness-example PR #13 (operator/tui.go, conversation.go, 19 files, +2,355 lines, open) is a conversation operator for the fleet worker, not a layout with panes, settings forms or a file picker.
- Install. A Go binary with `go:embed` assets has no Node or Electron runtime, installs with one download, and is already what CI builds on Linux, macOS and Windows. Electron adds a 100+ MB runtime, a signing and update path, and a second process model.
- Look and feel. CLI feel comes from design (monospace, dense, keyboard-first, streaming text, slash commands, no mouse needed), which a web page can deliver. The TUI client (K19) covers users who want it inside a terminal, so both are served by one API and one projection.
- Early evidence: a time-boxed spike (K12a, under one owner-day) builds the layout skeleton with a canary string in the sidebar and runs the AC-4 and AC-5 checks in three engines before K13 commits to the design. A spike failure triggers the reversal path below.
- Reversal trigger: if the click-test shows the browser cannot meet AC-5 (keyboard-only operation) or AC-4 on a supported browser, or cold start exceeds 2 s on the dev machine, or users need an OS tray or global hotkeys, wrap the same page in a webview shell (Wails or similar) as K20b. The API does not change.

## Kernel amendments required (not yet vocabulary)

None of these names exist in the kernel fact vocabulary (CONSOLE-KERNEL.md "Fact vocabulary"). Each needs a kernel-plan amendment and review before its UI slice starts. INV6 applies to all: facts hold enums, opaque ids, counts and keyed digests, never prompt bodies, key material, env values, hook command bodies, file contents or profile display names.

| `SettingsChanged{area,revision,keyedDigest}` with area in an enum (profiles, defaults, docs, hooks, env, goodqa:<capability enum>) | K1d | area, revision, keyed digest | AC-11 to AC-16 |

| Child liveness | K1d, K4 | display state held in memory, not a fact per ping; at most one fact per child per state change (alive to stalled) with a hard cap, so the 1,000,000-fact quota and must-append reserve are not spent | AC-9 |

Admission-relevant settings (permission mode, ladder order, cost ceiling, profile use flags, GoodQA capability flags) reach `Decide` only through `PolicyBound{revision}` in the projection, never through a side channel; a replay test shows the same admission decision on replay. Defaults are recorded with `SettingsChanged{defaults}`, while `CascadeSelected` stays a per-session fact. Fork and rollover (AC-17) need a kernel amendment that is decided before K10 and covered by the 10,000-seed operation set: a new receipt transition for carried-over open receipts, and rollover allowed only when no receipt is unresolved (INV3). If that amendment is rejected, AC-17 is removed. The kernel plan's "new UI design" out-of-scope entry is amended to exclude the K12+ work in this spec.

Provider usage, balances and reset timers are display data fetched on demand, not authority: they are not facts, are not replayed, and are shown with their fetch time and source or as `unavailable`. Profile use and rotation check boxes are settings state stored in the settings store with a `SettingsChanged` fact carrying only a digest.

## Cross-cutting rules

- Test gate: every AC and NEG maps to a named test. A CI gate runs `go test -count=1 -json` and `node --test`, and fails when a named test did not run, was skipped, or ran with zero cases or seeds; `[no tests to run]` is a failure. Each NEG also has a named failing control. NEG-n maps to a test named `TestNEGn_Topic` in its slice's package.
- Principals: commands for hooks, keys, env, import and export, permission mode, ladder, GoodQA capabilities and profile changes are user-principal only. An agent child process, or any request that carries a child's identity, is refused (AC-23).
- Local effects (git sync, worktree remove, terminal launch) are not provider effects: INV7 does not apply, they are idempotent or refuse on a repeat, and each leaves an audit record without paths beyond the cwd digest. They never go through a shell.
- Display ages come from the server (monotonic) and the browser advances them with `performance.now`, never with `Date.now`.
- K11 ships the existing baseline UI wired to the kernel through CONSOLE-API.md. K12 extends that contract and does not replace it. The K12 read model starts with the K1a fields and grows as K1b, K1c, K1d, K7 and K8 land; AC-1 is checked per field family as each lands. K20 is a release after K11.

## Risks

- Scope size: nine slices on top of K4 to K11. Mitigation: each slice has its own branch and inspection, K12 and K13 start only after the kernel slices they need are accepted; UI slices that need unlanded kernel facts (K14, K17) stay behind K1b and K1d.
- Vocabulary drift with the QAC loop owner: mitigation is the name review described above; kernel-plan names win.
- Browser-only selection checks differ across engines: mitigation is the three-engine Playwright run on dev2.
- Hooks editor can weaken harness safety: typed confirmation, backup, fact record, fixtures only in tests.
- Provider usage endpoints are undocumented or change: usage is shown only when the provider reports it, else explicit unavailable.
- Model of the user's intent is assumed from relayed text: mitigation is the provenance note and the review of the text by two independent reviewers.
