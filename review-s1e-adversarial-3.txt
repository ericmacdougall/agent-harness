R1 MEDIUM, HYPOTHESIS (the logic is confirmed by code reading; not probed): cursor presence still reveals that withheld
  entries exist, and roughly when.
  Whether a cursor exists still depends on `entries.length === limit`, which service.ts computes over the RAW page
  before withholding. Choose `limit` = (visible rows older than T) + 1 with a forged cursor at time T. The response then
  carries a cursor exactly when a withheld row older than T exists. Repeating this over T locates each withheld
  entry's timestamp: a colleague's personal entry, or the arrival time of a Gmail mailbox-read message. No content,
  title or id is exposed. It is metadata about Google user data and private notes, and it takes many requests (rate
  limited and ledgered, with q values stripped).
  Fix: filter withheld rows in SQL before LIMIT for an agent reader. `gmailMailboxReadEntry(db)` already exists as an
  SQL predicate, and the personal-visibility rule can be expressed the same way. Then the page, the cursor and
  fullness all cover visible rows only. Settle it with a probe: a contact with one visible and one withheld (personal or
  Gmail) entry; compare the bound session's cursor presence for limit=2 with and without the withheld entry.

R2 LOW to MEDIUM (correctness, not privacy): paging can stop early for a token session.
  Take entries [V1, H1, H2, V2] in time order, H hidden, limit=2. Page 1 shows [V1] with cursor V1. Page 2's raw rows
  are [H1, H2], so it shows nothing and returns cursor null, which ends paging. V2 is never reachable through the
  session. The code comment acknowledges this ("null when the page shows none, which ends paging"). The SQL-level fix
  for R1 removes it too.
