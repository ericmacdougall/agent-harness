NEW MATERIAL FINDINGS
M1 A2 is not implementable from existing data. A2 requires a grantee "created by a signed-in person's session (not by any user token, not by MCP pairing, not by an automation), at least 60 minutes old". On t2-dev the only creation provenance on keys is `createdByUserTokenId` (api-keys/service.ts:222, routes.ts:154); there is no record of session vs MCP pairing vs automation vs creation through another org API key (can an org key with agents.manage call POST /api-keys? an agent holding one gets the plaintext back and its key would look "human-created" under a null token id). Personas have no provenance field I could find. The spec adds no column, no migration, no backfill, and says nothing about pre-existing keys (all have null provenance: all eligible, or none?). Required: add a provenance column (e.g. created_via: 'session'|'user_token'|'api_key'|'mcp_pairing'|'automation'|'unknown') written by every key/persona creation path, backfill existing rows as 'unknown' (ineligible), eligibility = 'session' only; extend the census/guard so a new creation path must set it; add NEG: a key created through an org API key, a key with 'unknown', and a key whose provenance is re-tied by PATCH extend (`createdByUserTokenId` is mutable via tieTo, service.ts:377) are refused. Without this the central laundering control is unfalsifiable and a test can only pass by fixtures.
M2 AC-4 is not yet concrete or self-consistent. (a) The CLI step is a placeholder: "`goodqa vault-env reveal with the vault name and an output file argument` (or the equivalent shipped CLI invocation named by the tester)". Name the real command and flags from the repo (or state it does not exist, which makes AC-4 unrunnable). (b) `curl -H @file` sends the file's content as a whole header line; the revealed file holds the raw key, so the request would send no Authorization header and not return the claimed 200. Give a command that does not expose the value, e.g. `curl -K <(printf 'header = "Authorization: Bearer %s"\n' "$(cat FILE)")` run on the host with only the status code captured, and confirm the org-list route accepts an org API key. (c) The grantee "created through a signed-in session at least an hour earlier on the tester host" is a human act: CLAUDE.md says such steps are recorded as a disclosed limitation, but AC-4 then cannot complete without it. State who performs it (the human, once, outside AC-4) and that AC-4's evidence includes the grantee's key id, creation provenance and age. (d) Evidence list is still "mode + key id + authenticated call": add the hash of the command output transcript and the vault secret id, and the post-revoke read refusal (D10) as a live step; the cleanup line says revoke but does not prove the grantee read then fails. (e) The tester needs: a user token with tokens.mint_to_vault and without tokens.create_other_keys (whose, how obtained without the agent reading it), the flag enabled for a disposable org (who flips it), the grantee, and a non-grantee org API key. List them.
M3 Human session can read a blind secret; the "agent never obtains it" claim must be bounded. D3: "a signed-in person's session" may open. A GoodQA agent browser or computer-use session signed in as the person (cookie session, not a token) is a "signed-in session" and can click the vault reveal UI. The spec's Outcome ("the agent can never obtain") is therefore false for an agent driving a signed-in browser. Either (i) refuse the human reveal of a blind secret altogether (only the grantee reads; admin can delete/rotate, which is human-only, rotate re-hides) or (ii) keep it and state the limitation and that click-test browser sessions are not human sessions for this purpose (how is that distinguished? name the field). Option (i) is simpler and closer to "blind"; no decision of main's grants a human reveal. If kept, label it ASSUMPTION A5.
