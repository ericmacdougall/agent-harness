## 5. goodqa#15598 (P0: no route to mint an org API key whose value never passes through the agent)

Spec: `goodqa-artifacts/spec-15598-v32.md` (v3.2; the file name v3.1 in main's note is superseded). Attached to #15598 as comment `a72b157c`. Design (A, main 2026-11-10): `POST /v1/orgs/:orgId/api-keys/mint-to-vault` mints an org API key and seals it into an org vault secret that is blind to every credential except one named grantee principal; answers only key id, prefix and vault secret id.

Every decision made (all labelled in the spec; sources are main's messages of 2026-11-10 and the reviews):
- Design A (mint-to-vault, blind-pinned to a named grantee) and NOT design B (host file via the machine agent): main.
- No human approval and no `approvalAlways` on the route: main (key and token creation is never an ask). Compensating controls: scope ceiling (minted key never broader than the caller token), explicit grantee plus `org:manage_api_keys` (and `org:manage_vault`), per-token and per-org rate limit and audit, owner alert per mint, the token never in any response, log or agent context.
- A1: the route has its OWN token ability `tokens.mint_to_vault`; it does NOT imply `tokens.create_other_keys` and is NOT in `all`; a token holding it together with `tokens.create_other_keys` or `all` is refused (`user_token_ability_conflict`); no `approval` entry; refused to bound desktop sessions, commander-turn grants and org API keys. Reason: a token that can also call plain `POST /api-keys` gets plaintext back, defeating the purpose. The ability must be defined OUTSIDE the `all` expansion (see `packages/shared/src/user-tokens.ts` `USER_TOKEN_ABILITIES`/`expandUserTokenAbilities`; session abilities are the precedent for non-`all` abilities; NOT yet implemented, I had just started reading it).
- A2: human-created grantee: a persona or API key that was created by a signed-in person's session (a new `created_via` provenance column on `api_keys` and the personas table, set by every creation path; values session, user_token, mcp_pairing, automation, api_key, unknown), at least 60 minutes old, same org, not revoked, not a runner key, not user-scoped, not the key being minted, never created through any token, not later tied to a token (extend or re-scope); for a persona grantee the rule applies to the persona AND the key it speaks through, re-checked on every reveal. Every existing row is backfilled `unknown` with NO audit-based upgrade (the creation audit row records "user" for a session, a token and an API key alike), so NO existing key qualifies. Main asked me to look for an existing human-created key first: that cannot succeed by design; the live proof uses a key the tester creates in a signed-in session after deploy and waits 60 minutes (recorded as a limitation, not an ask). Grantee errors are uniform (`grantee_not_eligible`).
- A3: the mint transaction creates an allow-list row bound to the exact blind secret id and grantee (vault-env config writes are session-only today); not a prefix pattern, not an edit of the editable config.
- A4 (numbers, main: "The numbers are fine."): 5 mints per hour per token, 20 per day per org, `expiresAt` required and at most 90 days, replay of a revoked key 410 `mint_replay_revoked`, 409 `idempotency_key_reused`, 429 `api_key_mint_rate_limited`, 409 `vault_name_taken`; rate limit counted from the database under a per-token advisory lock; idempotency by a DB unique index on (org, minting token, hash).
- A5 (main: yes): the minted key OUTLIVES its minting token: it does not set `created_by_user_token_id` (the lifetime tie) but a separate `minted_via_user_token_id` marker that the personal-principal rules treat like it; mandatory expiry at most 90 days; revoking the minting token emails the owner the list of vault-minted keys.
- A human session also cannot reveal a blind secret (a browser agent signed in as the person would defeat the purpose); the human path is delete and re-mint; PATCH value, rename, grants and move are refused for everyone; only DELETE by a signed-in session with `org:manage_vault`. Rotation is re-mint under a new vault name (e.g. `name-v2`), switch the host, delete the old.
- Unmutable owner alert: direct account email (the vault already uses this pattern for rotate), not a mutable notification; never contains the value.
- Rollout: migration and choke point first, then the route behind platform flag `apiKeys.mintToVault` (default off); rollback is the flag, never dropping the table (dropping would unblind every minted secret); fail closed when the table is missing.
- Live-proof rule (main): NO disposable production org and NO production `vaultEnv` override (prod account or config creation needs the user). Order: (1) an existing org the user owns where `vaultEnv.enabled` is already on, checked read-only; (2) staging for the full AC-4 proof (staging is unprovisioned as of earlier notes: verify), production proof limited to what works with the flag as it is; (3) otherwise a disclosed limitation and main puts the flag decision to the user. The vault-env feature (`vaultEnv.enabled`) is DARK on every plan by default.
